# Модуль 1 «Архитектура компьютера» — независимый фактчек (второй исследователь, Sonnet 5.5)

> **Назначение документа.** Независимый research brief по `sources/1. Архитектура компьютера/` (41 статья, ≈970 КБ). Анализ выполнен «с нуля»: выводы других моделей/исследователей не использовались (файл `1-gemini-scout.md` в корне репозитория сознательно не открывался). Цель — максимальное независимое покрытие, а не согласие с чьим-либо эталоном.
>
> **Метод.** (1) Полностью прочитаны все 41 статья. (2) Все утверждения о Go проверялись по исходникам и поведению установленного тулчейна **Go 1.26.2 linux/amd64** (`/usr/local/go/src`, `go build -gcflags=-S/-m`, микробенчмарки; ядро Linux 7.2.8, CPU i9-12900K, `vm.overcommit_memory=0`). (3) Внешние факты (спецификации Intel/AMD/ARM, JEDEC, релиз-ноты Go, историческая атрибуция и т.п.) приведены **по памяти, без веб-поиска** — для них в колонке «Нужные доказательства» указан первоисточник, а отметка **✔ проверено локально** стоит только у пунктов, подтверждённых экспериментом на этой машине. Всё без отметки — гипотеза/знание, требующее сверки.
>
> **Формат строк:** статья/раздел → утверждение → проблема → нужные доказательства → приоритет. **High** — фактическая ошибка или вводящее в заблуждение утверждение, влияющее на практический вывод; **Medium** — неточность, устаревание, пропущенная оговорка; **Low** — терминология, округления, полировка.

## Часть A. Самое важное (приоритетная «срочная» выжимка)

Ниже — пункты, которые, на мой взгляд, стоит исправлять в первую очередь. Номера (`N.M`) указывают на строки в таблицах части D.

**A1. Опровергнуто экспериментом (код/числа из статьи не дают заявленного результата):**
- **13.1** — «отсортированный массив быстрее в 3–5 раз»: Go (`branchelim`) компилирует `if v>128 {sum+=v}` в `CMOVQGT`; на Go 1.26.2 sorted/unsorted ≈ 1× (0,50 vs 0,44 мс). Эффект появляется только при теле, которое нельзя if-конвертировать (≈8×). К тому же код не компилируется (`"sort"` не используется).
- **18.2** — бенчмарк матрицы: буквальный код статьи даёт Row 6,2 мс vs Column 7,0 мс (≈1,1×), т.к. `sum` не используется (loads удаляются); память к тому же никогда не записывалась (zero page).
- **11.5–11.7** — `sumFast` «в 2–3× быстрее на больших объёмах»: в L1 — 2,3×, на 64 МБ — 1,13×; цепочка `sum += x` для целых — не hazard (латентность ADD = 1); и «компилятор Go умеет разворачивать циклы» — неверно (в `cmd/compile` нет unroll-прохода; противоречит и ст.16).
- **27.2 / 28.2** — `make([]byte, 1<<40)` на машине с малой RAM: статья утверждает «не упадёт, Overcommit»; на дефолтном `vm.overcommit_memory=0` программа падает `fatal error: runtime: out of memory` (проверено).
- **2.12** — `struct{bool;bool;bool;bool}` «может раздуться до 8–16 байт»: `unsafe.Sizeof == 4`, `Alignof == 1`, паддинга нет (проверено).
- **9.1** — листинг `readSlice(s []int, i int)`: индекс в `DI`, не в `CX` (слайс занимает AX,BX,CX); реальный вывод — `CMPQ DI, BX; JCC …` (проверено); заголовок `-S` в Go 1.26 — `main.add … NOSPLIT|NOFRAME|ABIInternal`, а не `"".add`.
- **8.7** — кросс-компиляция с cgo: по умолчанию `CGO_ENABLED=0` ⇒ ошибка **`build constraints exclude all Go files`**, а не «ошибка линковщика» (проверено); при `CGO_ENABLED=1` падает сборка `runtime/cgo` ассемблером хоста.
- **21.1** — комментарий в `sync.Pool` выдан за цитату, а в исходнике: «Prevents false sharing on widespread platforms with 128 mod (cache line size) = 0» (проверено).
- **5.1** — «Graph Coloring Register Allocation» в Go: в `regalloc.go` прямо сказано «version of a linear scan register allocator» (проверено).
- **16.1** — «контекст горутины раздувается из-за XSAVE/ZMM, gobuf 128 байт»: `gobuf` содержит 6 полей (`sp, pc, g, ctxt, lr, bp`), все регистры в Go ABI caller-saved, горутины переключаются на вызовах (проверено по `runtime2.go`).
- **41.1** — «дженерики дают компактные предсказуемые циклы»: для pointer-типов один общий shape-инстанс и косвенный вызов через словарь (`CALL BX` в `Sum[go.shape.*uint8]`, проверено).
- **14.2 / 16.6 / 41.5** — «Go не добавит SIMD-интринсики»: в Go 1.26.2 есть экспериментальный `simd/archsimd` (`GOEXPERIMENT=simd`, AMD64); Green Tea GC включён по умолчанию (`internal/buildcfg/exp.go`); `GOMAXPROCS` учитывает cgroup-квоту (проверено по `go doc runtime.GOMAXPROCS`).

**A2. Принципиальные ошибки в объяснении механизмов:**
- **22.1** — Store Buffer: объяснение через «`ready=true` пишется прямо в L1, минуя буфер» неверно (FIFO-буфер; Store→Store на x86 не переупорядочивается; статья сама это говорит двумя абзацами ниже).
- **2.4** — «утечки заставляют чип рассеивать сотни ватт даже в простое»; **2.9** — «сложение 3–40 тактов» (целочисленное ADD — 1 такт); **2.16** — «CAS fast path за 1 такт» (`LOCK CMPXCHG` ≈ 18–25 тактов).
- **4.1** — схема SR-защёлки противоречит таблице/шагам (выходы Q и Q̄ перепутаны, в тексте оставлено «Стоп…»).
- **6.4 / 7.2 / 12.5** — кодирование `ADD RAX,RBX` (`48 01 c3` vs `48 01 d8` внутри модуля), синтаксис и семантика Plan 9 в примере с renaming.
- **5.4 / 5.5** — «`page-faults` = TLB-промахи»; «`go tool ptrace`» (нет такого инструмента); pprof использует SIGPROF, а не PMC.
- **5.7 / 5.8** — пример TCP-FSM (`LISTEN + SYN-ACK → ESTABLISHED`) не соответствует TCP; запись в `CLOSE_WAIT` разрешена.
- **27.1 / 28.1** — пользовательское адресное пространство 48-битного x86-64 = 128 ТиБ, а не 256.
- **27.3** — «аренa Go — сотни ГБ при старте» (с Go 1.11 — разреженные 64-МБ арены).
- **26.1** — Protobuf не Big Endian (fixed32/64 и varint — little-endian); «абсолютно все стандарты интернета» — оверстейтмент.
- **36.1** — диагноз «UPI — бутылочное горлышко для 7 ГБ/с NVMe» нереалистичен (один UPI-линк ≈ 20 ГБ/с); вероятны queue depth/page cache/синхронный I/O.
- **37.1 / 37.2** — WAF от мелких `write` (page cache и FTL склеивают записи); «LSM минимизирует WAF» (application-level WA у LSM, как правило, **выше**).
- **39.1** — «планировщик Go переключается каждые мкс, 70–80% времени — диспетчер» (на деле — вытеснение раз в 10 мс; цена миллиона горутин — память/GC).
- **17.6 / 40.7 / 10.7** — три разных рекомендации про `User` vs `*User` в одном модуле; логика «стек уже в L1» игнорирует чтение источника копии.
- **16.4** — пример aliasing (`a=data[0:3]`, `b=data[1:4]`) на самом деле допускает векторизацию.

**A3. Версии и атрибуция:**
- **1.2 / 7.4** — PGO: preview 1.20, GA 1.21 (не «1.22»); «100% попаданий в L1i»; разные диапазоны выигрыша в статьях модуля.
- **1.3 / 6.6 / 10.2** — четыре разных числа ускорения от регистрового ABI (5–12, 5–15, 5–12, «≈5»); в 1.17 ABIInternal — только amd64.
- **1.1 / 8.6 / 16 (диаграмма)** — inlining и escape analysis показаны как «SSA-оптимизации»; на самом деле выполняются на IR до SSA.
- **9.9** — пролог: `MOVQ (TLS), CX` устарел, с Go 1.17 `g` в `R14` (проверено).
- **38.1** — история «Latency Numbers» (Norvig 2001, Dean 2009, Bonér 2012).

## Часть B. Сквозные (между-статейные) проблемы модуля

1. **Внутренние противоречия чисел.** NVMe random read: 16 мкс (ст.38) / 10–50 мкс (ст.17) / 20–50 мкс (ст.1). L1: 1 такт (ст.7) / 3–4 (ст.18) / 4–5 (диагр. ст.18). Ускорение от ABI: 5–12 / 5–15. «sum» по `gobuf`: 128 байт (ст.16) vs «3 регистра» (ст.38). PGO: Go 1.20/1.22 (ст.1), 1.22+ (ст.7). Сетевой RTT/Redis, page-walk 40–100 нс vs 300–400 нс (ст.28/29).
2. **Размер кэш-линии «строго 64 байта»** повторяется в ст.18, 21, 25, 40; для Apple Silicon (128 Б), POWER (128 Б), z (256 Б), для arm64-порта Go (`CacheLinePadSize=128`, проверено) и для Intel spatial prefetcher (пары линий) это неверно или неполно. Затрагивает рекомендации по padding.
3. **«Горутина ждёт сеть ⇒ SMT/CPU занят другим»** (ст.32, 41): путаются микроархитектурные простои и блокировки на I/O.
4. **Единый шаблон завышенных множителей** («в десятки раз», «70–80% времени», «в 10–20 раз») без источников и без измерений (ст.12, 17, 19, 29, 39 и др.). Рекомендую заменить на измеренные цифры (с указанием CPU/Go/размера данных) или убрать.
5. **«Не проверено запуском» примеры кода.** Минимум пять сниппетов не компилируются или не воспроизводят заявленное: ст.13 (`sort` импорт; CMOV), ст.18 (бенчмарк), ст.21 (`counters := …` вне функции), ст.3 (`OP_ADD` не определён), ст.8/9 (листинги написаны от руки и расходятся с реальным `-S`). Предлагаю скриптовать их (`go vet`, `go test -bench`) в CI сборщика.
6. **Версионная база устарела** (до Go 1.24): не отражены Go 1.25/1.26 (container-aware GOMAXPROCS, Green Tea GC по умолчанию, `simd/archsimd`, `sync.Mutex` → `internal/sync`, Swiss maps). Нужна явная версионная справка в начале модуля.
7. **Терминология:** «Continuous» vs «Contiguous stacks» (ст.9/27); «Frame Pointer» для `FP`; «прерывание» для `SYSCALL`; «context switch» для mode switch (ст.35).
8. **Атрибуция Go-авторов:** трое создателей (Griesemer, Pike, Thompson), в ст.8/9/16 упомянуты двое.
9. **Модель «классический 5-стадийный конвейер/однотактный CU»** используется как описание реального CPU в ст.5–7 без достаточных оговорок (современные ядра: µop-cache, OoO, переименование, предсказание на fetch).
