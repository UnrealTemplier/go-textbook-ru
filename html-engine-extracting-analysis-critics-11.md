## 4. 🔴 В26. `CodeSpanIndex`: верное доказательство, неверная реализация

§ 2.2 ответа доказывает: номер строки при нормализации не меняется. Это верно. Но код § 4.2 работает не с номерами строк, а со смещениями символов:

```python
normalized_text = md_instance.preprocessors['normalize_whitespace'].run(raw_text.split('\n'))
norm_str = '\n'.join(normalized_text)
...
for m in FencedBlockPreprocessor.FENCED_BLOCK_RE.finditer(text):   # text = norm_str
    start_pos, end_pos = m.span()                                   # смещения в НОРМАЛИЗОВАННОМ тексте
    start_line = bisect_right(self.line_starts, start_pos)          # начала строк СЫРОГО текста
```

`NormalizeWhitespace` раскрывает TAB (+до 3 символов на каждый) и очищает строки из одних пробелов (`(?<=\n) +\n` → `\n`). После каждого такого места смещения в двух текстах расходятся всё сильнее. Начала строк сырого текста к позициям нормализованного не подходят.

**На корпусе:** маска § 4.2 отличается от построчной маски в **1 121 файле из 1 413** (21 058 строк). TAB есть в 740 файлах, строки из одних пробелов — в 734. Во всех 288 файлах без того и другого маски совпадают. Пример: `1. Архитектура компьютера/4. Последовательностная логика…`. Закрывающие ```` ``` ```` в строках 69, 129, 169 не помечены как код. Строки прозы 114, 115, 152 помечены как код. Что из этого следует:

* `[[…]]` и клише в «прозе-как-коде» **перестанут обрабатываться**. Это массовая регрессия, а не краевой случай.
* Строки кода вне маски снова открыты для wikilinks, то есть дефект U10 возвращается.

Ещё три расхождения с текстом ответа:

* **`splitlines()`** считает переводом строки FF, VT, `\x1c–\x1e`, `\x85`, ` `, ` `. Python-Markdown режет только по `\n`. В 2 файлах число строк различается. После U18 FF уйдёт, но движок делается для любых книг.
* **Выноски** («своя маска для каждого тела выноски») и **ограды с отступом** («после А3з») обещаны в тексте, а в коде их нет.
* Свойство-тест «маска = вывод того же `md`», согласованный в раунде 9, на этом коде упал бы в 1 121 файле. Значит, его не запускали.

**Предложение.** Считать строки в одном тексте, тогда инвариант ответа работает сам:

```python
class CodeLineMask:
    """Номера строк (0-based, по text.split('\n')), которые Python-Markdown считает кодом."""
    def __init__(self, text: str, md: markdown.Markdown, indented=None):
        lines = md.preprocessors['normalize_whitespace'].run(text.split('\n'))
        norm = '\n'.join(lines)
        starts = [0]
        for line in lines:
            starts.append(starts[-1] + len(line) + 1)
        self.lines: set[int] = set()
        for m in FencedBlockPreprocessor.FENCED_BLOCK_RE.finditer(norm):
            first = bisect_right(starts, m.start()) - 1
            last = bisect_right(starts, m.end() - 1) - 1
            self.lines.update(range(first, last + 1))
        if indented:   # тот же сканер, что у IndentedFencePreprocessor: одна функция, два потребителя
            for first, last in indented(lines):
                self.lines.update(range(first, last + 1))
```

* Потребители (`_clean_cliches`, wikilinks) работают по номерам строк `text.split('\n')`. Номер строки сырого текста равен номеру нормализованной: CR запрещён аудитом (U18), остальные замены перевод строки не трогают.
* Сканер оград с отступом вынести из `IndentedFencePreprocessor.run` в отдельную функцию `scan(lines) -> [(first, last)]`. Тогда препроцессор и маска не разойдутся.
* Маска строится на каждую единицу конвертации: статью и тело каждой выноски.
* Свойство-тест — до коммита: корпус + синтетика раунда 9 (TAB после ограды, CRLF, STX) + строки из одних пробелов + FF.

## 5. 🟠 В27. `HeadingTreeprocessor` на общем `md` задевает выноски

Ответ: «Не затрагивает заголовки внутри выносок (поскольку выноски парсятся в изолированных вызовах `md.convert`)». Но вызов не изолирован: `_render_callout_block` разбирает тело выноски **тем же** `self.md` (`converter.py:336`). Порядок шагов делает хуже: выноски (шаг 3) разбираются **до** `_process_headings` (шаг 5). Поэтому `slugs_provider` в этот момент отдаёт якоря **предыдущей** статьи.

На корпусе:

* в основном проходе `id` совпадают с якорями TOC на всех 1 413 страницах. Это верно;
* 2 заголовка в выносках (до А3е у них `id` нет) получили `id` из чужой статьи. Страница `3/14-udp…` получила `vvedenie-zachem-go-razrabotchiku-znat-algoritmy-kontrolya-peregruzki`, страница `3/20-http-1-1…` — `fundament-doveriya-pki-sertifikaty-i-tls-handshake`. Это якоря начала предыдущих статей модуля.

Сейчас ссылок на эти `id` нет. Но изменение незаявленное, и якорь на странице указывает на заголовок другой статьи.

Вторая проблема: если число `h2–h4` и число якорей разошлось, код молча раздаёт `id` первым заголовкам по порядку (`if idx < len(slugs)`). Расхождение возникнет, например, от заголовка Setext (`Текст` + `---`), который `_process_headings` не видит. Тогда все следующие `id` сдвинутся без единой ошибки.

**Предложение:**

* Якоря передаются **только в основной вызов** и сбрасываются после него (так сделан мой прототип раунда 9: `md.heading_ids` выставляется перед основным `convert` и снимается после). Выноски `id` не получают, как сейчас. Если владелец когда-нибудь захочет якоря в выносках, это будет отдельное решение.
* Если число `h2–h4` основного прохода не равно длине TOC, сборка падает с ошибкой, где указаны статья и оба списка.
* Оракул А3е дополняется: заголовки внутри выносок не меняются.

## 6. 🟠 Н10. Препроцессор списков правит код внутри выносок (ошибка моего прототипа)

**Как это работает сейчас.** Шаг 3 `convert_article` превращает каждую выноску в готовый HTML (`<aside>…<pre><code>…</code></pre>…</aside>`) и вставляет его обратно в Markdown-текст строками. В основном проходе Python-Markdown прячет такой HTML в `htmlStash` препроцессором `html_block` с приоритетом **20**. Всё, что стоит выше 20, видит строки кода из выносок как обычный текст.

**Что из этого следует.** Препроцессор списков с приоритетом 23 (критика №9) или 24 (раунд 9) видит в выноске строку `    - errcheck` внутри `<pre>`. Он принимает её за пункт: вставляет пустую строку и меняет отступ. Код в `<pre>` меняется:

```text
было:                      стало (прототип, приоритет 23):
linters:                   linters:
  disable-all: true          disable-all: true
  enable:                    enable:
    - errcheck
    - gosimple             - errcheck
                           - gosimple
```

* Только списки: 2 блока на 2 страницах (`8/19-konfiguratsiya-linterov`, `8/38-avtomatizatsiya-relizov`).
* Списки + А3з: 3 блока на 3 страницах (+ YAML `dnsConfig` на странице DNS).

Мой оракул А3л (проекция текста **без** `<pre>`) этого не увидел бы. Утверждение § 2.1 ответа «к моменту его запуска весь вложенный код уже надежно упакован в `htmlStash`» верно для оград основного текста и неверно для выносок. Моё предложение «списки — 23» в критике №9 из этого и исходило.

**Проверено:** препроцессор списков с приоритетом **19** (после `html_block`):

* 0 изменённых блоков кода (только списки и списки + А3з);
* псевдопунктов осталось столько же (123);
* отличие от варианта 23 — только пробельные строки внутри HTML выносок (294 страницы, 2 738 мест, все — пробелы);
* списки внутри выносок по-прежнему чинятся: тело выноски разбирается своим вызовом `md.convert` с тем же препроцессором.

**Предложение:**

* Препроцессор списков — приоритет **19**. Ограды с отступом остаются на 24.
* Оракул А3л дополняется: **мультимножество текстов `<pre><code>` на каждой странице не меняется**. Для А3з то же условие, кроме блоков, которые А3з создаёт или собирает из разлитых кусков (пример — страница о дедлоках: 3 обрывка → один блок).
* Общее правило для расширений движка, которые работают со строками: приоритет ниже 20, если им не нужно видеть сырой HTML. Это стоит записать в спецификацию. Иначе тот же дефект появится у следующего препроцессора.

## 9. 🟡 В31. `window.__BOOK__`: защита неполная, `?v=` не от того

### Запасной объект

```javascript
const B = window.__BOOK__ || {
  storageKey: function(k) { return 'go_encyclopedia_' + k; },
  readRetro: ..., applyRetro: ..., getTheme: ..., applyTheme: ...
};
```

* Адаптер `main.js` из ответа №8 (§ 4.4) вызывает `B.retroKey(theme)`, `B.defaultTheme` и `B.availableThemes.indexOf(...)`. В запасном объекте их нет. Значит, `toggleTheme()` упадёт с `TypeError` именно в том случае, ради которого защита и делалась.
* `'go_encyclopedia_'` в `engine/assets/main.js` — это префикс `go-textbook`, зашитый в ядро. В `go-workout` со старым HTML запасной объект писал бы в ключи `go-textbook` на общем origin. Как раз против этого вводили `storage_prefix`.

**Предложение.** Без запасного объекта. Если `window.__BOOK__` нет, `main.js` пишет предупреждение и **не запускает** `initThemeSwitcher` и `initRetroEffects`. Остальные модули работают. Старый HTML уже содержит свой anti-flicker, поэтому тема на странице правильная, просто до перезагрузки её нельзя переключить. В `test_runtime.py` — восьмой сценарий: страница без `window.__BOOK__` и новый `main.js`, 0 исключений.

### `?v=` — моя ошибка в критике №9

Я предложил `main.js?v=<версия>` с версией из `get_project_version()`. Это не работает:

* версия проекта (`AGENTS.md § 1.4`) меняется только при релизе. Деплой А3ж без смены версии даст тот же URL, и кэш не сбросится;
* при частичной сборке (`--module N`) на диске один файл `main.js`. Старый HTML с `?v=` получит новый файл так же, как без `?v=`.

**Предложение:** `?v=<первые 10 символов sha256 содержимого файла>` для `style.css`, `main.js`, `search-data.js`, `nav-data.js`. Тогда кэш сбрасывается при любом изменении файла, а `dist/` остаётся воспроизводимым. Частичную сборку закрывает только поведение `main.js` выше.

### Тест в браузере

Inline-скрипт § 4.4 изменён после раунда 9 (сила следа). По коду поведение то же, но 7 сценариев на окончательном коде нужно прогнать заново, вместе с восьмым сценарием. Это часть А3ж, а не довод против решения.
