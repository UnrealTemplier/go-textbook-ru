## 2. Прямые и исчерпывающие ответы на 8 вопросов Критики №3

### 2.1. Вопрос 1: Конфиг `go-textbook` и побайтный инвариант контента (Р2)
> *«Принимаете ли Р2: на этапах 1–2 конфиг `go-textbook` воспроизводит текущее поведение, а инвариант тела статьи проверяется в каждом коммите задачи А?»*

**Ответ: ДА, БЕЗОГОВОРОЧНО ПРИНИМАЕТСЯ.**

Мы полностью согласны с рецензентом: на Этапах 1 и 2 в конфигурации `book.toml` для `go-textbook` не должно быть включено ни одной новой фичи, меняющей результирующий HTML.

#### Фиксация эталонных значений `book.toml` для Этапов 1–2:
1. `clean_cliches = [текущие 5 регулярных выражений]` — сохраняет текущую редакционную зачистку 34 фраз в 31 статье (поскольку по U8 смысловой контент `go-textbook` неприкосновенен, отключение этого списка в `go-textbook` недопустимо). Для новых книг в движке по умолчанию — пустой список.
2. `navigation.mode = "static"` — сохраняет монолитный сайдбар на этапах 1–2. Переход на `"hybrid"` выносится строго на этап 3.
3. `conditional_scripts = false` — подключение Mermaid/KaTeX на всех страницах сохраняется до этапа 3.
4. `reading_time = { method = "bytes", divisor = 800, min = 2 }` — в точности сохраняет байтовую формулу расчета времени чтения.
5. `slug.max_lengths = { module = 35, section = 35, subsection = 20, subsection_leaf = 25, page = 55, anchor = 80 }` — воспроизводит текущие дифференцированные ограничения длины слагов.
6. `version_file = "AGENTS.md"`, `version_pattern = '\*\*Current project version:\*\*\s*`([^`]+)`'` — сохраняет канонический источник версии согласно § 1.4 `AGENTS.md`. Указание статического `version` при наличии `version_file` вызывает ошибку сборки.
7. `canonical_replacements` — упорядоченный массив пар `[[from, to], ...]` (30 правил), гарантирующий правильный порядок замен (`net_http_httptest` раньше `net_http`).
8. `[callouts.alias] critical = "note"` — сохраняет рендеринг неизвестных меток `[!CRITICAL]`.

#### Машинный инвариант контента (U8):
В репозитории создается верификатор `engine/tools/verify_diff.py`. В каждом коммите задачи А запускается автоматическая проверка:
1. `git diff --exit-code <база> -- sources/` пуст (0 байт изменений в исходниках `go-textbook`).
2. Побайтно сравнивается содержимое `<article class="article-body">...</article>` всех 1 413 сгенерированных страниц.
3. На этапах 1 и 2 diff равен строго 0. На этапе 3 допускаются только изменения, объявленные явными нормализаторами (дедупликация ID по таблице сопоставления) и белый список исключений (7 страниц исправления бага кода, см. п. 2.2).

### 2.2. Вопрос 2: Защита кода, перенос на этап 3 и расследование по 7 страницам (Р1)
> *«Согласны ли перенести обработку с учётом кода на этап 3, защищать только fenced-код и сохранить 94 ссылки в inline-коде?»*

**Ответ: ДА, ПЕРЕНОС НА ЭТАП 3 СОГЛАСОВАН. ПРИ ЭТОМ ПРОВЕДЕНО ГЛУБОКОЕ РАССЛЕДОВАНИЕ ПО ВЫНОСКАМ И ИНЛАЙН-КОДУ.**

Мы перепроверили утверждения рецензента на кодовой базе и получили критически важные результаты:

#### 1. Уточнение количества сломанных страниц (7 страниц вместо 5):
Рецензент указал 5 страниц, где wikilinks ломают fenced-код. Полное сканирование всех 1 413 страниц `dist/` с корректным селектором `<pre class="language-*"><code class="language-*">` показало ровно **7 страниц**, где артефакты `&lt;span class=&quot;wikilink...` или `&lt;a href...` попали внутрь блоков кода:
1. `docs/08-infrastruktura-yazyka-tuling-i-ci-c/19-konfiguratsiya-linterov.html` — YAML `arguments: [["ID", "HTTP"]]` превратился в `&lt;span class=&quot;wikilink-unresolved&quot;...`.
2. `docs/12-bazy-dannykh/07-mysql-i-forki/2-innodb-storage-engine.html` — комментарий в Go-коде с `[[...]]` превратился в `&lt;a href=...`.
3. `docs/21-zadachi-s-leetcode-i-sobesedovaniy/02-zadachi/01-massivy-i-stroki/4-three-sum.html` — тест-кейс `Вывод: [[-1, 0, 1]...]` превратился в битый wikilink.
4. `docs/21-zadachi-s-leetcode-i-sobesedovaniy/02-zadachi/17-zhadnye-algoritmy/7-non-overlapping-intervals.html` — тест-кейс `intervals = [[1,2],[2,3]...]` превратился в битый wikilink.
5. `docs/21-zadachi-s-leetcode-i-sobesedovaniy/02-zadachi/17-zhadnye-algoritmy/8-minimum-number-of-arrows.html` — тест-кейс `points = [[10,16]...]` превратился в битый wikilink.
6. `docs/22-voprosy-i-otvety-s-sobesedovaniy-po/16-standartnaya-biblioteka.html` — фрагмент кода с вложенными квадратными скобками.
7. `docs/17-bezopasnost-appsec-v-go/04-uyazvimosti/2-xss-i-csrf.html` — пример HTML-кода с ссылками внутри примера.

Все эти 7 страниц подпадают под санкционированное пользователем исправление (директива U10). Они вносятся в файл `engine/tools/content-exceptions.txt` и проверяются коммитом 3а.

#### 2. Развенчание мифа об «активных ссылках внутри inline-кода»:
Рецензент предположил в критике №3 (раздел 2, п. С1), что «94 wikilinks авторы намеренно обернули в обратные кавычки, и они работают как ссылки внутри `<code>`».  
**Мы проверили это утверждение в собранном `dist/`. Это не так!**
- Во всех 1 413 страницах обнаружено **53 случая**, где конструкция `` `[[Ссылка]]` `` вне выносок превратилась в:
  `<code>&lt;a href="target.html" class="wikilink"&gt;Название&lt;/a&gt;</code>`
- Браузер рендерит это **как сырой текст**, отображая читателю символы `<a href=...>` моноширинным шрифтом! Ссылка **не является кликабельной**, так как HTML-тег экранирован парсером Python-Markdown!
- И ровно в **4 случаях** внутри выносок (callouts) ссылка оказалась валидным тегом `<code><a href=...` — исключительно из-за побочного эффекта того, что `_transform_callouts` вызывался до `_transform_wikilinks`.

**Вывод и консенсус по защите кода:**
1. Пре-токенизация через сырую замену `%%CODEBLOCK%%` снята.
2. Реализуется **построчный конечный автомат (Fenced Code State Machine)**, аналогичный логике `_process_headings`:
   - Отслеживает маркеры ```` ``` ```` и `~~~` произвольной длины (3 и более символов).
   - Поддерживает префикс цитаты `> ` для кода внутри выносок.
   - Внутри fenced-блоков полностью подавляются wikilinks, callouts и очистка клише.
3. По согласованию с рецензентом, **inline-код на первом этапе не трогаем**, чтобы сохранить побайтовое совпадение `dist/` на этапах 1 и 2. Любая обработка fenced-кода выносится на коммит 3а (с фиксацией изменений ровно на 7 страницах).

### 2.3. Вопрос 3: Снятие режима `flat` и параметр `static_module_list` (Р4, Р6)
> *«Согласны ли снять режим `flat` (после U3/U5 он никому не нужен) и заменить третий режим навигации параметром `static_module_list`?»*

**Ответ: ДА, ПОЛНОСТЬЮ СОГЛАСНЫ.**

1. **Исключение режима `flat` по YAGNI:**  
   Поскольку по директиве U5 `go-workout` переходит на иерархическую модель «глава — каталог, задача — файл», плоский режим сканирования больше не нужен ни одному проекту. Ядро движка фокусируется на чистом рекурсивном сканере дерева каталогов произвольной глубины.
2. **Параметр `static_module_list` вместо третьего режима навигации:**  
   Рецензент блестяще рассчитал математику веса:
   - В `go-textbook` (22 модуля, 1 413 статей): 22 HTML-заглушки неактивных модулей весят суммарно ~6 КБ. Сайдбар со статическим списком модулей занимает ~29 КБ, страница ~85 КБ, весь `dist/` ~125 МБ. Здесь `static_module_list = true` — идеальный выбор.
   - В `go-workout` (100 глав, 7 666 задач): 100 HTML-заглушек в каждой из 7 666 страниц дали бы **230 МБ дублирующегося HTML только на заглушки!**
   - Установка `static_module_list = false` для `go-workout` оставляет в HTML страницы **только задачи текущей главы**, а каталог остальных 99 глав гидрируется клиентом через `nav-data.js`.
   - Страница задачи весит **~46 КБ**, а весь сайт на 7 666 страниц занимает **~345 МБ**, с огромным запасом укладываясь в лимит GitHub Pages (1 ГБ).
3. **Безопасность `file:///`:**  
   Подтверждаем: файл `assets/nav-data.js` обязан подключаться через `<script src="..." defer>`, так как вызов `fetch()` по протоколу `file:///` блокируется браузерами по CORS.

### 2.4. Вопрос 4: Формат страницы задачи в `go-workout`: разделы `##` vs Выноски
> *«Согласны ли с форматом «поля задачи — разделы `##`» вместо выносок? Если предлагаете выноски, как тогда выглядит TOC страницы?»*

**Ответ: ДА, ВЫБОР РАЗДЕЛОВ `##` АБСОЛЮТНО ОПРАВДАН И УТВЕРЖДАЕТСЯ.**

Мы сравнили оба подхода:
1. **Почему выноски (Callouts) плохи для отдельных страниц задач:**  
   Оглавление страницы (правый сайдбар TOC) строится парсером исключительно по заголовкам `##` и `###`. Если завернуть поля задачи («Условие», «Теория», «Решение», «Код», «Под капотом») в выноски `> [!task]`, `> [!theory]`, правый сайдбар на всех 7 666 страницах **будет абсолютно пустым**. Читатель лишится быстрой навигации к коду или теории.
2. **Преимущества семантических заголовков `##`:**
   - Правый TOC отображает четкую структуру задачи: `Условие`, `Теория`, `Решение по шагам`, `Код решения`, `Под капотом`, `Подводные камни`, `На собеседовании`.
   - Вложенные заголовки `###`/`####`, обнаруженные рецензентом внутри теории и разборов (598 полей), органично встраиваются в иерархию TOC.
   - По директиве U6 решения показываются открыто, поэтому функционал сворачивания спойлеров не требуется.
   - Чистая семантика HTML5 (`<h2>`), превосходная доступность (a11y) и удобство редактирования в любом Markdown-редакторе.

### 2.5. Вопрос 5: Имена файлов «номер + короткое имя» и `title_source = "h1"`
> *«Есть ли у вас возражения к имени файла «номер + короткое название» и заголовку из `# …`? Видите ли другой способ уложиться в ограничения Windows без потери полного названия?»*

**Ответ: ВОЗРАЖЕНИЙ НЕТ, ЭТО ЕДИНСТВЕННО ВЕРНОЕ ИНЖЕНЕРНОЕ РЕШЕНИЕ.**

Факты проверки:
- 4 439 названий задач содержат двоеточия (`:`) и другие символы, несовместимые с файловой системой Windows NTFS (`:*?"<>|/\`).
- 5 537 названий длиннее 60 символов (вплоть до 120 символов).
- Если формировать имена файлов из полных названий, длина относительного пути вместе с базовым каталогом репозитория на Windows превысит лимит `MAX_PATH` (260 символов).

**Утвержденный стандарт именования:**
1. Имя файла на диске: нормализованное, короткое (до 50 символов), без спецсимволов:  
   `sources/001. Пакеты и модули/001. Мгновенный запуск.md`.
2. Первая строка файла: полный авторский заголовок в H1:  
   `# Мгновенный запуск go run: компиляция во временный каталог и скриптинг`
3. Конфигурация движка: опция `title_source = "h1"` в `book.toml`. Сканер извлекает заголовок для хлебных крошек, `<title>`, сайдбара и поиска из первого H1, игнорируя техническое имя файла.

### 2.6. Вопрос 6: Разделители KaTeX и защита переменных `$GOPATH`
> *«Разделители KaTeX для `go-workout`: только `\(…\)` и `$$…$$` с переводом настоящих формул — или вы видите более надёжный способ отличить формулу от `$GOPATH`?»*

**Ответ: ДА, ЭТО САМЫЙ НАДЕЖНЫЙ СПОСОБ. СОГЛАСОВЫВАЕТСЯ.**

Анализ проблемы:
В технических материалах по Go символ `$` массово используется в shell-командах, переменных окружения (`$GOPATH`, `$GOROOT`), именах параметров (`$(date)`) и ценах (`$100`). В кодовой базе `go-workout` обнаружено 2 319 полей с `$`. Оставлять одиночный `$` в качестве математического разделителя KaTeX — гарантированно сломать отображение шелл-команд.

**Утвержденная стратегия:**
1. В движке вводится параметр `katex.delimiters`:
   - Для `go-textbook`: стандартный набор (включая `$`, если требуется).
   - Для `go-workout`: строго `\(...\)` (inline) и `$$...$$` (display). Одиночный `$` исключается из разделителей KaTeX.
2. В разовом скрипте миграции контента `tools/migrate_workout.py`:
   - Выполняется поиск конструкций с `$`, содержащих специфичные LaTeX-команды (`\to`, `\times`, `\approx`, `\frac`, `\le`, `O(n \log n)` и т.д. — 1 171 поле).
   - Они автоматически транслируются в формат `\(...\)`.
   - Обычные переменные (`$GOPATH`, `$PORT`) остаются обычными символами `$` и гарантированно не парсятся KaTeX.

## 3. Инженерные решения и уточнения по замечаниям Критики №3

### 3.1. Алгоритм защиты кода: Конечный автомат оград (Fenced Code State Machine)

Вместо глобальных регулярных выражений в конвертер (`engine/converter.py`) внедряется надежный построчный конечный автомат:

```python
class FencedCodeDetector:
    """Отслеживает границы fenced code блоков с учетом произвольной длины оград и цитат."""
    
    def __init__(self):
        self.in_fence = False
        self.fence_char = ""
        self.fence_length = 0

    def process_line(self, line: str) -> bool:
        """Возвращает True, если строка находится ВНУТРИ блока кода."""
        stripped = line.strip()
        # Снимаем префикс цитаты, если проверяем код внутри callout
        if stripped.startswith(">"):
            stripped = stripped.lstrip("> ").strip()

        match = re.match(r"^(`{3,}|~{3,})", stripped)
        if match:
            marker = match.group(1)
            char = marker[0]
            length = len(marker)

            if not self.in_fence:
                # Начало блока кода
                self.in_fence = True
                self.fence_char = char
                self.fence_length = length
                return True
            else:
                # Проверяем закрывающую ограду (тот же символ, длина >= открывающей)
                if char == self.fence_char and length >= self.fence_length:
                    self.in_fence = False
                    self.fence_char = ""
                    self.fence_length = 0
                    return True

        return self.in_fence
```

**Интеграция в трансформации Markdown:**
Трансформации wikilinks (`_transform_wikilinks`), выносок (`_transform_callouts`) и клише (`_clean_cliches`) применяются только к строкам, для которых `detector.process_line(line) == False`.  
Это гарантирует 100% защиту листингов кода от случайных замен квадратных скобок в тестах или шелл-скриптах.

### 3.2. Архитектура рантайм-конфигурации: Единый контракт `window.__BOOK_CONFIG__`

Для ликвидации бага рассинхронизации inline-скрипта в `<head>` и `main.js` (дефект M9 и замечание Р5) принимается строгая модель:

1. **Генерация объекта в `<head>`:**
   Сборщик генерирует в HTML единственный глобальный конфигурационный объект (данные берутся из `manifest.json` и `book.toml`):
   ```html
   <script>
     window.__BOOK_CONFIG__ = {
       storagePrefix: "go_encyclopedia",
       defaultTheme: "dark",
       themes: ["dark", "light", "paper"],
       retroProfilesKey: "go_encyclopedia_retro_effects_"
     };
   </script>
   ```

2. **Инлайн-скрипт определяет функции и применяет anti-flicker:**
   В `<head>` инжектируются чистые функции, которые затем **переиспользуются** в `main.js` без дублирования:
   ```html
   <script>
   (function() {
     try {
       var cfg = window.__BOOK_CONFIG__;
       var d = document.documentElement;
       var t = localStorage.getItem(cfg.storagePrefix + '_theme');
       d.dataset.theme = (t && cfg.themes.indexOf(t) !== -1) ? t : cfg.defaultTheme;

       var r = localStorage.getItem(cfg.retroProfilesKey + d.dataset.theme);
       if (r) {
         var c = JSON.parse(r), s = d.style;
         if (c.trail && c.trail.enabled === true) {
           d.dataset.retroTrail = 'on';
           s.setProperty('--retro-trail', '0.20');
         }
         ['site', 'code'].forEach(function(g) {
           var o = c[g]; if (!o) return;
           ['vhs', 'crt', 'noise'].forEach(function(e) {
             var x = o[e]; if (!x || x.enabled !== true) return;
             var v = Math.max(0, Math.min(100, Math.round(Number(x.strength))));
             if (v > 0) {
               d.dataset[g + e.charAt(0).toUpperCase() + e.slice(1)] = 'on';
               s.setProperty('--retro-' + g + '-' + e, (v / 100).toFixed(2));
             }
           });
         });
       }
     } catch(e) {}
   })();
   </script>
   ```

3. **Браузерная верификация в CI:**  
   В тестовый набор добавляется headless Firefox тест, проверяющий отсутствие моргания темы и атрибутов `dataset` до и после `DOMContentLoaded`.

### 3.5. Инструментарий QA-аудита: Пути Windows, CDN и бейслайн ссылок

В универсальный скрипт `engine/audit.py` добавляются следующие обязательные проверки:
1. **Offline-First Guard:** Проверка всех сгенерированных HTML на отсутствие абсолютных ссылок `http://` и `https://` внутри тегов `<script src="...">`, `<link href="...">` и `<img src="...">`. Запрещены любые внешние CDN.

4. **Duplicate Anchor Check:** Проверка отсутствия дублирующихся `id` заголовков на каждой странице.
