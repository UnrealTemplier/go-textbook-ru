## 3. 🟠 В33. Блок кода оказывается внутри `<p>`, а отступ плейсхолдера считается не в тех координатах

### 3.1. Что происходит

В корпусе ограда с отступом почти всегда стоит **сразу после строки пункта**, без пустой строки:

```markdown
2. **Блочное объявление**:
   ```go
   var (
       name string = "Go"
   )
   ```
3. **Короткое объявление** `:=`: доступно только внутри функций.
```

Препроцессор § 4.2 заменяет ограду одной строкой `    <плейсхолдер>`. Пустой строки перед ней нет. Python-Markdown читает её как продолжение абзаца пункта и подставляет блок внутрь `<p>`:

```html
<li>
<p><strong>Блочное объявление</strong>:<br />
    
<div class="code-block" data-lang="go"> … </div>
</p>
</li>
```

На верхнем уровне `fenced_code` такого не допускает: там `<p>text</p>` и `<pre>` идут раздельно. Ответ пишет «при отступе в 4 пробела Python-Markdown надёжно удерживает плейсхолдер внутри тега `<li>`». Внутри `<li>` блок действительно остаётся, но при этом попадает в `<p>`.

### 3.2. Чем это плохо

* `<div>` и `<pre>` внутри `<p>` — невалидный HTML. Браузер закрывает `<p>` перед `<div>`, а оставшийся `</p>` превращает в **новый пустой абзац** с полями. Под каждым таким блоком появляется лишний отступ, а перед ним висит `<br />`.
* Если после кода идёт строка текста, она остаётся вне `<p>` и теряет стили прозы (ширина 880 px, `line-height`).
* Масштаб: **178 из 243** новых блоков на **96** страницах. С препроцессором списков — 161 на 83.
* Согласованный оракул А3з этого **не увидит**. Текстовая проекция совпадает, `<li>` не растёт, старые блоки кода не меняются. Коммит прошёл бы проверку и ушёл бы в публикацию.

### 3.3. Почему простое «добавить пустую строку» не помогает

Я проверил очевидную правку: пустые строки до и после плейсхолдера. Она убирает `<p>`, но вскрывает две другие проблемы.

**(а) Текст после кода выпадает из списка.** В исходнике текст продолжения стоит с отступом 2–3, как в Obsidian. После пустой строки Python-Markdown требует 4, поэтому абзац уходит из пункта. Пример — страница «Барьеры памяти»: пункт `ARM64` превращается в строку `* **ARM64:** …` внутри абзаца, `<li>` −1. Таких страниц в корпусе 20.

**(б) Квантование отступа считает в чужих координатах.** Ответ ставит плейсхолдер на `((отступ_маркера // 4) + 1) * 4`. Это число в координатах Python-Markdown. Но препроцессор списков (приоритет 19) работает **после** препроцессора оград (24) и переводит отступы Obsidian в отступы Python-Markdown. Плейсхолдер он получает уже переведённым и переводит ещё раз. Для вложенного пункта с маркером на 3 и оградой на 5 (4 блока в корпусе: «Backward compatibility», «CASE выражения», «fork/exec», «Безопасность») ответ ставит 4. После перевода это продолжение **внешнего** пункта:

```text
вход (Obsidian):                      ответ №12 + пустые строки + списки:
1. **Фаза 1**                         <ol><li><p>Фаза 1</p>
   - поле                               <ul><li>поле</li><li>Бэкенд:</li></ul>
   - Бэкенд:                            <pre>type T struct{}</pre>      ← код поднялся на уровень
     ```go                              <ul><li>Релиз.</li></ul>        ← вложенный список разорван
     type T struct{}                  </li> …
     ```
   - Релиз.
```

Сейчас (б) скрыта: почти все ограды идут сразу после текста, и плейсхолдер подхватывается абзацем независимо от отступа. Как только (а) исправят, (б) проявится.

### 3.4. Предложение (проверено)

1. **Плейсхолдер — отдельный блок.** Перед ним пустая строка, если предыдущая строка не пустая. После него тоже пустая строка, если следующая не пустая.
2. **Отступ плейсхолдера — отступ самой ограды** (координаты исходника). Переводом в отступы Python-Markdown занимается только препроцессор списков, и делает это один раз.
3. **А3з не работает без А3л.** Без препроцессора списков правильного результата нет ни у одного варианта: Python-Markdown требует отступ 4, а в исходниках 2–3. Предлагаю в `book.toml` один флаг (например, `[markdown] obsidian_lists = true`), который включает оба препроцессора, или ошибку конфигурации, если включён только препроцессор оград. Для обеих книг это ничего не меняет: `go-workout` включает оба с первого дня, `go-textbook` получает их одним push (А3л + А3з).
4. **Препроцессор списков (А3л)** должен вставлять пустую строку перед пунктом, если текущий блок (от последней пустой строки) начался с более глубокого отступа. Иначе Python-Markdown склеит пункт `2.` с абзацем вложенного пункта или с текстом после кода (входы 16 и 17 ниже). Это правило касается именно пары А3л + А3з: пустые строки вокруг плейсхолдера создают такие блоки.

Эталон препроцессора оград на основе `scan_indented_fences` из ответа (сканер не меняется):

```python
def run(self, lines: list[str]) -> list[str]:
    blocks = {b['start_line']: b for b in scan_indented_fences(lines, self.warn)}
    out, i = [], 0
    while i < len(lines):
        b = blocks.get(i)
        if b is None:
            out.append(lines[i]); i += 1; continue
        code = '\n'.join(b['code_lines']) + '\n' if b['code_lines'] else ''   # байты как у fenced_code, включая пустой блок
        lang = f' class="language-{b["lang"]}"' if b['lang'] else ''
        ph = self.md.htmlStash.store(f'<pre><code{lang}>{self._escape_code(code)}</code></pre>')
        if out and out[-1].strip():
            out.append('')                      # плейсхолдер — отдельный блок, а не строка абзаца
        out.append(b['open_indent'] + ph)       # координаты исходника; перевод отступов — дело препроцессора списков
        nxt = b['end_line'] + 1
        if nxt < len(lines) and lines[nxt].strip():
            out.append('')
        i = nxt
    return out
```

Проверено на корпусе вместе с моим прототипом списков (приоритет 19, правило п. 4):

* блоков кода внутри `<p>`: **0** (у ответа №12 — 161);
* `<code>язык\n` вне `<pre>`: 222 → 2. Оставшиеся 2 — ограды в обычных цитатах `> ```go` («Zero Value», «Longest Common Prefix»). Это не списки, U13 их не покрывает;
* тексты старых блоков кода не изменились, кроме страницы о дедлоках (разрешено условием Н10);
* синтетика: 15 входов критики №11 и 3 новых (§ 3.5) — код в нужном пункте, 0 блоков в `<p>`. Во входе 18 мой прототип не превращает в список строки `- …` после текста. Это правило Н5 из А3л, на размещение кода оно не влияет.

Мой прототип списков грубый: например, вложенный список сразу после строки текста внутри пункта он не чинит (страница «Планировщик ОС»). Задача Н5 это уже покрывает, а на В33 не влияет. Цифры выше подтверждают решение для оград, а не служат эталоном А3л.

## 4. 🟡 В34. «Золотое правило» противоречит приоритету 24, а причину можно убрать

Ответ (§ 2.4) записывает: «Любые строчные препроцессоры ядра, модифицирующие отступы или структуру Markdown-текста, обязаны регистрироваться с приоритетом ниже 20». Но сам препроцессор оград стоит на **24**. И он обязан стоять выше 20: я проверил его на 19, и `html_block` уже спрятал строки кода вида `<div class="x">` как сырой HTML. Код превратился в разметку:

```text
- шаблон:                    приоритет 24: <pre><code>&lt;div class=&quot;x&quot;&gt; …
  ```html                    приоритет 19: <div class="x"> <p>hi</p> </div>   ← код стал HTML страницы
  <div class="x">
  <p>hi</p>
  </div>
  ```
```

Значит, правило в такой форме неверно. На 24 препроцессор оград видит строки HTML выносок в основном проходе (это и есть причина Н10). На корпусе он их не трогает, но гарантии этому нет.

**Предложение (проверено).** Убрать причину, а не обходить её приоритетами. Выноски прячутся в плейсхолдеры, как уже сделано для Mermaid: шаг 3 возвращает `\n\n<!--CALLOUT_N-->\n\n`, HTML выноски подставляется на шаге 7, до `_wrap_tables` и `_enhance_code_blocks`. Тогда ни один препроцессор основного прохода, wikilinks (шаг 4) и маска не видят HTML выносок. Wikilinks в теле выноски обрабатываются в той рекурсии, которая уже согласована для А3а′.

Проверка: выноски-плейсхолдеры вместе с рекурсией wikilinks по телу выноски дают на корпусе после нормализации пробелов отличия ровно на **6** страницах. Это те же 6 страниц А3а′ из раунда 7: 4 ссылки в inline-коде, `&amp;amp;`, `[[2], [2]]`. `<pre>` побайтно равны на всех 1 413 страницах. По байтам меняются только пустые строки вокруг `<aside>` на 1 380 страницах, поэтому место этому — в коммите **А3а′**, с нормализатором пробелов из А0.

Правило для спецификации тогда звучит так: «Строчные препроцессоры работают с Markdown, а не с готовым HTML: готовый HTML (Mermaid, выноски) всегда прячется в плейсхолдеры. Препроцессор оград — 24 (выше `html_block`, иначе HTML в коде станет разметкой), списки — 19».

Если автор ответа против плейсхолдеров выносок, минимальный вариант: правило с явным исключением для оград и причиной. Тогда в оракул А3з нужно добавить «HTML выносок не меняется».

## 5. 🟡 В35. Маска: на каком тексте и для каких единиц

Класс маски верен (§ 1). Но в ответе нет второй половины требования из критики №11: «маска строится на каждую единицу конвертации — статью и тело каждой выноски». Без неё остаются два пробела:

* **Выноски.** В телах выносок корпуса 22 ограды с отступом, и маска по тексту статьи их не видит: строки выноски начинаются с `>`. Сейчас это ни на что не влияет (в коде выносок 0 строк со `[[` или клише). Но движок делается не только для этого корпуса.
* **Номера строк.** Маска строится по `raw_text`, а wikilinks (шаг 4) обрабатывают текст **после** шагов 2–3. Mermaid и выноски к этому моменту заменены, и число строк другое. Номера строк `raw_text` к нему не подходят.

**Предложение.** Записать в спецификацию: маска строится по тому тексту, который правит потребитель, в момент правки. Клише (шаг 1) — по тексту статьи и отдельно по телу каждой выноски, со снятым префиксом `>`. Wikilinks — по тексту шага 4 (если выноски — плейсхолдеры, В34, в нём нет их HTML) и по телу каждой выноски в рекурсии А3а′. Свойство-тест сравнивает маску с выводом `md` для обеих единиц.
