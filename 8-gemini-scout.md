### Кандидат 1: Нерабочий листинг BuildKit Dockerfile из-за пропуска копирования файлов манифеста
* **article/section:** `25. Кэширование сборки Docker.md` / `## 3. Продвинутое кэширование зависимостей с BuildKit` (строки 96–113)
* **claim:** Листинг передового Dockerfile с постоянными томами кэша:
  ```dockerfile
  # syntax=docker/dockerfile:1.4
  FROM golang:1.22-alpine AS builder

  WORKDIR /app

  # Монтируем кэш Go Modules в специальный том
  # Он не попадет в финальный образ, но сохранится между сборками на машине
  RUN --mount=type=cache,target=/go/pkg/mod \
      --mount=type=cache,target=/root/.cache/go-build \
      go mod download

  COPY . .
  ```
* **why it needs checking:** Этот Dockerfile содержит фатальную синтаксическо-логическую ошибку и **не может быть собран**:
  1. Команда `WORKDIR /app` создает новую абсолютно пустую директорию внутри слоя контейнера.
  2. Инструкция `COPY go.mod go.sum ./` перед вызовом `RUN ... go mod download` полностью пропущена.
  3. При выполнении команды `go mod download` тулчейн Go аварийно завершится ошибкой:  
     `go: go.mod file not found in current directory or any parent directory`.  
  Сборка падает на первом же шаге. Читатель, скопировавший данный «production ready» шаблон, получит гарантированно сломанный билд.
* **evidence/source needed:** Проверка сборки приведенного листинга через `docker build`; официальная документация Docker BuildKit Cache Mounts.
* **priority:** 🔴 **High**

### Кандидат 2: Ошибочное утверждение о синтаксисе передачи флагов в `go run` для одиночных файлов
* **article/section:** `4. go run и быстрый цикл разработки.md` / `## Аргументы и флаги` (строки 67–73)
* **claim:** 
  ```bash
  # Неправильно: go run попытается интерпретировать -config как свой флаг и завершится с ошибкой
  go run main.go -config=dev.yaml

  # Правильно: флаги go run идут до точки/файла, аргументы приложения — после
  go run . -config=dev.yaml
  ```
* **why it needs checking:** Данное утверждение фактически ложно:
  1. В утилите `go run` позиционная схема парсинга аргументов строго регламентирована: аргументы, идущие **после** первого `.go`-файла (или точки пакета), безоговорочно передаются в запускаемую программу (`os.Args`).
  2. Команда `go run main.go -config=dev.yaml` работает абсолютно корректно и штатно передает `-config=dev.yaml` приложению. Ошибка `flag provided but not defined: -config` возникает только в том случае, если флаг указан **до** имени файла: `go run -config=dev.yaml main.go`.
  3. Текст утверждает, будто для передачи аргументов обязательно указывать пакет через точку (`go run . -config=...`), что является дезинформацией разработчиков о механике работы CLI Go.
* **evidence/source needed:** `go help run`; запуск в командной строке `go run main.go -flag=val`.
* **priority:** 🔴 **High**

### Кандидат 3: Вымышленный флаг `-name` в утилите `go install`
* **article/section:** `5. go install и установка CLI.md` / `## Замена бинарников и Конфликты` (строка 83)
* **claim:** «Имя файла бинарника определяется последним сегментом пути импорта (или значением `go install -name`, что используется редко).»
* **why it needs checking:** 
  1. Флага `-name` в утилите `go install` не существует и никогда не существовало в официальном тулчейне Go.

* **evidence/source needed:** `go help install`; исходный код `src/cmd/go/internal/work/build.go` и `src/cmd/go/internal/work/install.go`.

### Кандидат 4: Некомпилируемый листинг `unreachable code` в статье о статическом анализе `go vet`
* **article/section:** `7. go vet. Статический анализ.md` / `### 5. unreachable: Недостижимый код` (строки 106–117)
* **claim:** Листинг приводится как пример того, что компилятор Go пропускает недостижимый код, а `go vet` его отлавливает:
  ```go
  func getStatus() string {
      return "ok"
      fmt.Println("This will never print") // vet: unreachable code
  }
  ```
* **why it needs checking:** 
  1. Этот код **не компилируется компилятором Go**. При попытке сборки компилятор выдает фатальную ошибку: `missing return` (или ошибку терминации функции), и процесс сборки завершается с кодом 1.
  2. Утилита `go vet` производит анализ поверх успешно разобранного AST типов. При наличии синтаксических или терминальных ошибок компилятора `go vet` даже не запускает свои анализаторы, завершаясь с ошибкой компиляции: `vet: missing return`.
  3. Чтобы продемонстрировать проверку `unreachable` в `go vet`, код обязан быть валидным с точки зрения компилятора (например, бесконечный цикл `for {}` с кодом после него, либо вызов `panic()` в функции без возвращаемого значения). Приведенный в статье код неработоспособен.
* **evidence/source needed:** Тестовый запуск `go build` и `go vet` на приведенном фрагменте; Спецификация языка Go (Terminating statements).
* **priority:** 🔴 **High**

### Кандидат 5: Ложное утверждение об «откате к более старой версии» в MVS при директиве `exclude`
* **article/section:** `14. Dependency management. replace, exclude.md` / `## 3. Директива exclude: Исключение версий` (строки 63 и 68)
* **claim:** 
  - «Если ваш проект (или любая транзитивная зависимость) запрашивает `github.com/broken/lib v1.5.0`, Go исключит её из рассмотрения и выберет следующую подходящую версию (например, `v1.5.1` или откатится к совместимой `v1.4.0`)».
  - «Тогда MVS выберет `v1.4.0` (если она совместима) или `v1.5.1`».
* **why it needs checking:** 
  1. Алгоритм Minimal Version Selection (MVS) математически оперирует требованиями как **нижними границами (lower bounds)**.
  2. Если модуль требует `v1.5.0`, это означает требование `версия >= v1.5.0`. Версия `v1.4.0` строжайше меньше `v1.5.0` и не удовлетворяет этому требованию.
  3. При директиве `exclude lib v1.5.0` алгоритм MVS **никогда не может откатиться к `v1.4.0`**. Он перебирает исключительно более старшие версии (`v1.5.1`, `v1.6.0`), удовлетворяющие ограничению `>= v1.5.0`. Если более высокой версии нет в репозитории, сборка завершится ошибкой невозможности разрешения зависимостей. Утверждение об откате искажает фундаментальную семантику MVS.
* **evidence/source needed:** Официальная документация Go Modules Reference (Minimal Version Selection); статьи Расса Кокса по MVS (`research.swtch.com/vgo-mvs`).
* **priority:** 🔴 **High**

### Кандидат 6: Невалидный синтаксис загрузки `.env` в конфигурации Taskfile


### Кандидат 7: Ложное утверждение об обязательности файла `/etc/passwd` для запуска от non-root в образе `scratch`
* **article/section:** `24. Минимизация образов. scratch, distroless.md` / `## 3. Нюансы использования scratch` (строки 124–125)
* **claim:** «В `scratch` пользователя нет, поэтому там процесс всегда запускается от root (UID 0), если только вы не создали `/etc/passwd` вручную. Запуск от root в контейнере — серьезный риск безопасности».
* **why it needs checking:** 
  1. Спецификация ядра Linux и среды исполнения OCI/Docker **не требуют** наличия файла `/etc/passwd` для запуска процессов от непривилегированного пользователя.
  2. Контейнер на базе `scratch` можно запустить от любого non-root пользователя, просто указав **числовой UID:GID**:
     - В Dockerfile: `USER 65534:65534` (или `USER 10001:10001`).
     - В манифесте Kubernetes: `securityContext.runAsUser: 10001` и `securityContext.runAsNonRoot: true`.
  3. Ядро Linux оперирует исключительно числовыми идентификаторами в структурах `cred` процесса. Файл `/etc/passwd` в контейнере необходим только в том случае, если само Go-приложение использует функции преобразования строковых имен пользователей в UID (пакет `os/user`), либо если в Dockerfile пишется строковое имя `USER nobody` вместо числового ID. Утверждение, что без `/etc/passwd` процесс *всегда* запускается от root, технически неверно.
* **evidence/source needed:** Dockerfile Reference (`USER <UID>[:<GID>]`); OCI Runtime Specification; тесты запуска контейнера `scratch` с `USER 10001`.
* **priority:** 🔴 **High**

### Кандидат 8: Утверждение о «перемещении памяти сборщиком мусора» и опасная рекомендация финализаторов в CGO
* **article/section:** `34. CGO и его влияние на сборку.md` / `## 3. Передача данных между Go и C` (строка 103)
* **claim:** «Если вы передаете указатель на структуру Go во внешний C-код, а ссылка внутри Go теряется, сборщик мусора переместит или освободит этот участок памяти, что приведет к коварным гонкам и повреждению памяти (use-after-free). Для безопасной передачи данных необходимо использовать копирование через `C.GoString` / `C.CBytes` или явно регистрировать финализаторы через `runtime.SetFinalizer`».
* **why it needs checking:** 
  1. **GC в Go никогда не перемещает память:** Сборщик мусора Go (Tricolor Mark-Sweep) является неперемещающим (non-moving, non-compacting). Объекты на куче Go сохраняют фиксированный физический адрес на протяжении всей жизни. Заявление о том, что GC «переместит память», фундаментально ошибочно.
  2. **Финализаторы усугубляют проблему вместо защиты:** Рекомендация регистрировать `runtime.SetFinalizer` педагогически опасна. Механизм `SetFinalizer` срабатывает ровно тогда, когда сборщик мусора обнаруживает, что объект стал недостижим из графа Go-ссылок. Если ссылка осталась только на стороне C, вызов финализатора как раз преждевременно разрушит или очистит объект в то время, как C-код продолжает с ним работать!
  3. Для безопасного удержания памяти при работе с CGO стандарт требует либо использования `runtime.KeepAlive(p)` в вызывающей функции Go, либо фиксации адреса через современный примитив `runtime.Pinner` (Go 1.21+), либо явного выделения неуправляемой памяти через `C.malloc`.
* **evidence/source needed:** `src/runtime/mgc.go` (архитектура non-moving GC); документация `cmd/cgo` (Passing pointers); документация `runtime.Pinner` и `runtime.KeepAlive`.
* **priority:** 🔴 **High**

### Кандидат 9: Ошибочное утверждение об исполнении команд `go generate` через командную оболочку (shell)
* **article/section:** `9. go generate. Генерация кода.md` / `## 1. Концепция и назначение` (строка 26) и диаграмма (строка 43)
* **claim:** 
  - «...находит комментарий `//go:generate` и выполняет указанную после него команду (`stringer -type=Pill`) как обычный shell-процесс».
  - На диаграмме: `Поиск директив -> Извлечение команды -> Исполнение команды в shell`.
* **why it needs checking:** 
  1. В официальной документации `go help generate` прямо зафиксировано: тулчейн выполняет генераторы **напрямую** через вызов `os/exec` без промежуточной командной оболочки (shell). Никакого shell-процесса не создается.

### Кандидат 16: Ошибочные права доступа к файлам в `$GOMODCACHE` (`0555` vs `0444`)

  3. Для профилирования исключительно бенчмарков общепринятым стандартом является подавление запуска юнит-тестов регулярным выражением: `go test -run=^$ -bench=. -cpuprofile=cpu.out -memprofile=mem.out`.
* **evidence/source needed:** `go help testflag`; Go benchmarking best practices.
* **priority:** 🟢 **Low**

### Кандидат 25: Отсутствие информации об автоматическом управлении тулчейном (`GOTOOLCHAIN` в Go 1.21+)
* **article/section:** `2. go toolchain. Общая архитектура инструментов.md` и `12. Модули. go.mod и go.sum.md`
* **claim:** Описание установки и смены версий компилятора ограничено ручным скачиванием через `golang.org/dl` и пакетные менеджеры ОС.
* **why it needs checking:** 
  1. Начиная с Go 1.21 в тулчейне появилась революционная механика `toolchain`: если в `go.mod` указана директива `toolchain go1.23.1` (или `go 1.23.0`), стандартная команда `go build` автоматически скачивает нужную версию компилятора на лету и делегирует ей сборку.
  2. Механизм управляется переменной окружения `GOTOOLCHAIN` (`auto`, `local`, `path`). Это фундаментальное архитектурное изменение экосистемы Go, устраняющее проблемы с несовпадением версий в CI и на рабочих машинах разработчиков.
* **evidence/source needed:** Go 1.21 Release Notes (Toolchain management); `go.dev/doc/toolchain`.

## 🔍 Скрытые технические пробелы и белые пятна (Blind Spots)

В ходе сплошного анализа 41 статьи Модуля 8 выявлены важные системные механизмы экосистемы тулинга и контейнеризации, которые в текущем тексте либо не освещены, либо требуют явного инженерного акцента:

1. **Проблема базы часовых поясов (`tzdata`) и сертификатов (`ca-certificates`) в `scratch`:**  
   В статьях 22 и 24 подробно описываются преимущества минималистичного образа `scratch`. Однако полностью опущена критическая проблема продакшена: вызов `time.LoadLocation("Europe/Moscow")` в образе `scratch` завершается паникой или ошибкой `unknown time zone`, так как в образе отсутствуют файлы `/usr/share/zoneinfo`. Решение — либо копирование файлов таймзон из builder-этапа, либо импорт стандартного пакета-встраивателя: `_ "time/tzdata"`. Аналогично для HTTPS-запросов требуется явное копирование `/etc/ssl/certs/ca-certificates.crt`.

2. **Сетевой резолвер DNS в Go (`netgo` vs cgo-резолвер) и особенности сборок с Alpine/musl:**  
   В статьях 24 и 34 о CGO и контейнеризации не раскрыта тема переключения сетевого резолвера. В Linux Go по умолчанию может использовать резолвер на базе CGO (библиотечный `getaddrinfo`). При компиляции с `CGO_ENABLED=0` или при кросс-компиляции тулчейн переключается на встроенный Pure Go резолвер (`netgo`). В контейнерах Alpine (на базе `musl libc`) различия в обработке DNS (`/etc/resolv.conf`, таймауты, параллельные запросы A/AAAA) часто приводят к трудноуловимым сетевым задержкам и падениям. Инженерам необходимо знать теги сборки `-tags netgo,osusergo`.

3. **Profile-Guided Optimization (PGO) в современном тулчейне (Go 1.20–1.21+):**  
   В статьях 3 («go build») и 36 («Профилирование в CI») отсутствует упоминание механизма Profile-Guided Optimization. Начиная с Go 1.20 (экспериментально) и Go 1.21 (production ready), компилятор Go умеет принимать профиль рабочей нагрузки `default.pgo` и производить агрессивный инлайнинг и девиртуализацию «горячих» участков кода, давая 2–7% прироста производительности в продакшене без единой строчки нового кода. Внедрение PGO в сборочные конвейеры CI — современный отраслевой стандарт.

4. **Аудит безопасности зависимостей через `govulncheck` и генерация SBOM:**  
   В статьях 7, 18 и 30 о статическом анализе и Quality Gates не упомянут официальный инструмент от команды Go — **`govulncheck`**. В отличие от наивных сканеров, сверяющих только версии модулей в `go.mod`, `govulncheck` строит граф вызовов приложения (Call Graph) и сообщает об уязвимости только в том случае, если уязвимая функция стороннего пакета реально вызывается в коде. Также актуальна генерация Software Bill of Materials (SBOM) в CI через `cyclonedx-gomod` или встроенный `go version -m`.
