## 2. High

### J-01 — OUTDATED
- **Где / цитата:** ст. 19 целиком (`hmap`, `bmap`, `tophash`, load factor 6.5, эвакуация), врезка 19:29–30; ст. 18:41 («выделит необходимое число корзин (бакетов)»); ст. 19:104, 189 («полностью исключая внутренний padding»); ст. 19:115 («Векторный поиск внутри бакета»); ст. 44:52.
- **Вердикт:** модель `hmap/bmap` верна для Go 1.0–1.23. С Go 1.24 `map` — Swiss Tables. Врезка 19:30 это говорит, но всё остальное тело подаёт старую модель как текущую. Дополнительно:
  - **Раскладка.** В Swiss Tables по умолчанию слоты *чередуются* (KVKV…). Раздельная раскладка (KKKK…VVVV) — только с `GOEXPERIMENT=mapsplitgroup`. Утверждение «padding полностью исключён» для 1.24+ неверно.
  - **«Векторный поиск» в `bmap`** (19:115). В старой реализации это был скалярный цикл по `tophash`. SIMD-сравнение 8 контрольных байт — свойство Swiss Tables, и то только на amd64 (см. F-02).
  - **Старой реализации больше нет.** В go1.27.1 в `src/internal/goexperiment/` нет флага swissmap, `noswissmap` отключить нельзя. Отключение `GOEXPERIMENT=noswissmap` было в Go 1.24.
  - **Что осталось верным для обеих моделей:** после `delete` всех ключей память не возвращается (измерено, см. J-63), порядок обхода случаен.
- **Доказательство:**
  - go1.27.1 `src/internal/runtime/maps/map.go:18` — «The map design is based on Abseil's "Swiss Table"»; строки 27–29 — `H1`/`H2`.
  - `table.go:20` — `maxTableCapacity = 1024`; `group.go:20` — `maxAvgGroupLoad = 7` (из 8).
  - `src/cmd/compile/internal/reflectdata/map.go:43–70`: `if buildcfg.Experiment.MapSplitGroup { // Split layout (KKKKVVVV) } else { // Interleaved slot layout (KVKVKVKV) }`.
  - Go 1.24 release notes: «a new builtin `map` implementation based on Swiss Tables… may be disabled by setting `GOEXPERIMENT=noswissmap`».
- **Предлагаемая правка:**
  - Ст. 19: в заголовок и начало тела — «Классическая реализация (Go 1.0–1.23)». Отдельный короткий раздел «Go 1.24+: Swiss Tables»: группы по 8 слотов с контрольным словом (`ctrl uint64`, H2 — младшие 7 бит хэша); таблицы не больше 1024 слотов; directory таблиц; рост расщеплением одной таблицы; tombstones при удалении; слоты по умолчанию чередуются (`key, elem`).
  - Ст. 19:104 и итог п.2: «в Go ≤ 1.23 раздельное хранение ключей и значений исключало padding; в Swiss Tables 1.24+ слоты по умолчанию чередуются».
  - Ст. 19:115: «скалярный цикл по 8 байтам `tophash`».
  - Ст. 44:52: «хэш-таблица (с Go 1.24 — Swiss Tables)».

### J-06 — INCORRECT
- **Где / цитата:** ст. 4:149 «Лишь после того как рантайм и все пакеты полностью готовы к работе, планировщик создает первую пользовательскую горутину и запускает в ней функцию `main.main()`»; 4:122 «…переходит в платформонезависимую точку `runtime.rt0_go`»; 4:147 «инициализирует фоновые потоки сборщика мусора»; диаграмма 4:133–134.
- **Вердикт:**
  - Горутина `runtime.main` создаётся в `rt0_go` (`newproc`) **до** инициализации пакетов. В ней по очереди выполняются `doInit` рантайма, `gcenable()`, `doInit` всех пакетов, затем прямой вызов `main_main`. Новой горутины для `main.main` нет.
  - `rt0_go` — ассемблерная функция, своя для каждой архитектуры.
  - `gcenable()` запускает горутины `bgsweep`/`bgscavenge`, а не потоки.
- **Доказательство:**
  - go1.27.1 `src/runtime/asm_amd64.s:142` — `TEXT runtime·rt0_go`; :340 `CALL runtime·schedinit`; :343–345 `MOVQ $runtime·mainPC(SB), AX` / `CALL runtime·newproc`; :349 `CALL runtime·mstart`. `rt0_go` определён в 11 файлах `asm_*.s`.
  - `src/runtime/proc.go`, `func main()`: `doInit(runtime_inittasks)`, `gcenable()`, цикл `doInit(m.inittasks)`, затем `fn := main_main; fn()`.
  - `src/runtime/mgc.go`, `gcenable`: `go bgsweep(c); go bgscavenge(c)`.
- **Предлагаемая правка:**
  - 4:122: «…переходит в ассемблерную функцию `runtime·rt0_go` (у каждой архитектуры своя, `asm_amd64.s`, `asm_arm64.s`…)».
  - 4:147: «…и запускает фоновые горутины очистки (`bgsweep`) и возврата памяти ОС (`bgscavenge`)».
  - 4:149: «Ещё до инициализации пакетов `rt0_go` создаёт главную горутину с функцией `runtime.main`. Уже в ней рантайм инициализирует себя, включает GC, выполняет `init` всех пакетов в порядке зависимостей и, наконец, напрямую вызывает `main.main()`».
  - Диаграмма: узел `Main` — «runtime.main вызывает main.main».

### J-09 — INCORRECT
- **Где / цитата:** ст. 8:170 «процессор сгенерирует аппаратное исключение (прерывание `SIGFPE`), которое рантайм Go перехватит и превратит в `panic`, аварийно завершив текущую горутину».
- **Вердикт:**
  - gc вставляет явную проверку делителя на ноль и вызывает `runtime.panicdivide` — `SIGFPE` не возникает.
  - Неперехваченная паника завершает **весь процесс** (код 2), а не горутину.
  - Для `float64` деление на 0 даёт `±Inf`/`NaN` без паники.
- **Доказательство:** go1.27.1, `go build -gcflags=-S` для `func div(a, b int) int { return a / b }`: `TESTQ BX, BX` → `CALL runtime.panicdivide(SB)`, затем `IDIVQ`. Деление на ноль в фоновой горутине: `panic: runtime error: integer divide by zero`, `exit=2`, строка «main survived» не напечатана. `var fz float64; 1/fz, fz/fz` → `+Inf NaN`.
- **Предлагаемая правка:** «если делитель — переменная, равная нулю, компилятор заранее вставил проверку, и рантайм вызывает панику `integer divide by zero`. Не перехваченная `recover`, она завершает весь процесс с кодом 2. Деление вещественных чисел на ноль паники не вызывает: результат — `±Inf` или `NaN`».

### J-10 — INCORRECT
- **Где / цитата:** ст. 10:52 «рантайм помещает число `int` в регистр `RAX`, а указатель на структуру `error` — в регистр `RBX`»; диаграмма 10:66–67 «Результат в RAX<br>error в RBX».

### J-11 — INCORRECT
- **Где / цитата:** ст. 13:145 «Клиент получает статус `HTTP 500 Internal Server Error`».
- **Вердикт:** `net/http` перехватывает панику и пишет трассу в лог. Затем он закрывает соединение (HTTP/1.x) или шлёт `RST_STREAM` (HTTP/2). Ответ 500 не отправляется: его отправляют recovery-middleware фреймворков.
- **Доказательство:**
  - go1.27.1 `src/net/http/server.go:82–88`: «It recovers the panic, logs a stack trace to the server error log, and either closes the network connection or sends an HTTP/2 RST_STREAM… panic with the value [ErrAbortHandler]».
  - Запуск: `httptest.NewServer` с обработчиком `panic("boom")`, `http.Get` → `client err: Get "http://127.0.0.1:41389": EOF`.
- **Предлагаемая правка:** «паника внутри HTTP-обработчика не роняет сервер: `net/http` перехватывает её, пишет stack trace в лог и обрывает соединение (в HTTP/2 — поток). Клиент увидит обрыв, а не `500`. Статус 500 возвращают recovery-middleware (`chi`, `gin` и др.). Паника со значением `http.ErrAbortHandler` прерывает ответ без записи в лог».

### J-12 — INCORRECT
- **Где / цитата:** ст. 27:15 «Правило, зашитое… в лексический анализатор»; 27:20 «`scanner.Scan()` проверяет… `unicode.IsUpper(ch)`»; 27:21 «Name Mangling… Экспортируемые символы записываются… под своими чистыми именами… неэкспортируемые… дополняются префиксом… Линковщик аппаратно пресекает…»
- **Вердикт:** механизм вымышлен.
  - В объектных файлах все символы квалифицированы путём пакета, экспортируемые и неэкспортируемые одинаково.
  - Экспортируемость проверяет type checker. Сканер её не определяет: в `syntax/` `unicode.IsUpper` есть только в отладочном `dumper.go`.
  - Линкер доступ не контролирует. Обход — `//go:linkname`, с Go 1.23 ограниченный для внутренних символов stdlib.
- **Доказательство:**
  - go1.27.1 `go tool nm`: `T fmt.Fprintln`, `T fmt.newPrinter`, `T main.main` — одинаковая квалификация.
  - `grep IsUpper src/cmd/compile/internal/syntax/*.go` → только `dumper.go:211`.
  - `isExported` — `src/cmd/compile/internal/types2/object.go:66`, `go/types/object.go:69`.
  - Go 1.23 release notes: «The linker now disallows using a `//go:linkname` directive to refer to internal symbols in the standard library… `-checklinkname=0`».
- **Предлагаемая правка:** «Проверку выполняет type checker компилятора (`types2`): при обращении `pkg.name` он смотрит, начинается ли имя с заглавной буквы Unicode (категория Lu), и иначе сообщает об ошибке `name not exported by package`. - **Предлагаемая правка:**
  - «Contiguous Stacks (непрерывные стеки)»;
  - «направленных ациклических графов»;
  - ст. 30:111: «`RawMessage` — срез байтов (`[]byte`; с Go 1.27 — псевдоним `jsontext.Value`)…»;
  - ст. 41:168: «(вытеснение горутины отключается)»;
  - ст. 43:14: «Deadlock возможен, только если выполняются все четыре условия Коффмана».

### B-19 — INCORRECT
- **Где / цитата:** ст. 31:143–145 «Компилятор и рантайм Go не выбросят ошибку! Парсер просто сопоставит…»
- **Вердикт:**
  - Для `Format` день и месяц молча меняются местами.
  - `Parse` при дне > 12 вернёт ошибку `month out of range`: ошибка проявится на части данных.
  - `go vet` (`timeformat`) ловит именно `2006-02-01`.
- **Доказательство:** go1.27.1: `time.Parse("2006-02-01", "2024-10-15")` → `parsing time "2024-10-15": month out of range`; `"2024-10-05"` → без ошибки. `go vet` → `2006-02-01 should be 2006-01-02`.
- **Предлагаемая правка:** «Компилятор промолчит, но `go vet` предупредит. `Format` молча поменяет день и месяц местами. `Parse` будет работать, пока день ≤ 12, а на 13-м числе вернёт `month out of range` — ошибка всплывёт только на части данных».

### B-20 — PARTIALLY CORRECT
- **Где / цитата:** модуль целиком (`complex64`/`complex128` не упомянуты); ст. 17:112–113 «В этот момент `packet` выходит из области видимости. GC должен бы удалить 1 МБ. Но он этого НЕ СДЕЛАЕТ!».
- **Вердикт:**
  - Пропуск комплексных типов подтверждён.
  - GC учитывает живость, а не лексическую область. В примере `payload` после `_ = payload` мёртв, поэтому пример утечку не демонстрирует: она возникает, когда `payload` живёт дальше.
- **Доказательство:** `grep complex64\|complex128` по модулю → 0 файлов; `doc/go_spec.html:2289` — `complex64 complex128` среди предобъявленных типов.
- **Предлагаемая правка:** в ст. 6 строка про `complex64`/`complex128` (`real`, `imag`, `complex`). Пример ст. 17: `cache = append(cache, payload)` (глобальный кэш) — «пока `payload` хранится в кэше, весь 1 МБ остаётся в памяти».

## 8. Замечания к брифу и отчёту слепых зон

- **§ 5.9 брифа (`StringHeader`):** прав скаут. По release notes 1.21 deprecated — с **Go 1.21**; в 1.20 появились лишь функции `unsafe`. Текст ст. 20:23 («начиная с Go 1.20») нужно исправить (J-31).
- **§ 8 брифа («`WaitGroup`: счётчик в старших 32 битах»):** верно по коду go1.27.1. Комментарий в исходнике («bits[0:32] counter») нумерует биты от старших, его легко прочитать наоборот. Ст. 40:34 устарела только в том, что младших бит теперь 31 плюс флаг synctest (B-14).
- **J-27:** список vet-подмножества `go test` в брифе неточен (нет `stdversion`, искажены имена `bools`, `buildtag`).
- **J-47:** в go1.27.1 `gorecover` раскручивает стек и распознаёт кадры по PC; решающий критерий — число не-обёрточных кадров и `p.startSP`.
- **J-96:** «все указательные типы — одна форма» — только под basic-интерфейсом (`Shapify`).
- **J-111:** go1.27.1 не выносит чтение `flag` из `for !flag {}` (amd64): зависание разрешено моделью памяти, но в этой версии не воспроизводится.
- **J-41:** jump tables в go1.27.1 — amd64, arm64 и loong64 (release notes 1.19 называли только amd64 и arm64).
- **B-18 (`RawMessage`):** в Go 1.27 `json.RawMessage` — псевдоним `jsontext.Value`; утверждение статьи о псевдониме для 1.27 по сути верно.
- **J-01:** в go1.27.1 старой реализации `map` нет совсем: флаг `noswissmap` удалён, поэтому описание `hmap/bmap` — чистая история.
- **J-63:** замер на Swiss Tables (1.27) подтверждает: ≈ 56 МБ на 1 млн `map[string]int`, память после удаления всех ключей не освобождается.
- **J-129:** порядки обхода из примера ст. 18 невозможны и в Go 1.27 (там бывают только циклические сдвиги).
