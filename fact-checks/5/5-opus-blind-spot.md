### B-01 · `encoding/json` в Go 1.27 — обёртка над `encoding/json/v2`; разбор внутренностей в ст. 30 устарел · УСТАР. + ВЕРСИЯ
- **Где:** ст. 30, раздел «Mechanical Sympathy: Рефлексия и аллокации», строки 174–207 (диаграмма 192–200, список 203–207); раздел «Производительность», 211–219; «HTML-экранирование», 232–234.
- **Цитата:** строка 205 — «При каждом вызове рантайм Go вынужден исследовать внутреннее строение структуры, парсить строки структурных тегов и искать совпадения имён полей»; строка 234 — «Изменить эту настройку в функции `Marshal` невозможно. Единственный корректный способ отключить экранирование — использовать `Encoder`».
- **Утверждение:** стандартный `encoding/json` устроен как классический v1 (рефлексия, `FieldByName + Set`). Чтобы обогнать его, нужны сторонние `easyjson`, `go-json`, `sonic`. HTML-экранирование отключается только через `Encoder`.
- **Почему важно:**
  - На go1.27.1 эксперимент `JSONv2` включён по умолчанию (`internal/buildcfg/exp.go`, `baseline`: `JSONv2: true`).
  - Пакет `encoding/json` собирается только из `v2_*.go`. Документация пакета: «All the behavior of the v1 package is implemented in terms of the v2 package with the appropriate set of options».
  - Доступен стандартный `encoding/json/v2` (и `encoding/json/jsontext`) с другими умолчаниями. `jsonv2.Marshal` не экранирует HTML, значит, «единственный способ» — уже не единственный.
  - Статья не знает о v2 вовсе и предлагает только сторонние библиотеки.
  - Для фактчекера это меняет доказательную базу: проверять внутренности (J-87, J-88) нужно по `v2_*.go` и `encoding/json/v2`, а не по `encode.go`/`stream.go`.
- **[улика]** `go list -f '{{.GoFiles}}' encoding/json` → `[v2_decode.go v2_encode.go v2_indent.go v2_inject.go v2_options.go v2_scanner.go v2_stream.go]`. `encode.go` начинается с `//go:build !goexperiment.jsonv2`. Без `GOEXPERIMENT` программа с `import jsonv2 "encoding/json/v2"` собирается, `jsonv2.Marshal(map[string]string{"a":"<b>"})` → `{"a":"<b>"}`, а v1 → `{"a":"<b>"}`.
- **Что проверить и где:** release notes Go 1.25 (эксперимент `jsonv2`) и той версии, где он стал умолчанием (1.26 или 1.27 — сверить); `go doc encoding/json` (раздел «Migrating to v2»); `src/encoding/json/v2_*.go`, `src/encoding/json/v2/arshal*.go`. Решение для редактора: развести «API v1 (поведение сохранено)» и «реализация (с Go 1.2x — на v2)»; упомянуть `encoding/json/v2` как стандартную альтернативу перед сторонними библиотеками.
- **Тип:** УСТАР., ВЕРСИЯ, ПРОПУСК · **Приоритет:** High

### B-02 · «Возврат указателя → куча»: инлайнинг отменяет escape, а `-gcflags=-m` подтверждает миф · ФАКТ + УПРОЩ.
- **Где:** ст. 14, строки 61–63, 84 (ответ на собеседовании), 175 (итог п.2); ст. 44, строка 51.
- **Цитата:** ст. 14:63 — «Компилятор автоматически переносит аллокацию переменной `u` со стека … — **Кучу (Heap)**»; ст. 14:84 — «Компилятор выведет детальные отчёты вроде `moved to heap: u`»; ст. 44:51 — «возврат указателя из функции заставит компилятор выкинуть объект в кучу».
- **Утверждение:** конструктор `func NewUser(...) *User { u := User{…}; return &u }` всегда аллоцирует в куче, и `-m` это подтверждает.
- **Почему важно:** маленький конструктор инлайнится. Тогда escape analysis рассуждает уже в функции вызывающего, и если указатель дальше не убегает, объект остаётся на стеке. `-m` при этом печатает `moved to heap: u` для отдельной копии тела `NewUser`, а не для места вызова. Читатель, следуя совету статьи, сделает неверный вывод о собственном коде. Кластер К-3 брифа говорит «куча, если значение убегает», но этот случай (возврат указателя как каноническое «убегание») не разбирает.
- **[улика]** go1.27.1, `NewUser` из ст. 14 и `testing.AllocsPerRun(1000, func(){ u := NewUser("bob"); _ = u.Name })`: `-m` → `can inline NewUser`, `inlining call to NewUser`, `moved to heap: u`; `AllocsPerRun` → `0`.
- **Что проверить и где:** `go build -gcflags='-m=2'`, `testing.AllocsPerRun`; `src/cmd/compile/internal/escape/` (анализ после инлайнинга, `interleaved.DevirtualizeAndInlinePackage` до `escape.Funcs` в `gc/main.go`).
- **Тип:** ФАКТ, УПРОЩ. · **Приоритет:** Medium

### B-03 · Примеры happens-before в ст. 42 завершаются раньше горутины и ничего не печатают · КОД
- **Где:** ст. 42, строки 111–121 (пример «Горутины»), 162–176 (пример «Блокировки»).
- **Цитата:** строка 119 — `fmt.Println(a) // Безопасно, выведет "hello"`; строка 173 — `fmt.Println(a) // Безопасно`.
- **Утверждение:** запуск горутины (или `Unlock`) делает чтение `a` в горутине безопасным, и программа выведет `hello`.
- **Почему важно:** в обоих примерах `main` возвращается сразу после `go func()`, и программа завершается, не дождавшись горутины (спецификация: «It does not wait for other (non-main) goroutines to complete»). Утверждение о happens-before верно, но пример его не показывает. В статье о точности гарантий комментарий «выведет» учит обратному. В Go Memory Model тот же пример написан аккуратно: «will print "hello, world" at some point in the future (perhaps after hello has returned)».
- **[улика]** go1.27.1, пример строк 113–121, 200 запусков бинарника: `printed 0/200`.
- **Что проверить и где:** спецификация, раздел «Program execution»; `doc/go_mem.html`, раздел «Goroutine creation». Исправление: дождаться горутины (`WaitGroup`/канал), не нарушая сути примера.
- **Тип:** КОД · **Приоритет:** Medium

### B-04 · `defer` в цикле → `too many open files` на 10 000 файлах: Go сам поднимает `RLIMIT_NOFILE` · ВЕРСИЯ + ДОПУЩ.
- **Где:** ст. 11, строка 184 и итог п.7 (строка 207); ст. 29, строка 37.
- **Цитата:** ст. 11:184 — «Если в слайсе `files` содержится 10 000 элементов, операционная система заблокирует программу ошибкой `too many open files` из-за исчерпания лимита дескрипторов процесса (`ulimit`)».
- **Утверждение:** лимит — `ulimit -n` пользователя (обычно 1024), и 10 000 открытых файлов его исчерпают.
- **Почему важно:** при старте пакет `syscall` поднимает мягкий лимит `RLIMIT_NOFILE` до жёсткого (с поправкой `Max-1`). На современных Linux жёсткий лимит обычно 524 288 и выше (systemd), так что пример из статьи, скорее всего, не упадёт. Читатель, проверив его, решит, что ловушки нет. Ловушка реальна (дескрипторы держатся до выхода из функции, а жёсткий лимит конечен), но её порог зависит от окружения. «Заблокирует программу» тоже неточно: `open` вернёт ошибку `EMFILE`, программа продолжит работу.
- **[улика]** go1.27.1, `ulimit -Sn 1024`, затем программа печатает `soft 524287 hard 524288` и открывает 10 000 файлов без ошибки. Код: `src/syscall/rlimit.go`, `func init()` (`nlim.Cur = nlim.Max - 1`, `setrlimit(RLIMIT_NOFILE, &nlim)`).
- **Что проверить и где:** release notes Go 1.19 (os/syscall: raise open file limit), `src/syscall/rlimit.go`. Исправление: сказать о подъёме лимита и привести реальный порог (жёсткий лимит, `LimitNOFILE` в systemd, `--ulimit` в Docker).
- **Тип:** ВЕРСИЯ, ДОПУЩ., ФАКТ · **Приоритет:** Medium

### B-05 · Утечки горутин: в Go 1.27 есть встроенный профиль `goroutineleak` · ПРОПУСК + УСТАР.
- **Где:** ст. 34, строки 145–149 и итог п.4 (216); ст. 43, строка 92 (врезка «Частичный (Локальный) Deadlock»), строка 158, «Итог и диагностика» (241–244).
- **Цитата:** ст. 43:92 — «Рантайм не может математически доказать, что эти две горутины зависли навсегда. Они просто останутся висеть в памяти (статус `_Gwaiting`) до перезапуска сервиса».
- **Утверждение:** зависшие горутины (частичный deadlock, брошенный канал) рантайм обнаружить не может; диагностика — только рост `/debug/pprof/goroutine`.
- **Почему важно:** в go1.27.1 у `runtime/pprof` есть предопределённый профиль `goroutineleak` («stack traces of all leaked goroutines»). Его запись запускает GC с обнаружением утечек: горутина, заблокированная на примитиве, недостижимом из живых горутин, получает статус `_Gleaked`. Именно этот класс — горутина, навсегда застрявшая на `ch <- res` (ст. 43:169), и AB-BA пара на недостижимых мьютексах — теперь доказуемо обнаруживается. Тезис «не может доказать» для этого класса устарел, а в разделе «диагностика» нет самого точного инструмента. Утверждение ст. 34 «GC не может собрать» остаётся верным: профиль находит утечки, но не освобождает их.
- **[улика]** `src/runtime/pprof/pprof.go:109` — `goroutineleak  - stack traces of all leaked goroutines`; профиль в `profiles.m` без условий сборки (строка 265); `src/runtime/mgc.go:1300` — `casgstatus(gp, _Gwaiting, _Gleaked)`.
- **Что проверить и где:** release notes Go 1.26 и 1.27 (когда появился эксперимент и когда профиль стал стандартным — сверить); документация `runtime/pprof`; ограничения детектора (только горутины на недостижимых примитивах; горутина, ждущая на глобальном канале, утечкой не считается).
- **Тип:** ПРОПУСК, УСТАР., ВЕРСИЯ · **Приоритет:** Medium

### B-06 · Решения компилятора и тулчейна приписаны «рантайму» · ФАКТ + УПРОЩ.
- **Где:**
  - ст. 10, строка 173: «рантайм Go автоматически переносит их со стека в кучу»;
  - ст. 10, строка 78: «рантайм создаёт полную побитовую копию»;
  - ст. 22, строка 69: «При вызове метода рантайм создаёт полную побитовую копию»;
  - ст. 23, строка 140: «строгих правилах рантайма Go относительно множества методов»;
  - ст. 23, строка 170: «Почему рантайм так строг?»;
  - ст. 28, строка 101 (диаграмма MVS): «Игнорируется рантаймом»;
  - ст. 9, строка 90: «рантайм процессора будет копировать 1 КБ».
- **Утверждение:** перенос переменных в кучу, правила method sets, выбор версий модулей и копирование аргументов выполняет рантайм во время работы программы.
- **Почему важно:**
  - Escape analysis решает при компиляции, где разместить переменную, и во время работы программы ничего «со стека в кучу» не переносится. При этом перемещение стеков рантаймом существует (ст. 14, 34), и на этом фоне фраза создаёт ложную модель.
  - Method sets проверяет type checker, а ошибка `Job does not implement Worker` — ошибка компиляции.
  - MVS выполняет команда `go` при разрешении зависимостей. Рантайм собранной программы о версиях модулей не знает.
  - Учебник, который обещает разобрать, «как конструкции ложатся на кремний», должен различать время компиляции и время выполнения. Бриф видит это только в одном месте: J-10 («раскладку делает компилятор, а не рантайм»). Кластер К-9 касается фаз компилятора, а не этой границы.
- **Что проверить и где:** `src/cmd/compile/README.md`; спецификация, «Method sets»; `go.dev/ref/mod#minimal-version-selection`. Правка механическая: «компилятор», «команда `go`», «сгенерированный код».
- **Тип:** ФАКТ, УПРОЩ. · **Приоритет:** Medium

### B-07 · «Мусор от предыдущих процессов ОС» в неинициализированной памяти C · ФАКТ
- **Где:** ст. 5, строка 6 (вводный список) и строка 99.
- **Цитата:** строка 6 — «Неинициализированной памяти (с „мусором“ от работы предыдущих процессов операционной системы) в Go не существует»; строка 99 — «„мусор“ — случайную комбинацию битов, оставшуюся от предыдущих вычислений операционной системы. Это исторический источник сотен уязвимостей безопасности (Buffer Overflows, …)».
- **Утверждение:** неинициализированная переменная в C может содержать данные других процессов.
- **Почему важно:** современные ОС отдают процессу только обнулённые страницы (иначе это была бы утечка данных между процессами). «Мусор» в неинициализированной переменной C — это остатки **того же процесса**: прежних кадров стека и освобождённых блоков `malloc`. Отсюда реальные классы уязвимостей: утечки информации (CWE-457/CWE-908) и неопределённое поведение, а не переполнения буфера. Для учебника, построенного на «механическом сочувствии», это неверная модель памяти.
- **Что проверить и где:** `man 2 mmap` (`MAP_ANONYMOUS`: «contents are initialized to zero»); C11 §6.7.9 p10 (automatic storage — indeterminate value); CWE-457, CWE-908.
- **Тип:** ФАКТ · **Приоритет:** Medium

### B-08 · ст. 13 противоречит сама себе: «Let it crash» против `recover()` в каждой горутине · ПРОТИВ. + МНЕНИЕ
- **Где:** ст. 13, строка 6 против строк 127–134; строка 57 против строки 190.
- **Цитата:** строка 6 — «мгновенно уронить упавший процесс несравнимо безопаснее, чем позволить ему продолжать работу в зомби-состоянии»; строка 127 — «любая фоновая горутина … **обязана** содержать собственный локальный барьер `defer recover()`», в примере — «Возвращаем горутину в пул или аккуратно завершаем»; строка 190 — «существует ровно два сценария, когда использование `panic` … абсолютно оправдано».
- **Утверждение:** паника означает нарушенные инварианты и требует падения, и одновременно любая фоновая горутина должна панику гасить и продолжать работу.
- **Почему важно:** это противоположные политики. «Вернуть горутину в пул» после паники посреди изменения разделяемого состояния (под мьютексом, в середине записи) — ровно то «зомби-состояние», от которого предостерегает введение. Кроме того, `recover` не ловит фатальные ошибки рантайма (J-49, К-12), так что «обязательный барьер» даёт ложное чувство защищённости. В строке 57 тот же текст узаконивает третий сценарий паники (прерывание рекурсии в парсере, как в `encoding/json`), а строка 190 говорит «ровно два». J-50 разбирает атрибуцию Армстронга, но не это противоречие.
- **Что проверить и где:** Effective Go, «Recover»; Go Code Review Comments, «Don't Panic»; Go FAQ «Why does Go not have exceptions?». Решение редактора: одна согласованная политика — recover на границе запроса/задачи с логом и метрикой, без продолжения работы над повреждённым состоянием.
- **Тип:** ПРОТИВ., МНЕНИЕ · **Приоритет:** Medium

### B-09 · `append` внутри функции «оригинал ничего не узнает» — неверно при свободной ёмкости · ФАКТ
- **Где:** ст. 10, строка 104 (врезка «Передача слайсов и мап»).
- **Цитата:** «если вы вызовете функцию `append` внутри функции, и слайс превысит свою ёмкость … **либо просто увеличит длину**, оригинальный срез снаружи об этом ничего не узнает».
- **Утверждение:** `append` в пределах ёмкости никак не затрагивает вызывающего.
- **Почему важно:** в пределах ёмкости `append` пишет в **общий** базовый массив за пределами `len` вызывающего. Снаружи не видна только новая длина, данные же изменены: `s[:len(s)+1]` у вызывающего их покажет, а его следующий `append` их перезапишет. Это тот самый алиасинг, который ст. 17 (§ «Заражение через append») называет порчей данных. ст. 10 утверждает обратное. J-127 касается вывода примера `modify` в ст. 16, а не этой формулировки.
- **Что проверить и где:** запуск: `s := make([]int, 3, 10); f(s) /* append(s, 42) */; fmt.Println(s[:4][3])` → `42`; спецификация, «Appending to and copying slices».
- **Тип:** ФАКТ, ПРОТИВ. · **Приоритет:** Medium

### B-10 · До Go 1.14 один бесконечный цикл вешал всю программу через STW сборщика · ПРОПУСК
- **Где:** ст. 35, строка 186; ст. 43, строка 197.
- **Цитата:** ст. 35:186 — «эта горутина захватывала M навсегда, вызывая дедлок всего приложения (если таких циклов было больше, чем ядер)».
- **Утверждение:** до 1.14 зависание всего приложения требовало столько тесных циклов, сколько ядер (`GOMAXPROCS`).
- **Почему важно:** достаточно **одного** цикла без точек вытеснения. Когда GC запрашивал stop-the-world, все остальные горутины останавливались и ждали эту одну — программа замирала целиком. Это главный мотив асинхронного вытеснения (proposal 24543) и самый частый симптом в старых баг-репортах. Условие «больше, чем ядер» прячет главное.
- **Что проверить и где:** design doc «Proposal: Non-cooperative goroutine preemption» (golang/go#24543), issue golang/go#10958; release notes Go 1.14.
- **Тип:** ПРОПУСК, УПРОЩ. · **Приоритет:** Low–Medium

### B-11 · `go run` «удаляет временный файл» — с Go 1.24 бинарник кэшируется · УСТАР.
- **Где:** ст. 3, строки 77, 79.

### B-12 · Не сказано, что `break` внутри `switch` выходит только из `switch` · ПРОПУСК
- **Где:** ст. 9, раздел «switch: Мощь и Mechanical Sympathy» (строки 116–136), итог п.4 (строка 196).
- **Цитата:** строка 120 — «В Go оператор `break` подставляется компилятором автоматически».
- **Утверждение:** (пропуск) поведение явного `break` в `switch` не описано.
- **Почему важно:** раз `break` в Go «не нужен», в `for { switch … { case …: break } }` его ставят, чтобы выйти из цикла, а он выходит только из `switch`. Нужен `break` с меткой или `return`. Это классический вопрос собеседования. Бриф (J-105) называет ту же ловушку только для `select` (ст. 38). Статья об управляющих конструкциях, где о ней естественно сказать, её не упоминает. Не упомянуто и то, что `fallthrough` запрещён в type switch и в последней ветке.
- **Что проверить и где:** спецификация, «Break statements», «Fallthrough statements».
- **Тип:** ПРОПУСК · **Приоритет:** Low–Medium

### B-13 · `:=` «создаёт новые переменные» — не сказано о повторном объявлении в той же области · ПРОПУСК + УПРОЩ.
- **Где:** ст. 5, строка 63 и врезка «Как защитить архитектуру от Shadowing?» (85–93).
- **Цитата:** строка 63 — «Оператор `:=` создаёт **новые переменные в текущей локальной области видимости (scope)**».
- **Утверждение:** `:=` всегда создаёт новые переменные.
- **Почему важно:** в **той же** области `:=` с хотя бы одной новой переменной слева **переиспользует** уже объявленные (`a, err := f(); b, err := g()` — `err` один). Затенение возникает только во вложенной области. Без этого правила читатель не поймёт, почему одна и та же строка `x, err := …` в одном месте перезаписывает `err`, а в другом затеняет. Именно на этом и строится ловушка, которую разбирает статья.
- **Что проверить и где:** спецификация, «Short variable declarations» («Unlike regular variable declarations, a short variable declaration may redeclare variables provided they were originally declared earlier in the same block …»).
- **Тип:** ПРОПУСК, УПРОЩ. · **Приоритет:** Low–Medium

### B-17 · Семантика целочисленных операций: сдвиг ≠ деление, знак `%`, константы против переменных · ПРОПУСК + УПРОЩ.
- **Где:** ст. 8, строка 84 и врезка «Деление и %» (168–170); ст. 6, врезка 81–91.
- **Цитата:** ст. 8:84 — «старшие освобождающиеся биты дублируют знаковый бит, чтобы сохранить знак отрицательного числа при делении на степени двойки».
- **Почему важно:**
  - Фраза подсказывает, что `x >> 1` равно `x / 2`. Для отрицательных нечётных это не так: `/` округляет к нулю, `>>` — к минус бесконечности.
  - Не сказано, что знак `%` следует за делимым (`-7 % 3 == -1`, в Python `2`). Это частая ошибка при переходе с Python.
  - В ст. 6 пример `0.1 + 0.2 == 0.3` верно даёт `false` только потому, что операнды — переменные. Те же литералы в одном выражении — точная константная арифметика, и результат `true`. Читатель, проверив «короткую» версию, запутается. Связь с разделом о нетипизированных константах ст. 5 не проведена.
- **[улика]** go1.27.1: `fmt.Println(-7%3, -7/2, -7>>1)` → `-1 -3 -4`; `fmt.Println(0.1+0.2 == 0.3)` → `true`.
- **Что проверить и где:** спецификация, «Integer operators» (truncated division, `x % y` знак), «Constant expressions».
- **Тип:** ПРОПУСК, УПРОЩ. · **Приоритет:** Low

### B-19 · Опечатка в шаблоне даты: `time.Parse` вернёт ошибку · ФАКТ
