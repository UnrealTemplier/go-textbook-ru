### A-01. MVS: «Go выбирает более свежий patch» противоречит самому MVS
- **Где:** `13. Versioning. SemVer и совместимость` → «Семантика версий», пункт PATCH.
- **Цитата:** «Go без колебаний выбирает более свежий patch-релиз в рамках алгоритма MVS.»
- **Утверждение:** при появлении PATCH-релиза Go берёт его автоматически.
- **Проблема:** MVS выбирает минимальную версию, удовлетворяющую всем требованиям. Та же статья (ст. 12) прямо пишет: Go «никогда не установит её автоматически». Противоречие в центральной для модуля теме.
- **Что проверить:** go.dev/ref/mod, раздел «Minimal version selection»; `go help modules`.
- **Тип:** факт.
- **Приоритет:** High.

### A-02. «До появления модулей (Go 1.16)» — неверная датировка модулей и `go get`
- **Где:** `5. go install и установка CLI` → «Версионирование: Суффикс @version».

### A-03. Имя бинарника: флага `go install -name` нет, для `/v2` берётся другой сегмент

### A-05. Пример «unreachable code» не компилируется
- **Где:** `7. go vet. Статический анализ` → «Самые частые проверки», пункт 3.

- **Приоритет:** Medium.

### A-16. Процесс в `scratch` не обязан быть root
- **Где:** `24. Минимизация образов. scratch, distroless` → «`distroless`: Безопасность «из коробки»», блок «Под капотом».
- **Цитата:** «В `scratch` пользователя нет, поэтому там процесс всегда запускается от root (UID 0), если только вы не создали `/etc/passwd` вручную.»
- **Утверждение:** в `scratch` нельзя запустить процесс не от root без `/etc/passwd`.
- **Проблема:** Dockerfile принимает числовой UID в `USER` (например, `USER 65532:65532`) без записи в `/etc/passwd`. Docker не требует, чтобы пользователь существовал в образе, если задан числовой UID. Статья утверждает обратное.
- **Что проверить:** docs.docker.com, раздел Dockerfile `USER`; проверка через `docker run` в окружении с Docker (его здесь нет).
- **Тип:** факт.
- **Приоритет:** Medium.

### A-19. `COPY --from` и Kaniko: путаница с аутентификацией базового образа
- **Где:** `28. GitLab CI для Go` → «Сборка контейнеров», Gotcha после примера Kaniko.
- **Цитата:** «вы не можете использовать инструкции `COPY --from=builder`, если базовый образ недоступен или требует аутентификации»
- **Утверждение:** `COPY --from=builder` в Kaniko не работает при аутентификации базового образа.
- **Проблема:** `COPY --from` относится к многоэтапной сборке и работает в Kaniko. Аутентификация реестра касается `FROM` (базового образа), а не `COPY --from` внутри того же Dockerfile. Формулировка смешивает два разных механизма.
- **Что проверить:** документация Kaniko (multi-stage builds, `.docker/config.json`).
- **Тип:** факт.
- **Приоритет:** Medium.

### A-21. Утилиты `standard-version` и `semantic-release` не обновляют `go.mod`

### A-23. Куча Go не перемещается, и финализатор не защищает переданный указатель
- **Где:** `34. CGO и его влияние на сборку` → «Производительность и безопасность: Скрытые риски», пункт 2.
- **Цитата:** «сборщик мусора переместит или освободит этот участок памяти»; «явно регистрировать финализаторы через `runtime.SetFinalizer`»
- **Утверждение:** GC может переместить объект, переданный в C; защита — финализаторы.
- **Проблема:** GC Go не перемещает объекты в куче (non-moving); перемещаются стеки. Опасность — освобождение объекта, на который больше нет Go-ссылок. Финализатор этого не предотвращает. - **Что проверить:** go.dev/cmd/cgo (раздел «Passing pointers»); пакет `runtime`, `Pinner`.
- **Тип:** факт.
- **Приоритет:** Medium.

## 3. Сквозные проблемы

1. **Устаревшие инструменты и версии в примерах.** `golangci-lint` v1 (A-14), Kaniko (A-18), `setup-go@v4`/`cache@v3` и матрица 1.21/1.22 (A-41), `GOPATH`-эпоха и «модули по умолчанию в 1.13» (A-02, A-09), `Phlare` (A-70), `DOCKER_BUILDKIT=1` (A-54).
2. **Примеры, которые не работают так, как описано.** Недостижимый код, не компилирующийся в `vet` (A-05), `go work use` (A-11), `-workfile=off` (A-13), `.env` в Taskfile (A-15), `GOCACHE=off` (A-08), `go fix` для `ioutil` (A-07), имена бинарников `/v2` (A-03), `replace`-примеры не проверялись.
3. **Overclaim.** «Никогда», «невозможно в принципе», «стопроцентный признак», «нулевого дня», «сведут к нулю» — A-10, A-26, A-47, A-53.
4. **Механика описана неточно.** CGO-дефолт (A-22), подвижность кучи Go и финализаторы (A-23), `BUILDPLATFORM` (A-24), `covermode` (A-20), `GOTOOLCHAIN` (A-45), `GOWORK` и флаги (A-13).
5. **Внутренние противоречия между статьями.** MVS (A-01 против ст. 12), годы модулей (A-02 против A-09 и ст. 1), `-s -w` 20–30% против 25–35% (A-30), размер `golang`-образа (A-52), race-замедление (A-33).
6. **Числа и атрибуции без источника.** Почти в каждой статье есть цифры вида «в 99%», «90%», «в 10–50 раз», «экспоненциально», цитаты Пайка, Кокса, Керниган–Плоджера, история Фельдмана (A-27, A-43, A-50, A-55, A-69, A-71, A-73, A-74). Для раздела, где читатель будет копировать команды, это стоит вычистить или подкрепить ссылками.
