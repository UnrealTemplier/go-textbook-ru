#### 1. Вымышленная автоматическая настройка `GOMEMLIMIT` из Cgroup v2 в Go runtime
* **Статья / Раздел:** 
  - `01. Linux/1. Обзор раздела. Среда выполнения backend.md` (строки 78–82)
  - `01. Linux/5. Systemd и управление сервисами.md` (строки 298–300, 357)
  - `03. Docker/1. Контейнеризация. Основы.md` (строки 107, 208)
* **Утверждение (Claim):**
  > *«...начиная с Go 1.19 рантайм умеет автоматически учитывать лимиты cgroupv2 (параметр `memory.max`) для настройки `GOMEMLIMIT`...»*  
  > *«Начиная с Go 1.19 рантайм Go получил поддержку cgroup v2. Если сервис запускается в современном systemd-слайсе или контейнере с установленным `MemoryMax=512M`, рантайм умеет автоматически считывать это значение...»*
* **Почему требует проверки (Why it needs checking):**
  Это опаснейший технический миф и вымышленная функциональность. Ни в Go 1.19, ни в 1.20, 1.21, 1.22, 1.23, ни в 1.24 рантайм Go **НИКОГДА автоматически не считывал лимиты cgroups (ни `memory.max`, ни `memory.limit_in_bytes`) для инициализации `GOMEMLIMIT`**!
  В официальном предложении (proposal golang/go#48409) Майкл Кнышек (Michael Knyszek) прямо указал, что автоопределение лимита памяти из cgroups намеренно исключено из рантайма из-за неопределенности учета страничного кэша ядра, swap-памяти и оверхеда самого процесса. Значение `GOMEMLIMIT` читается **исключительно** из одноименной переменной окружения или устанавливается явно через API `runtime/debug.SetMemoryLimit()`.
  Именно по причине полного отсутствия автоопределения в официальном рантайме сообщество разработало сторонние библиотеки (например, `github.com/KimMachineGun/automemlimit`). Если разработчик поверит тексту статьи и не задаст `GOMEMLIMIT` явно, приложение в Cgroup v2 продолжит удваивать кучу по `GOGC=100` и будет без предупреждения уничтожено системным `OOM Killer` (`SIGKILL`).
* **Необходимые источники / Свидетельства:**
  1. Исходный код Go: `src/runtime/mgcpacer.go` (функция `gcControllerState.init`), `src/runtime/debug/garbage.go`.
  2. Дизайн-документ Go: [Go Memory Limit Proposal (issue #48409)](https://github.com/golang/go/issues/48409).
  3. Репозиторий библиотеки: `github.com/KimMachineGun/automemlimit`.
* **Приоритет:** 🔴 **High**

#### 2. Ложное описание поведения `syscall.Setuid` в современном Go и опасный "рецепт"
* **Статья / Раздел:** `01. Linux/4. Права доступа и безопасность.md` (строки 90–94)
* **Утверждение (Claim):**
  > *«В Go стандартный вызов `syscall.Setuid()` долгое время был источником тяжелейших уязвимостей. Дело в том, что в Linux системный вызов `setuid` меняет привилегии только для текущего потока ОС (M). В рантайме Go, где горутины прыгают между потоками, одна горутина может стать `nobody`, а соседняя остаться `root`! Единственный надежный способ в Go — зафиксировать поток через `runtime.LockOSThread()`, выполнить `syscall.Setuid()` и порождать дочерние горутины строго из него.»*
* **Почему требует проверки (Why it needs checking):**
  Утверждение содержит двойную критическую ошибку:
  1. **Устарело с релиза Go 1.16 (вышедшего в начале 2021 года):** Начиная с Go 1.16, вызовы `syscall.Setuid()`, `syscall.Setgid()`, `syscall.Setgroups()` вызывают внутреннюю функцию рантайма `AllThreadsSyscall` (`doAllThreadsSyscall` на ассемблере). Она отправляет POSIX real-time сигналы (SIGSETXID) абсолютно всем потокам ОС (`M`) процесса Go, синхронно меняя учетные данные процесса во всех системных нитях! Поведение стало полностью безопасным и консистентным на уровне процесса.
  2. **Рекомендуемый "рецепт" фатально сломан:** Совет *«зафиксировать поток через `runtime.LockOSThread()`, вызвать `Setuid` и порождать дочерние горутины строго из него»* фундаментально противоречит устройству планировщика Go. Горутины, созданные через `go func()` внутри заблокированного потока, **НЕ наследуют привязку к этому потоку ОС M**! Они помещаются в локальную очередь запуска P и могут быть подхвачены любым свободным потоком рантайма. Обучение такому псевдо-решению создает иллюзию безопасности в критическом системном коде.
* **Необходимые источники / Свидетельства:**
  1. Go 1.16 Release Notes: *"On Linux, the `syscall` package now uses `AllThreadsSyscall` for `Setuid`, `Setgid`, etc."*
  2. Исходный код: `src/syscall/syscall_linux.go` (`AllThreadsSyscall`), `src/runtime/sys_linux_amd64.s` (`doAllThreadsSyscall`).
  3. Документация `runtime.LockOSThread`: привязка действует только на текущую горутину, дочерние горутины стартуют непривязанными.
* **Приоритет:** 🔴 **High**

#### 3. Нерабочий код `fsnotify` для отслеживания ConfigMap в Kubernetes
* **Статья / Раздел:** `04. Kubernetes/3. ConfigMap и Secret.md` (строки 148–156)
* **Утверждение (Claim):**
  > Предлагается код hot-reload для примонтированного ConfigMap:
  > ```go
  > for {
  >     select {
  >     case event, ok := <-watcher.Events:
  >         if !ok { return }
  >         // Проверяем, изменился ли наш файл конфигурации
  >         if filepath.Base(event.Name) == targetFileName {
  >             if event.Has(fsnotify.Write) || event.Has(fsnotify.Create) {
  >                 log.Println("Конфигурация обновлена на диске! Запуск reload...")
  >                 reloadFn()
  >             }
  >         }
  >     ...
  > ```
* **Почему требует проверки (Why it needs checking):**
  Этот код **никогда не сработает в реальном Kubernetes**!
  В Kubernetes монтирование томов ConfigMap/Secret использует паттерн атомарного свопа симлинков (`atomic_writer.go` в Kubelet):
  ```text
  /config/app.yaml -> ..data/app.yaml
  ..data -> ..data_2026_10_05_12_00_00.123456789
  ```
  При обновлении ConfigMap Kubelet создает новый каталог с временной меткой `..data_tmp`, записывает файлы туда, а затем атомарно переименовывает его в `..data` через `rename(2)`. 
  Сам файл `targetFileName` (например, `app.yaml`) **никогда не перезаписывается и не создается заново**! 
  В библиотеку `fsnotify` прилетает событие `Create/Rename` для каталога `..data_tmp` или симлинка `..data`. Условие `filepath.Base(event.Name) == targetFileName` **всегда возвращает `false`**, и функция `reloadFn()` никогда не будет вызвана. В продакшене приложение молча останется на старой конфигурации. Для отслеживания изменений в K8s необходимо мониторить изменение симлинка `..data` или директории.
* **Необходимые источники / Свидетельства:**
  1. Kubernetes codebase: `pkg/volume/util/atomic_writer.go`.
  2. Стандартный паттерн отслеживания ConfigMap в Go: проверка `event.Name == "..data"` или `filepath.Base(event.Name) == "..data"`.
* **Приоритет:** 🔴 **High**

#### 5. Миф о том, что unhandled `SIGINT`/`SIGTERM` вызывает `os.Exit(2)`
* **Статья / Раздел:** `01. Linux/2. Процессы и сигналы.md` (строки 154–157)
* **Утверждение (Claim):**
  > *«По умолчанию рантайм Go перехватывает `SIGINT` и `SIGTERM`. Если вы не зарегистрировали свой канал в `signal.Notify`, рантайм выполняет «грязное» завершение: вызывает системный вызов `exit_group` с кодом возврата 2 (`os.Exit(2)`). Сервер не успевает сбросить буферы на диск...»*
* **Почему требует проверки (Why it needs checking):**
  Это грубая фактологическая ошибка относительно поведения рантайма Go.
  Если Go-приложение не настраивает перехват `SIGINT` (сигнал 2) или `SIGTERM` (сигнал 15) через `signal.Notify`, рантайм **НЕ вызывает `os.Exit(2)`** и не завершает процесс кодом 2!
  В исходном коде `src/runtime/signal_unix.go` (обработчик `sighandler`): при получении смертельного сигнала рантайм сбрасывает обработчик сигнала в системный дефолт (`SIG_DFL`) и повторно посылает этот же сигнал процессу через `raise(sig)` / `tgkill`. Процесс убивается **ядром по сигналу** (статус завершения ядра `WIFSIGNALED`, сигнал `SIGINT` или `SIGTERM`).
  В оболочке Bash и в Docker код возврата такого процесса равен `128 + signal_number`:
  - Для `SIGINT`: `128 + 2 = 130`
  - Для `SIGTERM`: `128 + 15 = 143`
  Код выхода 2 в Go зарезервирован для паники рантайма или системных ошибок парсинга флагов.
* **Необходимые источники / Свидетельства:**
  1. Исходный код Go: `src/runtime/signal_unix.go` (ветка `_SigKill` / `dieFromSignal`).
  2. Проверка в терминале: запуск бинарника Go и `kill -TERM <pid>`; проверка `echo $?` выдает ровно 143, а не 2.
* **Приоритет:** 🔴 **High**

#### 8. Миф об утрате имён функций и строк в panic stack traces при сборке с `-ldflags="-s -w"`
* **Статья / Раздел:** `03. Docker/2. Dockerfile best practices.md` (строки 94–96)
* **Утверждение (Claim):**
  > *«Предостережение: Флаг `-s` вырезает таблицу символов. Если в продакшене сервис запаникует, в логах вместо читаемых имен функций и номеров строк (`main.go:42`) будут лишь шестнадцатеричные адреса памяти (`0x4012ab`). Это усложняет отладку и ломает утилиты вроде `runtime.Caller()`...»*
* **Почему требует проверки (Why it needs checking):**
  Широко распространенный, но фактологически неверный миф.

* **Необходимые источники / Свидетельства:**
  1. Исходный код Go: `src/runtime/symtab.go`, `src/runtime/traceback.go`.
  2. Экспериментальная проверка: компиляция программы с паникой через `go build -ldflags="-s -w"` демонстрирует полные пути и строки `main.go:XX`.

  1. Исходный код Go: `src/runtime/proc.go` (`handoffp`, `startm`).
  2. Документация пакета `runtime/debug.SetMaxThreads`.

#### 17. Рекомендация настраивать `GOMEMLIMIT` для борьбы с CFS CPU Throttling
* **Статья / Раздел:** `05. Практика/4. Мониторинг инфраструктуры.md` (строки 133–135)
* **Утверждение (Claim):**
  > *«Если вы видите рост графика `cfs_throttled` — немедленно увеличивайте лимиты, убирайте CPU limits вовсе либо настраивайте переменную `GOMEMLIMIT`, чтобы сгладить пики аллокаций.»*
* **Почему требует проверки (Why it needs checking):**
  Здесь допущено смешивание лимитов процессора и оперативной памяти.
  Переменная `GOMEMLIMIT` управляет сборщиком мусора памяти. Установка жесткого `GOMEMLIMIT` при нехватке памяти заставляет GC работать чаще и агрессивнее, что **увеличивает нагрузку на процессор и лишь усиливает CPU Throttling**!
  Для предотвращения CFS Throttling в Go необходимо настраивать параметр потоков процессора `GOMAXPROCS` (например, через библиотеку `uber-go/automaxprocs`), оптимизировать аллокации или убирать директиву `resources.limits.cpu`.
* **Необходимые источники / Свидетельства:**
  1. Документация Go GC Guide по `GOMEMLIMIT`.
  2. Документация ядра Linux: CFS Bandwidth Control.
* **Приоритет:** 🟡 **Medium**

#### 18. Антипаттерн добавления метки `version` во все векторы метрик Prometheus
* **Статья / Раздел:** `05. Практика/3. Canary и blue green deploy.md` (строки 240–254)
* **Утверждение (Claim):**
  > Рекомендуется добавлять метку `version` непосредственно в вектор гистограммы задержек приложения:
  > ```go
  > var HttpRequestDuration = prometheus.NewHistogramVec(
  >     prometheus.HistogramOpts{
  >         Name: "http_request_duration_seconds",
  >         ...
  >     },
  >     []string{"method", "path", "status", "version"},
  > )
  > ```
* **Почему требует проверки (Why it needs checking):**
  Это грубое нарушение официальных рекомендаций Prometheus Best Practices (Target labels vs Metric labels).
  Добавление `version` в высоконагруженные векторы метрик приводит к резкому росту кардинальности (Cardinality Explosion) и постоянному сбросу временных рядов при каждом деплое. 
  Канонический паттерн Prometheus:
  1. Использование паттерна **Info Metric**: `app_build_info{version="v2.1.0"} 1` и связывание через PromQL-оператор `group_left`.
  2. Использование сервисных меток скрейпинга Kubernetes (`relabel_configs`), которые автоматически добавляют лейбл пода `pod_label_version` или `app_kubernetes_io_version` на стороне сервера Prometheus без изменения кода самого приложения.
* **Необходимые источники / Свидетельства:**
  1. Prometheus Best Practices: [Metric and Label Naming](https://prometheus.io/docs/practices/naming/).
  2. Prometheus Design Patterns: The "Info" metric pattern.
* **Приоритет:** 🟡 **Medium**

#### 19. Ошибочное описание `gsignal` как отдельной системной горутины
* **Статья / Раздел:** `01. Linux/2. Процессы и сигналы.md` (строки 72–75)
* **Утверждение (Claim):**
  > *«В Go каждый поток ОС `M` имеет специальную системную горутину `gsignal`. Когда ядро доставляет сигнал...»*
* **Почему требует проверки (Why it needs checking):**
  В архитектуре рантайма Go `gsignal` — это не горутина в привычном понимании планировщика (она не планируется, не находится в очереди выполнения runqueue и не имеет собственного контекста выполнения Go-кода). Это специальный служебный псевдо-дескриптор `g`, указывающий на альтернативный сигнальный стек, выделенный через системный вызов `sigaltstack(2)`. Исполнение C/ассемблерного кода обработчика сигнала происходит непосредственно на этом стеке. Называть его "горутиной" педагогически некорректно.
* **Необходимые источники / Свидетельства:**
  1. Исходный код Go: `src/runtime/runtime2.go` (структура `m`, поле `gsignal *g`).
  2. `src/runtime/os_linux.go` (`minitSignals`).
* **Приоритет:** 🟡 **Medium**

#### 20. Ложное утверждение о слепом убийстве подов StatefulSet при потере кворума
* **Статья / Раздел:** `04. Kubernetes/6. Stateful приложения.md` (строки 211–214)
* **Утверждение (Claim):**
  > *«Если база данных не успела восстановить кворум после перезапуска `pod-2`, а StatefulSet слепо пошел обновлять `pod-1`, кластер потеряет кворум и база перейдет в аварийный режим Read-Only...»*
* **Почему требует проверки (Why it needs checking):**
  Контроллер `StatefulSet` в Kubernetes работает по строго детерминированному алгоритму: обновление подов происходит в строгом обратном порядке (например, 2 -> 1 -> 0), и контроллер **жестко ждет, пока обновляемый под не перейдет в статус Running и Ready**. Он никогда не пойдет "слепо" обновлять следующий под, пока предыдущий не прошел проверки `readinessProbe`! Потеря кворума возможна только при неправильно написанной проверке готовности, о чем и нужно сделать акцент.
* **Необходимые источники / Свидетельства:**
  1. Документация Kubernetes: StatefulSet Rolling Updates.
* **Приоритет:** 🟡 **Medium**

## 4. Критические слепые зоны модуля (Omissions & Blind Spots)

1. **CFS Quota в современном Go (Go 1.25 cgroup awareness vs automaxprocs):**  
   В статьях подробно описана проблема троттлинга CFS и `GOMAXPROCS`, однако полностью отсутствует упоминание индустриального стандарта `go.uber.org/automaxprocs`, а также новейших разработок в Go 1.25 по нативному чтению квот CPU из cgroups.
2. **Gateway API как официальный преемник Kubernetes Ingress:**  
   Статья 04.04 посвящена исключительно классическому `Ingress`, который переведен Kubernetes в режим поддержки. В 2026 году промышленным стандартом стал `Gateway API` (`HTTPRoute`, `GatewayClass`), решающий проблемы кросс-неймспейс маршрутизации и L7-манипуляций без хаоса вендорных аннотаций Nginx.
3. **Cilium и eBPF-based CNI вместо Kube-proxy:**  
   В статьях о сетях K8s подробно описаны `iptables` и `IPVS` режимы `kube-proxy`, но отсутствует упоминание бессерверного роутинга на eBPF (Cilium CNI), являющегося доминирующим стандартом современных Cloud-Native инфраструктур.
4. **Механика фрагментации кучи и `madvise` (`MADV_DONTNEED` vs `MADV_FREE`):**  
   В статьях о памяти Cgroups и Go не раскрыто, как взаимодействие рантайма Go с ядром через `madvise` порождает разницу между `Resident Set Size (RSS)` и физическим освобождением страниц операционной памяти.
5. **Dual-stack IPv6 в Kubernetes и Docker:**  
   Модуль полностью ориентирован на IPv4 (`10.0.0.0/8`, `172.17.0.0/16`). В современных инфраструктурных средах отсутствие упоминания Dual-stack IPv6 создает пробел в понимании сетевого стека.
