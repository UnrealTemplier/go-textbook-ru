3. **Поведение зависит от строки `go` в `go.mod` или от умолчаний сборки, а текст подаёт его безусловно:**

4. **Обработка ошибок, которая не срабатывает:** при таймауте `exec.CommandContext` возвращается `*exec.ExitError` («signal: killed», код −1), а не ошибка контекста. Ветка «отмена контекста» в примере ст. 43 недостижима (B-05).
5. **Ложное чувство безопасности:**
   - `regexp` «полностью иммунен к ReDoS» даже с паттерном злоумышленника (B-06);

## 2. Новые находки

### B-01 · Стриминг JSON: одна переменная `item` на весь поток — поля «протекают» между объектами · КОД + БЕЗОП.
- **Где:** ст. 29, пример `handleStream`, строки 64–79 (объявление 69, `Decode` 70–71); итог п. 2, строка 181.
- **Цитата:** строка 64 — `// ✅ Хорошо: стриминг, минимизация аллокаций`; строка 69 — `var item PayloadItem`; строки 70–71 — `for dec.More() {` / `if err := dec.Decode(&item); err != nil {`.
- **Утверждение:** переиспользовать одну переменную для всех элементов потока — правильный и экономный паттерн.
- **Почему важно:** `Decode` в существующую структуру не обнуляет её. Поля, которых нет в очередном объекте, сохраняют значения от прошлого. Для потока объектов разной «полноты» это тихая порча данных. Если среди полей есть флаги прав или идентификаторы владельца, это уже уязвимость: объект без поля наследует права предыдущего. Бриф (J-124) разбирает этот пример по другим поводам: `w.Write`, массив и `dec.Token()`, буферизация `Decoder`. Этот дефект в бриф не попал.
- **[улика]** поток `{"id":1,"admin":true,"name":"root"} {"id":2}` и тот же цикл с `var item` вне цикла → `{ID:1 Admin:true Name:root}`, затем `{ID:2 Admin:true Name:root}`.
- **Что проверить и где:** doc `encoding/json.Unmarshal` (поведение для существующих map и struct), `Decoder.Decode`. Исправление: объявлять `var item PayloadItem` внутри цикла или обнулять `item = PayloadItem{}` перед каждым `Decode`.
- **Тип:** КОД, БЕЗОП. · **Приоритет:** High

### B-02 · `setupDebugServer`: при пустом `DEBUG_PASS` вход с пустым паролем · БЕЗОП. + КОД
- **Где:** ст. 36, пример `setupDebugServer`, строки 81–104 (проверка — строка 95); раздел «Идиомы production-безопасности», строка 79.
- **Цитата:** строка 95 — `if !ok || user != "admin" || pass != os.Getenv("DEBUG_PASS") {`.
- **Утверждение:** базовая аутентификация из примера закрывает отладочные эндпоинты.
- **Почему важно:** если переменная окружения не задана (забыли секрет в манифесте, локальный запуск, новый стенд), `os.Getenv` возвращает `""`. Тогда запрос `Authorization: Basic YWRtaW46` (`admin:`) проходит проверку. Пример подан как образец защиты, а за ним — `pprof` (CPU-профили и trace как DoS) и `expvar` (`cmdline`, часто с секретами). Бриф (J-143) отмечает только сравнение через `!=` не за постоянное время — на фоне этой дыры это мелочь.
- **Что проверить и где:** запуск примера без `DEBUG_PASS` и `curl -u admin: http://127.0.0.1:6060/debug/pprof/`. Исправление: не стартовать отладочный сервер при пустом секрете; сравнивать через `subtle.ConstantTimeCompare`; слушать `127.0.0.1` или отдельный порт за firewall (раздел это советует, пример — нет).
- **Тип:** БЕЗОП., КОД · **Приоритет:** High

### B-03 · Импорт `net/http/pprof` и `expvar` публикует эндпоинты на `DefaultServeMux` — статья описывает обратный риск · БЕЗОП. + ФАКТ
- **Где:** ст. 36, строка 10 (врезка «Под капотом»), строки 85–90 (комментарий «без импорта» и регистрация на своём `mux`), диаграмма строки 51 (`expvar.Publish`).
- **Цитата:** строка 10 — «если вы не используете `http.ListenAndServe` на default-мультиплексоре, профилировщик останется недоступным. Всегда явно привязывайте `pprof` к админскому `http.ServeMux` или отдельному порту»; строка 85 — `// Явная регистрация pprof (без импорта _ "net/http/pprof")`.
- **Утверждение:** главная опасность побочного эффекта `init()` — что профилировщик окажется недоступен; если регистрировать хендлеры на своём `mux`, побочного эффекта нет.
- **Почему важно:**
  - Реальная опасность обратная. `init()` пакета `net/http/pprof` **всегда** вешает `/debug/pprof/…` на `http.DefaultServeMux`, `init()` пакета `expvar` — `/debug/vars` и публикует `cmdline` и `memstats`. Сервис, у которого основной сервер запущен как `http.ListenAndServe(":8080", nil)`, открывает эти эндпоинты наружу без аутентификации.
  - Импорт может прийти транзитивно, из сторонней библиотеки.
  - «Без импорта» в примере невозможно: чтобы вызвать `pprof.Index` и `expvar.Handler()`, пакеты нужно импортировать, и их `init()` выполнится. Админский `mux` из примера не отменяет регистрацию на `DefaultServeMux`, он лишь добавляет вторую.
- **[улика]** `src/net/http/pprof/pprof.go:95–104` — `func init()` с `http.HandleFunc(prefix+"/debug/pprof/", Index)` и ещё четырьмя путями; `src/expvar/expvar.go:382–387` — `http.HandleFunc("/debug/vars", expvarHandler)`, `Publish("cmdline", …)`, `Publish("memstats", …)`.
- **Что проверить и где:** указанные `init()`; doc `net/http/pprof` («The package is typically only imported for the side effect of registering its HTTP handlers»). Совет для редактора: основной сервер — только с собственным `ServeMux`, никогда с `nil`; отладочный — на `127.0.0.1`.
- **Тип:** БЕЗОП., ФАКТ · **Приоритет:** High

### B-04 · Паттерны `ServeMux` Go 1.22 работают только при `go 1.22`+ в `go.mod`; иначе — молчаливый 404 · ВЕРСИЯ
- **Где:** ст. 33, строки 14–20 («Эволюция ServeMux (Go 1.22+)»), 160–161 (собеседование), итог п. 6 (строка 179); ст. 1, строка 133; ст. 48, строка 52.
- **Цитата:** ст. 33:16–17 — «Начиная с Go 1.22, встроенный роутер претерпел фундаментальную модернизацию … Методы в маршрутах: `GET /users/{id}`».
- **Утверждение:** на тулчейне Go 1.22+ новый синтаксис паттернов доступен.
- **Почему важно:** новое поведение `ServeMux` включается версией языка основного модуля (`GODEBUG=httpmuxgo121`). Если в `go.mod` стоит `go 1.21` или ниже, паттерн `"GET /users/{id}"` разбирается по старым правилам как буквальный путь с пробелом. Он не совпадает ни с одним запросом, и сервер отвечает 404 без ошибки при регистрации. Обновить тулчейн, не подняв строку `go`, — частый сценарий миграции. Бриф ловит ту же ловушку для таймеров (J-094) и `loopvar` (J-160), но не для `ServeMux`.
- **[улика]** `mux.HandleFunc("GET /users/{id}", …)` + `httptest`-запрос `GET /users/42`: при `go 1.21` в `go.mod` → `404 404 page not found`; при `go 1.22` → `200 id=42`. `src/internal/godebugs/table.go:48` — `{Name: "httpmuxgo121", Package: "net/http", Changed: 22, Old: "1"}`.
- **Что проверить и где:** Go 1.22 release notes (`net/http`: enhanced routing patterns, `httpmuxgo121`); `doc/godebug.md`.
- **Тип:** ВЕРСИЯ · **Приоритет:** Medium

### B-05 · Таймаут `exec.CommandContext` даёт `*exec.ExitError` («signal: killed»), а не ошибку контекста · КОД + ФАКТ
- **Где:** ст. 43, пример `runExternalTask`, строки 112–138 (ветвление 126–135, комментарий 133); собеседование, строка 222.
- **Цитата:** строки 127–133 — `// Если процесс завершился с ненулевым кодом выхода:` … `// Если произошла отмена контекста или ошибка системного вызова`; строка 222 — «Обычный `error` свидетельствует о том, что процессу **не удалось запуститься вовсе** (… контекст был отменен до вызова системного вызова `fork`). Ошибка типа `*exec.ExitError` означает, что процесс … отработал, но завершился с ненулевым кодом выхода (exit code != 0)».
- **Утверждение:** отмену контекста можно отличить по тому, что ошибка — не `*exec.ExitError`.
- **Почему важно:**
  - Когда контекст истекает во время работы процесса, `CommandContext` убивает его сигналом, и `Run`/`Wait` возвращают `*exec.ExitError` с текстом `signal: killed` и `ExitCode() == -1`. `errors.Is(err, context.DeadlineExceeded)` при этом `false`.
  - В примере таймаут попадёт в первую ветку и будет залогирован как «process failed with code -1» вместе с частичным stderr. Ветка «отмена контекста» для этого случая недостижима. Ответ на собеседовании описывает ту же неверную классификацию.
  - Правильная проверка — `ctx.Err() != nil` после `Run`.
  - Мелочь в том же ответе: `exitErr.Stderr` заполняется только методом `Output()` и только если `cmd.Stderr == nil`. В примере с собственным буфером он пуст.
- **[улика]** `exec.CommandContext(ctx /*200ms*/, "sleep", "5").Run()` → `err=signal: killed`, `errors.As(err, &exitErr) == true`, `ExitCode() == -1`, `errors.Is(err, context.DeadlineExceeded) == false`.
- **Что проверить и где:** doc `os/exec.CommandContext`, `Cmd.Wait`, `ExitError.Stderr`; `src/os/exec/exec.go` (`Wait`, `awaitGoroutines`, обработка `ctx.Done`).
- **Тип:** КОД, ФАКТ · **Приоритет:** Medium

### B-06 · `regexp` «полностью иммунен к ReDoS», в том числе с паттерном злоумышленника · БЕЗОП. + УПРОЩ.
- **Где:** ст. 28, строки 7, 115 (собеседование), итог п. 1 (строка 131).
- **Цитата:** строка 7 — «На практике это делает Go-приложения полностью иммунными к атакам **ReDoS** …, где злоумышленник отправляет специально составленный паттерн или строку»; строка 115 — «В коде, где паттерн формируется динамически из пользовательского ввода, всегда используйте `regexp.Compile` и обрабатывайте ошибку».
- **Утверждение:** если паттерн задаёт пользователь, достаточно проверить ошибку `Compile`.
- **Почему важно:**
  - Гарантия RE2 — линейность по длине **входа** при фиксированном паттерне. Время — O(m·n), где m — размер скомпилированной программы. Паттерн злоумышленника с повторами (`(a{1000}){1000}` упирается в лимит, но близкие к нему конструкции проходят) раздувает m. Сочетание с большим входом даёт секунды CPU на запрос.
  - У самого `regexp/syntax` были DoS-уязвимости при компиляции пользовательских паттернов: исчерпание стека на глубокой вложенности и неограниченная память при разборе (CVE-2022-24921, CVE-2022-41715 — сверить номера и версии исправлений).
  - Бриф (J-120) поправляет устройство движка (нет DFA, O(m·n)), но не этот вывод о безопасности. Совет для пользовательских паттернов: лимит длины паттерна и входа, таймаут или отдельный воркер.
- **Что проверить и где:** doc `regexp` («the time … is linear in the size of the input» — при каком фиксированном выражении), `src/regexp/syntax/parse.go` (`maxHeight`, `maxSize`, лимит повторов 1000); Go security announcements 2022 (`regexp`). Бенчмарк: паттерн из нескольких сотен альтернатив на 1 МБ входа.
- **Тип:** БЕЗОП., УПРОЩ. · **Приоритет:** Medium

### B-07 · `ReadBytes`/`ReadString` предложены для сетевого ввода и «потоковой обработки длинных строк» — без лимита памяти · БЕЗОП.
- **Где:** ст. 6, таблица ловушек, строки 183–184.
- **Цитата:** 183 — «Установите лимит через `scanner.Buffer()` или используйте `bufio.Reader.ReadBytes('\n')` для потоковой обработки длинных строк»; 184 — «`ReadString` или `ReadBytes` предпочтительнее для сетевого IO. Они возвращают полный фрагмент до разделителя включительно».
- **Утверждение:** когда лимит `Scanner` мешает, правильная замена — `ReadBytes`.
- **Почему важно:** `ReadBytes`/`ReadString` копят строку целиком, пока не встретят разделитель, и **ничем не ограничены**. Клиент, приславший гигабайты без `\n`, выбивает процесс по памяти. Лимит `Scanner` (`ErrTooLong`) — это и есть защита, и совет «обойти его через `ReadBytes`» её снимает. Это не «потоковая обработка»: строка всё равно собирается в памяти целиком. Для сетевого ввода нужны `io.LimitReader`/`http.MaxBytesReader` поверх, `Scanner.Buffer` с осознанным максимумом или `ReadSlice`/`ReadLine` с обработкой `ErrBufferFull`/`isPrefix`. В брифе по ст. 6 (J-004, J-005, J-061, J-062, J-185–J-187) этого нет.
- **Что проверить и где:** `src/bufio/bufio.go` (`collectFragments` — цикл без ограничения размера), doc `Reader.ReadBytes`, `Reader.ReadSlice`.
- **Тип:** БЕЗОП. · **Приоритет:** Medium

### B-08 · `strconv.ParseFloat` молча принимает `NaN`, `Inf`, `0x1p-2` и `1_000` — проверка `err` не валидирует ввод · ПРОПУСК + БЕЗОП.
- **Где:** ст. 9, раздел 2 «Работа с плавающей точкой» (строки 45–61), раздел 6 «Ловушки и нюансы» (143–155), итог п. 3 (строка 163).
- **Цитата:** строка 163 — «**Всегда проверяйте ошибки.** Парсинг внешних данных (HTTP, БД, конфиги) никогда не бывает гарантированно успешным»; строка 146 — «необходимо предварительно заменять запятые на точки через `strings.Replace`».
- **Утверждение:** успешный `ParseFloat` без ошибки означает «обычное десятичное число».
- **Почему важно:**
  - `ParseFloat` принимает (без учёта регистра) `NaN`, `Inf`, `+Inf`, `Infinity`, шестнадцатеричные литералы и подчёркивания между цифрами. `ParseInt(s, 0, 64)` принимает `0x`, `0o`, `0b` и `_`.
  - Для сумм, лимитов и координат из запроса `NaN` проходит проверку `err == nil`, а дальше любое сравнение `amount > limit` даёт `false` — классический обход проверок. `Inf` ломает агрегаты.
  - Совет «заменить запятую на точку» ломает `1.234,56` (немецкий формат с разделителем тысяч) — тихо получится `1.234`.
  - Нужна оговорка: после разбора проверять `math.IsNaN`/`math.IsInf` и диапазон, для денег — не `float`. Бриф (J-008, J-068, J-194, J-195) этого не касается.
- **[улика]** `ParseFloat`: `"NaN"` → `NaN <nil>`, `"nan"` → `NaN <nil>`, `"-Inf"` → `-Inf <nil>`, `"infinity"` → `+Inf <nil>`, `"0x1p-2"` → `0.25 <nil>`, `"1_000"` → `1000 <nil>`; `ParseInt("0x10", 0, 64)` → `16`, `ParseInt("1_000", 0, 64)` → `1000`; `Atoi("1_000")` → `invalid syntax`.
- **Что проверить и где:** doc `strconv.ParseFloat` (абзац про `NaN`, `Inf`, подчёркивания), `strconv.ParseInt` (base 0).
- **Тип:** ПРОПУСК, БЕЗОП. · **Приоритет:** Medium

### B-09 · «Статическая линковка по умолчанию, один файл в `scratch`» — при `CGO_ENABLED=1` программа с `net` динамическая · ФАКТ + УПРОЩ.
- **Где:** ст. 47, строки 3, 5; ст. 44, строка 20; ст. 14, строка 6; ст. 48, строка 103.
- **Цитата:** ст. 47:3 — «возврат к бескомпромиссной **статической линковке по умолчанию**»; ст. 47:5 — «Вы просто копируете один файл в чистый Docker-образ `scratch` — и сервис мгновенно запускается»; ст. 44:20 — «В скомпилированном бинарнике Go нет неявной зависимости от динамического линковщика `libc` (если не используется cgo)».
- **Утверждение:** обычный `go build` даёт статический бинарник.
- **Почему важно:**
  - Если на машине сборки есть C-компилятор, `CGO_ENABLED` по умолчанию равен `1`. Тогда `net` (cgo-резолвер) и `os/user` неявно тянут cgo, и бинарник линкуется динамически с `libc` и `libresolv`.
  - Оговорка «если не используется cgo» не помогает: разработчик cgo не «использует», он включён неявно.
  - В `scratch` такой бинарник падает с загадочным `exec /app: no such file or directory` — нет интерпретатора `ld-linux`.
  - Статичность гарантирует `CGO_ENABLED=0` (с Go 1.20 — по умолчанию там, где нет C-тулчейна, — сверить) или теги `netgo,osusergo`.
- **[улика]** программа `fmt.Println(http.StatusOK)` с `import "net/http"`: `go env CGO_ENABLED` → `1`, `file app` → `dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2`, `ldd` → `libresolv.so.2`, `libc.so.6`; с `CGO_ENABLED=0` → `statically linked`.
- **Что проверить и где:** Go 1.20 release notes (cgo off without C toolchain), doc `net` (Name Resolution, `netgo`), `go help buildconstraint`.
- **Тип:** ФАКТ, УПРОЩ. · **Приоритет:** Medium

### B-13 · Ст. 4: буфер «уходит в кучу из-за цикла» — на деле из-за вызова через интерфейс · ФАКТ / УПРОЩ.
- **Где:** ст. 4, врезка «Под капотом» после примера ручного чтения, строка 143; пример строк 120–140.
- **Цитата:** «Если создавать буфер внутри цикла, Escape Analysis гарантированно отправит его в кучу, создавая колоссальную работу для GC. Вынос буфера за пределы цикла позволяет выделить память ровно один раз».

- **Почему важно:** escape analysis не зависит от того, в цикле ли `make`. Буфер убегает, потому что передаётся в `r.Read` через интерфейс `io.Reader` и компилятор не видит, что метод его не сохранит. - **[улика]** `-gcflags=-m`: `make([]byte, 4096)` в цикле с `r io.Reader` → `escapes to heap`; тот же код с `r *bytes.Reader` → `does not escape`.
- **Что проверить и где:** `go build -gcflags=-m` на двух вариантах; `src/cmd/compile/internal/escape/`.

## 3. Замечания к брифу

- **J-011 / К-3 — не все места.** Тот же тезис «синхронный I/O не блокирует потоки ОС благодаря планировщику» стоит в ст. 4: таблица, строка 249 («Синхронная, но планировщик Go паркует горутину, не блокируя OS thread»), и итог п. 5, строка 277 («`io` пакет работает синхронно, но не блокирует потоки ОС»). Для `*os.File` с обычным файлом это неверно. Править вместе с ст. 11 и 14.
- **J-027 — ещё одно место.** Ст. 38, `createSecureHTTPClient`, строки 222–225: литерал `&http.Transport{TLSClientConfig: tlsConfig, …}`. Непустой `TLSClientConfig` тоже отключает HTTP/2 (без `ForceAttemptHTTP2: true`), и `Proxy` не задан. Это пример из статьи про безопасность, поэтому важнее, чем кажется.
- **J-028 — неполон для Go 1.24+.** Бриф пишет, что ручной `rand.Seed` переключает глобальный генератор на `lockedSource`. С `go 1.24` в `go.mod` `rand.Seed` по умолчанию **ничего не делает** (`GODEBUG=randseednop`). Старый код и тесты, которые полагались на `rand.Seed(42)` ради воспроизводимости, молча теряют детерминизм. Ст. 37:111 («Не вызывайте `rand.Seed()`… Удаляйте legacy-код») нужна именно эта оговорка. **[улика]** `src/math/rand/rand.go:400–403` — `func Seed(seed int64) { if randseednop.Value() != "0" { return } …`; `src/internal/godebugs/table.go:60` — `{Name: "randseednop", Package: "math/rand", Changed: 24, Old: "0"}`.
- **J-030 — ещё одно ложное применение.** Ст. 42:7 приписывает zlib-обёртку не только HPACK, но и «сетевым протоколам (SSH, **TLS**…)». Сжатие на уровне TLS (DEFLATE) отключено повсеместно после CRIME и запрещено в TLS 1.3. `crypto/tls` его никогда не реализовывал. Править одним заходом с HPACK.
