### Кандидат 1: Бесконечный цикл и 100% CPU при дренаже канала из-за `break` внутри `select`
* **article/section:** `11. Каналы и синхронизация.md` (раздел `## Как реализовать "дрейн" канала (drain channel)?`, строки 2200–2208)
* **claim:**  
  В статье приводится пример очистки буфера канала перед повторным использованием:
  ```go
  for {
      select {
      case v := <-ch:
          processDrain(v)
      default:
          // буфер пуст, можно выходить
          break
      }
  }
  ```
* **why it needs checking:**  
  В языке Go оператор `break` внутри конструкции `select` прерывает выполнение **самого блока `select`**, а **НЕ** внешнего цикла `for`!  
  Когда канал пуст (или опустошается), выполнение немедленно проваливается в ветку `default`, выполняет `break` (выходя из `select`) и тут же переходит на следующую итерацию бесконечного цикла `for`.  
  Программа превращается в **бесконечный цикл активного ожидания (busy loop)**, который утилизирует 100% ядра CPU и никогда не завершается.  
  Для корректного выхода из цикла в Go обязательно требуется использование именованной метки (`break DrainLoop`) либо возврат из функции (`return`). Это классическая ловушка на собеседованиях, и приведение неработающего кода в обучающем руководстве недопустимо.
* **evidence/source needed:**  
  Спецификация языка Go (The Go Programming Language Specification, раздел "Break statements"):
  > *"A "break" statement terminates execution of the innermost "for", "switch", or "select" statement within the same function."*  
  Эмпирический запуск тестового стенда на Go подтверждает бесконечный цикл: горутина крутится в `default`, выполняя сотни миллионов пустых итераций в секунду.
* **priority:** 🔴 **High**

### Кандидат 2: Некомпилируемый вызов `errors.Is(r, runtime.PanicNilError)` и некорректная типизация
* **article/section:** `05. Ошибки, defer, panic recover.md` (раздел `## Что такое "panic wrapping" в Go 1.21+?`, строки 1885, 1899)
* **claim:**  
  В тексте утверждается:
  > *"Теперь `recover` возвращает `*runtime.PanicNilError`, и `errors.Is(r, runtime.PanicNilError)` истинно."*  
  > *"Проверить `if r == nil || errors.Is(r, runtime.PanicNilError)`"*
* **why it needs checking:**  
  Приведенный код содержит сразу две грубые ошибки, препятствующие компиляции:
  1. **Передача типа вместо выражения:** `runtime.PanicNilError` — это имя типа (`type PanicNilError struct{}`), а не значение. Сигнатура `errors.Is(err, target error) bool` ожидает вторым аргументом значение интерфейса `error`. Попытка передать имя типа вызывает фатальную ошибку компилятора:  
     `runtime.PanicNilError (type) is not an expression`.
  2. **Несовместимость типов `any` и `error`:** Переменная `r`, возвращаемая функцией `recover()`, имеет тип `any` (`interface{}`). Функция `errors.Is` принимает первым параметром `error`. В Go пустой интерфейс `any` статически не реализует интерфейс `error` (отсутствует метод `Error() string`), что вызывает ошибку компилятора:  
     `cannot use r (variable of interface type any) as error value in argument to errors.Is`.
  3. Идиоматичный и единственный рабочий способ проверить панику на `PanicNilError` в Go — это утверждение типа (type assertion):  
     ```go
     if _, ok := r.(*runtime.PanicNilError); ok { ... }
     ```
* **evidence/source needed:**  
  Попытка компиляции кода компилятором Go:
  ```text
  cannot use r (variable of interface type any) as error value in argument to errors.Is: interface{} does not implement error
  runtime.PanicNilError (type) is not an expression
  ```
* **priority:** 🔴 **High**

### Кандидат 3: Гарантированная паника `index out of range [0]` на пустом кольце Consistent Hashing
* **article/section:** `25. Практические задачи.md` (раздел `## Как реализовать согласованное хеширование (consistent hashing)?`, строки 1908–1914)
* **claim:**  
  Реализация метода поиска узла в кольце консистентного хеширования:
  ```go
  func (c *ConsistentHash) Get(key string) string {
      hash := hashFunc(key)
      idx := sort.SearchInts(c.ring, hash)
      if idx >= len(c.ring) { idx = 0 }
      return c.nodes[c.ring[idx]]
  }
  ```
* **why it needs checking:**  
  Если в кольце нет узлов (`len(c.ring) == 0` — например, кольцо только что создано или все ноды временно выведены из эксплуатации):
  1. `sort.SearchInts(c.ring, hash)` возвращает `0`.
  2. Условие `idx >= len(c.ring)` превращается в `0 >= 0`, что истинно, и ветка устанавливает `idx = 0`.
  3. На следующей строке выполняется выражение `c.ring[idx]` -> `c.ring[0]`. Обращение по индексу 0 к пустому срезу длины 0 приводит к мгновенной аварийной панике рантайма:  
     `panic: runtime error: index out of range [0] with length 0`.  
  В коде полностью отсутствует обязательная граничная проверка:
  ```go
  if len(c.ring) == 0 {
      return ""
  }
  ```
* **evidence/source needed:**  
  Эмпирический запуск `(&ConsistentHash{}).Get("test_key")` на Go немедленно роняет процесс с паникой `index out of range [0] with length 0`.
* **priority:** 🔴 **High**

### Кандидат 4: Математическое искажение и зануление результатов в `ConcurrentMapReduce` при `len(input) < NumCPU`
* **article/section:** `25. Практические задачи.md` (раздел `## Как реализовать конкурентный map-filter-reduce?`, строки 2203–2239)
* **claim:**  
  В статье приводится generic-реализация конкурентного `MapReduce`:
  ```go
  func ConcurrentMapReduce[T, U, V any](input []T, mapper func(T) U, reducer func(U, U) U) U {
      n := runtime.NumCPU()
      chunkSize := (len(input) + n - 1) / n
      var wg sync.WaitGroup
      results := make([]U, n) // промежуточный результат по чанкам
      for i := 0; i < n; i++ {
          start := i * chunkSize
          end := start + chunkSize
          if end > len(input) { end = len(input) }
          if start >= end { continue }
          wg.Add(1)
          go func(idx, s, e int) {
              defer wg.Done()
              var acc U
              for j := s; j < e; j++ {
                  mapped := mapper(input[j])
                  if j == s { acc = mapped } else { acc = reducer(acc, mapped) }
              }
              results[idx] = acc
          }(i, start, end)
      }
      wg.Wait()
      // reduce комбинированных результатов
      var final U
      for i, r := range results {
          if i == 0 {
              final = r
          } else {
              final = reducer(final, r)
          }
      }
      return final
  }
  ```
* **why it needs checking:**  
  Алгоритм содержит две критические ошибки:
  1. **Искажение и зануление результатов при малом объеме входа:** Срез `results` выделяется фиксированного размера `n` (`runtime.NumCPU()`, например 8). Если `len(input) < n` (например, 2 элемента), то для $i \ge 2$ условие `if start >= end { continue }` пропускает запуск горутины. Ячейки `results[2..7]` остаются незаполненными и содержат дефолтное нулевое значение типа `U` (`zero value`, для чисел — `0`). Финальный цикл `for i, r := range results` бежит по **всем `n` элементам** и сворачивает реальные данные с шестью нулями! Если `reducer` вычисляет произведение чисел (`a * b`), функция вместо правильного ответа $2 	imes 3 = 6$ возвращает **0**! Если тип `U` — указатель или структура, не допускающая zero value, произойдет паника рантайма.
  2. **Некорректная обработка пустого входа:** При `len(input) == 0` пропускаются все горутины, и функция возвращает неинициализированный `final`, свернутый сам с собой $n-1$ раз.
  3. **Мертвый параметр типа в сигнатуре:** В определении `[T, U, V any]` тип `V` вообще нигде не используется.
* **evidence/source needed:**  
  Тестовый прогон:
  ```go
  ConcurrentMapReduce([]int{2, 3}, func(x int) int { return x }, func(a, b int) int { return a * b })
  // Вывод: 0 (Ожидалось: 6)
  ```
* **priority:** 🔴 **High**

### Кандидат 5: Гонка данных (Data Race) и порча памяти в `Broker` (Pub/Sub) при конкурентном `Unsubscribe`
* **article/section:** `25. Практические задачи.md` (раздел `## Как реализовать паттерн «издатель-подписчик» (pub/sub)?`, строки 543–567)
* **claim:**  
  В статье приводится реализация потокобезопасного in-memory брокера:
  ```go
  func (b *Broker) Unsubscribe(topic string, ch <-chan interface{}) {
      b.mu.Lock()
      defer b.mu.Unlock()
      subs := b.subscribers[topic]
      for i, sub := range subs {
          if sub == ch {
              b.subscribers[topic] = append(subs[:i], subs[i+1:]...)
              break
          }
      }
  }

  func (b *Broker) Publish(topic string, msg interface{}) {
      b.mu.RLock()
      subs := b.subscribers[topic] // копия слайса, безопасно? Нужно копировать, т.к. мутабельно
      b.mu.RUnlock()
      for _, ch := range subs {
          select {
          case ch <- msg:
          default:
          }
      }
  }
  ```
* **why it needs checking:**  
  Здесь допущена классическая гонка данных на разделяемом базовом массиве среза:
  1. Присваивание `subs := b.subscribers[topic]` в методе `Publish` копирует **только 24-байтный заголовок слайса** (ptr, len, cap). Указатель `array` продолжает указывать на **тот же самый базовый массив в памяти**.
  2. Горутина-публикатор отпускает блокировку `b.mu.RUnlock()` и начинает итерироваться по элементам массива: `for _, ch := range subs`.
  3. В этот же момент параллельная горутина вызывает `Unsubscribe`, захватывает монопольный `Lock` и выполняет:  
     `b.subscribers[topic] = append(subs[:i], subs[i+1:]...)`.  
     Функция `append` со сдвигом элементов **модифицирует данные в базовом массиве in-place**!
  4. Происходит одновременное несинхронизированное чтение и запись одной и той же области памяти. Детектор гонок `go test -race` немедленно фиксирует Data Race, а сообщения могут быть отправлены не тем подписчикам либо пропущены из-за сдвига индексов. В комментариях автор сам оставил сомнение (`// копия слайса, безопасно? Нужно копировать`), но защитную копию так и не сделал.
* **evidence/source needed:**  
  Запуск теста с флагом `-race` выдает:
  ```text
  WARNING: DATA RACE
  Read at 0x... by goroutine A in Broker.Publish
  Previous write at 0x... by goroutine B in Broker.Unsubscribe
  ```
  Необходимо копировать срез под замком:
  ```go
  subs := append([]chan interface{}(nil), b.subscribers[topic]...)
  ```
* **priority:** 🔴 **High**

### Кандидат 6: Скрытая гонка данных при потоковом чтении CSV: использование `ReuseRecord = true` с передачей срезов в канал
* **article/section:** `25. Практические задачи.md` (раздел `## Как реализовать потоковую обработку большого CSV/JSON файла?`, строки 2330–2350)
* **claim:**  
  В коде рекомендуется совмещать `ReuseRecord = true` с конкурентной передачей строк воркерам через канал:
  ```go
  reader := csv.NewReader(file)
  reader.ReuseRecord = true // переиспользуем слайс для экономии памяти
  for {
      record, err := reader.Read()
      if err == io.EOF { break }
      // обработать record (возможно отправить в канал)
  }

  // Для параллелизма:
  rows := make(chan []string, 1000)
  go func() {
      // read and send to rows
      close(rows)
  }()
  // пул воркеров читает rows
  ```
* **why it needs checking:**  
  Это крайне опасный антипаттерн, приводящий к порче данных в продакшене.

### Кандидат 7: Астрономический выброс токенов и срыв лимита при инициализации `TokenBucket`
* **article/section:** `25. Практические задачи.md` (раздел `## Как реализовать rate limiter?`, строки 196–220)
* **claim:**  
  В структуре `TokenBucket`:
  ```go
  type TokenBucket struct {
      rate       float64
      burst      int
      tokens     float64
      lastUpdate time.Time
      mu         sync.Mutex
  }

  func (tb *TokenBucket) Allow() bool {
      tb.mu.Lock()
      defer tb.mu.Unlock()
      now := time.Now()
      elapsed := now.Sub(tb.lastUpdate).Seconds()
      tb.tokens += elapsed * tb.rate
      if tb.tokens > float64(tb.burst) {
          tb.tokens = float64(tb.burst)
      }
      tb.lastUpdate = now
      if tb.tokens >= 1 {
          tb.tokens--
          return true
      }
      return false
  }
  ```
* **why it needs checking:**  
  При обычной инициализации структуры `tb := &TokenBucket{rate: 10, burst: 5}` поле `tb.lastUpdate` имеет нулевое значение (`time.Time{}`, 0001-01-01 00:00:00 UTC).  
  При самом первом вызове метода `Allow()` выражение `now.Sub(tb.lastUpdate).Seconds()` вычисляет разницу более чем в 2026 лет (~$6.4 	imes 10^{10}$ секунд).  
  Значение `tb.tokens` мгновенно получает сотни миллиардов фиктивных токенов, что сразу же выравнивает `tokens` на максимальный `burst`, полностью игнорируя начальное состояние или стартовый баланс.  
  Кроме того, отсутствуют проверки на `burst <= 0` и `rate <= 0`: при `burst = 0` метод `Allow()` навсегда блокирует все запросы (`tokens` всегда $\le 0$).
* **evidence/source needed:**  
  Поведение `time.Time{}` в Go: метод `IsZero()` возвращает `true`. Требуется инициализация `lastUpdate: time.Now()` в конструкторе либо явная проверка `if tb.lastUpdate.IsZero() { tb.lastUpdate = now }`.

### Кандидат 8: Вымышленный механизм "panic wrapping" с извлечением обеих паник через `recover`
* **article/section:** `05. Ошибки, defer, panic recover.md` (раздел `## Что такое "panic wrapping" в Go 1.21+?`, строки 1885, 1901)
* **claim:**  
  В статье утверждается о появлении в Go 1.21 новой системы обёртывания паник:
  > *"Кроме того, в 1.21 добавили экспериментальную поддержку "wrapping panic": если внутри `defer` вызывается `panic` с новым значением, оно оборачивает исходную панику (через структуру `_panic`) и `recover` может извлечь обе. Однако пока это нестабильно."*  
  > *"Что такое wrapped panic? Механизм, позволяющий добавить контекст к панике, как обёртка ошибок, но пока не для production."*
* **why it needs checking:**  
  Это техническая фикция (галлюцинация). Ни в Go 1.21, ни в последующих релизах Go не существует механизма "wrapped panic" в публичном API языка.  
  Вызов `recover()` в Go фундаментально возвращает **только значение самой последней активной паники** текущей горутины. `recover` не возвращает списки или цепочки паник, и функции вроде `errors.Unwrap` к паникам неприменимы. Внутренний связный список `_panic.link` в `src/runtime/panic.go` используется исключительно рантаймом для форматирования аварийного дампа стека при краше программы, чтобы показать, что паника случилась во время раскрутки другой паники. Приписывание рантайму возможности «извлечь обе паники через recover» вводит кандидатов в глубокое заблуждение.
* **evidence/source needed:**  
  Примечания к релизу Go 1.21; исходники `src/runtime/panic.go`. В Go 1.21 появилось только одно изменение вокруг паник: `panic(nil)` теперь транслируется в `*runtime.PanicNilError` (чтобы `recover()` не возвращал вводящий в заблуждение `nil`).
* **priority:** 🔴 **High**

### Кандидат 10: Миф о "сдвиге элементов при удалении из map для линеаризации цепочки"

  В стандартной реализации ассоциативного массива Go (`runtime/map.go`) функция `mapdelete` **никогда не сдвигает ключи или значения в бакетах**!

### Кандидат 13: Недостоверное утверждение об уязвимости движка `regexp` к ReDoS

  > *"В Go стандартный `regexp` использует алгоритм с гарантированной линейной сложностью, но уязвимость может проявиться при использовании множественных жадных квантификаторов внутри друг друга... Go regexp не имеет backtracking кроме некоторых ограниченных случаев (по стандарту RE2)."*

### Кандидат 14: Искажение механизма создания процессов `os/exec` в Linux (fork vs clone/vfork)

* **claim:**  
  > *"`os/exec`, который под капотом вызывает `fork/exec`... `os/exec` использует `fork` с последующим `exec`, минимизируя промежуток."*
* **why it needs checking:**  
  Прямой вызов `fork()` в многопоточных процессах на Linux (где рантайм Go всегда имеет несколько системных потоков M) категорически опасен: `fork` клонирует только поток, вызвавший форк, а все мьютексы и внутренние очереди других потоков остаются в неопределенном или заблокированном состоянии.

### Кандидат 16: Ошибочное утверждение о сохранении проблемы ABA в наивном lock-free стеке Трейбера в Go
* **article/section:** `12. Продвинутая конкурентность.md` (раздел `## Как работает lock-free стек или очередь на атомиках?`, строки 853, 856)

### Кандидат 22: Неполная реализация `LRU[K, V]` при некорректной емкости `cap <= 0`
* **article/section:** `25. Практические задачи.md` (строки 144–154)
* **claim:**  
  В методе `Put` проверка вытеснения реализована как:
  ```go
  if l.list.Len() >= l.cap {
      oldest := l.list.Back()
      if oldest != nil {
          l.list.Remove(oldest)
          delete(l.items, oldest.Value.(*entry[K, V]).key)
      }
  }
  ```
* **why it needs checking:**  
  Если кэш сконфигурирован с `cap <= 0`, то при первой же вставке `l.list.Len() >= l.cap` истинно ($0 \ge 0$), но `oldest := l.list.Back()` возвращает `nil`. Вытеснения не происходит, узел добавляется в список, и кэш продолжает неограниченно расти, игнорируя нулевой лимит. Требуется явная валидация `if cap <= 0 { ... }` в конструкторе.
* **evidence/source needed:**  
  Граничные условия реализаций LRU-кэша.
* **priority:** 🟢 **Low**

## 🔍 Системные белые пятна и архитектурно-педагогические пробелы модуля (Blind Spots)

В ходе сплошного анализа всех 28 глав Модуля 22 выявлены четыре ключевых пробела, требующих обязательного дополнения при дальнейшей авторской доработке:

1. **Отсутствие глубокого разбора итераторов Go 1.23+ (`iter.Seq`, `iter.Seq2`, `iter.Pull`):**  
   В главах 02 и 03 подробно разбираются классические циклы `for`, `for range` и нововведения Go 1.22 (`range over int`). Однако стандарт итераторов Go 1.23 — один из самых фундаментальных архитектурных сдвигов в языке со времён дженериков — практически не представлен в вопросах и практических задачах. На собеседованиях уровня Middle+/Senior сейчас регулярно требуют объяснить разницу между push-итераторами (`iter.Seq[V]`) и pull-итераторами (`iter.Pull[V]`), механику работы прерывания цикла через `yield() bool`, а также интеграцию с пакетами `slices` и `maps`.
2. **Детерминированное тестирование конкурентного кода (`testing/synctest` в Go 1.24+):**  
   В главах по тестированию и практическим задачам тестирование конкурентных конструкций по-прежнему предлагается делать через недетерминированные задержки `time.Sleep` или каналы-координаторы. Появление пакета `testing/synctest` с изоляцией горутин в виртуальном времени (`synctest.Run`) решает проблему «flaky tests» в асинхронном коде Go, но в материалах этот важнейший инструмент не освещен.
3. **Механизмы Zero-GC Highload архитектуры и арены памяти (`arena`):**  
   В главах 06, 08 и 22 глубоко описаны стек, куча и GC, но обойдена вниманием проблематика проектирования сервисов с нулевой нагрузкой на GC при нагрузках 500k–1M RPS. Не раскрыты паттерны работы с плоскими сериализованными аренами памяти, пулами байтовых срезов без указателей и off-heap буферами, которые являются обязательными знаниями для Staff/Principal инженеров в финтехе и adtech.
4. **Слабые ссылки в Go 1.24+ (пакет `weak`):**  
   В Go 1.24 стандартизирован пакет `weak` (`weak.Pointer`), позволяющий реализовывать канонические ассоциативные кэши и пулы структур без удержания объектов от сборщика мусора и без тяжеловесных финализаторов. В главах про кэширование (LRU, `sync.Pool`) этот примитив отсутствует.
