## Детальные результаты

### 1. Type Erasure в C# — **INCORRECT**
- **Текст:** `2. История создания Go…md:84` — «(как в Java/C# с Type Erasure)».
- **Оценка:** в .NET CLR дженерики реифицированы: информация о типах сохраняется в рантайме, для value-типов JIT создаёт специализированный код (без boxing). Type erasure — особенность JVM/Java. Это общеизвестный факт (ECMA-335, Kennedy & Syme, 2001). В этом сеансе он не перепроверялся экспериментом, он взят из спецификации и литературы.
- **Вывод:** фраза неверна в части C#. Заменить на «как в Java с Type Erasure» либо противопоставить Java (стирание) и C# (реификация и JIT-специализация). Сама «дилемма трёх зол» верна.

### 2. Правило `internal/` — **INCORRECT**
- **Текст:** `22. Пакеты…md:109` — «доступен… только пакетам, расположенным **в дереве каталогов выше** родительской директории `internal/`».
- **Проверка (эксперимент, go 1.27.1):** `a/internal/tok`. Импорт из `a/sub` (потомок родителя) — сборка прошла. Импорт из `up` (вне поддерева `a/`) — `use of internal package i/a/internal/tok not allowed`.
- **Правило:** импорт разрешён только из пакетов в поддереве, корнем которого служит **родитель** `internal` (то есть сам родитель и его потомки), а не из «вышестоящих».
- **Вывод:** формулировка в статье неверна и противоречит собственной диаграмме (там внешний проект запрещён). Исправить на «в поддереве родителя каталога `internal/`».

### 3. Встраивание `sync.Mutex` — ст. 13 **VERIFIED**, ст. 20 **INCORRECT** (как «золотое правило»)
- **Ст. 13 (`:158–170`):** встраивание делает `Lock/Unlock` частью публичного API и структура становится некопируемой (`go vet copylocks`). Это согласуется с Go Code Review Comments и практикой stdlib.
- **Ст. 20 (`:165`):** утверждение «встраивайте `sync.Mutex` по значению» подано как правило. В части **zero value** оно верно: `var s Server; s.Lock()` работает без инициализации (проверено в тестовой программе). Но встраивание экспортирует `Lock/Unlock`. Корректная идиома: неэкспортируемое поле `mu sync.Mutex`, которое тоже полезно без инициализации.
- **Вывод:** противоречие внутри модуля реально. Ст. 20 нужно привести к `mu sync.Mutex`. Для приватного неэкспортируемого типа встраивание допустимо, это стилистический спор, а не «золотое правило».

### 4. `CanSet()` и `json.Marshal` — **INCORRECT** (объяснение)
- **Поведение — VERIFIED:** `json.Marshal(C{"h",1})` вернул `{"port":1}`. Поле `host` пропускается. Дополнительно `go vet` выдаёт `struct field host has json tag but is not exported`.
- **Причина (по scout):** `Marshal` читает значения, `CanSet()` относится к записи (`Unmarshal`). Поле исключается при построении списка полей по признаку неэкспортируемости (`PkgPath != ""`). Исходник `encoding/json` в этом сеансе **не открывался**, так что механизм подтверждён лишь логикой API `reflect` (`CanSet` — про запись).
- **Вывод:** формулировка про `CanSet()` вводит в заблуждение. Заменить на «неэкспортируемые поля кодер не обходит».

### 5. `GODEBUG=loopvar=1` — **INCORRECT**
- **Текст:** `27. Совместимость…md:58`.
- **Проверка 1 (поведение):** `go 1.21` в `go.mod` → вывод `3 3 3`; `go 1.22` → `0 1 2`. Старая семантика действительно сохраняется по версии в `go.mod`, то есть поведение статьёй описано верно.
- **Проверка 2 (механизм):** в `src/internal/godebugs/table.go` в Go 1.27.1 нет настройки `loopvar` (grep пустой). Переключение происходит по языковой версии модуля, а не через `GODEBUG`.
- **Замечание scout о `GOEXPERIMENT=loopvar` (Go 1.21):** по памяти, в этом сеансе не проверялось → **NOT CHECKED**. На вывод не влияет.
- **Вывод:** убрать упоминание `GODEBUG=loopvar=1`. Правильно: «семантика определяется директивой `go` в `go.mod`».

### 6. Статическая линковка и `FROM scratch` — **PARTIALLY CORRECT**
- **Эксперимент (linux/amd64, Fedora, gcc есть):** программа с `net/http`, `go build` → `dynamically linked, interpreter /lib64/ld-linux-x86-64.so.2`, `ldd` показывает `libresolv.so.2`, `libc.so.6`. С `CGO_ENABLED=0` → `statically linked`.
- **Контекст:** динамическая линковка возникает при включённом cgo (то есть есть C-компилятор) и использовании `net`/`os/user`. Без gcc в окружении cgo автоматически отключается и бинарник статический. Поэтому формулировка scout «ошибка: no such file or directory» верна, но зависит от среды.
- **Вывод:** тезис «Go статически линкуется по умолчанию, поэтому `FROM scratch` подойдёт» неполон. Нужна оговорка: для `net`/`os/user` на Linux использовать `CGO_ENABLED=0`. Тексты ошибки Docker (`standard_init_linux.go…`) в этом сеансе не воспроизводились → **NOT CHECKED**.

### 7. `recover()` и фатальные ошибки — **PARTIALLY CORRECT**
- **Эксперимент:** бесконечная рекурсия при `defer … recover()` → `fatal error: stack overflow`, `recover` не сработал. Подтверждено для stack overflow.
- **Остальные примеры** (`concurrent map writes`, `out of memory`, `all goroutines are asleep`) известны из поведения рантайма, но в этом сеансе **не воспроизводились** → **NOT CHECKED**.
- **Текст статьи:** в `:48` «единственный штатный способ перехватить падающую горутину» формально верно для паник, но не упоминает неперехватываемые фатальные ошибки. Это педагогический пробел, не ложь.
- **Вывод:** рекомендуется добавить врезку. Приоритет средний.

### 8. AVX2/AVX-512 в `memclrNoHeapPointers` — **INCORRECT**
- **Исходник:** `/usr/local/go/src/runtime/memclr_amd64.s` содержит ветки на AVX2 (`hasAVX2`), ERMS и `REP; STOSQ`. Упоминаний `ZMM`/`AVX512` нет.
- **Вывод:** «AVX-512» в статье неверно, верно «SSE2/AVX2/`REP STOSQ`». Вывод scout о том, что «стековая память зануляется не через `memclr` на каждый фрейм», в этом сеансе **не проверялся** → **NOT CHECKED**.
- Утверждение про «сотни байт за единицы тактов» — **OPINION / NOT CHECKED** (бенчмарка нет).

### 9. Сравнение интерфейсов «побайтово» — **INCORRECT** (упрощение)
- **Эксперимент:** `any(F{NaN}) == any(F{NaN})` → `false`; `F{0.0} == F{-0.0}` → `true`. Эти результаты невозможны при побайтовом сравнении: у `NaN` одинаковые биты, у `+0`/`-0` разные.
- **Вывод:** фраза «рантайм производит побайтовое сравнение» неверна в общем случае. Верно: сравнение выполняется по функции равенства типа (для `memequal`-совместимых типов она сводится к побайтовому сравнению). Исправить.

### 10. Recovery middleware и `http.ErrAbortHandler` — **VERIFIED** (с оговоркой)
- **Исходник:** `net/http/server.go:1905–1909`: `ErrAbortHandler` — сигнальное значение, при нём стек-трейс не логируется. Сам сервер проверяет `err != ErrAbortHandler` (`:1936`).
- **Оценка:** пример статьи перехватывает любое значение и пытается отдать 500, то есть для `ErrAbortHandler` поведение отличается от стандартного. Это не фактическая ошибка листинга, а риск, который стоит пояснить. Утверждение статьи `:165` о встроенном `recover` на каждое соединение в `net/http` — **VERIFIED** косвенно (тот же код), но детали не изучались.

### 11. `panic(nil)` → `*runtime.PanicNilError` — **OUTDATED** (пропуск в статье)

### 12. `hchan` и «спинлок» — **PARTIALLY CORRECT**

### 14. `[]User` «без единого указателя» — **INCORRECT**
- Для `User{Name string}` строка содержит указатель на данные (заголовок: `Data`, `Len`). Сами заголовки лежат подряд, а байты строк — в других местах. Это верно по определению `string` (тип описан в `unsafeheader`). Тезис про кэш-локальность верен только для заголовков.
- **Вывод:** заменить на «без индирекции на каждую структуру», либо оговорить, что строки не inline.

### 15. GCShape для `int` и `float64` — **VERIFIED** (scout ошибся)
- **Источник:** в тестах компилятора встречаются имена вида `go.shape.int`, `go.shape.struct{…}`. Фрагмент статьи «`int` и `float64` получают разные GCShape» согласуется с этим. Часть scout о том, что скаляры не группируются, совпадает с текстом статьи, то есть претензии нет.
- **Неточность:** формулировка «оптимизируя регистровую передачу аргументов» — **NOT CHECKED**, это не доказано.
- **Оговорка:** детали реализации менялись между версиями, поэтому «всё про GCShape» — **CONTEXT-DEPENDENT**.

### 16. Стек потока 8 МБ — **CONTEXT-DEPENDENT**
- Статья `:50` пишет «по умолчанию 1–8 МБ», диаграмма — 8 МБ. Для потоков Java (HotSpot, linux x64) стандартный `-Xss` — 1 МБ; 8 МБ — типичный `ulimit -s` (и размер стека потока по умолчанию в glibc `pthread`). Из памяти, не проверено → **NOT CHECKED**.
- **Вывод:** текст («1–8 МБ») нормален, диаграмма иллюстративна. Правка желательна, но не критична.

### 17. `github.com/lib/pq` — **CONTEXT-DEPENDENT / OPINION**
