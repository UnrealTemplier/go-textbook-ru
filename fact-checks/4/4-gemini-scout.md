### Кандидат 1: Приписывание механизма Type Erasure языку C# (смешение архитектуры CLR с JVM)
* **article/section:** `2. История создания Go. Google, Rob Pike, Ken Thompson, Robert Griesemer.md` / `## Смещение парадигмы: От академичности к инженерии` (блок «Собеседование»)
* **claim:**  
  *«Любая реализация дженериков — это выбор из трех зол: ... 2. Медленное исполнение из-за упаковки типов (boxing) и виртуальных вызовов (как в Java/C# с Type Erasure)»*.
* **why it needs checking:**  
  Язык C# и среда выполнения .NET CLR **НЕ используют стирание типов (Type Erasure)**!  
  В .NET реализованы полноправные реифицированные дженерики (Reified Generics):
  1. Информация о типах сохраняется во время выполнения (`typeof(List<int>) != typeof(List<string>)`).
  2. Для размерных типов (`struct`, `int`, `double`) JIT-компилятор CLR на лету генерирует специализированный машинный код (мономорфизация без упаковки `boxing`).
  3. Для ссылочных типов (`class`) код функций разделяется, но оперирует типизированными ссылками без стирания до `object` и без накладных приведений типов.
  Стирание типов до `Object` с боксингом примитивов — это отличительная черта платформы Java, в то время как C# традиционно приводится в литературе по Computer Science как образцовый контрпример к Java. Приписывание Type Erasure к C# — грубая фактологическая ошибка.
* **evidence/source needed:**  
  ECMA-335 Common Language Infrastructure (CLI) Specification, Partition II (Generics); Don Syme et al., *Design and Implementation of Generics for the .NET Common Language Runtime*.
* **priority:** **High**

### Кандидат 2: Диаметральное искажение правила видимости компилятора для каталогов `internal/`
* **article/section:** `22. Пакеты и структура проекта как часть философии Go.md` / `### 3. internal/ (Магия инкапсуляции компилятора)`
* **claim:**  
  *«...код внутри любой папки с именем `internal/` доступен для импорта только тем пакетам, которые расположены в дереве каталогов выше родительской директории этого `internal/`»*.
* **why it needs checking:**  
  Утверждение в статье **противоположно** реальному правилу компилятора Go!  
  Согласно официальной спецификации *Go 1.4 Internal Packages Design Document*:
  > *«An import of a path containing the element `internal` is only allowed from packages rooted in the tree rooted at the parent of the `internal` directory»*.
  
  Это означает:
  - Пакет `internal` доступен **только родительской директории и ее потомкам (внутри поддерева родителя)**.
  - Пакеты, находящиеся в дереве каталогов **выше** родителя (предки и внешние модули), импортировать этот `internal` **НЕ ИМЕЮТ ПРАВА**!
  
  *Пример:* если путь пакета — `myproject/pkg/auth/internal/token`, то:
  - Пакет `myproject/pkg/auth` и его дочерние пакеты (`myproject/pkg/auth/...`) могут импортировать `token`.
  - Пакеты, расположенные «выше» (`myproject/pkg` или корневой `myproject`), при попытке импорта получат ошибку компилятора: `use of internal package ... not allowed`.
  
  Формулировка статьи («расположены в дереве каталогов выше») дезинформирует разработчиков относительно базового механизма инкапсуляции в Go.
* **evidence/source needed:**  
  Go Command Documentation: *Internal Packages* (`go help packages`); `src/cmd/go/internal/load/pkg.go` (проверка `disallowedByInternal`).
* **priority:** **High**

### Кандидат 3: Педагогическое противоречие: встраивание `sync.Mutex` как «Золотое правило» vs «Смертельная опасность»
* **article/section:**  
  1. `13. Embedding. Как в Go реализуется композиция.md` / `> [!warning] Ловушка / Gotcha: Встраивание sync.Mutex`  
  2. `20. Zero Value как часть дизайна языка.md` / `## Ловушка: Встраивание и Zero Value`
* **claim:**  
  - В статье 13 встраивание мьютекса названо смертельно опасной ошибкой:  
    *«Начинающие разработчики часто встраивают мьютекс прямо в бизнес-структуру... Однако в этом кроется смертельная опасность: структура Cache становится строго некопируемой! ... Рекомендация: Объявляйте мьютексы как явные приватные поля структуры: mu sync.RWMutex»*.
  - В статье 20 то же самое действие объявляется эталонным стандартом:  
    *«Золотое правило: Встраивайте примитивы синхронизации (`sync.Mutex`, `sync.RWMutex`) и внутренние состояния строго по значению: `type Server struct { sync.Mutex; State int }`... В этом случае объявленная переменная сразу готова к вызову прямо на стеке!»*.
* **why it needs checking:**  
  Прямое смысловое противоречие между статьями одного модуля.  
  Кроме того, рекомендация из статьи 20 нарушает базовые правила проектирования надежного API в Go:
  1. Встраивание `sync.Mutex` делает методы `Lock()` и `Unlock()` публичной частью интерфейса структуры `Server` (экспортируемое API), позволяя внешнему вызывающему коду несанкционированно захватывать внутреннюю блокировку сервиса и провоцировать дедлоки.
  2. Делает саму структуру `Server` некопируемой (`go vet` выдает предупреждение `passes lock by value`).
  Идиоматичный способ использования Zero Value для мьютекса без утечки методов наружу — явное неэкспортируемое поле: `mu sync.Mutex`. В этом случае `var s Server; s.mu.Lock()` работает мгновенно из коробки, не ломая инкапсуляцию.
* **evidence/source needed:**  
  Go Code Review Comments: *Synchronous Functions / Mutexes*; `src/sync/mutex.go`; статический анализатор `go vet (copylocks)`.
* **priority:** **High**

### Кандидат 4: Некорректное объяснение пропуска неэкспортированных полей в `json.Marshal` через `reflect.Value.CanSet()`
* **article/section:** `23. Public и Private через экспортируемость имен.md` / `## Mechanical Sympathy: Рефлексия и сериализация в JSON`
* **claim:**  
  Листинг демонстрирует структуру с неэкспортируемым полем:
  ```go
  type Config struct {
      host string `json:"host"` // ❌ не экспортируется
      Port int    `json:"port"`
  }
  ```
  И дает объяснение:  
  *«Поле host было тихо проигнорировано упаковщиком JSON! Пакет encoding/json лежит за пределами вашего пакета main, поэтому он видит поле host через рефлексию, но метод reflect.Value.CanSet() для него возвращает false»*.
* **why it needs checking:**  
  Объяснение содержит фундаментальную путаницу между сериализацией (чтением) и десериализацией (записью):
  1. Метод `reflect.Value.CanSet()` проверяет возможность **записи** в ячейку памяти. Он используется исключительно при десериализации (`json.Unmarshal`).
  2. При **сериализации** (`json.Marshal`) данные только **читаются**! Метод `CanSet()` здесь вообще не вызывается.
  3. В пакете `encoding/json` для чтения значения поля структуры используется метод `Field(i).Interface()`. Но если вызвать `.Interface()` на неэкспортированном поле структуры из внешнего пакета, рантайм вызовет фатальную панику: `reflect: call of reflect.Value.Interface on zero Value` или `panic: reflect: Object.Interface: cannot return value obtained from unexported field`.
  4. Поэтому кодировщик JSON на этапе сканирования полей (`typeFields`) явно исключает поля, у которых `sf.PkgPath != ""` (признак неэкспортируемости).
  Апелляция к `CanSet()` при объяснении поведения `json.Marshal` технически неверна.
* **evidence/source needed:**  
  `src/encoding/json/encode.go` (функция `typeFields`), `src/reflect/value.go` (методы `CanSet` и `Interface`).
* **priority:** **High**

### Кандидат 5: Вымышленный селектор `GODEBUG=loopvar=1` и подмена механизма управления областью видимости цикла
* **article/section:** `27. Совместимость Go 1 и стабильность экосистемы.md` / `## Под капотом: Как Go управляет изменениями (GODEBUG)`
* **claim:**  
  *«...если в вашем файле `go.mod` указана версия `1.21` или более ранняя, компилятор Go 1.22 автоматически активирует флаг `GODEBUG=loopvar=1`, транслируя цикл по прежним правилам. Ваш старый код продолжит работать без сюрпризов»*.
* **why it needs checking:**  
  Утверждение содержит тройную техническую ошибку:
  1. В рантайме Go **нет и никогда не существовало переменной окружения `GODEBUG=loopvar`**. Переменные `GODEBUG` управляют динамическим поведением рантайма и сетевого стека во время исполнения (`http2server`, `panicnil`, `tls10`, `gctrace`), но не семантикой компилятора.
  2. Область видимости переменной цикла (`for loop scoping`) в Go 1.22 переключается **на этапе компиляции** на основе директивы языка в `go.mod` (флаг компилятора `-lang=go1.22` против `-lang=go1.21`).
  3. Исторически в релизе Go 1.21 существовал флаг компиляторного эксперимента `GOEXPERIMENT=loopvar` (`-d=loopvar=1`). Но это значение (`loopvar=1`) включало **НОВОЕ** поведение (отдельная аллокация на каждую итерацию), а не сохраняло старое! Для отключения использовалось значение `loopvar=0` или `GOEXPERIMENT=noloopvar`.
* **evidence/source needed:**  
  Go 1.22 Release Notes (Language change: Loop variable scoping); Go Design Doc: *Fixing For Loops in Go* (Russ Cox); `src/cmd/compile/internal/loopvar/loopvar.go`.
* **priority:** **High**

### Кандидат 6: Опасное утверждение о статической линковке по умолчанию и запуске в `FROM scratch`
* **article/section:** `3. Какие проблемы существующих языков пытался решить Go.md` / `## 3. Ад зависимостей и сложность деплоя`
* **claim:**  
  *«Статическая линковка по умолчанию. Компилятор Go пакует весь ваш код, рантайм языка (GC, планировщик) и стандартную библиотеку в один независимый исполняемый файл (Fat Binary). Вам больше не нужна среда выполнения. Вы можете взять пустой Docker-контейнер (`FROM scratch`), положить туда бинарник Go, и он будет работать на любом дистрибутиве Linux с подходящей архитектурой процессора»*.
* **why it needs checking:**  
  Это классическая «ловушка номер один» при контейнеризации Go-приложений:
  1. На Linux стандартная сборка `go build` запускается с включенным cgo (`CGO_ENABLED=1`).
  2. Если проект импортирует базовые сетевые пакеты `net`, `net/http` или системный `os/user`, компилятор Go по умолчанию использует нативные резолверы glibc (`getaddrinfo`) и собирает **динамически слинкованный ELF-бинарник**, зависящий от `/lib64/ld-linux-x86-64.so.2`, `libc.so.6` и `libresolv.so.2`.
  3. Если разработчик скопирует такой бинарник в пустой образ `FROM scratch`, приложение вообще не запустится, завершаясь фатальной системной ошибкой Linux: `standard_init_linux.go: exec user process caused: no such file or directory` (ядро не находит динамический загрузчик `ld-linux`).
  Для сборки полностью автономного статического бинарника для `FROM scratch` обязательно требуется сборка с отключенным cgo: `CGO_ENABLED=0 go build`. Утверждать, что статический бинарник для `FROM scratch` получается «по умолчанию», педагогически опасно.
* **evidence/source needed:**  
  Вывод утилит `file` и `ldd` на Linux для сборки `net/http` с `CGO_ENABLED=1` против `CGO_ENABLED=0`; Docker Best Practices for Go.
* **priority:** **High**

### Кандидат 7: Архитектурное белое пятно: Фатальные сбои рантайма (`fatal error`), не перехватываемые через `recover()`
* **article/section:** `11. Panic и Recover. Когда они нужны, а когда вредны.md`
* **claim:**  
  Статья создает представление о функции `recover()` как об универсальном предохранителе, способном изолировать любые сбои в горутине:  
  *«Встроенная функция recover() — это единственный штатный способ перехватить падающую горутину и предотвратить крах процесса... Восстановление (recover): Служит исключительно защитным периметром на границах системы... изолируя крах отдельной операции от падения всего сервиса»*.
* **why it needs checking:**  
  В статье полностью обойден важнейший класс аварийных ситуаций Go Runtime: **фатальные системные ошибки (Fatal Runtime Errors)**, которые **ПРИНЦИПИАЛЬНО НЕЛЬЗЯ перехватить через `recover()`**:
  1. Гонка данных при модификации хэш-таблицы (`fatal error: concurrent map read and map write` / `concurrent map writes`).
  2. Исчерпание стека горутины (`fatal error: stack overflow`).
  3. Ошибка выделения системной памяти (`fatal error: out of memory`).
  4. Тупиковая взаимная блокировка всех горутин процесса (`fatal error: all goroutines are asleep - deadlock!`).
  5. Прямой вызов `runtime.throw()` из недр рантайма.
  В этих случаях рантайм намеренно обходит списки отложенных вызовов `defer`, не дает шанса `recover()`, выводит трассировку и мгновенно убивает процесс через `SIGABRT` / `exit 2`. Без этого разъяснения у разработчиков возникает опасная иллюзия абсолютной неуязвимости сервиса под `recover()`.
* **evidence/source needed:**  
  `src/runtime/panic.go` (функция `fatalthrow`, `fatalpanic`); Go Language Specification (Handling panics).
* **priority:** **High**

### Кандидат 8: Недостоверное утверждение об использовании векторных инструкций AVX-512 в `memclrNoHeapPointers`
* **article/section:** `8. Go Proverbs. Практический смысл известных цитат.md` / `> [!info] Под капотом: Быстрая инициализация памяти`
* **claim:**  
  *«Внутри рантайма Go за мгновенное обнуление стековой памяти отвечает функция `memclrNoHeapPointers`, написанная вручную на чистом ассемблере с использованием векторных инструкций SIMD (AVX2/AVX-512)»*.
* **why it needs checking:**  
  1. В кодовой базе рантайма Go (`src/runtime/memclr_amd64.s`) инструкции **AVX-512 (регистры `ZMM`, префикс `EVEX`) не применяются вовсе**! Реализация `memclrNoHeapPointers` опирается на 256-битный AVX2 (`YMM`), SSE2 (`XMM`) и оптимизированную строковую инструкцию микрокода процессора `REP STOSQ` (ERMSB).
  2. До версии Go 1.26 рантайм Go в принципе не сохранял верхние половины 512-битных регистров при асинхронном вытеснении горутин сигналом `SIGURG`.
  3. `memclrNoHeapPointers` обнуляет память кучи, не содержащую указателей. Стековая память горутин зануляется компилятором инлайн через `DUFFZERO` или явные ассемблерные инструкции очистки регистров (`XORPS`) в прологе вызываемой функции, а не вызовом `memclrNoHeapPointers` на каждый фрейм.
* **evidence/source needed:**  
  `src/runtime/memclr_amd64.s`; `src/cmd/compile/internal/amd64/ggen.go` (генерация нулевых стековых кадров).
* **priority:** **Medium**

### Кандидат 9: Упрощенное объяснение сравнения интерфейсов через «побайтовое сравнение памяти» (`memcmp`)
* **article/section:** `14. Интерфейсы в Go как альтернатива классическому ООП.md` / `> [!tip] Собеседование`
* **claim:**  
  *«Если внутри интерфейса упаковано конкретное значение типа-значения (например, число int или структура), рантайм производит побайтовое сравнение содержимого памяти»*.
* **why it needs checking:**  
  Слепое побайтовое сравнение (`memcmp`) памяти структур в Go **неприменимо** в общем случае:
  1. **Паддинг и выравнивание:** Структуры могут содержать неинициализированные байты выравнивания (Padding Bytes). Побайтовое сравнение вернуло бы `false` для двух структур с абсолютно одинаковыми полями, если их байты выравнивания содержали разный остаточный мусор. Компилятор Go генерирует специализированную функцию сравнения полей (`equal` в структуре `_type`), которая поочередно сравнивает только значащие поля.
  2. **Числа с плавающей точкой (IEEE 754):** Значение `NaN != NaN`. Если в интерфейсе лежит структура с полем `float64(math.NaN())`, побайтовое сравнение сочло бы их равными, нарушив контракт IEEE 754. Сравнение интерфейсов вызывает алгоритм равенства типа, где `NaN == NaN` вернет `false`.
  3. Побайтовое сравнение `runtime.memequal` используется рантаймом только тогда, когда компилятор статически гарантирует отсутствие паддинга, чисел с плавающей точкой и ссылочных типов.
* **evidence/source needed:**  
  The Go Programming Language Specification (Comparison operators); `src/runtime/alg.go` (`typealg`, `equal`); `src/cmd/compile/internal/reflectdata/alg.go`.
* **priority:** **Medium**

### Кандидат 10: Ловушка скрытого повреждения контракта `http.ErrAbortHandler` в демонстрационном HTTP Recovery Middleware

  ```go
      return http.HandlerFunc(func(w http.ResponseWriter, r *http.Request) {
          defer func() {
              if err := recover(); err != nil {
                  log.Printf("PANIC RECOVERED: %v\n%s", err, debug.Stack())

              }
          }()
          next.ServeHTTP(w, r)
      })
  }
  ```
* **why it needs checking:**  
  В стандартной библиотеке Go (`net/http`) существует зарезервированное сигнальное значение паники: `http.ErrAbortHandler`.  
  Оно намеренно инициируется хендлерами (или библиотеками), когда обработка запроса должна быть немедленно прервана без отправки ответа клиенту (например, после `Hijack()`, сброса соединения или в обратном прокси). Встроенный сервер `net/http` при перехвате `http.ErrAbortHandler` подавляет логирование стек-трейса и не пытается писать ответ клиенту.  
  Приведенный в статье код «ловит» `http.ErrAbortHandler`, засоряет логи ложными паниками с дампом стека и пытается записать `500 Internal Server Error` в уже перехваченный/закрытый сокет, генерируя системное предупреждение `http: superfluous response.WriteHeader call`.  
  Идиоматичный middleware обязан проверять:
  ```go
  if err := recover(); err != nil && err != http.ErrAbortHandler {
      // логируем и отвечаем 500
  } else if err != nil {
      panic(err) // пробрасываем дальше для net/http
  }
  ```
* **evidence/source needed:**  
  `src/net/http/server.go` (константа `ErrAbortHandler` и комментарий к ней).
* **priority:** **Medium**

### Кандидат 11: Умолчание об изменении поведения `panic(nil)` и введении `*runtime.PanicNilError` (Go 1.21+)
* **article/section:** `11. Panic и Recover. Когда они нужны, а когда вредны.md` / `### Механика Recover`
* **claim:**  
  *«Когда функция recover() срабатывает... Извлекает и возвращает пользовательское значение, переданное аргументом в panic()»*.
* **why it needs checking:**  
  Исторически в Go вызов `panic(nil)` приводил к коварному багу: функция `recover()` возвращала `nil`, из-за чего вызывающий код ошибочно считал, что паники не происходило вовсе.  
  Начиная с **Go 1.21**, это поведение было официально изменено: при вызове `panic(nil)` функция `recover()` возвращает специальную структуру `*runtime.PanicNilError` (с возможностью временного отката через селектор `GODEBUG=panicnil=1`). Это фундаментальное исправление механики восстановления, которое необходимо упомянуть в учебнике, актуальном для современных версий Go.
* **evidence/source needed:**  
  Go 1.21 Release Notes (Core library: panic/recover behavior); `src/runtime/panic.go` (`PanicNilError`).
* **priority:** **Medium**

### Кандидат 12: Неточная терминология: подмена системного futex-мьютекса понятием «локальный спинлок» в устройстве канала
* **article/section:** `8. Go Proverbs. Практический смысл известных цитат.md` / `> [!info] Под капотом: Очереди каналов`
* **claim:**  
  *«Канал в Go... состоит из кольцевого буфера, защищенного локальным спинлоком, и двух списков ожидания (wait queues)...»*
* **why it needs checking:**  
  Поле блокировки структуры `hchan` объявлено как `lock mutex` (`src/runtime/chan.go`).  
  Тип `runtime.mutex` в недрах рантайма Go — это **не спинлок** (busy-wait), а полноценный примитив синхронизации операционной системы, реализованный поверх системного вызова `futex` в Linux или семафоров ядра в macOS/Windows.  
  Он выполняет лишь несколько быстрых итераций активного ожидания (adaptive spin) при наличии свободных ядер процессора, после чего переводит системный поток `M` в полноценный сон на уровне ядра ОС. Называние его спинлоком порождает неверное представление о том, что конкуренция за каналы приводит к бессмысленному прожиганию тактов CPU.
* **evidence/source needed:**  
  `src/runtime/chan.go` (`type hchan`); `src/runtime/lock_futex.go` (реализация `lock2` / `unlock2`).
* **priority:** **Medium**

### Кандидат 14: Неточность в представлении данных: «Срез структур без единого указателя» при наличии `string`
* **article/section:** `4. Почему Go не похож на Java, C++ и C#.md` / `## 1. Представление данных: Mechanical Sympathy и кэш-линии`
* **claim:**  
  При сопоставлении Java `User[]` и Go `[]User` (где `User` содержит `Name string`):  
  *«Среда выполнения аллоцирует один непрерывный блок памяти. Все 10 000 структур User уложены в памяти строго вплотную друг к другу, без единого указателя и без фрагментации»*.
* **why it needs checking:**  
  Тип `string` в Go под капотом представляет собой 16-байтную структуру `StringHeader` (`Data unsafe.Pointer, Len int`).  
  Поле `Data` — это **физический указатель** на массив байт в памяти!  
  Хотя сами 10 000 заголовков `User` действительно уложены в памяти среза непрерывно, строки внутри них содержат прямые указатели на символы в куче или секции констант. Утверждать, что массив структур `User` хранится «без единого указателя», фактически неверно. Для честного отсутствия указателей поля должны быть скалярными числами либо фиксированными массивами байт `[N]byte`.
* **evidence/source needed:**  
  `src/runtime/string.go`; The Go Programming Language Specification (String types).
* **priority:** **Low**

### Кандидат 15: Упрощение внутренней механики компиляции дженериков (GCShape для базовых типов)
* **article/section:** `28. Generics. Почему Go так долго жил без них.md` / `> [!info] Под капотом: Что такое GCShape?`
* **claim:**  
  *«Базовые типы int и float64 также имеют размер 8 байт, но не содержат адресов в памяти — компилятор присваивает им разные GCShape, оптимизируя регистровую передачу аргументов»*.
* **why it needs checking:**  
  В компиляторе Go механизм объединения форм (GCShape Stenciling) работает **только для указательных типов** (все указатели, каналы и мапы разделяют общую форму `go.shape.*uint8`).  
  Для типов-значений (скалярных примитивов и структур) компилятор Go **не группирует типы по сходству структуры или регистров**: каждый конкретный тип (`int`, `int64`, `float64`, `uint64`) имеет свой уникальный изолированный `gcshape` (например, `go.shape.int`), что приводит к **полной мономорфизации** функций для каждого базового типа. Фраза статьи может создать ошибочное впечатление, будто компилятор объединяет разные типы одинакового размера в общие группы.
* **evidence/source needed:**  
  Go Compiler Source: `src/cmd/compile/internal/noder/stencil.go`; Go Design Doc: *Generics implementation - Dictionaries and GCShape Stenciling*.
* **priority:** **Low**

### Кандидат 16: Преувеличение размера стека потока ОС в Java (8 МБ против 1 МБ)

  В виртуальной машине Java (HotSpot JVM 64-bit) размер стека потока по умолчанию составляет **1 МБ** (флаг `-Xss1m`), а не 8 МБ. Преувеличение размера стека потоков Java в 8 раз искажает масштаб накладных расходов.
* **evidence/source needed:**

* **priority:** **Low**

## 🧩 Систематизация архитектурных белых пятен (Blind Spots & Omissions)

Помимо анализа конкретных утверждений, в Модуле 4 выявлены важные концептуальные пробелы:

1. **Отсутствие формальной модели памяти (The Go Memory Model):**  
   Статьи 24 и 25 подробно обсуждают лозунг *«Share Memory By Communicating»* и каналы против мьютексов. Однако фундаментальная концепция **Happens-Before** (какие операции записи в память гарантированно видны другим горутинам при отправке/чтении из каналов, вызове `sync.Mutex`, старте горутины или инициализации пакетов) не раскрыта. Без понимания Happens-Before абстрактное обсуждение конкурентности остается неполным.
2. **Игнорирование Workspace Mode (`go.work`, Go 1.18+):**  
   В статье 22 детально рассматривается структура проекта и пакетов (`cmd/`, `internal/`), но совершенно опущен современный механизм Go Workspaces (`go.work`), ставший стандартом для монорепозиториев и совместной разработки нескольких связанных модулей.
3. **Современные расширения пакета `context` (Go 1.21+):**  
   В статьях 18 и 19 многократно подчеркивается роль явной передачи `context.Context`. При этом не упомянуты современные стандартные функции `context.WithoutCancel` (необходимая для безопасного фонового аудита/логирования после отмены клиентского контекста) и `context.AfterFunc` (замена громоздким горутинам ожидания отмены).
