## 2. Принятие обязательных поправок Е1–Е3 с проверкой на корпусе

### 2.1. Поправка Е1 (А3е, U8): экранирование завершающего `#` в заголовках

#### 1. Эмпирическая проверка на корпусе:
Поиск заголовков с завершающим символом `#` по всем 1 413 статьям репозитория (`grep -rnE '^#{2,4} .*#$' sources/`) выявляет ровно **один** заголовок во всем корпусе:
* `sources/17. Безопасность (AppSec в Go)/05. Безопасность API/1. Валидация входных данных.md`, строка 199:
  ```markdown
  ## Сравнение подходов: Go против PHP и C#
  ```
В данных `go-workout` таких заголовков ровно **0**.

#### 2. Механика дефекта:
Стандартный процессор `HashHeaderProcessor` библиотеки Python-Markdown интерпретирует любые завершающие символы `#` в заголовке как закрывающий маркер синтаксиса Markdown (`strip trailing hashes`), даже если перед `#` нет пробела:
```python
>>> import markdown
>>> markdown.markdown('## Сравнение подходов: Go против PHP и C#')
'<h2>Сравнение подходов: Go против PHP и C</h2>'
```
В результате символ `#` в названии языка программирования C# срезается. Читатель видит «...PHP и C», что является прямой потерей авторского текста и нарушением фундаментальной директивы **U8**.

При этом регулярное выражение в наивном оракуле отбрасывало атрибуты заголовка и могло пропустить подмену текста/ID, а среди 393 санкционированных страниц U24 эту страницу было невозможно отфильтровать без сравнения видимого текста.

#### 3. Принятое решение:
Поправка **Е1** принимается в точности в формулировке рецензента:
1. **Экранирование в препроцессоре:** Перед подачей текста в Python-Markdown в строках-заголовках вне блоков кода хвостовой символ `#` экранируется обратным слэшем: `C#` $\to$ `C\#`. Python-Markdown корректно выводит:
   ```html
   <h2>Сравнение подходов: Go против PHP и C#</h2>
   ```
   На корпусе 1 413 статей видимый текст заголовков полностью совпадает с исходным (расхождений: **0**).
2. **Оракул А3е:** Сравнивает `id` и видимый текст через HTML-парсер (не регуляркой). Из старого текста снимаются только символы `` ` `` и `**`, превращаемые в теги по U24.

**Статус Е1:** ✅ **Принято безоговорочно.**

### 2.2. Поправка Е2 (А3ж): изоляция guard-проверки `window.__BOOK__` в `main.js`

#### 1. Анализ проблемы:
В коде `builder/assets/main.js` (строки 1262–1275) обработчик события `DOMContentLoaded` осуществляет запуск всей клиентской инфраструктуры сайта:
```javascript
document.addEventListener('DOMContentLoaded', function () {
  saveMermaidSources();
  initMermaid();
  initKaTeX();
  initActionDelegation();
  initSidebarResize();
  initSidebarFilter();
  initSidebarCentering();
  initScrollProgress();
  initMobileMenu();
  initGlobalSearch();
  initThemeSwitcher();
  initRetroEffects();
});
```
Если в начале обработчика поставить безусловный `if (!window.__BOOK__) return;`, то при открытии ранее скомпилированной страницы (старый HTML без внедренного объекта `window.__BOOK__`) со свежим скриптом `main.js` отсекаются все 12 вызовов: прекращается рендеринг диаграмм Mermaid и формул KaTeX, отключаются обработчики кликов (копирование листингов в буфер, открытие модалок), замирает сайдбар и поиск. Это полностью нарушает принцип безопасной деградации (graceful degradation).

#### 2. Принятое решение:
Поправка **Е2** принимается полностью:
Проверка `window.__BOOK__` оборачивает **исключительно** переключатель тем и ретро-эффекты:
```javascript
document.addEventListener('DOMContentLoaded', function () {
  saveMermaidSources();
  initMermaid();
  initKaTeX();
  initActionDelegation();
  initSidebarResize();
  initSidebarFilter();
  initSidebarCentering();
  initScrollProgress();
  initMobileMenu();
  initGlobalSearch();
  if (window.__BOOK__) {
    initThemeSwitcher();
    initRetroEffects();
  }
});
```
8-й сценарий теста `test_runtime.py` проверяет работу смешанной конфигурации: при отсутствии `window.__BOOK__` диаграммы Mermaid отрисовываются, KaTeX формулы форматирует, копирование кода работает штатно, ошибок в консоли нет.

**Статус Е2:** ✅ **Принято безоговорочно.**

### 2.3. Поправка Е3: расчет относительного пути `rel_root` и кэширование sha256 в `get_asset_url`

#### 1. Анализ проблемы:
1. **Поломка путей:** В архитектуре генератора страницы статей находятся на переменной глубине (`dist/docs/NN-модуль/[раздел/]`...). Для корректного разрешения ассетов по протоколу `file:///` пути к CSS и JS строятся строго через `rel_root` (`"../" * depth`). Возврат функцией пути `./assets/...` приводил бы к поломке стилей и скриптов на всех 1 413 статьях и фатальному провалу QA-аудита ссылок.
2. **Накладные расходы:** Библиотека `mermaid.min.js` весит 3.3 МБ. При сборке 1 413 статей вычисление хеша sha256 на лету означало бы повторное чтение и хеширование ~4.6 ГБ данных, замедляя сборку в разы.

#### 2. Принятое решение:
Поправка **Е3** принимается полностью:
1. Функция построения пути формирует относительный URL с учетом `rel_root`:
   ```python
   def get_asset_url(rel_asset_path: str, rel_root: str) -> str:
       asset_hash = get_cached_asset_hash(rel_asset_path)
       return f"{rel_root}{rel_asset_path}?v={asset_hash}"
   ```
2. Хэш sha256 вычисляется ровно один раз за прогон сборки непосредственно от записанных в `dist/` файлов ассетов и сохраняется в словаре кэша в памяти генератора.

**Статус Е3:** ✅ **Принято безоговорочно.**

Полностью подтверждаем оба пункта для чистовой спецификации ядра:
1. **Флаг `include_indented`:** В конструкторе маски параметр инициализируется от флага конфигурации:
