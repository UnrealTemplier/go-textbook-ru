## Executive Summary

Модуль 10 («Проектирование API и Сетевые протоколы») — один из самых технически насыщенных и архитектурно зрелых модулей энциклопедии. Он сочетает изложение спецификаций сетевых протоколов (IETF RFC, W3C, OpenAPI Initiative) с низкоуровневым анализом стандартной библиотеки Go (`net/http`, `net/http/httputil`, `crypto/tls`, `log/slog`), экосистемных библиотек (`google.golang.org/grpc`, `google.golang.org/protobuf`, `github.com/golang-jwt/jwt`) и физики взаимодействия с ядром ОС и CPU (Mechanical Sympathy: сокеты Linux, `epoll`, буферы сокетов, AES-NI, выравнивание структур).

Наиболее рискованными с точки зрения фактчека являются три ключевые зоны:
1. **Безопасность и криптография:** Механизмы валидации JWT и атака Key Confusion в `golang-jwt/jwt`, протоколы TLS 1.3 в mTLS (целостность пакетов AEAD vs ошибочно упомянутый HMAC блочных шифров), принудительная аутентификация клиентов в Go `crypto/tls`.
2. **Низкоуровневые детали рантайма Go:** Механика переповтора запросов `isReplayable` в `net/http` и его поддержка заголовков `Idempotency-Key`, архитектура нового API `httputil.ProxyRequest` в Go 1.20+ (`SetURL` vs `SetXForwarded`), реальная структура дерева маршрутизации `ServeMux` в Go 1.22 (decision tree с бэктрекингом против ошибочно приписанного Radix Tree), а также синтаксическая компиляционная ошибка в листинге SSE.
3. **Соответствие стандартам IETF и актуальность RFC:** Устаревание спецификаций (RFC 7234 заменен на RFC 9111; RFC 7807 заменен на RFC 9457; RFC 8594 определяет только Sunset, а Deprecation регламентирован в RFC 9745), а также расхождение формата заголовка `RateLimit-Reset` в драфте IETF (числовые delta-seconds) с устаревшим форматом Unix timestamp.

Кроме того, в модуле обнаружена грубая структурная рассинхронизация: статья 35 озаглавлена и заполнена как «Graceful Shutdown и устойчивость API в Go», тогда как имя файла (`35. Chaos testing API.md`) и анонсирующий переход в статье 34 обещают читателю полноценный разбор «Chaos Engineering в Go API». Это критический дефект целостности учебного плана.

Большинство концептуальных объяснений (пагинация, ETag, HTTP-статусы, Protobuf wire format, gRPC backpressure, W3C TraceContext) написаны на высоком инженерном уровне и подкреплены точными моделями. ## Claim 1: Синтаксическая ошибка компиляции Go в примере обработчика SSE (многострочные строки в двойных кавычках)

File: `sources/10. Проектирование API и Сетевые протоколы/23. Server Sent Events.md`  
Section: `### Полный производственный HTTP-хэндлер SSE в Go`  
Claim: В коде обработчика `SSEHandler` конструирование сообщений написано с переносом строк внутри двойных кавычек `""`:
```go
// Строки 173-177:
msg := fmt.Sprintf("id: %d\n
event: time_tick\n
data: {\"time\": \"%s\"}\n
\n
",
    eventID, t.Format(time.RFC3339))

// Строки 188-190:
if _, err := w.Write([]byte(": keepalive\n
\n
")); err != nil {
```
Claim type: FACTUALLY WRONG / COMPILATION ERROR  
Severity: High  
Historical / Current / Unclear: Current  

Why verification matters:  
В спецификации языка Go (The Go Programming Language Specification, Lexical elements / String literals) строковые литералы в двойных кавычках `""` (interpreted string literals) **категорически не могут содержать символ новой строки (`\n`)**. Наличие сырого переноса строки внутри кавычек приводит к фатальной ошибке компилятора: `syntax error: newline in string literal`. Любой читатель, скопировавший этот "производственный пример", получит неработающий код. Для многострочных литералов в Go обязаны использоваться сырые строки в обратных апострофах (raw string literals `` `...` ``) либо однострочные литералы с экранированными символами `\n`.

Primary source: The Go Programming Language Specification (String literals)  
Source URL: https://go.dev/ref/spec#String_literals  
Relevant section: `String literals: "Interpreted string literals ... cannot contain newlines"`  

What specifically must be verified:  
1. Убедиться, что `go vet` или `go build` выдает ошибку `newline in string literal` на данном фрагменте.  
2. Проверить, какие еще строковые литералы в статье содержат сырые переносы строк.  

Potential correction direction:  
Заменить многострочный литерал в двойных кавычках либо на однострочную запись с `\n\n`:
`msg := fmt.Sprintf("id: %d\nevent: time_tick\ndata: {\"time\": \"%s\"}\n\n", eventID, t.Format(time.RFC3339))`
либо на raw string literal с backticks (с учетом форматирования Sprintf).

## Claim 3: Искажение формата заголовка IETF RateLimit-Reset (Unix Timestamp вместо delta-seconds)

File: `sources/10. Проектирование API и Сетевые протоколы/30. API rate limiting и quotas.md`  
Section: `### Заголовки стандарта IETF RateLimit`  
Claim: В примере и описании приводится:
```http
RateLimit-Limit: 10000
RateLimit-Remaining: 0
RateLimit-Reset: 1714521600
Retry-After: 60
```
Текст утверждает:
> `RateLimit-Reset:` Время в формате Unix Timestamp, когда квота или окно лимита будет полностью сброшено.

Claim type: FACTUALLY WRONG / SPECIFICATION VIOLATION  
Severity: High  
Historical / Current / Unclear: Current (IETF draft standard)  

Why verification matters:  
В официальном драфте IETF `draft-ietf-httpapi-ratelimit-headers` заголовок `RateLimit-Reset` строго определен как **относительное число секунд (delta-seconds)** до сброса текущего окна квоты (non-negative integer, e.g. `RateLimit-Reset: 60`). Это было сделано комитетом IETF намеренно, чтобы исключить рассинхронизацию настенных часов клиента и сервера (clock skew) и проблемы часовых поясов.  
Unix Epoch Timestamp использовался исключительно в **устаревших нестандартных** заголовках `X-RateLimit-Reset` (GitHub API, Twitter v1). Приписывание Unix timestamp официальному проекту IETF дезинформирует разработчиков, проектирующих современные контракты.

Primary source: IETF Internet-Draft `draft-ietf-httpapi-ratelimit-headers`  
Source URL: https://datatracker.ietf.org/doc/draft-ietf-httpapi-ratelimit-headers/  
Relevant section: Section 3.3 `RateLimit-Reset`: *"The RateLimit-Reset field indicates the number of seconds until the reset of the current window of the rate limit policy."*  

What specifically must be verified:  
1. Сверить определение `RateLimit-Reset` в последних драфтах рабочей группы IETF HTTPAPI.  
2. Проверить различие между `X-RateLimit-Reset` (Unix timestamp) в статье 11 и `RateLimit-Reset` (delta-seconds) в статье 30.  

Potential correction direction:  
Скорректировать пример в статье 30: `RateLimit-Reset: 60` (или число секунд), явно пояснив читателю ключевое отличие современного стандарта IETF (delta-seconds) от легаси-заголовков `X-RateLimit-Reset` (где передавался абсолютный epoch timestamp).

## Claim 4: Некорректное описание механики атаки Key Confusion в библиотеке golang-jwt/jwt

File: `sources/10. Проектирование API и Сетевые протоколы/28. Security API. Auth, OAuth2.md`  
Section: `## 4. Ловушка пакета golang-jwt/jwt: Атака Key Confusion`  
Claim: В тексте описано:
```go
// НЕБЕЗОПАСНЫЙ КОД: Уязвим к Key Confusion!
token, err := jwt.Parse(tokenStr, func(t *jwt.Token) (interface{}, error) {
    return rsaPublicKey, nil // Библиотека преобразует rsaPublicKey в байты и выполнит HMAC!
})
```
И далее: *"Библиотека применит HMAC-SHA256, используя публичный ключ как секрет, подпись сойдется, и атакующий получит полный административный доступ."*  
Claim type: MISLEADING / IMPLEMENTATION INACCURACY  
Severity: High  
Historical / Current / Unclear: Current  

Why verification matters:  
Библиотека `github.com/golang-jwt/jwt` (и `jwt-go`) **НЕ преобразует объект `*rsa.PublicKey` в байты** автоматически! Метод `SigningMethodHMAC.Verify(signingString, sig, key)` требует, чтобы `key` реализовывал приведение `keyBytes, ok := key.([]byte)`. Если из `Keyfunc` вернуть типизированный `*rsa.PublicKey`, метод проверки подписи немедленно вернет ошибку `ErrInvalidKeyType` ("key is of invalid type"), и валидация завершится сбоем.  
Атака Key Confusion в Go реально воспроизводится только в одном из двух сценариев:
1. Разработчик считывает публичный ключ с диска (`pemBytes, _ := os.ReadFile("pubkey.pem")`) и возвращает в `Keyfunc` сырой срез байт `[]byte(pemBytes)` вместо распарсенной структуры `*rsa.PublicKey`.
2. Разработчик вручную сериализует ключ в `[]byte` или использует самописный валидатор.  
Называть приведенный пример "уязвимым" из-за того, что библиотека якобы сама преобразует `rsaPublicKey` в байты — технически недостоверно и искажает работу системы типов Go.

Primary source: Исходный код `github.com/golang-jwt/jwt` (файл `hmac.go`, метод `Verify`)  
Source URL: https://github.com/golang-jwt/jwt/blob/main/hmac.go  
Relevant section: `SigningMethodHMAC.Verify`: `keyBytes, ok := key.([]byte); if !ok { return ErrInvalidKeyType }`  

What specifically must be verified:  
Поведение `jwt.Parse` при возврате `*rsa.PublicKey` при токене с `alg: HS256`. Убедиться, что возвращается `ErrInvalidKeyType`.  

Potential correction direction:  
Пояснить, что уязвимость возникает, когда разработчик возвращает публичный ключ в виде сырого среза байт `[]byte` (например, прочитанный PEM-файл `rsaPublicKeyBytes`), либо явно подчеркнуть условие: "если публичный ключ возвращается как `[]byte`".

## Claim 5: Приписывание целостности TLS 1.3 блочным шифрам и HMAC

File: `sources/10. Проектирование API и Сетевые протоколы/29. mTLS в сервисах.md`  
Section: `### Что дает mTLS из коробки:`, пункт 3  
Claim:
> `3. **Защита от модификации трафика (Integrity):** Изменение хотя бы одного бита в сетевом пакете приводит к сбросу сессии (HMAC-контроль в блочных шифрах).`

Claim type: FACTUALLY WRONG / PROTOCOL MISREPRESENTATION  
Severity: High  
Historical / Current / Unclear: Current (TLS 1.3 specification)  

Why verification matters:  
В контексте статьи, где на диаграмме и в коде форсируется **TLS 1.3** (`MinVersion: tls.VersionTLS13`), утверждение об "HMAC-контроле в блочных шифрах" является грубой криптографической ошибкой.  
В спецификации TLS 1.3 (RFC 8446) блочные шифры в режиме CBC (Cipher Block Chaining) и схемы аутентификации MAC-then-Encrypt на базе HMAC **были полностью удалены** из-за исторической уязвимости к атакам Padding Oracle (POODLE, Lucky 13). В TLS 1.3 разрешены **исключительно шифры семейства AEAD** (Authenticated Encryption with Associated Data: AES-128-GCM, AES-256-GCM, ChaCha20-Poly1305). Контроль целостности в них обеспечивается не HMAC, а криптографическим имитовставочным тегом аутентификации AEAD (Auth Tag: GHASH в GCM, Poly1305). HMAC в TLS 1.3 остался только в механизме генерации ключей HKDF, но не в защите сетевых пакетов данных.

Primary source: RFC 8446 ("The Transport Layer Security (TLS) Protocol Version 1.3")  
Source URL: https://datatracker.ietf.org/doc/html/rfc8446  
Relevant section: Section 1.2 "Major Differences from TLS 1.2": *"All symmetric cipher suites are now Authenticated Encryption with Associated Data (AEAD) algorithms."*  

What specifically must be verified:  
Проверить список разрешенных cipher suites в RFC 8446 и стандартной библиотеке `crypto/tls` (файл `cipher_suites.go`).  

Potential correction direction:  
Скорректировать формулировку: "Изменение хотя бы одного бита в сетевом пакете приводит к сбросу сессии (контроль целостности через AEAD Auth Tag — GHASH/Poly1305)".

## Claim 6: Утверждение о том, что `ProxyRequest.SetURL()` настраивает заголовки `X-Forwarded-For`

File: `sources/10. Проектирование API и Сетевые протоколы/25. API Gateway.md`  
Section: `> [!info] Под капотом: Новое API в Go 1.20+ (Rewrite вместо Director)`  
Claim:
> `Метод ProxyRequest.SetURL() корректно перенаправляет запрос на целевой хост, автоматически очищает заголовки перехода и безопасно настраивает заголовок Forwarded / X-Forwarded-For.`

Claim type: FACTUALLY WRONG / API INACCURACY  
Severity: High  
Historical / Current / Unclear: Current (Go 1.20+)  

Why verification matters:  
В стандартной библиотеке Go (`net/http/httputil/reverseproxy.go`) метод `(r *ProxyRequest) SetURL(target *url.URL)` **НЕ настраивает** заголовки `Forwarded` или `X-Forwarded-For`!  
Его реализация выполняет только перезапись URL:
```go
func (r *ProxyRequest) SetURL(target *url.URL) {
    rewriteRequestURL(r.Out, target)
    r.Out.Host = ""
}
```
Для безопасной настройки заголовков `X-Forwarded-For`, `X-Forwarded-Host` и `X-Forwarded-Proto` в структуре `ProxyRequest` предусмотрен отдельный специализированный метод: **`r.SetXForwarded()`**.  
Если разработчик поверит тексту статьи и вызовет только `SetURL()`, upstream-сервисы не получат клиентские IP-адреса в `X-Forwarded-For`. Примечательно, что в коде ниже в той же статье автор вручную пишет `pr.Out.Header.Set("X-Forwarded-Host", pr.In.Host)`, что подтверждает неполноту `SetURL()`.

Primary source: Go Standard Library Source Code (`net/http/httputil/reverseproxy.go`)  
Source URL: https://cs.opensource.google/go/go/+/refs/tags/go1.22.0:src/net/http/httputil/reverseproxy.go;l=57-81  
Relevant section: `ProxyRequest.SetURL` vs `ProxyRequest.SetXForwarded`  

What specifically must be verified:  
Проверить документацию и исходный код `ProxyRequest.SetURL()` и `ProxyRequest.SetXForwarded()` в `/usr/local/go/src/net/http/httputil/reverseproxy.go`.  

Potential correction direction:  
Разделить описание: `SetURL()` перенаправляет целевой запрос, очищая hop-by-hop заголовки, а для настройки заголовков `X-Forwarded-*` вызывается метод `pr.SetXForwarded()`.

```go
func (r *Request) isReplayable() bool {
    if r.Body == nil || r.Body == NoBody || r.GetBody != nil {
        switch valueOrDefault(r.Method, "GET") {
        case "GET", "HEAD", "OPTIONS", "TRACE":
            return true
        }
        // The Idempotency-Key, while non-standard, is widely used to
        // mean a POST or other request is idempotent. See
        // https://golang.org/issue/19943#issuecomment-421092421
        if r.Header.has("Idempotency-Key") || r.Header.has("X-Idempotency-Key") {
            return true
        }
    }
    return false
}
```
Рантайм Go **умеет автоматически повторять POST-запросы**, если у них установлен заголовок `Idempotency-Key` или `X-Idempotency-Key` и тело может быть перечитано (`GetBody != nil`)! Это поразительная инженерная деталь, которая идеально дополняет тему статьи, но была выброшена из листинга в учебнике, из-за чего утверждение о "немедленной блокировке POST" стало фактически неполным.

Primary source: Go Standard Library Source Code (`src/net/http/request.go:1534`)  
Source URL: https://cs.opensource.google/go/go/+/refs/tags/go1.22.0:src/net/http/request.go;l=1534-1548  
Relevant section: `func (r *Request) isReplayable() bool`  

What specifically must be verified:  
1. Убедиться, что `isReplayable` находится в `request.go`, а не `transport.go`.  
2. Проверить наличие обработки `Idempotency-Key` в `isReplayable()`.  

Potential correction direction:  
Указать реальное местоположение метода (`request.go`) и добавить упоминание о том, что Go net/http делает исключение для POST-запросов, если в них передан заголовок `Idempotency-Key` / `X-Idempotency-Key`.

### Рискованные абсолютные формулировки ("всегда / никогда / 100%")
1. `4. Resource oriented design.md`: *"Сложность поиска маршрута в таком дереве составляет $O(K)$, где $K$ — длина входящего URL-адреса, и абсолютно не зависит от общего числа маршрутов в системе!"*  
   *Risk:* В `ServeMux` Go 1.22 сегментное дерево использует бэктрекинг при перекрытии шаблонов с wildcard, поэтому оценка строго $O(K)$ без учета количества конфликтующих шаблонов излишне абсолютизирована.
2. `18. gRPC streaming.md`: *"Попытка параллельной записи в поток из двух горутин приведет к немедленной панике: fatal error: concurrent write to grpc stream и падению процесса."*

   *Risk:* Библиотека `golang-jwt` не преобразует `*rsa.PublicKey` в байты, а возвращает ошибку `ErrInvalidKeyType`.
