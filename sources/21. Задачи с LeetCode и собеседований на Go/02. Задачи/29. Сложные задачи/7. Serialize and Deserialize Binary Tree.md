## Сериализация и десериализация бинарного дерева: проектирование протоколов и строковая инженерия

Задача проектирования алгоритма сериализации и десериализации бинарного дерева (**Serialize and Deserialize Binary Tree**, LeetCode 297) венчает раздел алгоритмических задач.  
В отличие от задач на вычисление одного числового ответа, здесь проверяется **системный инженерный дизайн**:
- **Сериализация:** преобразование древовидной структуры в компактную строку или поток байтов.
- **Десериализация:** однозначное, детерминированное восстановление исходной структуры дерева из строки.

В распределенных бэкенд-системах этот процесс лежит в основе сетевых протоколов (gRPC / Protocol Buffers, JSON RPC), передачи деревьев выражений в SQL-оптимизаторах и персистентного сохранения деревьев состояний на диск.

## 1. Архитектура протокола: почему одного обхода обычно недостаточно?

В классической теории деревьев ([[1. Теория. Деревья]]) известно: чтобы однозначно восстановить бинарное дерево по значениям узлов, требуются **два** обхода (например, Preorder + Inorder).  
Однако если мы сохраняем **маркеры пустых указателей (Nil / Null Sentinel)**, например символ `#`, то дерево однозначно восстанавливается всего по **одному Preorder (или Postorder) обходу**!

### Сравнение форматов обхода:
1. **Preorder DFS (Корень → Лево → Право):**  
   Самый лаконичный и естественный формат. Десериализация строится через прямую рекурсию без очередей.
2. **BFS (Поуровневый обход):**  
   Использует очередь. Удобен для потокового чтения без глубокого рекурсивного стека вызовов, но требует хранения очередей в памяти.

## 2. Идиоматичная реализация на Go: Zero-Allocation парсинг

Наивный подход использует `strings.Split(data, ",")`. Это порождает огромный срез строк в куче, создавая двойное потребление памяти.  
В промышленной реализации мы используем:
- `strings.Builder` для линейной конкатенации строки сериализации.
- Посимвольный парсинг по указателю смещения `pos` для десериализации (срезы строк без выделения памяти).

```go
package treecodec

import (
	"strconv"
	"strings"
)

// TreeNode представляет узел бинарного дерева
type TreeNode struct {
	Val   int
	Left  *TreeNode
	Right *TreeNode
}

// Codec инкапсулирует логику кодирования и декодирования
type Codec struct{}

func Constructor() Codec {
	return Codec{}
}

// Serializes a tree to a single string.
func (c *Codec) Serialize(root *TreeNode) string {
	var sb strings.Builder
	c.buildString(root, &sb)
	return sb.String()
}

func (c *Codec) buildString(node *TreeNode, sb *strings.Builder) {
	if node == nil {
		sb.WriteString("#,")
		return
	}

	sb.WriteString(strconv.Itoa(node.Val))
	sb.WriteByte(',')

	c.buildString(node.Left, sb)
	c.buildString(node.Right, sb)
}

// Deserializes your encoded data to tree.
func (c *Codec) Deserialize(data string) *TreeNode {
	if len(data) == 0 {
		return nil
	}
	pos := 0
	return c.buildTree(data, &pos)
}

func (c *Codec) buildTree(data string, pos *int) *TreeNode {
	if *pos >= len(data) {
		return nil
	}

	// Извлекаем следующий токен до запятой за O(1) памяти
	start := *pos
	for *pos < len(data) && data[*pos] != ',' {
		*pos++
	}
	token := data[start:*pos]
	*pos++ // пропускаем разделительную запятую

	if token == "#" {
		return nil
	}

	val, err := strconv.Atoi(token)
	if err != nil {
		return nil
	}

	node := &TreeNode{Val: val}
	node.Left = c.buildTree(data, pos)
	node.Right = c.buildTree(data, pos)

	return node
}
```

## 3. Аппаратная эффективность и механика строк в Go

### Zero-Copy срезы строк
В коде `token := data[start:*pos]` не происходит копирования символов.  
В рантайме Go строка представляется структурой `StringHeader`:
```go
type StringHeader struct {
    Data unsafe.Pointer
    Len  int
}
```
Срез строки лишь сдвигает указатель `Data` и изменяет `Len`. Он живет в регистрах процессора и не аллоцируется в куче.

### Преимущества `strings.Builder`
Вызов оператора `+` для строк выделяет новую строку в куче на каждом шаге ($O(N^2)$ аллокаций).  
`strings.Builder` использует внутренний байтовый буфер `[]byte`, удваивающийся геометрически, что гарантирует амортизированное линейное время $O(N)$ и минимальную фрагментацию памяти.

## 4. Вопросы для собеседования

> [!INTERVIEW]
> **Вопрос:** Что произойдет при десериализации вырожденного дерева (длинной цепочки из 10 000 левых узлов)?  
> **Ответ:** Рекурсивная функция `buildTree` зайдет на глубину $10\,000$ вызовов. В Go стек горутины начинается с $2$ КБ и динамически расширяется в куче вплоть до лимита (по умолчанию $1$ ГБ на 64-битных ОС). Поэтому глубина $10^4$ не вызовет паники переполнения стека (Stack Overflow). Однако для ультраглубоких деревьев ($10^6$ узлов) безопаснее использовать полностью итеративную десериализацию на базе BFS и явной очереди.

> [!INTERVIEW]
> **Вопрос:** Как адаптировать этот алгоритм для сериализации бинарного дерева поиска (BST), чтобы уменьшить размер строки?  
> **Ответ:** Для BST маркеры `#` не нужны вовсе! В силу свойства упорядоченности ($Left < Root < Right$) дерево поиска можно однозначно восстановить из чистого Preorder-обхода чисел, восстанавливая границы диапазона $[\text{min}, \text{max}]$ на каждом шаге. Это сократит объем передаваемых данных почти в два раза.

## Резюме

1. Добавление маркеров пустых узлов (`#`) позволяет восстановить структуру дерева всего по одному обходу.
2. Использование `strings.Builder` и посимвольного извлечения токенов исключает ненужные аллокации памяти в рантайме Go.
3. Механическая симпатия проявляется в использовании zero-copy срезов строк, что делает сериализатор масштабируемым под высокие нагрузки.
