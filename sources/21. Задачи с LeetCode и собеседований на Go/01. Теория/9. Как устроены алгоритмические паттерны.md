> — Брайан Керниган

В предыдущей лекции [[8. Что такое алгоритмический паттерн]] мы определили паттерн как мета-каркас, связывающий класс математических проблем с классом программных решений. Теперь пришло время заглянуть внутрь этого механизма: **как именно устроен алгоритмический паттерн на атомарном уровне?**

Из каких шестерёнок он собирается? Как доказывается математическая строгость его работы? Как из двух простых паттернов конструируется решение сложнейшей олимпиадной задачи уровня Hard? И как всё это воплощается в коде на Go с учётом процессорных кэшей и особенностей сборщика мусора?

## Паттерн как конечный автомат (State Machine)

Любой итеративный алгоритмический паттерн можно строго представить как **вычислительный автомат**, который шаг за шагом трансформирует состояние системы от начального к целевому, непрерывно защищая заложенный в него инвариант.

Взглянем на динамику паттерна «Скользящее окно»:

- **Пространство состояний:** Кортеж $\{left, right, windowMetric, bestAnswer\}$, где $left$ и $right$ — границы отрезка, $windowMetric$ — текущая агрегация (сумма, частота символов, число уникальных элементов), а $bestAnswer$ — накопленный экстремум.
- **Начальное состояние:** $left = 0, right = 0$, окно пусто, $bestAnswer$ инициализирован нейтральным значением ($0$ или $\infty$).
- **Целевое состояние:** $right = N$ (все элементы последовательности обработаны), $bestAnswer$ содержит глобальный оптимум.
- **Переходы состояний:** Эволюция автомата определяется соблюдением инварианта:

## Атомарная декомпозиция паттерна

Любой алгоритмический каркас собирается из фиксированного набора базовых операций:

1. **Инициализация состояния:** Создание переменных на стеке. В Go мы опираемся на идиоматичные zero-values: `var totalSum int` уже равен $0$, а `var result []int` — корректный nil-слайс без лишних аллокаций.
2. **Внешний цикл прогресса:** Итерация `for right < len(data)` продвигает правую границу мира.
3. **Инкрементальный пересчет (State Transition):** Добавление элемента `data[right]` в агрегатор за $O(1)$.
4. **Восстановление инварианта:** Внутренний цикл `for invariantViolated(state)`, сдвигающий левую границу $left$ и вычитающий влияние `data[left]` на агрегат.
5. **Фиксация промежуточного оптимума:** Сравнение текущего окна с лучшим известным результатом.
6. **Терминальная фаза:** Возврат ответа с корректной обработкой случая, когда решение не найдено.

> [!info] Под капотом: Арифметика регистров против обращений в память
> Когда операция обновления инварианта выглядит как `currentSum += nums[right]`, на уровне ассемблера x86-64/ARM64 это одна инструкция `ADDQ`, выполняемая в регистре процессора за долю такта. Если же для пересчета инварианта вы вызываете поиск в `map[byte]int`, процессор вынужден вычислять хэш, прыгать по указателям бакетов и ожидать данные из RAM. Понимание атомарных операций учит держать «горячий цикл» максимально легковесным.

## Математический инвариант: Гарантия надежности

**Инвариант** — это математическое условие, которое истинно перед входом в цикл, сохраняется на каждой итерации и гарантирует корректность результата при выходе.

На собеседовании умение сформулировать инвариант вслух производит неизгладимое впечатление на интервьюера, так как демонстрирует способность строго доказывать правильность систем.

### Пример: Remove Duplicates from Sorted Array (LeetCode 26)

Дан отсортированный массив `nums`. Нужно удалить дубликаты in-place за один проход и вернуть новую длину.

```go
func removeDuplicates(nums []int) int {
    if len(nums) == 0 {
        return 0
    }

    // slow указывает на последний записанный уникальный элемент
    slow := 0

    for fast := 1; fast < len(nums); fast++ {
        if nums[fast] != nums[slow] {
            slow++
            nums[slow] = nums[fast]
        }
    }

    return slow + 1
}
```

**Формулировка инварианта:**
> *«В начале каждой итерации внешнего цикла срез `nums[0..slow]` содержит строго уникальные элементы из уже просмотренного префикса `nums[0..fast-1]` в их исходном порядке сортировки»*.

**Доказательство по индукции:**
- **База индукции:** До входа в цикл `slow = 0, fast = 1`. Префикс `nums[0..0]` состоит из одного элемента. Один элемент всегда уникален — инвариант истинен.
- **Индукционный переход:** Если `nums[fast] == nums[slow]`, мы встретили дубликат. Указатель `slow` не двигается, мы просто инкрементируем `fast`. Префикс `nums[0..slow]` остался неизменным и уникальным. Если же `nums[fast] != nums[slow]`, мы нашли новый уникальный элемент (так как массив отсортирован). Мы делаем `slow++` и перезаписываем значение. Срез `nums[0..slow]` расширился ровно на один новый уникальный элемент. Инвариант сохранён!
- **Терминальное состояние:** Когда `fast` доходит до конца среза, `nums[0..slow]` содержит все уникальные элементы исходного массива. Ответ равен `slow + 1`.

> [!tip] Как обосновать задачу Container With Most Water
> Вопрос интервьюера: *«Почему сдвиг указателя с меньшей высотой никогда не пропустит максимальную площадь?»*.
> 
> Ответ Senior-инженера:
> *«Площадь контейнера равна $(right - left) \times \min(h[left], h[right])$. Если мы попытаемся сдвинуть указатель с большей высотой, ширина $(right - left)$ гарантированно уменьшится на 1, а новая высота контейнера не сможет превысить высоту меньшего указателя. Следовательно, площадь может только уменьшиться! Единственный теоретический шанс увеличить площадь при сужении ширины — это найти более высокую стенку на замену меньшей. Поэтому мы обязаны сдвигать указатель с меньшей высотой. Инвариант гарантирует, что мы отсекаем только заведомо неоптимальные варианты»*.

## Композиция паттернов: Конструирование сложных решений

Задачи уровня Hard редко поддаются одному изолированному паттерну. Они требуют **композиции нескольких структурных механизмов**.

### Разбор: Sliding Window Maximum (LeetCode 239)

**Условие:** Дан массив `nums` и размер окна `k`. Найти максимум в каждом окне размера $k$ при его движении от начала до конца массива.

Если решать задачу в лоб через скользящее окно, на каждом шаге нам придется искать максимум среди $k$ элементов, что дает $O(N \cdot k)$ — при $k = 10^5$ это гарантированный провал.

**Инженерный синтез двух паттернов:**
1. **Скользящее окно (внешний каркас):** Управляет продвижением границ диапазона $[i-k+1, i]$.
2. **Монотонная очередь (внутренний механизм):** Двусторонняя очередь (Deque), которая поддерживает индексы элементов в порядке **строгого убывания их значений**.

```go
func maxSlidingWindow(nums []int, k int) []int {
    if len(nums) == 0 || k <= 0 {
        return nil
    }

    result := make([]int, 0, len(nums)-k+1)
    
    // deque хранит индексы элементов.
    // Значения по этим индексам строго убывают: nums[deque[0]] > nums[deque[1]] > ...
    deque := make([]int, 0, k)

    for i, v := range nums {
        // 1. Очистка головы: удаляем индексы, вышедшие за левую границу окна
        if len(deque) > 0 && deque[0] < i-k+1 {
            deque = deque[1:]
        }

        // 2. Поддержание монотонности: выбиваем с конца очереди все элементы,
        // которые меньше или равны текущему кандидату v.
        // Они никогда не станут максимумом, пока жив более свежий и крупный элемент v!
        for len(deque) > 0 && nums[deque[len(deque)-1]] <= v {
            deque = deque[:len(deque)-1]
        }

        // 3. Добавляем индекс текущего элемента в хвост очереди
        deque = append(deque, i)

        // 4. Записываем максимум окна, как только накопили первые k элементов.
        // Максимум текущего окна ВСЕГДА лежит в голове очереди: deque[0]!
        if i >= k-1 {
            result = append(result, nums[deque[0]])
        }
    }

    return result
}
```

### Разбор работы композиции:
- **Асимптотика:** Каждый элемент массива попадает в `deque` ровно один раз и удаляется из нее не более одного раза. Внутренний цикл `for` амортизированно выполняет не более $N$ операций на всем протяжении работы функции! Суммарное время — строго **$O(N)$**.
- **Mechanical Sympathy в Go:** Двусторонняя очередь `deque` реализована поверх компактного среза целых чисел `[]int`. Операции извлечения из головы `deque[1:]` и удаления с хвоста `deque[:len-1]` не аллоцируют память — они лишь мгновенно меняют длину и смещение заголовка среза.
- Предвыделение `make([]int, 0, len(nums)-k+1)` гарантирует отсутствие реаллокаций для итогового ответа.

> [!warning] Ловушка / Gotcha: Аллокации при использовании `append`
> Если объявить очередь без вместимости (`deque := []int{}`), многократный вызов `append` будет заставлять рантайм Go выделять новые массивы в куче по мере роста емкости. Задание предвыделенной вместимости `make([]int, 0, k)` оставляет массив очереди компактным и кэш-дружественным.

|---|---|---|---|
| **Скользящее окно (ASCII)** | Поиск последней позиции символа | `[128]int` или `[26]int` | Стековая аллокация ($0$ B/op), прямая адресация в L1-кэше, $0$ работы для GC. |
