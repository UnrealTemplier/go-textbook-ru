### 2.2. Вопрос 2: Единый детектор оград Python-Markdown, рекурсивные выноски и свойство-тест (В2)
> *«Согласны ли, что детектор повторяет `FENCED_BLOCK_RE` Python-Markdown, проверяется свойство-тестом на всех 1 413 файлах, а тело выноски обрабатывается рекурсивно (В2)?»*

**Ответ: ДА, ПОЛНОСТЬЮ СОГЛАСЕН.**

Архитектурный анализ подтвердил несостоятельность детектора оград из раунда 4:
* `line.strip().startswith(...)` ложно срабатывал на строках внутри списков, которые сам Python-Markdown кодом не считает.
* Закрывающая ограда в Python-Markdown должна **в точности** совпадать со строкой открывающей ограды (`(?P=fence)`). Если блок открыт четырьмя тильдами `~~~~`, закрыть его тремя или пятью тильдами в Python-Markdown невозможно.
* Префикс `>`: наивное срезание `lstrip("> ")` без отслеживания контекста блока приводило к «перетеканию» незакрытого состояния за пределы выноски.

#### Принятая архитектура детектора оград:
1. **Класс `EngineFenceDetector` в ядре:**
   Единый детектор напрямую эмулирует регулярное выражение `FENCED_BLOCK_RE` расширения `markdown.extensions.fenced_code`:
   ```python
   # Семантика строго повторяет Python-Markdown FencedBlockPreprocessor:
   FENCE_START_RE = re.compile(r'^(?P<fence>`{3,}|~{3,})[ ]*(?P<lang>[a-zA-Z0-9_+-]*)[ ]*$')
   ```
   Детектор сохраняет состояние активной ограды: он открывается только в том случае, если строка начинается строго с позиции 0 (без отступа), и закрывается только тогда, когда встречается строка `^(?P=fence)[ ]*$`, состоящая строго из того же набора символов той же длины.
2. **Единый потребитель в пайплайне:**
   Класс `EngineFenceDetector` становится единым источником правды для:
   - Зачистки клише (`_clean_cliches`);
   - Подстановки wikilinks (`_transform_wikilinks`);
   - Сбора заголовков для оглавления TOC (`_process_headings`).
   Старый детектор `stripped.startswith(fence_marker)` из `_process_headings` полностью удаляется.
3. **Рекурсивная обработка выносок (Obsidian Callouts):**
   Применяется полноценный рекурсивный конвейер (Р1 из критики №3):
   ```text
   Исходный Markdown 
     ──> Извлечение выносок [!type] 
     ──> Снятие префикса '> ' с тела выноски
     ──> Препроцессинг тела: cliches, wikilinks (с тем же EngineFenceDetector)
     ──> md.convert(тело) через Python-Markdown
     ──> Формирование HTML-обертки <div class="callout callout-type">
     ──> Замена на плейсхолдер <!--CALLOUT_BLOCK_N-->
   ```
   Благодаря этому код внутри выносок экранируется естественным образом в самом `md.convert(тело)`, а wikilinks и формулы внутри выносок обрабатываются корректно и изолированно.
4. **Свойство-тест (Property-Based Test):**
   В тестовый набор `engine/tests/test_code_detector.py` добавляется автоматический валидатор, который прогоняет все 1 413 файлов `sources/` через `EngineFenceDetector` и сравнивает множество строк, помеченных детектором как «код», с множеством строк, фактически попавших внутрь `<pre><code>` после работы `markdown.Markdown(extensions=['fenced_code'])`. Тест гарантирует 100% эквивалентность семантики на всем корпусе статей.

3. **Ветка расхождения (~3 000 задач):**

   ### Исходная формулировка

### 2.4. Вопрос 4: Общие функции в inline-скрипте рантайма `window.__BOOK__` (В4)
> *«Согласны ли на общие функции в inline-скрипте, а не только общие константы (В4)?»*

**Ответ: ДА, БЕЗОГОВОРОЧНО СОГЛАСЕН.**

Вынесение одних лишь констант в объект `window.__BOOK_CONFIG__` в раунде 4 не решало проблему инцидента `eb135e7d`: логика применения ретро-эффектов оставалась раздвоенной между шаблонизатором Python (inline-скрипт в `<head>`) и клиентским файлом `main.js`. При любом изменении названий CSS-атрибутов (`data-retro-scanlines` и др.) они неминуемо разошлись бы снова. Кроме того, хранение независимого ключа `retroProfilesKey: "go_encyclopedia_retro_effects_"` дублировало префикс `storagePrefix`.

#### Принятая архитектура рантайма `window.__BOOK__`:
Inline-скрипт в `<head>` (генерируемый функцией `make_anti_flicker_script()` в `template.py`) объявляет единое глобальное API функций рантайма, выполняет немедленную установку темы/эффектов до первого рендера браузера (anti-flicker), а затем **эти же самые функции** переиспользуются в `main.js`:

```html
<script>
window.__BOOK__ = {
  cfg: {
    storagePrefix: "go_textbook_",
    defaultTheme: "paper",
    themes: ["paper", "light", "dark"]
  },
  storageKey: function(name) {
    return this.cfg.storagePrefix + name;
  },
  retroKey: function(theme) {
    return this.storageKey("retro_") + theme;
  },
  readJson: function(key) {
    try {
      var item = localStorage.getItem(key);
      return item ? JSON.parse(item) : null;
    } catch(e) { return null; }
  },
  applyRetroAttributes: function(profile) {
    var cl = document.documentElement.classList;
    var el = document.documentElement;
    if (!profile || !profile.enabled) {
      el.removeAttribute("data-retro-scanlines");
      el.removeAttribute("data-retro-glow");
      el.removeAttribute("data-retro-bloom");
      return;
    }
    if (profile.scanlines) el.setAttribute("data-retro-scanlines", "true");
    else el.removeAttribute("data-retro-scanlines");

    if (profile.glow) el.setAttribute("data-retro-glow", "true");
    else el.removeAttribute("data-retro-glow");

    if (profile.bloom) el.setAttribute("data-retro-bloom", "true");
    else el.removeAttribute("data-retro-bloom");
  },
  applyTheme: function(theme) {
    document.documentElement.setAttribute("data-theme", theme);
  }
};

/* Немедленное исполнение Anti-Flicker: */
(function() {
  var B = window.__BOOK__;
  var savedTheme = null;
  try { savedTheme = localStorage.getItem(B.storageKey("theme")); } catch(e) {}
  var theme = (savedTheme && B.cfg.themes.indexOf(savedTheme) !== -1) ? savedTheme : B.cfg.defaultTheme;
  B.applyTheme(theme);
  var retro = B.readJson(B.retroKey(theme));
  B.applyRetroAttributes(retro);
})();
</script>
```

#### Поведение `main.js`:
Файл `main.js` полностью освобождается от собственной реализации `applyRetroEffects` и констант ключей хранилища. При переключении темы или тумблеров ретро-эффектов в модальном окне `main.js` напрямую вызывает:
* `window.__BOOK__.applyTheme(newTheme);`
* `window.__BOOK__.applyRetroAttributes(newProfile);`
* `localStorage.setItem(window.__BOOK__.retroKey(theme), JSON.stringify(newProfile));`

#### Инфраструктура верификации:
В `engine/tests/test_runtime.py` создается интеграционный тест на базе headless Firefox, эмулирующий 6 сценариев коммита `eb135e7d`:
1. Первое посещение (чистый `localStorage`) -> установка `defaultTheme`.
2. Сохраненная тема `dark` -> мгновенная установка `data-theme="dark"`.
3. Сохраненный ретро-профиль со сканлайнами -> атрибут `data-retro-scanlines="true"`.
4. Поврежденный/невалидный JSON в ключе ретро-эффектов -> тихий сброс без падения JS.
5. Заблокированный доступ к `localStorage` (SecurityError в iframe/инкогнито) -> безопасный fallback.
6. Сравнение DOM-дерева `<html>` непосредственно после выполнения inline-скрипта и после события `DOMContentLoaded` -> 0 расхождений.

### 2.5. Вопрос 5: Защита формул KaTeX плейсхолдерами (Н1) и препроцессор оград в списках (Н2)
> *«Согласны ли с защитой формул плейсхолдерами (Н1) и препроцессором оград с отступом (Н2) в ядре?»*

**Ответ: ДА, БЕЗОГОВОРОЧНО СОГЛАСЕН. ЭТО КРИТИЧЕСКИ ВАЖНЫЕ УЛУЧШЕНИЯ ДВИЖКА.**

#### 1. Защита математики KaTeX (`math.protect`, Н1):
* **Причина бага:** Стандартный препроцессор экранирования Python-Markdown перехватывает символы `\(` и `\[` и превращает их в обычные круглые и квадратные скобки. В результате клиентский `katex.min.js` (через `auto-render`) не находит формул для отрисовки. В `go-textbook` (модуль 22, статья 14) закон Литтла выводился как обычный текст `( \text{concurrency} = \text{throughput} \times \text{latency} )`. В `go-workout` это уничтожило бы рендеринг всех 1 171 формулы.
* **Решение в ядре:**
  - В конфигурацию вводится секция:
    ```toml
    [math]
    protect = true              # false для go-textbook на этапах 1-2; true для workout и этапа А3и
    delimiters = [
      { left = "\\(", right = "\\)", display = false },
      { left = "$$",  right = "$$",  display = true }
    ]
    ```
  - Разрабатывается препроцессор `MathProtector`:
    До передачи текста в Python-Markdown все формулы, соответствующие сконфигурированным разделителям (вне блоков кода, определяемых через `EngineFenceDetector`), вырезаются и заменяются на уникальные плейсхолдеры:
    `<!--MATH_BLOCK_0042-->` или `<!--MATH_INLINE_0042-->`.
    Python-Markdown оставляет комментарии нетронутыми.
  - Постпроцессор конвертера возвращает формулы на место с обязательным HTML-экранированием спецсимволов (`&`, `<`, `>`), гарантируя защиту от XSS и корректность отображения.
  - Список `delimiters` из `book.toml` транслируется в рантайм `auto-render` в `main.js`: один источник правды исключает рассинхронизацию.

#### 2. Препроцессор оград с отступом в списках (Н2):
* **Причина бага:** В `go-textbook` обнаружено 446 строк-оград (220 открывающих блоков с языком в 116 статьях), оформленных с отступом в 2–4 пробела внутри пунктов списков `li`. Расширение `fenced_code` Python-Markdown распознает ограды **строго с начала строки** (`^`). Из-за этого блоки не оборачивались в `<pre><code>`, а превращались в уродливые инлайн-фрагменты `<code>asm\n   SUBQ $64, SP</code>` с названием языка в качестве первой строки кода. В `go-workout` таких блоков 239.
* **Решение в ядре:**
  - Разрабатывается бескомпромиссный препроцессор `IndentedFencePreprocessor` (без сторонних тяжелых зависимостей типа `pymdown-extensions`).
  - Препроцессор обнаруживает ограды внутри элементов списков:
    ```python
    INDENTED_FENCE_RE = re.compile(
        r'^(?P<indent>[ \t]+)(?P<fence>`{3,}|~{3,})[ ]*(?P<lang>[a-zA-Z0-9_+-]*)[ ]*\n'
        r'(?P<code>[\s\S]*?\n)'
        r'(?P=indent)(?P=fence)[ ]*$',
        re.MULTILINE
    )
    ```
  - Препроцессор извлекает блок кода, срезает базовый отступ списка с тела кода, изолирует его в плейсхолдер `<!--INDENTED_CODE_N-->`, форматирует стандартным механизмом движка `_enhance_code_blocks` и возвращает в результирующий HTML.
  - В `go-textbook` на этапах 1–2 препроцессор отключен (`indent_code_fix = false`), обеспечивая нулевой diff. В коммите А3з он включается по директиве **U13**, восстанавливая правильный рендеринг ~220 блоков кода на 116 страницах.

### 2.6. Вопрос 6: Расширение инварианта рантайм-проекцией в headless Firefox (Н4)
> *«Согласны ли добавить рантайм-проекцию KaTeX/Mermaid в инвариант (Н4)?»*

**Ответ: ДА, БЕЗОГОВОРОЧНО СОГЛАСЕН.**

Статическое побайтовое сравнение `<article class="article-body">` — необходимое, но недостаточное условие неизменности контента:
1. Если в `book.toml` для `go-textbook` допустить опечатку в списке разделителей KaTeX (например, потерять одиночный `$`), то 7 814 формул в 747 статьях не будут отрендерены браузером, но побайтный diff HTML будет абсолютно чист!
2. При оптимизации условной загрузки (коммит А3г), если эвристика детектора математики ошибется, скрипт `katex.min.js` не загрузится на странице с формулами, и читатель увидит сырой текст `$x^2$`.
3. При любых изменениях в санитизаторе Mermaid синтаксическая ошибка приведет к падению рендера в браузере, даже если HTML-тег `<pre class="mermaid">` визуально валиден.

#### Инженерная реализация рантайм-проекции:
Инструмент верификации `engine/tools/verify_diff.py` дополняется режимом `--runtime-projection`. Используя уже отлаженный механизм headless Firefox (работающий в `audit_all.py`), скрипт открывает скомпилированные страницы по протоколу `file:///` и собирает для каждой статьи числовую сигнатуру:
```json
{
  "doc_path": "docs/02-ustroystvo-i-rabota-os/18-mmap.html",
  "katex_elements": 12,
  "katex_display_elements": 2,
  "katex_errors": 0,
  "mermaid_rendered_svgs": 3,
  "mermaid_errors": 0
}
```
* **Эталонный снимок (Baseline Snapshot):** На этапе А0 формируется эталонный файл `runtime-projection-baseline.json` для всех 1 413 страниц `go-textbook`.
* **Правило прохождения инварианта:** В коммитах А1, А2 и А3г сигнатуры всех страниц обязаны побайтно совпадать с эталоном. В коммитах А3и (исправление закона Литтла) и А3з (исправление оград в списках) допускаются строго детерминированные изменения на санкционированных страницах.

## 4. Инженерные решения по дополнительным замечаниям В5–В8

### 4.1. Совместимость с протоколом `file:///` в Chromium: внутристраничные SVG `<symbol>`
Рецензент абсолютно прав: внешние SVG-спрайты (`<use href="icons.svg#copy">`) и CSS-свойства `mask-image: url(...)` в браузерах на движке Blink/Chromium блокируются политикой безопасности Same-Origin Policy при открытии по протоколу `file:///`. Поскольку AGENTS.md § 1.3 требует безупречной работы портала «напрямую из локальной файловой системы без веб-сервера», это критическая угроза.

#### Принятое решение:
1. В подвал шаблона страницы (`template.py`) инжектируется компактный скрытый блок символов:
   ```html
   <svg style="display:none;" xmlns="http://www.w3.org/2000/svg">
     <defs>
       <symbol id="icon-copy" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2">
         <rect x="9" y="9" width="13" height="13" rx="2" ry="2"></rect>
         <path d="M5 15H4a2 2 0 0 1-2-2V4a2 2 0 0 1 2-2h9a2 2 0 0 1 2 2v1"></path>
       </symbol>
       <symbol id="icon-check" viewBox="0 0 24 24" fill="none" stroke="currentColor" stroke-width="2">
         <polyline points="20 6 9 17 4 12"></polyline>
       </symbol>
     </defs>
   </svg>
   ```
2. Кнопки копирования в блоках кода используют локальную внутристраничную ссылку:
   `<svg class="copy-icon"><use href="#icon-copy"></use></svg>`
3. **Результат:** 100% гарантия работы в Firefox, Chromium, WebKit/Safari по `file:///`, `http://`, `https://`. Полное устранение дублирования путей SVG (экономия ~1.8 КБ на каждый блок кода).
4. **Кроссбраузерный аудит:** В `audit_all.py` добавляется проверка рендеринга иконок по `file:///` в Firefox **и** в Chromium (через `playwright` или headless chromium при наличии).

### 4.2. Изоляция изменений шапки блоков кода: нормализатор `code_chrome`
Поскольку функция `_enhance_code_blocks` встраивает шапку с кнопками и ретро-эффектами непосредственно внутрь контейнера статьи:
`<div class="code-block-header">...</div><pre><code>...</code></pre>`
любая оптимизация разметки шапки блока (коммит А3е) привела бы к изменению побайтного diff тела `<article>`.

#### Принятое решение:
В верификатор `engine/tools/verify_diff.py` добавляется именованный нормализатор `code_chrome`:
* Перед побайтным сравнением нормализатор удаляет элементы с классом `code-block-header` и любые декоративные обертки ретро-эффектов, сводя код к канонической структуре `<pre><code ...>...</code></pre>`.
* Это позволяет коммиту А3е оптимизировать обвязку кнопок и иконок, гарантируя при этом, что смысловой контент и исходный текст программного кода не изменились ни на один байт.

### 4.4. Всеобъемлющий Offline-First Guard и проверка путей Windows по всему репозиторию
В соответствии с замечаниями В8 аудит расширяется:
1. **Offline-First Guard (`engine/audit.py`):**

## 5. Детализированная техническая спецификация ядра `html-textbook-engine`

### 5.1. Алгоритм `EngineFenceDetector` и оракул на базе Python-Markdown
Класс `EngineFenceDetector` оформляется в модуле `engine/converter.py` и реализует строгое следование правилам Python-Markdown:

```python
class EngineFenceDetector:
    """
    Единый конечный автомат оград кода. 
    Семантически эквивалентен markdown.extensions.fenced_code.FencedBlockPreprocessor.
    """
    FENCE_START_RE = re.compile(r'^(?P<fence>`{3,}|~{3,})[ ]*(?P<lang>[a-zA-Z0-9_+-]*)[ ]*$')

    def __init__(self):
        self.in_code_block = False
        self.active_fence = None

    def process_line(self, line: str) -> bool:
        """
        Принимает строку текста. Возвращает True, если строка является 
        содержимым блока кода (включая открывающую и закрывающую ограду).
        """
        # Если мы вне блока кода, ограда распознается только с позиции 0 (без отступа)
        if not self.in_code_block:
            m = self.FENCE_START_RE.match(line)
            if m:
                self.in_code_block = True
                self.active_fence = m.group('fence')
                return True
            return False
        else:
            # Закрывающая ограда должна точно совпадать по символу и длине
            if line.rstrip() == self.active_fence:
                self.in_code_block = False
                self.active_fence = None
                return True
            return True
```

### 5.2. Препроцессор `MathProtector`: изоляция формул плейсхолдерами
Модуль защиты формул `MathProtector` в `engine/converter.py`:

```python
class MathProtector:
    """
    Защищает математические формулы KaTeX от экранирования символов в Python-Markdown.
    Использует плейсхолдеры <!--MATH_INDEX-->.
    """
    def __init__(self, delimiters: list[dict]):
        self.delimiters = delimiters
        self.placeholders: list[str] = []

    def protect(self, text: str, fence_detector: EngineFenceDetector) -> str:
        self.placeholders.clear()
        lines = text.split('\n')
        out_lines = []
        
        for line in lines:
            if fence_detector.process_line(line):
                out_lines.append(line)
                continue
            
            # Поиск и замена формул вне блоков кода
            processed_line = line
            for delim in self.delimiters:
                left = re.escape(delim['left'])
                right = re.escape(delim['right'])
                pattern = re.compile(rf'{left}([\s\S]+?){right}')
                
                def _repl(match):
                    idx = len(self.placeholders)
                    raw_formula = match.group(0)
                    self.placeholders.append(raw_formula)
                    return f"<!--MATH_PLACEHOLDER_{idx}-->"
                
                processed_line = pattern.sub(_repl, processed_line)
            out_lines.append(processed_line)
            
        return '\n'.join(out_lines)

    def restore(self, html: str) -> str:
        for idx, formula in enumerate(self.placeholders):
            # Безопасное HTML-экранирование спецсимволов внутри формулы
            escaped = html_escape_math(formula)
            html = html.replace(f"<!--MATH_PLACEHOLDER_{idx}-->", escaped)
        return html
```

### 5.3. Препроцессор `IndentedFencePreprocessor`: нормализация оград в списках
Препроцессор оград с отступом в `engine/converter.py`:

```python
class IndentedFencePreprocessor:
    """
    Обнаруживает блоки кода с отступом внутри списков (Н2) 
    и изолирует их в плейсхолдеры <!--INDENTED_CODE_N-->.
    """
    INDENTED_BLOCK_RE = re.compile(
        r'^(?P<indent>[ \t]+)(?P<fence>`{3,}|~{3,})[ ]*(?P<lang>[a-zA-Z0-9_+-]*)[ ]*\n'
        r'(?P<code>[\s\S]*?\n)'
        r'(?P=indent)(?P=fence)[ ]*$',
        re.MULTILINE
    )

    def process(self, text: str, enhance_callback) -> str:
        def _replace_block(m):
            indent = m.group('indent')
            lang = m.group('lang')
            code = m.group('code')
            
            # Срезаем базовый отступ со всех строк тела кода
            clean_lines = []
            for line in code.splitlines():
                if line.startswith(indent):
                    clean_lines.append(line[len(indent):])
                else:
                    clean_lines.append(line.lstrip())
            clean_code = '\n'.join(clean_lines)
            
            # Рендерим блок кода через стандартный механизм enhance_callback
            rendered_html = enhance_callback(clean_code, lang)
            return f"\n\n<!--INDENTED_CODE_START-->\n{rendered_html}\n<!--INDENTED_CODE_END-->\n\n"

        return self.INDENTED_BLOCK_RE.sub(_replace_block, text)
```
