## Executive Summary

Module 2 represents the architectural bedrock of the entire encyclopedia, connecting low-level hardware physics and Linux kernel mechanics with high-level Go systems programming. With 63 comprehensive articles, it establishes the mental models that subsequent modules (concurrency, networking, databases, distributed systems) rely upon. The pedagogical quality is generally very high: topics such as virtual memory translation, page faults, CPU protection rings, Meltdown/KPTI mitigations, and the Go G-M-P scheduler architecture are explained clearly with excellent visual ASCII/Mermaid diagrams and practical engineering analogies.

However, an exhaustive line-by-line audit across all 63 articles revealed **several critical factual bugs, broken code examples that fail compilation or cause runtime panics/leaks, hallucinated Go features, and direct cross-article contradictions**. These errors fall into five major categories:

1. **Broken Code Recipes & Compilation Failures:**
   - Article 30 provides an uncompilable and dangerous systemd socket activation recipe: it treats the descriptor *count* (`LISTEN_FDS`) as the descriptor *number*, hijacking stdout (FD 1); uses `net.FileConn` where `net.FileListener` is required; and instructs readers *not* to close the original `os.File`, which directly causes descriptor leaks.
   - Article 56 presents code calling `os.Setuid(1000)` and `os.Setgid(1000)` — functions that do not exist in package `os` (compiler error).
2. **Gross Conflation of Go Scheduler & OS Kernel Mechanics:**
   - Article 22 features pseudocode depicting a goroutine during a blocking syscall calling `runtime.gopark()` and `runtime.munpin()` to detach itself from OS thread `M`, claiming thread `M` executes another goroutine while waiting in the kernel. In reality, a thread blocked in a kernel syscall cannot execute anything in userspace; it is logical processor `P` that is detached and handed off to a separate thread `M2`.
   - Article 23 claims the slow path of `sync.Mutex` directly invokes `futex(FUTEX_WAIT/WAKE)`, contradicting Article 33 and the Go runtime design, where goroutines park in user-space runtime queues (`_Gwaiting`) via runtime semaphores, and OS threads only park via futex when `M` has no runnable work.
3. **Netpoller Implementation Misconceptions:**
   - Articles 36 and 38 state that Go's netpoller uses `EPOLLONESHOT` on Linux and `EV_ONESHOT` on BSD, requiring socket re-registration on every event. Primary source verification of `/usr/local/go/src/runtime/netpoll_epoll.go` and `netpoll_kqueue.go` proves Go registers sockets **once in Edge-Triggered mode (`EPOLLET` / `_EV_CLEAR`)** and never uses `EPOLLONESHOT` (the runtime's `netpollarm` function literally throws `"runtime: unused"`). Article 62 contradicts both by claiming Go uses `EPOLL_CTL_MOD` / `EPOLL_CTL_DEL`.
4. **Kernel ABI & Protocol Errors:**
   - Article 27 claims the 108-byte `UNIX_PATH_MAX` limit for Unix Domain Sockets was lifted in Linux 3.4+. In reality, `struct sockaddr_un.sun_path` is fixed at 108 bytes in `/usr/include/linux/un.h` across all Linux kernel versions.
   - Article 50 claims adjusting `net.ipv4.tcp_fin_timeout` helps recover sockets stuck in `CLOSE_WAIT`. In reality, `tcp_fin_timeout` strictly governs `FIN-WAIT-2`; `CLOSE_WAIT` sockets are held by the local application and can only be closed by `close(fd)`.
   - Article 29 claims calling `signal.Notify` twice on the same channel panics with `panic: runtime error: invalid channel use`, directly contradicting the official Go specification.
5. **Hallucinated Versions & Features:**
   - Article 54 claims Go 1.13 automatically detects CFS quotas from `/sys/fs/cgroup/...` when `GOMAXPROCS=0`. In reality, standard Go ignored cgroup quotas for a decade (requiring `uber-go/automaxprocs`), and native cgroup detection was only introduced in Go 1.25.
   - Article 22 claims Go 1.21+ actively integrates `io_uring` into standard netpoller and `os`, and that Go 1.22+ scheduler uses futex to "predict" syscall completion. Both are non-existent in Go standard library releases.

This brief provides the downstream fact-checking agent (Sonnet) with rigorous primary sources, file paths, line numbers, and actionable correction plans to eliminate these inaccuracies while preserving pedagogical flow.

# 1. HIGH-PRIORITY CLAIMS (CRITICAL / FACTUALLY WRONG)

## Claim 1: Blocking Syscall Handling in G-M-P (Hand-off & Pinning Blunder)

- **File:** `sources/2. Устройство и работа ОС/22. Системные вызовы. Как программа просит ОС что-то сделать.md`
- **Section:** "Механизм Hand-off и Pinning" (lines 119–138)
- **Exact Quotation:**
  > "1. **Pinning:** В момент входа в syscall Go runtime 'прибивает' (pin) горутину к текущему треду M. Это гарантирует, что ядро не потеряет дескрипторы и контекст.
  > 2. **Detection:** Планировщик (в отдельном треде `sched`) видит, что тред M ушел в blocking syscall.
  > 3. **Hand-off:** Планировщик 'отцепляет' горутину от треда, переводит её в состояние `Gwaiting` (вызывает `gopark`), и передает управление другой горутине на этом же треду. Если тредов не хватает, он создает новый тред ОС (`mksyscall` -> `newm`).
  > 4. **Wake-up:** Когда syscall завершается, ядро возвращает управление. Go runtime видит это, переводит горутину в `Grunnable` (`goready`), и добавляет её в очередь планировщика (P).
  >
  > ```go
  > // Псевдокод внутреннего устройства runtime в Go 1.14+
  > // Когда горутина делает blocking syscall:
  > if isBlockingSyscall() {
  >     runtime.gopark(lockAddr, waitReason, traceEv) // Усыпляем горутину
  >     runtime.munpin() // Отцепляем от треда M
  >     // Планировщик может создать новый тред или переназначить P
  > }
  > ```"
- **Claim Classification:** FACTUALLY WRONG
- **Severity:** Critical
- **Context:** Current Go runtime internals
- **Why It Matters:**
  This description completely inverts the fundamental design of Go's G-M-P scheduler:
  1. An OS thread `M` executing a blocking syscall (e.g. `read()` from disk) is trapped inside the kernel in `TASK_INTERRUPTIBLE` or `TASK_UNINTERRUPTIBLE`. It **cannot execute userspace instructions**, cannot call `gopark()`, and **cannot run another goroutine**!
  2. The goroutine `G` remains bound to `M` in state `_Gsyscall`. It is the logical processor `P` that is detached (`handoffp()`) and given to an idle or newly spawned OS thread `M2`, which then runs runnable goroutines.
  3. `runtime.munpin()` does not exist in this context (`runtime.pinner` introduced in Go 1.21 is for cgo pointer pinning, entirely unrelated).
  4. There is no separate OS thread called "`sched`"; syscall disassociation is monitored by `sysmon` (a background thread running without a `P`).
  5. The article also states that TCP reads are blocking syscalls; in Go, network I/O is non-blocking and managed by the netpoller.
  This creates an entirely broken mental model for students and engineers preparing for systems interviews.
- **Primary Sources:**
  - Go Runtime Source: `/usr/local/go/src/runtime/proc.go` (functions `entersyscall`, `entersyscallblock`, `exitsyscall`, `handoffp`, `sysmon`)
  - Go Scheduler Design Doc: https://golang.org/s/go11sched
- **Actionable Correction Plan:**
  Rewrite the section to explain the real G-M-P handoff mechanism:
  - Entering syscall: `entersyscall()` saves PC/SP, transitions `G` to `_Gsyscall`, keeps `G` on `M`, and releases `P`'s write barrier buffer.
  - If the syscall is known to block (`entersyscallblock`), `P` is immediately detached. If not, `sysmon` checks running `M`s every 20μs–10ms; if an `M` is stuck in `_Gsyscall` for over 10ms, `sysmon` steals `P` via `handoffp()`.
  - While `M` is asleep in the kernel, another thread `M2` acquires `P` and runs other goroutines.
  - On return (`exitsyscall()`), `M` attempts to reacquire its old `P` or any idle `P`. If none is available, `G` is moved to `_Grunnable` on the global runqueue, and `M` parks itself.
  - Delete the hallucinated pseudocode with `runtime.munpin()`.

## Claim 2: Go Netpoller Flags (`EPOLLONESHOT` / `EV_ONESHOT` vs Edge-Triggered `EPOLLET`)

- **Files:**
  - `sources/2. Устройство и работа ОС/36. select, poll и epoll.md` (lines 263–269)
  - `sources/2. Устройство и работа ОС/38. Как netpoller Go использует epoll и kqueue.md` (lines 115–124)
- **Exact Quotations:**
  - Article 36:
    > "Go регистрирует дескрипторы с флагом `EPOLLONESHOT`. Это заставляет ядро отключать уведомления после первого же события, передавая контроль над повторной активацией дескриптора в руки рантайма Go. Это защищает от ситуации Thundering Herd..."
  - Article 38:
    > "Флаги `EPOLLONESHOT` и `EV_ONESHOT` гарантируют точечный контроль над событиями дескрипторов. Когда ядро возвращает событие, дескриптор отключается от мониторинга, пока Go-рантайм явно не взведет его снова через `epoll_ctl(EPOLL_CTL_MOD)`."
- **Claim Classification:** FACTUALLY WRONG
- **Severity:** Critical
- **Context:** Current Go runtime internals
- **Why It Matters:**
  This is a widespread urban myth in the Go community that made its way into the textbook.
  Checking the actual Go standard library runtime source reveals:
  ```go
  // /usr/local/go/src/runtime/netpoll_epoll.go:
  func netpollopen(fd uintptr, pd *pollDesc) uintptr {
      var ev linux.EpollEvent
      ev.Events = linux.EPOLLIN | linux.EPOLLOUT | linux.EPOLLRDHUP | linux.EPOLLET
      tp := taggedPointerPack(unsafe.Pointer(pd), pd.fdseq.Load())
      *(*taggedPointer)(unsafe.Pointer(&ev.Data)) = tp
      return linux.EpollCtl(epfd, linux.EPOLL_CTL_ADD, int32(fd), &ev)
  }

  func netpollarm(pd *pollDesc, mode int) {
      throw("runtime: unused")
  }
  ```
  And in `/usr/local/go/src/runtime/netpoll_kqueue.go`:
  ```go
  // Arm both EVFILT_READ and EVFILT_WRITE in edge-triggered mode (EV_CLEAR)
  // for the whole fd lifetime. The notifications are automatically unregistered
  // when fd is closed.
  ev[0].flags = _EV_ADD | _EV_CLEAR
  ```
  Go registers sockets **once for their entire lifetime in Edge-Triggered mode** (`EPOLLET` on Linux, `EV_CLEAR` on BSD/macOS). It **NEVER** uses `EPOLLONESHOT` or `EV_ONESHOT`, and it **NEVER** re-arms descriptors with `EPOLL_CTL_MOD` after events! The function `netpollarm` is literally dead code that calls `throw("runtime: unused")`. Readiness is tracked purely in userspace inside `pollDesc.rg` and `pollDesc.wg`.
  Additionally, Article 62 contradicts Articles 36 & 38 by claiming Go uses `EPOLL_CTL_DEL` and `EPOLL_CTL_MOD` instead of `EPOLLONESHOT`.
- **Primary Sources:**
  - Linux epoll runtime: `/usr/local/go/src/runtime/netpoll_epoll.go` (lines 49–64)
  - BSD kqueue runtime: `/usr/local/go/src/runtime/netpoll_kqueue.go` (lines 32–41)
  - Netpoller state machine: `/usr/local/go/src/runtime/netpoll.go`
- **Actionable Correction Plan:**
  - In Article 36 and Article 38: Replace all mentions of `EPOLLONESHOT` and `EV_ONESHOT` with Edge-Triggered mode (`EPOLLET` / `EV_CLEAR`). Explain that Go uses edge-triggering so that notifications fire only when state changes, avoiding syscall storms without needing continuous `EPOLL_CTL_MOD` re-arming.
  - In Article 62: Remove claims that Go calls `EPOLL_CTL_MOD` or `EPOLL_CTL_DEL` during ordinary packet processing. Clarify that `EPOLL_CTL_ADD` is called once in `netpollopen()`, and `EPOLL_CTL_DEL` is called only upon `netpollclose()`.

## Claim 3: Systemd Socket Activation Recipe (Broken Code & Leaks)

- **File:** `sources/2. Устройство и работа ОС/30. systemd. Управление сервисами в Linux.md`
- **Section:** "Пример получения FD от systemd" & "Ловушка / Gotcha" (lines 126–147)
- **Exact Quotation:**
  > ```go
  > // Пример получения FD от systemd
  > func getListenFD() (net.Listener, error) {
  > 	if fdStr, ok := os.LookupEnv("LISTEN_FDS"); ok {
  > 		fd, err := strconv.Atoi(fdStr)
  > 		if err != nil {
  > 			return nil, fmt.Errorf("invalid LISTEN_FDS: %w", err)
  > 		}
  > 		f := os.NewFile(uintptr(fd), "")
  > 		conn, err := net.FileConn(f)
  > 		if err != nil {
  > 			return nil, fmt.Errorf("net.FileConn failed: %w", err)
  > 		}
  > 		return conn, nil
  > 	}
  > 	return net.Listen("tcp", ":8080")
  > }
  > ```
  > > [!warning] Ловушка / Gotcha
  > > Не используйте `os.NewFile(uintptr(fd), "").Close()` после получения `net.FileConn`. `net.FileConn` создает обертку, которая **не закроет** базовый FD при `Close()`. Это намеренно: systemd должен контролировать жизненный цикл сокета...
- **Claim Classification:** FACTUALLY WRONG / COMPILATION & RUNTIME FAILURE
- **Severity:** Critical
- **Context:** Production code recipe in Linux systemd environment
- **Why It Matters:**
  This snippet contains four severe bugs:
  1. `LISTEN_FDS` is an environment variable containing the **count** of passed file descriptors (almost always `"1"`), **not the file descriptor number**! File descriptors passed by systemd always start at `SD_LISTEN_FDS_START = 3`. By doing `uintptr(strconv.Atoi("1"))`, the code wraps file descriptor **1**, which is `stdout`!
  2. `net.FileConn(f)` returns `(net.Conn, error)`. `net.Conn` does NOT implement `net.Listener` (it lacks `Accept() (Conn, error)`). The code will **not even compile** (`cannot use conn (variable of type net.Conn) as net.Listener value in return statement`). For listening sockets, `net.FileListener(f)` must be used.
  3. `net.FileListener(f)` and `net.FileConn(f)` execute `dup(fd)` internally to obtain an independent descriptor set to non-blocking mode. Because of this `dup()`, the caller **MUST close the original `os.File`** (`f.Close()`).
  4. The warning in lines 145–147 tells the developer *never to close `f`*, claiming `net.FileConn` doesn't close it to let systemd manage it. Following this advice causes an immediate file descriptor leak on every service restart or initialization!
- **Primary Sources:**
  - systemd API: `man 3 sd_listen_fds`, header `systemd/sd-daemon.h` (`#define SD_LISTEN_FDS_START 3`)
  - Go Standard Library: `pkg.go.dev/net#FileListener` ("FileListener returns a copy of the network listener corresponding to the open file f. It is the caller's responsibility to close ln when finished. Closing ln does not affect f, and closing f does not affect ln.")
  - `coreos/go-systemd/activation`: Canonical Go implementation of systemd socket activation.
- **Actionable Correction Plan:**
  Replace the broken snippet with canonical socket activation code:
  ```go
  func getListenFD() (net.Listener, error) {
      if os.Getenv("LISTEN_PID") == strconv.Itoa(os.Getpid()) {
          nfds, err := strconv.Atoi(os.Getenv("LISTEN_FDS"))
          if err == nil && nfds > 0 {
              const SD_LISTEN_FDS_START = 3
              f := os.NewFile(uintptr(SD_LISTEN_FDS_START), "systemd-listen-fd")
              defer f.Close() // Mandatory: net.FileListener dups the fd; close the original to avoid leak
              return net.FileListener(f)
          }
      }
      return net.Listen("tcp", ":8080")
  }
  ```
  Rewrite the warning callout to explain that `net.FileListener` duplicates the FD via `dup()`, so `f.Close()` is strictly required.

## Claim 4: Go 1.13 Automatic Cgroup CFS Quota Detection for GOMAXPROCS

- **File:** `sources/2. Устройство и работа ОС/54. Изоляция процессов в Linux.md`
- **Section:** Main body (lines 147–152)
- **Exact Quotation:**
  > "До версии Go 1.13 системная функция `runtime.GOMAXPROCS()` всегда возвращала количество физических ядер хоста (`runtime.NumCPU()`), абсолютно игнорируя квоты cgroups. Начиная с Go 1.13, при запуске с `GOMAXPROCS=0` (по умолчанию) рантайм автоматически пытается прочитать квоты CFS из `/sys/fs/cgroup/cpu,cpuacct/cpu.cfs_quota_us`..."
- **Claim Classification:** FACTUALLY WRONG
- **Severity:** Critical
- **Context:** Historical vs Current Go behavior
- **Why It Matters:**
  This claim is completely false. Go 1.13 never introduced cgroup quota detection.
  For ten years (from Go 1.5 through Go 1.24), Go's `runtime.GOMAXPROCS(0)` strictly defaulted to `runtime.NumCPU()` (or CPU affinity mask), completely blind to CFS bandwidth limits (`cpu.cfs_quota_us` and `cpu.max`). This blind spot caused severe CPU throttling in Kubernetes containers and led Uber to develop `uber-go/automaxprocs`.
  Native cgroup quota detection was only added in **Go 1.25** (2025) via `src/runtime/cgroup_linux.go` and the `GODEBUG=updatemaxprocs=1` / `containermaxprocs` setting!
  Claiming this existed in Go 1.13 misinforms engineers running Go in Kubernetes, who might mistakenly omit `uber-go/automaxprocs` on Go 1.13–1.24 applications.
  Furthermore, it contradicts Article 8 and Article 52, which instruct developers to always import `uber-go/automaxprocs`.
- **Primary Sources:**
  - Go 1.13 Release Notes: https://go.dev/doc/go1.13 (no mention of cgroup quotas)
  - Go 1.25 Source Code: `/usr/local/go/src/runtime/cgroup_linux.go` (`// Copyright 2025 The Go Authors... cgroup-aware GOMAXPROCS default`)
  - Uber Automaxprocs repository: https://github.com/uber-go/automaxprocs
  - Go Issue #33803: Proposal for container-aware GOMAXPROCS.
- **Actionable Correction Plan:**
  Correct the version history:
  - State that historically (Go 1.5 through Go 1.24), Go was completely unaware of cgroup quotas, leading to CPU throttling in containers unless `uber-go/automaxprocs` was used.
  - Mention that native cgroup awareness and dynamic GOMAXPROCS updating were introduced in Go 1.25 (`GODEBUG=containermaxprocs`, `updatemaxprocs`).

## Claim 7: UNIX_PATH_MAX = 108 Limit "Lifted" in Linux 3.4+

- **File:** `sources/2. Устройство и работа ОС/27. Unix Domain Socket.md`
- **Section:** "Ловушки и ограничения" (line 204)
- **Exact Quotation:**
  > "Лимит `UNIX_PATH_MAX = 108` байт был снят в современных ядрах Linux 3.4+..."
- **Claim Classification:** FACTUALLY WRONG
- **Severity:** High
- **Context:** Linux kernel ABI
- **Why It Matters:**
  The 108-byte limit has **never** been lifted for filesystem-bound Unix Domain Sockets in Linux. The kernel ABI definition in `/usr/include/linux/un.h` is rigid:
  ```c
  #define UNIX_PATH_MAX 108
  struct sockaddr_un {
      __kernel_sa_family_t sun_family; /* AF_UNIX */
      char sun_path[UNIX_PATH_MAX];    /* pathname */
  };
  ```
  Attempting to bind or connect a Unix domain socket to a filesystem path longer than 108 bytes returns `EINVAL` or `ENAMETOOLONG` across all Linux kernel versions (including Linux 6.x). (While abstract namespace sockets and relative paths via `openat`/`dirfd` offer workarounds, the `sockaddr_un.sun_path` buffer itself remains 108 bytes).
- **Primary Sources:**
  - Linux Kernel Header: `/usr/include/linux/un.h` (`#define UNIX_PATH_MAX 108`)
  - Linux Kernel Source: `net/unix/af_unix.c`
  - Man page: `man 7 unix` ("Pathname: a UNIX domain socket can be bound to a null-terminated filesystem pathname using bind(2)... sun_path is an array of size 108")
- **Actionable Correction Plan:**
  Remove the statement that the limit was lifted in Linux 3.4+. Emphasize that the 108-byte limit remains a strict kernel ABI limitation, and explain workarounds (relative paths, working directory switching, or abstract sockets where path length is still bounded by 108 bytes).

# 4. CLAIM CLUSTERS

### Cluster A: Memory Reclaim Mechanics (`MADV_DONTNEED` vs `MADV_FREE` vs `munmap`)
- **Files Involved:** Articles 2, 12, 13, 15, 19, 21
- **The Issue:**
  Across these 6 articles, the explanation of how Go returns memory to the OS is fragmented and contradictory:
  - Article 19 says Go calls `munmap`.
  - Articles 12 and 21 state Go calls `madvise(MADV_DONTNEED)`.
  - Article 2 and 15 mention `MADV_FREE`.
- **The Ground Truth:**
  1. Go **never** unmaps heap memory with `munmap` during normal execution; virtual addresses remain mapped to avoid VMA fragmentation.
  2. In Go 1.12, Go defaulted to `MADV_FREE` on Linux 4.5+ because it avoided immediate page clearing.
  3. However, in **Go 1.16**, the Go team **reverted the default back to `MADV_DONTNEED`** on Linux (`debug.madvdontneed = 1` in `runtime1.go`). The rationale: `MADV_FREE` causes memory monitoring tools (`top`, Prometheus, Kubernetes OOM estimators) to report high RSS because the kernel only frees the pages under memory pressure, causing widespread confusion.
- **Actionable Plan:** Unify all 6 articles: Go uses `madvise(MADV_DONTNEED)` as the canonical default since Go 1.16; `MADV_FREE` is available via `GODEBUG=madvdontneed=0`.

### Cluster B: Netpoller Architecture & Epoll State Tracking
- **Files Involved:** Articles 3, 36, 38, 62
- **The Issue:**
  - Article 36 & 38 say Go uses `EPOLLONESHOT` and `EV_ONESHOT`, requiring explicit re-arming.
  - Article 62 says Go does *not* use `EPOLLONESHOT`, but instead modifies descriptors with `EPOLL_CTL_MOD` or unregisters them with `EPOLL_CTL_DEL`.
- **The Ground Truth:**
  Both explanations are wrong. Go uses **Edge-Triggered (`EPOLLET` / `_EV_CLEAR`)** registration. Sockets are added once in `netpollopen()`, never re-armed via `epoll_ctl`, and removed only in `netpollclose()`.
- **Actionable Plan:** Synchronize all 4 articles with `/usr/local/go/src/runtime/netpoll_epoll.go`.

### Cluster C: G-M-P Blocking Syscalls vs Network I/O
- **Files Involved:** Articles 2, 5, 8, 9, 22, 62
- **The Issue:**
  - Article 22 portrays file/network syscalls as detaching goroutines from thread M via `gopark` and `munpin()`, claiming thread M keeps running other goroutines.
  - Article 62 correctly notes that thread M blocks in the OS kernel and processor P is handed off.
- **The Ground Truth:**
  An OS thread blocked in a kernel syscall cannot execute anything in userspace. `P` is detached via `handoffp` and acquired by a different thread `M2`. Network I/O does not make blocking syscalls at all — it parks the goroutine and registers the fd in the netpoller.
- **Actionable Plan:** Bring Article 22 into strict alignment with Article 62 and standard Go scheduler architecture.

### Cluster D: Cgroups, Containers, and `GOMAXPROCS` Evolution
- **Files Involved:** Articles 8, 11, 52, 53, 54
- **The Issue:**

  - Articles 8 and 52 state that Go ignores container limits and requires `uber-go/automaxprocs`.

- **The Ground Truth:**
  1. Go respects CPU affinity masks (`sched_getaffinity`), setting `GOMAXPROCS` accordingly.

### Cluster E: Linux Credentials, Multithreading, and `setuid`
- **Files Involved:** Articles 55, 56, 57, 58
- **The Issue:**
  Article 56 provides uncompilable code calling `os.Setuid` / `os.Setgid`, while mentioning `syscall.AllThreadsSyscall`.
- **The Ground Truth:**

Standard C glibc synchronizes signals across threads (`SIGSETXID`), but Go bypasses libc. Go 1.16 introduced `syscall.AllThreadsSyscall` to send the `setuid` syscall to all OS threads managed by the runtime.

# 7. NUMERICAL & ABSOLUTE CLAIMS

### High-Risk Numerical Claims Requiring Qualification

1. **"100 000 горутин потребуют всего ~250 МБ оперативной памяти"** (Art 5, line 185)
   - *Status:* CONTEXT-DEPENDENT.
   - *Reality:* 100,000 × 2 KB = 200 MB (stack only) + ~40–50 MB for runtime `g` structs, mspan headers, and scheduler bookkeeping. This holds true **only for completely idle/sleeping goroutines**. Active goroutines will allocate heap and grow stacks, consuming far more memory.
   - *Recommendation:* Explicitly label as "overhead for 100k *idle* goroutines".
2. **"Стоимость переключения горутины: ~100–200 наносекунд (в 20–50 раз быстрее, чем тред ОС)"** (Art 9, line 150)
   - *Status:* CONTEXT-DEPENDENT.
   - *Reality:* Goroutine switches can take 10–50 ns in optimal L1 cache conditions or 200+ ns under NUMA/cache eviction. OS thread switches typically cost 1–3 μs (not 15 μs unless heavy TLB shootdowns occur).
   - *Recommendation:* Present as "typical orders of magnitude on modern x86_64 servers", not as an invariant speedup constant.
3. **"Для 30 ГБ памяти размер таблиц страниц составляет около 60 МБ! Копирование 60 МБ ... пауза до 20–50 мс"** (Art 6, line 160)
   - *Status:* TECHNICALLY SOUND ESTIMATE.
   - *Reality:* 30 GB / 4 KB = 7,864,320 PTEs × 8 bytes ≈ 62.9 MB of leaf page tables. Copying and write-protecting 60 MB of page tables during `fork()` under memory lock can indeed induce 20–50 ms latency spikes.
   - *Recommendation:* Keep intact; it effectively illustrates why Redis background saving (BGSAVE) experiences latency spikes.
4. **"Лимит размера стека eBPF в 512 байт"** (Art 61, line 140)
   - *Status:* EXACT ARCHITECTURAL CONSTANT.
   - *Reality:* Hardcoded BPF verifier limit (`MAX_BPF_STACK = 512`). Keep intact.
5. **"Лимит тредов рантайма по умолчанию 10 000"** (Art 2, line 140)
   - *Status:* EXACT RUNTIME CONSTANT.
   - *Reality:* Defined by `sched.maxmcount = 10000` in Go runtime. Keep intact.

# 9. LIKELY OUT-OF-DATE AREAS

1. **io_uring in Go Standard Library (Articles 22, 35, 45, 60):**
   Textbook articles frequently reference `io_uring` as the impending or already adopted replacement for `epoll` in Go. In reality, security vulnerabilities in `io_uring` and complexity in Go's cooperative scheduler have kept standard library integration on hold. All claims asserting standard Go uses `io_uring` are stale/untrue.
2. **CFS Cgroup Quota Reading (Article 54):**
   Claiming this was added in Go 1.13 is completely stale. The actual transition happened in Go 1.25.
3. **MADV_FREE as the Primary Reclaim Mechanism (Articles 2, 15):**
   Articles describing `MADV_FREE` as the active default on Linux are reflecting the Go 1.12–1.15 era. In Go 1.16+, `MADV_DONTNEED` is the default.
