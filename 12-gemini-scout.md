### Кандидат 1: Ложный миф об изоляции сбоев бэкенда в архитектуре PostgreSQL
* **article/section:** `06. PostgreSQL/1. Архитектура PostgreSQL.md` / `## 1. Архитектурная модель: Процессы, а не потоки` (строки 59–63)
* **claim:**  
  > *«Если один backend-процесс терпит крах (например, падает по SIGSEGV из-за ошибки в сложном C-расширении или исчерпания памяти запроса), погибает исключительно этот изолированный процесс. Операционная система бережно изолирует адресные пространства. Сетевое соединение одного клиента обрывается, но сам сервер, Postmaster и сотни остальных клиентов продолжают функционировать без единой паузы».*
* **why it needs checking:** Это грубейшая фактологическая ошибка об архитектуре PostgreSQL, создающая опасную иллюзию отказоустойчивости.
  1. В PostgreSQL все обслуживающие бэкенды используют единый общий сегмент разделяемой памяти (Shared Memory: буферный пул, блокировки LWLock, состояние транзакций `ProcArray`, WAL-буферы).
  2. Если процесс падает аварийно (`SIGSEGV`, `SIGBUS`, `SIGILL` или `kill -9`), ядро ОС не очищает разделяемую память. Postmaster детектирует падение дочернего процесса через `SIGCHLD` и признает состояние разделяемой памяти потенциально поврежденным (corrupted), так как упавший процесс мог держать спинлоки или модифицировать структуры данных в момент гибели.
  3. В этот же момент Postmaster отправляет сигнал **`SIGQUIT` всем остальным работающим бэкендам**, принудительно обрывая сессии всех клиентов, удаляет сегмент разделяемой памяти, инициализирует его заново и запускает процедуру **Crash Recovery из WAL (Redo)**.
  4. Аварийное падение хотя бы одного бэкенда в PostgreSQL неизбежно влечет за собой **полный перезапуск всего сервера базы данных** со сбросом всех клиентских соединений.
* **evidence/source needed:** Документация PostgreSQL: Глава *Server Administration -> Signaling the Server*; исходный код PostgreSQL `src/backend/postmaster/postmaster.c` (функции `LogChildExit`, `HandleChildCrash`).
* **priority:** 🔴 **High**

### Кандидат 2: Катастрофический баг пула соединений в коде Two-Phase Commit (XA) на Go
* **article/section:** `08. Распределенные базы данных/9. Two Phase Commit.md` / `### Координатор на Go` (строки 141–187)
* **claim:**  
  В примере реализации 2PC-координатора на Go команды XA выполняются напрямую через интерфейс пула `*sql.DB`:
  ```go
  // Фаза Prepare
  _, err1 := db1.ExecContext(ctx, "XA START "+xid)
  _, err2 := db1.ExecContext(ctx, "UPDATE accounts SET balance = balance - 100 WHERE id = 1")
  _, err3 := db1.ExecContext(ctx, "XA END "+xid)
  _, err4 := db1.ExecContext(ctx, "XA PREPARE "+xid)
  ...
  // Фаза Commit
  _, err := db1.ExecContext(ctx, "XA COMMIT "+xid)
  ```
* **why it needs checking:** Данный листинг кода фундаментально неработоспособен из-за механики пула `database/sql`:
  1. Переменная `db1` имеет тип `*sql.DB`, представляющий собой пул соединений (Connection Pool).
  2. Каждый отдельный вызов `db1.ExecContext(...)` берет случайное свободное TCP-соединение из пула, отправляет запрос и **немедленно возвращает соединение обратно в пул**!
  3. В результате `XA START` выполняется на соединении A, последующий `UPDATE` — на соединении B, а `XA END` — на соединении C.
  4. На шаге `XA END` или `XA PREPARE` СУБД (PostgreSQL/MySQL) вернет фатальную ошибку протокола: `ERROR 1397 (XAE04): XAER_NOTA: Unknown XID`, так как на соединении B транзакция XA вообще не начиналась.
  5. Для выполнения связанных последовательностей SQL-команд вне стандартного `tx := db.BeginTx(...)` в Go категорически необходимо явно захватывать выделенное соединение через **`conn, err := db.Conn(ctx)`** и выполнять все фазы XA через `conn.ExecContext(ctx, ...)`.
* **evidence/source needed:** Документация пакета Go `database/sql` (`DB.Conn` vs `DB.Exec`); спецификация MySQL XA Transactions; спецификация PostgreSQL Prepared Transactions (`PREPARE TRANSACTION`).
* **priority:** 🔴 **High**

### Кандидат 3: Состояние гонки и потеря изоляции в Outbox Pattern (`FOR UPDATE SKIP LOCKED` вне транзакции)
* **article/section:** `10. Практика и архитектура/11. Outbox pattern.md` / `### 1. Polling Publisher на Go` (строки 154–178)
* **claim:**  
  ```go
  func (p *OutboxPoller) ProcessEvents(ctx context.Context) error {
      // 1. Читаем пачку событий с блокировкой
      query := `
          SELECT id, aggregate_type, aggregate_id, type, payload 
          FROM outbox_events 
          ORDER BY id 
          LIMIT 100 
          FOR UPDATE SKIP LOCKED
      `
      rows, err := p.db.QueryContext(ctx, query)
      ...
      // 2. Отправляем в брокер
      for _, event := range events {
          err = p.broker.Publish(ctx, event.Type, event.Payload)
          ...
      }
      // 3. Удаляем отправленные
      deleteQuery := `DELETE FROM outbox_events WHERE id = ANY($1)`
      _, err = p.db.ExecContext(ctx, deleteQuery, pq.Array(ids))
  }
  ```
* **why it needs checking:** Листинг содержит критический антипаттерн конкурентного программирования баз данных:
  1. Запрос `SELECT ... FOR UPDATE SKIP LOCKED` вызывается напрямую через `p.db.QueryContext(...)` **без открытой транзакции**.
  2. В реляционных базах (PostgreSQL, MySQL) любой запрос вне явной транзакции выполняется в режиме `autocommit`. Как только чтение строк завершено и курсор закрыт, транзакция немедленно автоматически фиксируется, а все строчные блокировки `FOR UPDATE` **мгновенно снимаются**!
  3. Если в кластере запущены два параллельных инстанса воркера, второй воркер выполнит `SELECT ... FOR UPDATE SKIP LOCKED` через 1 миллисекунду после первого, захватит **ровно те же самые 100 строк**, и оба воркера отправят дублирующие сообщения в Kafka/RabbitMQ!
  4. Паттерн `FOR UPDATE SKIP LOCKED` имеет смысл только тогда, когда выборка, публикация и удаление (или обновление статуса) происходят внутри единого блока `tx, err := p.db.BeginTx(ctx, nil)`.
* **evidence/source needed:** Документация PostgreSQL: *Explicit Locking -> Row-Level Locks*; Martin Kleppmann, "Designing Data-Intensive Applications".
* **priority:** 🔴 **High**

### Кандидат 4: Несуществующий синтаксис Go, выдуманные ошибки и ложное поведение Connection Pool
* **article/section:** `10. Практика и архитектура/2. Connection pool.md` (строки 40, 78, 173–197, 307, 345–353)
* **claim:**  
  1. В описании внутреннего устройства `sql.DB`:
     ```go
     numOpen atomic.Int[int] // актуальное число открытых сокетов
     ```
  2. В описании горутины открытия соединений `connectionOpener`:
     > *«Она слушает канал запросов на новые подключения. Как только в канале появляется сигнал... горутина не блокируется, а инициирует асинхронный коннект к СУБД: `go db.openNewConnection()`».*
  3. В описании обработки исчерпания пула:
     > *«Приложение получает ошибку `sql: connection pool exhausted` или `sql: connection pool timeout`».*
* **why it needs checking:** В тексте допущены сразу четыре технические ошибки в описании стандартной библиотеки Go:
  1. **Синтаксическая ошибка в Go:** Тип `atomic.Int` в стандартном пакете `sync/atomic` не является generic-типом (нет параметров типа `[int]`). В Go есть конкретные типы: `atomic.Int64`, `atomic.Int32`, `atomic.Uint64`, `atomic.Pointer[T]`. При этом в реальном исходном коде `database/sql` поле `numOpen` — это обычный примитивный `int`, защищенный мьютексом `db.mu`!
  2. **Ложное описание многопоточности:** Горутина `connectionOpener` в стандартной библиотеке Go крутится в синхронном цикле `for req := range db.openerCh` и открывает соединения строго последовательно, без порождения неконтролируемых горутин `go db.openNewConnection()`.
  3. **Несуществующие ошибки:** В пакете `database/sql` не существует ошибок с текстом `sql: connection pool exhausted` или `sql: connection pool timeout`.
  4. **Поведение при исчерпании пула:** Когда лимит соединений исчерпан (`SetMaxOpenConns`), запрос ставит горутину в очередь ожидания и блокируется до тех пор, пока соединение не освободится, либо пока не истечет контекст запроса. При таймауте возвращается стандартная ошибка `context.DeadlineExceeded`, а не ошибка базы данных.
* **evidence/source needed:** Исходный код стандартной библиотеки Go: `src/database/sql/sql.go` (структура `DB`, методы `connectionOpener`, `conn`).
* **priority:** 🔴 **High**

### Кандидат 5: Ложное утверждение об использовании предикатных блокировок в `REPEATABLE READ` PostgreSQL
* **article/section:** `05. Транзакции и внутренности/3. Read Committed, Repeatable Read, Serializable.md` (строки 33, 128–130, 309)
* **claim:**  
  > *«PostgreSQL на уровне Repeatable Read использует предикатные блокировки (predicate locking)... Если конкурирующая транзакция делает INSERT строки, попадающей в диапазон WHERE первой транзакции, возникает конфликт сериализации (could not serialize access)».*
* **why it needs checking:** Это грубое искажение теории транзакций и архитектуры PostgreSQL, противоречащее даже соседней статье курса (`05. Транзакции и внутренности/4. Уровни изоляции на практике.md`):
  1. В PostgreSQL уровень `REPEATABLE READ` реализован исключительно на базе **Snapshot Isolation (MVCC)** со снимком данных на момент первого запроса транзакции.
  2. `REPEATABLE READ` в PostgreSQL **вообще не использует предикатные блокировки**!
  3. Если параллельная транзакция вставляет новые строки (`INSERT`), транзакция на уровне `REPEATABLE READ` просто не видит эти строки в своем снимке MVCC. Никаких конфликтов сериализации, прерываний транзакций или блокировок при обычном чтении и конкурентном `INSERT` **не возникает**!
  4. Предикатные блокировки без блокировки данных (SIREAD locks) и выявление циклов опасных зависимостей (rw-antidependencies) используются **исключительно на уровне `SERIALIZABLE` (Serializable Snapshot Isolation — SSI)**.
* **evidence/source needed:** Документация PostgreSQL: Глава 13 *Concurrency Control -> Transaction Isolation*; научная статья Michael Cahill et al., "Serializable Isolation for Snapshot Databases".
* **priority:** 🔴 **High**

### Кандидат 6: Миф о зависании открытых транзакций при панике в Go
* **article/section:** `10. Практика и архитектура/2. Connection pool.md` (строки 337–358) и `1. Работа с БД в Go. database_sql.md` (строки 98–107, 201–208)
* **claim:**  
  > *«Если в коде между BeginTx и Commit происходит паника (panic), и вы не обработаете её через recover(), транзакция никогда не завершится, а соединение останется в состоянии inUse навсегда, вызвав утечку соединений в пуле».*  
  В качестве единственного спасения предлагается сложная конструкция:
  ```go
  defer func() {
      if p := recover(); p != nil {
          tx.Rollback()
          panic(p)
      }
  }()
  ```
* **why it needs checking:** Утверждение демонстрирует глубокое заблуждение относительно рантайма языка Go:
  1. Когда в Go возникает `panic()`, рантайм начинает размотку стека (Stack Unwinding) текущей горутины.
  2. Во время размотки стека **гарантированно выполняются все зарегистрированные отложенные функции (`defer`)**!
  3. Идиоматичный, канонический паттерн работы с транзакциями в Go:
     ```go
     tx, err := db.BeginTx(ctx, nil)
     if err != nil { return err }
     defer tx.Rollback() // Безопасно вызывается и при return, и при панике!
     ```
  4. Если произойдет паника, `defer tx.Rollback()` отработает безукоризненно, пошлет в сокет откат транзакции и вернет TCP-соединение обратно в пул свободных соединений.
  5. Громоздкая обертка с ручным `recover()` и повторным `panic(p)` не требуется для освобождения соединения и создает антипаттерн «мусорного кода», который в реальных проектах приводит к ошибкам проглатывания стектрейса.
* **evidence/source needed:** Спецификация языка Go (The Go Programming Language Specification -> Defer statements, Handling panics); документация пакета `database/sql`.
* **priority:** 🔴 **High**

### Кандидат 7: Опасное заблуждение об обеспечении уникальности в ClickHouse `ReplacingMergeTree`
* **article/section:** `09. NoSQL базы/11. ClickHouse. OLAP база.md` / `## 3. Движки семейства MergeTree` (строка 67)
* **claim:**  
  > *«ReplacingMergeTree: удаляет дубликаты по первичному ключу. Если вам нужна уникальность, используйте этот движок».*
* **why it needs checking:** Это классическая и крайне опасная ловушка для новичков, переходящих в OLAP из мира реляционных баз данных:
  1. `ReplacingMergeTree` в ClickHouse **НЕ гарантирует уникальность данных** ни при вставке (`INSERT`), ни при обычном чтении (`SELECT`)!
  2. При вставке ClickHouse сохраняет данные в независимые несжатые парты (Parts). Дублирующиеся записи по первичному ключу физически присутствуют в таблице.
  3. Схлопывание дубликатов происходит исключительно во время **фонового слияния партов (Background Merges)**, которое запускается планировщиком в недетерминированное время и может не произойти никогда для отдельных кусков данных.
  4. Обычный запрос `SELECT * FROM table` возвратит **все дубликаты**.
  5. Чтобы гарантированно отфильтровать дубликаты при чтении, разработчик обязан либо явно использовать модификатор `SELECT ... FROM table FINAL` (что критически замедляет аналитические запросы), либо использовать агрегатные функции (`argMax`).
  6. Называть `ReplacingMergeTree` средством «обеспечения уникальности» без этого важнейшего предупреждения категорически недопустимо.
* **evidence/source needed:** Официальная документация ClickHouse: *Engines -> MergeTree Family -> ReplacingMergeTree*; Alexey Milovidov, ClickHouse Architecture Talks.
* **priority:** 🔴 **High**

### Кандидат 8: Фантастическое смешение концепций — планировщик G-M-P языка Go внутри демона Valkey/Redis
* **article/section:** `09. NoSQL базы/6. Valkey.md` / `## Внутренняя архитектура: Под капотом форка` (строка 55)
* **claim:**  
  > *«Архитектурные нововведения Valkey:  
  > 1. Модель G-M-P внутри сервера (в контексте потоков — main thread + I/O threads)...»*
* **why it needs checking:** Абсурдная терминологическая путаница:
  1. Valkey (форк Redis от Linux Foundation) написан на чистом языке **C** (C99/C11).

### Кандидат 9: Неверный токен ограждения (Fencing Token) в распределенных блокировках etcd
* **article/section:** `08. Распределенные базы данных/11. Distributed locks.md` / `### Реализация в Go` (строка 160)
* **claim:**  
  ```go
  // Получаем уникальный fencing token (монотонно растущий ID сессии/ревизии)
  fencingToken := int64(session.Lease())
  log.Printf("Получена блокировка! Fencing token (Lease ID): %d", fencingToken)
  ```
* **why it needs checking:** Грубая ошибка реализации паттерна Fencing Token Мартина Клеппмана:
  1. Идентификатор аренды (`session.Lease()`) в etcd генерируется на базе случайного 64-битного числа или хэша узла при создании сессии.

  3. Внешняя система хранения данных, сверяющая fencing token (`UPDATE ... WHERE fence_token > stored_token`), ошибочно отклонит операцию легитимного клиента.
  4. Истинным монотонно возрастающим токеном в распределенном мьютексе etcd является **ревизия создания ключа мьютекса** в raft-журнале: `mutex.Header().Revision`.
* **evidence/source needed:** Martin Kleppmann, "How to do distributed locking" (Fencing Tokens); документация `go.etcd.io/etcd/client/v3/concurrency`.

## 🔍 Системные белые пятна и архитектурные упущения (Blind Spots)

В ходе анализа выявлены 6 критических системных тем, без которых понимание промышленной разработки бэкенда на Go остается неполным:

1. **Конфликт PgBouncer в режиме Transaction Pooling с Prepared Statements:**  
   В современных высоконагруженных системах на PostgreSQL промышленным стандартом является использование пулера **PgBouncer** в режиме `pool_mode = transaction`. Однако если Go-приложение использует `database/sql` или `pgx` в стандартном режиме с подготовленными выражениями (Prepared Statements), возникает критический сбой: бэкенды PgBouncer меняются от транзакции к транзакции, и подготовленный стейтмент перестает существовать (ошибка `prepared statement does not exist`). Необходимо подробно объяснить режимы работы драйверов (`prefer_simple_protocol` в `pgx`, именованные vs неименованные стейтменты) и поддержку server-side prepared statements в PgBouncer 1.21+.

2. **Зависание транзакций (In-Doubt Transactions) при отказе координатора в 2PC:**  
   В статье по 2PC рассмотрен исключительно идеальный сценарий (Happy Path). Полностью упущен ключевой недостаток протокола двухфазной фиксации — его **блокирующая природа**. Если координатор падает после того, как участники ответили `PREPARED`, транзакции на узлах базы зависают в состоянии неопределенности (In-Doubt), удерживая эксклюзивные блокировки таблиц и строк до бесконечности. Необходимо разобрать эвристические решения (Heuristic Commit/Rollback) и архитектуру распределенного журнала транзакций координатора.

3. **Аварийное исчерпание диска из-за слотов логической репликации в PostgreSQL:**  
   В материалах по репликации и паттернам CDC (Debezium / Outbox) упущена классическая авария: если консьюмер слота репликации (сервис на Go, вычитывающий WAL) останавливается или начинает отставать, PostgreSQL **прекращает удалять старые сегменты WAL** в каталоге `pg_wal`. Это неминуемо приводит к 100% заполнению дискового пространства и аварийной остановке всего кластера базы данных. Обязательно раскрыть спасительный параметр `max_slot_wal_keep_size` (появившийся в PostgreSQL 13).

4. **Методология Jepsen-тестирования распределенных систем:**  
   В подразделе о распределенных БД и консенсусе Raft подробно описаны теоретические аспекты, но отсутствует упоминание **Jepsen** (тестового фреймворка Кайла Кингсбери). Это де-факто мировой стандарт верификации гарантий консистентности (Linearizability, Strict Serializability) распределенных баз данных при разделении сети (Network Partition) и сбоях дисков.

5. **Катастрофическое влияние Transparent Huge Pages (THP) на задержки СУБД:**  
   Упущен важнейший инфраструктурный аспект настройки ядра Linux для СУБД (PostgreSQL, Redis, ClickHouse). Включение Transparent Huge Pages (`transparent_hugepage=always`) вызывает в многопоточных базах периодические зависания на десятки миллисекунд (Stop-the-world latency spikes) из-за дефрагментации страниц памяти ядром (`khugepaged`). Базам данных требуется режим `madvise` или полное отключение THP.

6. **Оптимизация GIN-индексов для JSONB (`jsonb_path_ops` vs `jsonb_ops`):**  
   В главе по NoSQL возможностям PostgreSQL подробно разбирается JSONB, но упущена ключевая разница операторных классов GIN-индекса: стандартный класс `jsonb_ops` индексирует и ключи, и значения, приводя к раздуванию индекса на гигабайты. Специализированный класс `jsonb_path_ops` хэширует полные пути атрибутов, благодаря чему индекс занимает в 2–3 раза меньше места на диске и работает значительно быстрее для проверок вхождения (`@>`).
