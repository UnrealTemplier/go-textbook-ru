### Кандидат 1: Ложное утверждение о потере номеров строк при `-ldflags="-s -w"` и прямое противоречие между статьями 7 и 44
* **article/section:** `44. Linker и Build Modes.md` / `### 1. Оптимизация размера: Флаги -s и -w` vs `7. Устройство бинарника Go.md` / `### Шаг 1: Удаление DWARF и таблицы символов`
* **claim:** 
  - В статье 44 утверждается: *«Флаги `-s -w` уменьшают физический размер бинарного файла на 25–35% без какого-либо влияния на скорость исполнения кода! (Единственный компромисс: если вызов panic прервет программу, в стектрейсе будут выводиться только шестнадцатеричные адреса функций вместо читаемых номеров строк)»*.
  - В статье 7 утверждается противоположное: *«Эта процедура абсолютно безопасна для production-окружения: размер бинарника сокращается на 25–35%, при этом секция `.gopclntab` остается нетронутой! Ваши паники по-прежнему будут печатать понятный стек-трейс с номерами строк, а сборщик мусора и pprof продолжат функционировать в штатном режиме»*.
* **why it needs checking:** 
  1. Это прямое, взаимоисключающее противоречие внутри одного тематического модуля.
  2. Утверждение статьи 44 **фактически неверно**: флаг `-s` вырезает стандартную таблицу символов ELF/Mach-O/PE (`.symtab`), а `-w` отключает отладочную информацию DWARF (`.debug_*`). Однако стек-трейсы паник в Go формируются рантаймом **не из DWARF**, а из служебной таблицы соответствия адресов инструкций строкам исходного кода — **`.gopclntab`** (`runtime.gopclntab`). Секция `.gopclntab` сохраняется при сборке с `-s -w`, и даже полностью «подрезанный» бинарник при панике печатает полные имена функций, пути к исходным файлам и точные номера строк.
* **evidence/source needed:** `src/runtime/symtab.go`, тестовый запуск скомпилированного с `-ldflags="-s -w"` бинарника с вызовом `panic()`.
* **priority:** 🔴 **High**

### Кандидат 2: Нарушение аппаратного выравнивания памяти в примере и диаграмме Tiny Allocator
* **article/section:** `22. Tiny Allocator и маленькие объекты.md` / `## Механика упаковки (Tiny Block)` и диаграмма `BLOCK`
* **claim:** Листинг и схема утверждают, что после записи 1-байтового `bool` по смещению 0 следующий 4-байтовый `int32` размещается непосредственно по смещению 1:
  > *«Он размещает наш bool по смещению 0, устанавливает значение tinyoffset = 1... Когда та же горутина следом запрашивает еще один bool, рантайм... размещает второй bool в тот же самый блок по смещению 1 и инкрементирует tinyoffset = 2... SLOT1: bool 1 байт (смещение 0), SLOT2: int32 4 байта (смещение 1..4), SLOT3: Свободно 11 байт (смещение 5..15)»*.
* **why it needs checking:** Это грубое нарушение законов выравнивания памяти (Memory Alignment). В исходном коде аллокатора `src/runtime/malloc.go` смещение `tinyoffset` перед размещением объекта принудительно выравнивается под требования типа:
  ```go
  if size&7 == 0 { off = alignUp(off, 8) }
  else if size&3 == 0 { off = alignUp(off, 4) }
  else if size&1 == 0 { off = alignUp(off, 2) }
  ```
  Для 4-байтового `int32` (`size&3 == 0`) вызов `alignUp(1, 4)` сдвигает смещение на **4**, оставляя байты 1, 2 и 3 в качестве внутреннего паддинга (padding). Размещение `int32` по нечетному адресу (смещение 1) на архитектурах с жесткими требованиями к выравниванию (ARM, MIPS) привело бы к аппаратному сбою (Alignment Fault / SIGBUS), а на x86 — к расщепленному чтению шины памяти. Текст и схема вводят читателя в заблуждение относительно логики упаковщика.
* **evidence/source needed:** `src/runtime/malloc.go` (блок `c.tinyoffset` и `alignUp`).
* **priority:** 🔴 **High**

### Кандидат 3: Противоречие в коде роста слайса: «Выведет 4? Нет!» при фактическом выводе 4
* **article/section:** `30. Рост slice. append, realloc и copy.md` / `## 4. Скрытый хак: Size Classes и выравнивание памяти`
* **claim:** Листинг приводит код с комментарием:
  ```go
  s := make([]int, 0) // cap = 0
  s = append(s, 1)    // len = 1, cap = 1 (всё логично)
  s = append(s, 2)    // len = 2, cap = 2 (удвоилось)
  s = append(s, 3)    // len = 3, требуемый cap = 4. А какой будет реальный?
  fmt.Println(cap(s)) // Выведет 4? Нет!
  ```
  При этом в тексте ниже автор сам делает расчет и пишет: *«Рантайм выделяет блок ровно на 32 байта, и вместимость фиксируется как 4»*.
* **why it needs checking:** 
  1. Комментарий `Выведет 4? Нет!` прямо опровергается текстом этой же статьи, где доказано, что вместимость будет равна 4.
  2. Фактическое поведение в Go 1.18+ еще сильнее расходится с комментариями в коде: для пустого слайса `make([]int, 0)` первый же вызов `append(s, 1)` на 64-битной системе аллоцирует память сразу под класс размеров 32 байта, поэтому `cap(s)` становится равен **4 уже на первом шаге** (после добавления числа 1)! Комментарии `cap = 1` и `cap = 2` не соответствуют реальному выполнению программы.
* **evidence/source needed:** Запуск фрагмента в `go run` на Go 1.20+; исходный код `src/runtime/slice.go` (`growslice`).
* **priority:** 🔴 **High**

### Кандидат 4: Смешение ABIInternal и ABI0 в ассемблерном листинге функции `Add`
* **article/section:** `5. Go assembler и внутренний ассемблерный синтаксис.md` / `## Анатомия ассемблерной функции`
* **claim:** Листинг объявляет функцию со служебным флагом `ABIInternal`, но тело функции использует стековые инструкции устаревшего `ABI0`:
  ```asm
  TEXT "".Add(SB), NOSPLIT|ABIInternal, $0-24
      FUNCDATA $0, gclocals·g2BeySu+wFnoycgXfElmcg==(SB)
      FUNCDATA $1, gclocals·g2BeySu+wFnoycgXfElmcg==(SB)
      MOVQ "".a+8(SP), AX
      MOVQ "".b+16(SP), CX
      ADDQ CX, AX
      MOVQ AX, "".~r2+24(SP)
      RET
  ```
* **why it needs checking:** 
  1. В заголовке указан флаг `ABIInternal`, но в реальном Go (начиная с Go 1.17) функция `Add(a, b int) int` под `ABIInternal` на amd64 принимает параметры в регистрах `AX` и `BX`, а возвращает результат в регистре `AX`. Ее тело состоит из единственной инструкции `ADDQ BX, AX` и не содержит никаких чтений и записей в стек `(SP)`!
  2. Даже с точки зрения устаревшего `ABI0` адресация через псевдорегистр `SP` со смещением и именем символа (`"".a+8(SP)`) в синтаксисе Plan 9 означает локальную переменную функции, тогда как входящие параметры адресуются через виртуальный фрейм-поинтер `FP` (`a+0(FP)`, `b+8(FP)`).
  3. Дескриптор `$0-24` резервирует 24 байта под стек аргументов, что также принадлежит конвенции ABI0.
* **evidence/source needed:** Дизассемблирование через `go tool compile -S` функции `func Add(a, b int) int { return a + b }`; Go Internal ABI Specification.
* **priority:** 🔴 **High**

### Кандидат 5: Ошибочное определение GCshape как типов «одинакового размера в памяти»
* **article/section:** `3. Фазы компиляции. Lexer, Parser, Type Checker, SSA.md` / `## 3. Type Checking (Проверка типов)`
* **claim:** «для типов одинакового размера в памяти (GCshape, например все указатели) генерируется одна общая функция с передачей словаря типов, а для примитивов (`int`, `float64`) создаются мономорфные специализированные копии».
* **why it needs checking:** Определение GCshape как просто типов «одинакового размера» категорически неверно. Например, типы `int64` и `*int` на 64-битной платформе имеют абсолютно одинаковый размер (8 байт), но `*int` отслеживается сборщиком мусора (pointer bitmap содержит 1), а `int64` является скаляром (pointer bitmap 0). Они имеют принципиально разные формы для сборщика мусора и никогда не могут объединяться в один GCshape! Концепция GCshape группирует типы, которые имеют одинаковый размер, одинаковое выравнивание **и идентичный шаблон указателей для GC** (например, все указатели на объекты приводятся к единой форме `go.shape.*uint8`).
* **evidence/source needed:** Go Generics Design Doc (`go.dev/design/43651-type-parameters`); `src/cmd/compile/internal/typecheck/subr.go`.
* **priority:** 🔴 **High**

### Кандидат 6: Устаревший пролог проверки стека через `MOVQ (TLS), CX` и противоречие со статьей 43
* **article/section:** `11. Стек горутины. Рост и shrink стека.md` / `## Как компилятор определяет переполнение?` vs `43. Preemption. Как Go останавливает горутины.md`
* **claim:** 
  - В статье 11 приводится устаревший пролог функции:
    ```asm
    MOVQ (TLS), CX              // Загрузка указателя на текущую горутину 'g'
    CMPQ SP, 16(CX)             // Сравнение SP с g.stackguard0
    JLS  morestack              // Если места мало — прыжок в morestack
    ```
  - В статье 43 того же модуля приводится современный пролог:
    ```asm
    CMPQ SP, 16(R14) // Сравнение SP со значением stackguard0
    JBE  morestack   // Если SP < stackguard0, прыгаем в выделение памяти
    ```
* **why it needs checking:** 
  1. В современном Go (Go 1.17+ ABIInternal) на архитектуре amd64 указатель на текущую горутину `g` **постоянно закреплен за аппаратным регистром `R14`** (на arm64 — за `R28`). Чтение из сегмента потоковой памяти `MOVQ (TLS), CX` на каждом входе в функцию больше не производится — это рудимент эпохи Go 1.0–1.16 (ABI0).
  2. Разнобой между статьями 11 и 43 одного модуля сбивает читателя с толку.
* **evidence/source needed:** `src/cmd/compile/internal/amd64/ggen.go`; вывод `go tool compile -S`.
* **priority:** 🔴 **High**

### Кандидат 7: Заниженное число Size Classes (67 вместо 68) и Span Classes (134 вместо 136)
* **article/section:** `21. Аллокатор памяти Go. mcache, mcentral, mheap.md` / `### 1. mcache` и `### 2. mcentral`
* **claim:** «Внутри mcache хранится массив активных указателей на mspan... для каждого из 67 классов размеров в mcache выделено по два спана... Итого $67 \times 2 = 134$ спана прямо под рукой. В рантайме существует ровно 67 центральных менеджеров mcentral — по одному на каждый класс размера (точнее, по паре для scan и noscan)».
* **why it needs checking:** В рантайме Go константа `NumSizeClasses` строго равна **68** (индексы от 0 до 67, где 0 зарезервирован под крупные объекты и пустые спаны, а 1..67 — классы малых объектов). Соответственно, число Span Classes равно `NumSizeClasses << 1` = **136**, а не 134! Массив `central` в структуре `mheap` имеет длину 136 (`central [136]mcentral`), и массив `alloc` в `mcache` также содержит ровно 136 указателей на `mspan`. Утверждение про 67 менеджеров и 134 спана упускает базовый нулевой класс размера.
* **evidence/source needed:** `src/internal/runtime/gc/sizeclasses.go` (`NumSizeClasses = 68`); `src/runtime/mheap.go` (`numSpanClasses = gc.NumSizeClasses << 1`); `src/runtime/mcache.go`.
* **priority:** 🔴 **High**

### Кандидат 8: Утверждение о жесткой привязке `g0` исключительно к потоку `m0`
* **article/section:** `1. Обзор раздела. Что происходит внутри Go после запуска программы.md` / `## Фаза 1. Ассемблерный бутстрап (rt0_go)`
* **claim:** «`g0 (Goroutine 0)` — системная горутина, жестко привязанная к `m0`... На стеке `g0` выполняются все системные операции: переключение контекста планировщика... Пользовательский код никогда не выполняется на стеке `g0`».
* **why it needs checking:** В рантайме Go горутина `g0` есть у **каждого** рабочего потока операционной системы (`M`), а не только у `m0` (поле `m.g0` определено в структуре `m`). `m0` — это просто первый (первичный) поток ОС, запускающий `rt0_go`, для которого `g0` выделена статически в секции данных. Все последующие потоки `M`, создаваемые рантаймом по ходу работы (`newm`), создают свой собственный экземпляр `g0` с собственным системным стеком. Формулировка статьи создает ложное ощущение, что в программе существует только одна `g0`.
* **evidence/source needed:** `src/runtime/runtime2.go` (структура `type m struct { g0 *g ... }`); `src/runtime/proc.go` (`allocm`).
* **priority:** 🟡 **Medium**

### Кандидат 9: Неточный текст ошибки и поведение `runtime.Goexit()` в `main.main`
* **article/section:** `12. Как создается и завершается goroutine.md` / `> [!tip] Собеседование: Что делает функция runtime.Goexit()?`
* **claim:** «Однако если `runtime.Goexit()` вызывается внутри главной горутины `main.main`, программа аварийно упадет с паникой `fatal error: no goroutines (main goroutine was killed by Goexit)`, если в системе больше нет других активных горутин».
* **why it needs checking:** 
  1. Вызов `runtime.Goexit()` провоцирует не «панику» (которую можно перехватить через `recover`), а фатальное завершение процесса рантаймом (`fatal error`).
  2. Точный текст сообщения в рантайме: `fatal error: no goroutines (main called runtime.Goexit) - deadlock!`.
  3. Если в момент вызова `runtime.Goexit()` в `main.main` в системе работают другие пользовательские горутины, программа **не падает немедленно**: она продолжает исполнять фоновые горутины в штатном режиме до тех пор, пока они не завершатся либо не войдут во взаимную блокировку.
* **evidence/source needed:** `src/runtime/proc.go` (`checkdead()`); запуск тестовой программы с `runtime.Goexit()`.
* **priority:** 🟡 **Medium**

   В статьях подробно описаны вызовы между `ABIInternal` и `ABI0`, однако отсутствует разбор того, как компилятор генерирует адаптеры для рефлексивных вызовов (`reflect.Value.Call`) и передачи аргументов через память в регистровые функции.
2. **Файловый I/O и `io_uring` vs фоновые треды:**  
   В статье 40 прекрасно объяснена природа блокирующего дискового ввода-вывода, однако полезно явно зафиксировать текущий статус поддержки `io_uring` в рантайме Go и почему стандартная библиотека по-прежнему использует традиционные системные вызовы на выделенных потоках ОС.
3. **Pread / Pwrite и LLD (Linker internal design):**  
   В статье 44 о линкере описан общий процесс компоновки, но не упомянута масштабная переработка линкера Go в версии 1.15–1.16, перешедшая на параллельную запись объектных файлов через `pwrite` и радикально ускорившая сборку.
4. **SwissMap (Swiss Tables) в Go 1.24:**  
   Поскольку архитектура словарей в Go 1.24 претерпевает фундаментальный сдвиг в сторону Swiss Tables (`GOEXPERIMENT=swissmap`), в статьях 31–33 стоит добавить краткий архитектурный дисклеймер о различиях между исторической организацией бакетов `bmap` и современной групповой SIMD-фильтрацией Swiss Tables.
