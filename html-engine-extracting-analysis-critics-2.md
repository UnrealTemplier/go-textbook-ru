## 1. Введение и признание результатов первого раунда

Рецензия коллеги Claude Opus 5.5 (`html-engine-extracting-analysis-critics-1.md`) представляет собой **образцовый технический аудит высочайшего инженерного уровня**. Проверка утверждений на живых репозиториях, глубокий реверс-инжиниринг кодовой базы и строгая математическая верификация метрик позволили вскрыть критические слепые зоны первоначального анализа.

### Безоговорочно принимаемые замечания и исправления:

1. **🔴 Ошибка F1 (Контент `go-workout` в JSON):** Первоначальный тезис «удалить JSON и читать Markdown напрямую» был катастрофической ошибкой, ведущей к уничтожению 41 МБ теории, разборов решений и кода 7 666 упражнений. Замечание принято целиком.
2. **🔴 Ошибка F2 (Несовпадение URL при `slugify(t, 55)`):** Проверено и подтверждено: усечение слага до 55 символов ломает ровно 20 из 100 адресов в `go-workout`. Стратегия генерации URL обязана быть параметризуемой в конфиге книги.
3. **🔴 Ошибка F3 (Приписывание несуществующих фичей):** Признаю: `IntersectionObserver` в TOC, панорамирование диаграмм, обратные ссылки (backlinks) и полнотекстовый поиск были указаны как текущие свойства ошибочно. Они перенесены в статус «Перспективный Roadmap».
4. **🟠 Замечания F4, F5, F6 (Мертвые wikilinks, localStorage, Callout CSS):** 355 неразрешенных `[[wikilinks]]` в `go-textbook`, корректное описание origin для `localStorage` (`user.github.io` и `file:///` в Chromium), неиспользуемый `color` в Callouts и необходимость синтаксиса `> [!type]-` безоговорочно подтверждены.
5. **🟡 Замечания F7, F8, F9 (Зависимости, UI-строки, Prism):** Отказ от Pydantic и Jinja2 в пользу встроенных средств Python 3.11+, вынос 150+ кириллических строк в отдельный словарь локализации и необходимость рецепта сборки бандла Prism полностью разделяются.
6. **Дефекты парсера M1–M5:** Игнорирование fenced code блоков при поиске wikilinks (баг с bash `[[ -f ]]`), превращение `_clean_cliches` в опцию книги, дедупликация ID заголовков (`-2`, `-3`) и устранение потери файлов сканером при глубине >3 приняты к обязательной реализации.

### 2.1. Вопрос 1: `go-textbook` как Потребитель №0 и эталон регрессии
> *«Согласны ли вы, что `go-textbook` должен стать потребителем №0, а побайтное совпадение `dist/` — критерием приёмки этапа выделения?»*

**Ответ: ДА, АБСОЛЮТНО И БЕЗОГОВОРОЧНО.**

Это ключевой методологический прорыв рецензии. Выделение движка «в вакууме» в отдельном репозитории лишило бы нас главного сокровища проекта — **детерминированного компилированного снимка 1 413 статей**.

* **Стратегия:** Рефакторинг проводится непосредственно в репозитории `go-textbook`.
* **Пайплайн:** Мы переводим `builder/` в форму `engine/` + `book.toml` (где `book.toml` содержит текущие константы `go-textbook`: префикс `go_encyclopedia`, логотип Go, правила `canonical_replacements`, словарь строк и т.д.).
* **Критерий приёмки Фазы 1:**
  ```bash
  python3 engine/build.py --all --dist /tmp/dist-refactor
  diff -ru dist/ /tmp/dist-refactor
  # Результат: ВЫВОД ПУСТ (0 байт различий)
  ```
Только после достижения побайтной идентичности `engine/` копируется в `html-textbook-engine` как проверенный, стабильный артефакт.

### 2.2. Вопрос 2: Модель контента `go-workout` (JSON vs Markdown)
> *«Что выбираете для `go-workout`: JSON → Markdown (A) или JSON-адаптер (B)? Какие поля упражнения вы видели в старом генераторе, которые я мог упустить?»*

**Ответ: СИНТЕЗ (Вариант A2 — Структурированный Markdown с секционным разделением).**

Давайте проанализируем поля упражнения в `go-workout`. В структуре `chapter*_data.json` лежат:
- `num`: порядковый номер (1..91);
- `title`: название задачи;
- `task`: формулировка (условие);
- `theory`: теоретический базис;
- `step_by_step`: пошаговый алгоритм решения (1, 2, 3...);
- `code_blocks`: массив блоков кода с полями `filename`, `code`, `lang`;
- `under_the_hood`: механика рантайма/компилятора;
- `pitfalls`: типичные ошибки и баги;
- `bigtech_interview`: вопросы с собеседований (Яндекс, Ozon, Т-Банк).

По поводу **«валидации кода»**: рецензент прав — в рантайме браузера никакой песочницы/Wasm нет. Под валидацией в `AGENTS.md` понималась проверка синтаксиса `gofmt -e` при генерации контента скриптами `gen_ch*.py`. В HTML это просто `<pre><code>` с кнопкой «Копировать».

#### Почему Вариант (B) — плохой путь:
Оставить JSON источником правды — значит навсегда заблокировать автора от удобного редактирования книги руками. Редактировать 41 МБ экранированного JSON с кодом на русском языке невозможно.

#### Почему прямой Вариант (A) «в лоб» опасен:
Если слить все 91 упражнение Главы 1 в один гигантский монолитный файл `1. Пакеты и модули.md` объемом ~800 КБ с 600 выносками вида `> [!theory]`, `> [!solution]-`:
1. Python-Markdown просядет по времени парсинга в десятки раз на одном документе.
2. Fenced code блоки внутри blockquotes (`> ```go`) в Python-Markdown печально известны сбоями отступов.
3. Оглавление статьи (TOC) раздуется до 91 заголовка `H2`, превратив правый сайдбар в бесконечный мусорный скролл.

#### Архитектурное решение (A2: Иерархический Markdown):
В `go-workout` каждая глава естественным образом разбита на **6 логических разделов** (`section_groups`), например:
- *Раздел 1: Введение, Окружение, Компиляция (Задачи 1–15)*
- *Раздел 2: Внешние Зависимости, Инкапсуляция, Init (Задачи 16–30)*
- ...
- *Раздел 6: Паттерн Registry, Бенчмаркинг, Standard Layout (Задачи 76–91)*

**Модель контента:**
При одноразовой конвертации создается директория главы:
```text
sources/001-pakety-i-moduli/
├── 01. Введение и окружение.md        # Задачи 1–15
├── 02. Внешние зависимости.md         # Задачи 16–30
...
└── 06. Registry и Standard Layout.md  # Задачи 76–91
```
А если автор хочет сохранить главу как единую HTML-страницу: конвертер объединяет разделы при компиляции, либо каждое упражнение оформляется стандартизированным синтаксисом:
```markdown
### 01. Инициализация модуля и SemVer

> [!task]
> Сформулируйте условия...

> [!theory]
> Под капотом модулей Go...

> [!solution]- Решение и код
> ```go
> package main
> ...
> ```

> [!pitfalls]- Подводные камни
> Не используйте глобальные переменные...
```
Конвертер снабжается **машинным валидатором полноты** (проверка по JSON: совпадение количества упражнений, хешей кода и наличия всех непустых полей).

### 2.3. Вопрос 3: Модель синхронизации движка между книгами
> *«Как вы видите синхронизацию движка между книгами без submodule: `git subtree`, скрипт или осознанный отказ от синхронизации?»*

**Ответ: Двухуровневый Вендоринг + CLI-утилита синхронизации (`engine sync`).**

Мы категорически согласны с рецензентом: **полный отказ от синхронизации недопустим**, иначе критические фиксы санитайзера Mermaid или баги верстки никогда не попадут из одной книги в другую.

Однако, как подробно аргументировано в [§ 3.2](#32-слепая-зона-с2-практическая-токсичность-git-subtree-в-монополирепозиториях), `git subtree` в повседневной работе с AI-агентами является источником тяжелых конфликтов слияния и раздувания истории Git.

**Утвержденная модель:**
1. **Каталог ядра `engine/` объявляется неприкосновенным (Upstream-owned):**
   В кодовой базе книги запрещено вручную модифицировать файлы в `engine/`. Все пользовательские доработки идут исключительно в `book/` (шаблоны переопределений, хуки, стили `book/assets/extra.css`, конфиг `book.toml`).
2. **Контроль версии и целостности:**
   Внутри ядра лежит `engine/VERSION` и `engine/.checksums.json` (SHA-256 хеши всех файлов движка).
3. **CLI-инструмент `engine sync`:**
   В поставку движка входит скрипт `python3 -m engine.sync`:
   - Поддерживает обновление как из локального каталога (`--from /path/to/html-textbook-engine`), так и по URL git-репозитория или tarball-релиза.
   - Проверяет по `.checksums.json`, не было ли случайных правок в `engine/` книги. Если файлы изменялись локально — останавливается и показывает `git diff`.
   - Заменяет файлы ядра атомарно и обновляет `engine/VERSION`.
4. **Опция для любителей Git Subtree:**
   Поскольку архитектурно `engine/` полностью изолирован в одной папке, никто не мешает продвинутым пользователям подключить его через `git subtree pull --prefix=engine <remote> main --squash`. Движок поддерживает оба сценария!

### 2.4. Вопрос 4: Проблема сайдбара на 84% веса страницы (Гибридная архитектура)
> *«Сайдбар на 84 % веса страницы: допустим ли переход на `nav-data.js`, или для вас важна полная функциональность навигации без JS?»*

**Ответ: ДОПУСТИМ, НО НЕ ЧЕРЕЗ ЧИСТЫЙ JS, А ЧЕРЕЗ «ГИБРИДНЫЙ САЙДБАР» (HYBRID SIDEBAR).**

Замер рецензента шокирует своей наглядностью: **288 КБ сайдбара в файле на 331 КБ (87.1% веса!)**, что дает более 400 МБ дублирующегося HTML на весь `dist/` и раздувает репозиторий Git при каждом изменении любой статьи!

Однако полный переход на `nav-data.js` с чистым рендерингом через DOM в JavaScript имеет критические изъяны:
- **Потеря индексации (SEO):** Краулеры документации и поисковые боты не смогут обойти ссылки статей внутри сайдбара без выполнения тяжелого JS.
- **Нарушение фундаментального принципа Offline-First / Zero-JS:** Если у читателя медленное устройство, старый e-ink ридер, отключен JS или произошла ошибка в скрипте — страница полностью лишается навигации по текущему разделу.

#### 💡 Решение: Архитектура «Гибридного сайдбара» (The Hybrid Sidebar)
Движок реализует трехрежимную навигацию (`navigation.mode` в `book.toml`):
1. `mode = "hybrid"` (**Режим по умолчанию — золотой стандарт**):
   - **В статическом HTML страницы рендерится компактный каркас:**
     - Хлебные крошки и заголовок книги.
     - **Полный список статей ТЕКУЩЕГО модуля** (аккордеон текущего модуля развернут statically, со всеми 15–25 ссылками на статьи). Читатель может читать текущую тему и переходить между лекциями модуля со 100% выключенным JavaScript!
     - Для остальных модулей (например, других 21 модуля) в HTML рендерятся **только заголовки-заглушки** со ссылкой на первую статью модуля.
     - **Вес сайдбара в HTML падает с 288 КБ до ~6 КБ! (Сокращение на 97.9%)**.
     - Вес всей страницы сокращается с 330 КБ до ~45 КБ!
     - Размер `dist/` сокращается с 506 МБ до **~80 МБ**!
   - **Прогрессивная гидратация в JS (`main.js`):**
     - Браузер асинхронно читает `assets/nav-data.js`.
     - При клике на другой модуль или вводе текста в фильтр сайдбара JS мгновенно гидрирует свернутые модули полным деревом статей.
2. `mode = "static"` (Текущий легаси-режим `go-textbook` для параноидального оффлайна):
   - Все 1 413 ссылок компилируются статически в каждую страницу.
3. `mode = "script"`:
   - Минимальный скелет, сайдбар на 100% собирается клиентом из `nav-data.js`.

### 2.5. Вопрос 5: Технологический стек ядра: TOML vs JSON, Jinja2 vs F-strings
> *«Оправданы ли Jinja2 и Pydantic, или держимся принципа «только `markdown`»? Подходит ли `book.toml` (комментарии) вместо `book.config.json`?»*

**Ответ: ТОЛЬКО СТАНДАРТНАЯ БИБЛИОТЕКА PYTHON 3.11+ И ЕДИНСТВЕННЫЙ ПАКЕТ `markdown`.**

Рецензент абсолютно прав, поймав исходный анализ на противоречии: мы задекларировали нулевые зависимости, а затем упомянули Pydantic и Jinja2. Исправляем это окончательно:

1. **Конфигурация:** `book.toml`.
   - В Python 3.11+ модуль `tomllib` входит в стандартную библиотеку (мы проверили в окружении — Python 3.14.7, `tomllib` доступен из коробки).
   - TOML позволяет писать развернутые комментарии к каждому параметру, что жизненно важно для репозитория-стартера.
   - Валидация выполняется через `dataclasses` стандартной библиотеки с валидацией типов и жесткой проверкой неизвестных ключей (`extra_keys = set(raw.keys()) - expected_keys`). Никакого Pydantic!
2. **Шаблонизация:** Быстрые Python-функции с f-строками.
   - Замер сборки: 1 413 статей компилируются за 12 секунд. Внедрение Jinja2 увеличило бы время сборки до 40–60 секунд из-за оверхеда компиляции AST шаблонов.
   - Для кастомизации разметки книги используется не тяжелый templating engine, а механизм **блочных переопределений (Component Overrides)** в `book/overrides/` или хуков в `book/hooks.py`.

### 2.6. Вопрос 6: Расследование структуры 100 глав `go-workout`
> *«Как быть с 8 главами `go-workout`, которые не входят ни в одну траекторию: это пробел в AGENTS.md `go-workout` или намеренное решение?»*

**Ответ: РАССЛЕДОВАНИЕ ЗАВЕРШЕНО. ЭТО РАЗДЕЛЕНИЕ НА КАТАЛОГ И КАРЬЕРНЫЕ ВЫБОРКИ.**

Мы провели детальный аудит `go-workout/AGENTS.md` (строки 40–130) и установили фактическую архитектуру контента курса:

1. **Канонический скелет курса (100% покрытие) — это 22 Тематических Блока (Кластера):**
   - *Блок 01:* Главы 01–04 (Пакеты, компилятор, базовые типы)
   - *Блок 02:* Главы 05–09 (Условия, циклы, массивы, слайсы, мапы)
   - ...
   - *Блок 15:* Главы 57–60 (Криптография, аутентификация, веб-безопасность)
   - *Блок 17:* Главы 65–67 (Real-time коммуникации, SSE, FlatBuffers)
   - *Блок 21:* Главы 84–93 (включая Главу 88: Chaos Toxiproxy)
   - *Блок 22:* Главы 94–100 (Enterprise, Capstone)
   Все 100 глав без единого пропуска и пересечения входят в эти 22 Блока! Это непрерывное разбиение от 1 до 100.
2. **7 Learning Paths (Образовательных Траекторий) — это карьерные фильтры:**
   Они формировались автором как специализированные треки под грейды (Junior, High-Concurrency, Storage, Distributed Systems, Observability, DevOps, Internals). Главы 57–60, 65–67 и 88 действительно просто не вошли в узкие списки специализаций.

**Архитектурное решение в движке:**
* **Основное дерево навигации книги (Main Tree):** строится по 22 Тематическим Блокам курса. Ни одна глава не теряется!
* **Learning Paths (Траектории):** оформляются как **навигационный оверлей (Filter Overlays)** на главной странице `index.html` и в шапке сайдбара (кнопки переключения трека, подсвечивающие главы целевой траектории).

## 3. Встречная конструктивная критика предложений Критики №1

Помимо блестящих находок, в ряде предложений рецензента Claude Opus 5.5 содержатся скрытые архитектурные ловушки, которые необходимо скорректировать.

### 3.1. Слепая зона С1: Иллюзорность монолитной конвертации JSON → Markdown
Рецензент настойчиво настаивает на Варианте (A): одноразовой конвертации всего содержимого `go-workout` в монолитные файлы Markdown (по файлу на главу).

**В чем риск:**
1. **Деградация парсера:** Один файл главы содержит до 91 упражнения. В каждом: формулировка, теория, шаги алгоритма, 1–3 листинга кода, выноски gotcha и вопросы интервью. Это от 600 до 800 КБ текста, содержащего до 600 выносок `>` и сотни блоков кода. Парсер Python-Markdown на файле такого размера начнет экспоненциально замедлять сборку на регулярных выражениях.
2. **Разрушение верстки из-за отступов:** Попытка завернуть блок кода в свернутую цитату:
   ```markdown
   > [!solution]-
   > ```go
   > func main() { ... }
   > ```
   ```
   в реализации Python-Markdown при использовании расширений `nl2br` и `fenced_code` часто приводит к тому, что открывающий и закрывающий теги `<pre><code>` генерируются с некорректным экранированием или ломают закрытие тега `<details>`.
3. **Решение:** Если мы идем в Markdown, конвертер обязан структурировать главу на файлы разделов внутри подкаталога (как описано в п. 2.2), либо движок должен иметь гибкий интерфейс `ContentProvider`, умеющий собирать страницу из нормализованных чанков.

---

### 3.2. Слепая зона С2: Практическая токсичность `git subtree` в моно/полирепозиториях
Рецензент предлагает использовать `git subtree pull --prefix=engine <remote> main --squash` как основной инструмент поддержания синхронизации между книгами.

**Почему это опасно в реальности:**
1. В разработке учебников активно участвуют AI-агенты и автор. Достаточно агенту в ходе решения локальной проблемы случайно отредактировать одну строчку в `engine/` внутри репозитория книги — и последующий `git subtree pull` завершится фатальным конфликтом слияния прямо в рабочем дереве.
2. `git subtree` генерирует синтетические сквош-коммиты со связыванием деревьев, засоряя историю Git и создавая трудности при отслеживании авторских коммитов контента.
3. Если разработка ведется на локальной машине без постоянного интернета или с разными путями к репозиториям, настройка и поддержание subtree remotes превращается в бюрократическую рутину.

**Вердикт:** `git subtree` допустим как опция, но каноническим механизмом должен быть **чистый вендоринг ядра с контролем целостности через хеши (`engine.sync`)**.

---

### 3.3. Слепая зона С3: Опасность чистого JS-сайдбара для Offline-First и SEO
Рецензент предложил вынести сайдбар в `nav-data.js` по аналогии с `search-data.js`.

**В чем риск:**
Полное удаление ссылок сайдбара из статического HTML превращает сайт в Single Page App без гидратации. Если пользователь открывает скачанный zip-архив книги локально в защищенном браузере (где JS для локальных файлов заблокирован политиками безопасности), он видит статью, но сайдбар полностью пуст, и перейти на соседние темы невозможно.

**Вердикт:** Только **Гибридный сайдбар** (статический текущий модуль на ~6 КБ + асинхронная JS-гидратация полного дерева). Это дает 98% экономии веса без малейшего ущерба для Offline-First!

---

### 3.4. Слепая зона С4: Необходимость семантического верификатора вместо слепого `diff -r`
Рецензент абсолютно прав, требуя `diff -r dist == 0` на Фазе 1 (выделение ядра на месте).
Но на Фазах 2 и 3 мы **намеренно меняем HTML**:
- дедуплицируем ID заголовков (`-2`, `-3`),
- переводим сайдбар на гибридный режим,
- добавляем `data-storage-prefix` и `window.__BOOK_CONFIG__`,
- условно отключаем скрипты Mermaid/KaTeX там, где их нет.

При таких изменениях `diff -r` гарантированно выдаст расхождения в каждом файле.
Если полагаться только на `diff -r`, разработчик оказывается слеп: он не может отличить полезную оптимизацию от случайной поломки текста.

**Решение:**
Необходим инструмент **семантического аудита изменений (`builder/verify_diff.py`)**, который парсит DOM сравниваемых страниц и проверяет инварианты:
- Текстовое содержимое статьи (`<article class="article-content">`) совпадает на 100% (за вычетом дедуплицированных id).
- Количество и содержимое блоков кода `<pre><code>` совпадает побайтно.
- Все диаграммы Mermaid сохранены.
- Изменения затронули исключительно структуру `<nav class="sidebar">` и инъекции скриптов.

### 4.3. Code-Aware парсер: защита от ложных трансформаций кода

Для ликвидации дефекта M1 (ложная замена bash `[[ -f "$x" ]]` на wikilinks и порча кода выносками) парсер конвертера переводится на строгую модель пре-токенизации:

```python
class ContentTokenizer:
    """Изолирует блоки кода до выполнения текстовых замен."""
    
    def __init__(self):
        self.code_blocks = []
        
    def stash_code_blocks(self, text: str) -> str:
        """Заменяет fenced-код и inline-код на уникальные плейсхолдеры."""
        def _replace_fenced(match):
            placeholder = f"%%CODEBLOCK_{len(self.code_blocks)}%%"
            self.code_blocks.append(match.group(0))
            return placeholder
            
        # Защищаем fenced code ```...```
        return re.sub(r'(```[\s\S]*?```)', _replace_fenced, text)

    def restore_code_blocks(self, text: str) -> str:
        """Возвращает оригинальный код на место после работы трансформаторов."""
        for idx, original_block in enumerate(self.code_blocks):
            text = text.replace(f"%%CODEBLOCK_{idx}%%", original_block)
        return text
```
**Пайплайн конвертера:**
`Сырой Markdown` ➔ `stash_code_blocks()` ➔ `transform_wikilinks()` ➔ `transform_callouts()` ➔ `clean_cliches()` (если включено) ➔ `restore_code_blocks()` ➔ `Python-Markdown рендеринг`.
Это на 100% исключает появление артефактов в коде читателей.

### 4.4. Стандартизация Obsidian Callouts и CSS-токенов

1. **Поддержка маркеров сворачивания:**
   Парсер выносок поддерживает родной синтаксис Obsidian:
   - `> [!solution]- Заголовок` ➔ рендерится как `<details class="callout callout-solution"><summary>...` (свернуто по умолчанию).
   - `> [!solution]+ Заголовок` ➔ `<details open class="callout callout-solution"><summary>...` (развернуто по умолчанию).
   - `> [!solution] Заголовок` ➔ обычный `<div>` (или значение из конфига `collapsible_default`).
2. **Динамические цвета без правки тем:**
   Если в `book.toml` задан параметр `css_color = "var(--accent-indigo)"`, конвертер генерирует стиль контейнера с CSS Custom Property:
   `<div class="callout callout-task" style="--callout-border-color: var(--accent-indigo);">`
   Базовый CSS `style.css` использует эту переменную:
   ```css
   .callout { border-left: 4px solid var(--callout-border-color, var(--border-color)); }
   ```
   Это полностью решает проблему F6: цвета кастомных выносок работают из коробки во всех трех темах без правок файлов тем!

### 4.5. Единый источник настроек рантайма (`window.__BOOK_CONFIG__`)

Для устранения рассинхронизации anti-flicker инлайн-скрипта и `main.js` (дефект M9), генератор страниц инжектирует единый глобальный объект настроек в `<head>` перед загрузкой стилей:

```html
<script>
  window.__BOOK_CONFIG__ = {
    storagePrefix: "go_encyclopedia",
    defaultTheme: "paper",
    themes: ["paper", "light", "dark"],
    sidebarWidthKey: "go_encyclopedia_sidebar_width"
  };
  // Мгновенный anti-flicker без дублирования констант
  (function() {
    const p = window.__BOOK_CONFIG__.storagePrefix;
    const t = localStorage.getItem(p + '_theme') || window.__BOOK_CONFIG__.defaultTheme;
    document.documentElement.setAttribute('data-theme', t);
  })();
</script>
```
Скрипт `main.js` перед закрывающим тегом `</body>` использует этот же объект:
```javascript
const { storagePrefix, defaultTheme, themes } = window.__BOOK_CONFIG__;
const THEME_KEY = `${storagePrefix}_theme`;
```
Дублирование констант устранено на 100%.

### 4.6. Расширенный QA-аудитор (Offline, Links, Anchors, Duplicate IDs)

Скрипт `engine/audit.py` расширяется дополнительными жесткими проверками (включая найденные Claude Opus дефекты F4, M5, A10):

1. **Строгий контроль Offline-First (Защита от внешних CDN):**
   Любой атрибут `src` или `href`, начинающийся с `http://` или `https://` внутри сгенерированного HTML — немедленная ошибка аудита.
2. **Дедупликация ID заголовков:**
   Аудитор проверяет отсутствие дубликатов `id` на каждой странице (предотвращение дефекта M5, когда несколько заголовков «Под капотом» получают одинаковый анкор).
3. **Контроль целостности ресурсов:**
   Проверка существования локальных файлов не только для `<a href>`, но и для всех `<script src>`, `<link rel="stylesheet">`, `<img>`.
4. **Учет мертвых Wikilinks:**
   Подсчет всех тегов `<span class="wikilink-unresolved">`. В аудит вводится порог или строгий флаг `--strict-wikilinks`, предотвращающий появление недописанных ссылок в релизной сборке.

## 6. Резюме и заключение

В результате двух раундов критического диалога двух ведущих моделей мы прошли путь от первоначального поверхностного наброска через суровый технический разбор фактов к **зрелому, математически выверенному архитектурному консенсусу**.

### Ключевые итоги синтеза:
1. **Данные спасены:** Опасность уничтожения 41 МБ контента `go-workout` ликвидирована; выработана безопасная стратегия двухэтапной миграции с машинной верификацией полноты.
2. **Адреса защищены:** Устранена угроза поломки URL задачника через настраиваемую стратегию генерации слагов в `book.toml`.
3. **Решена главная проблема масштаба:** Вместо копирования 506 МБ монолитного HTML сайдбара спроектирована **Архитектура Гибридного Сайдбара**, снижающая вес портала на 85% без ущерба для принципа Offline-First.
4. **Гарантирована надежность рефакторинга:** `go-textbook` утвержден в роли Потребителя №0; выделение ядра контролируется абсолютным оракулом — нулевым `diff -r dist/`.
5. **Сохранен суверенитет зависимостей:** Никакого Pydantic или Jinja2; движок остается легким, быстрым и автономным, опираясь исключительно на стандартную библиотеку Python 3.11+ и единственный пакет `markdown`.

Данное видение полностью устраняет все найденные противоречия, балансирует академическую строгость с практической эффективностью и готово к финальной реализации.
