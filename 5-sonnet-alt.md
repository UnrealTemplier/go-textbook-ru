## 2. Сквозные проблемы (X)

**X-1 · High · Поведение, зависящее от строки `go` в `go.mod`, подано как «с версии N».**
- Утверждение: «Начиная с Go 1.22 переменная цикла новая на каждой итерации» (ст. 9, 34); «в Go 1.23+ таймеры собираются GC, `Reset` безопасен» (ст. 31); GOMAXPROCS по умолчанию «равен числу логических ядер» (ст. 35); `panic(nil)` и др.
- Проблема: эти семантики включаются **по языковой версии модуля** (`go` / `godebug` в `go.mod`), а не по версии тулчейна. Модуль с `go 1.21`, собранный Go 1.27, ведёт себя по-старому.
- Доказательство: ✅ эксперимент — модуль `go 1.21` на тулчейне 1.27 печатает `3 3 3` для замыканий в `for i := 0; i < 3; i++`; ✅ `doc/godebug.md` («Default GODEBUG Values»: defaults берутся из `go.mod`); ✅ `runtime/debug.go` — `containermaxprocs=0`/`updatemaxprocs=0` «default for language version 1.24 and below»; ✅ `doc/godebug.md`: «Go 1.27 removed the `asynctimerchan` setting» (то есть новая семантика таймеров в 1.27 безусловна, для 1.23–1.26 зависела от `go.mod`).

**X-2 · High · Две поколения реализации `map` смешаны.** См. A18-1 и A19-1: тело статей 18–19 — реализация ≤ Go 1.23; текущие версии (1.24–1.27) используют Swiss tables. Статья 44 (чек-лист) закрепляет «`map` — бакеты и эвакуация».

**X-3 · Medium · Внутренние противоречия между статьями.**
- ст. 6 подаёт `reflect.StringHeader` как актуальный, ст. 16 и ст. 20 верно называют `SliceHeader`/`StringHeader` deprecated с Go 1.20 (✅ `reflect/value.go`: «Deprecated: Use unsafe.String or unsafe.StringData»).
- ст. 10, 18 категорично: «слайсы и мапы по ссылке — ложь», ст. 36: «каналы — ссылочный тип (как map и slice)».
- Стоимость переключения горутины: ст. 34 — «~200 нс», ст. 35 — «несколько десятков нс», ст. 33 — «десятки нс».
- ст. 12: `error` «передаётся через регистры как 16 байт»; ст. 10: «error в RBX».
- ст. 14: «передача по указателю → объект в куче → паузы STW»; ст. 14 же (диаграмма): «передана по указателю вниз → стек».

**X-4 · Medium · Атрибуция и «создатели Go».**
- ст. 29: «те же авторы (Томпсон и Ритчи) перенесли это в Go» — Ритчи не автор Go (Гризмер, Пайк, Томпсон).
- ст. 32/33: дженерики «под руководством Расса Кокса» / GCShape stenciling «Кокса и команды» — дизайн Иэна Лэнса Тейлора и Роберта Гризмера, реализация — Кит Рэндалл и Дэн Скейлз; Кокс — «The Generics Dilemma» и общее руководство 📚 (proposal golang/go#43651, design doc «Generics implementation — GC Shape Stenciling»).

**X-5 · Medium · Числа и микробенчмарки без источников.** «1–2 нс на косвенный вызов», «~200 нс на переключение горутины», «20 тактов на Mutex», «10–100× медленнее `reflect.Select`», «2–4× быстрее `easyjson`», «25–35% меньше бинарник», «1–2 мкс переключение потока», «~35–50 нс → ~1 нс для `defer`». ## 3. Находки по статьям

### Статья 1 · Обзор раздела

**A01-1 · Medium · «Архитектура Go-программы», врезка про Go Runtime**
- Утверждение: «полностью автономный, статически слинкованный машинный код»; «Fat Binary».
- Проблема: без оговорок — на macOS бинарник всегда линкуется с `libSystem` (Go вызывает libc/syscall-обёртки), на Windows — с системными DLL, на Linux с cgo (`net`, `os/user`) — динамически (оговорка есть только в ст. 2). «Fat binary» — устоявшийся термин для multi-arch Mach-O.
- Доказательство: 📚 документация `cmd/link`, Go 1.12 release notes (macOS: syscalls через libSystem).

**A01-2 · Medium · «Value Semantics и Mechanical Sympathy»**
- Утверждение: «вы сами решаете, где будет жить значение: по значению — на стеке, по указателю — в куче».
- Проблема: размещение определяет escape analysis, а не вид передачи; указатель вниз по стеку остаётся на стеке, значение может уйти в кучу. Противоречит ст. 3 и 14 этого же модуля.
- Доказательство: ✅ `testing.AllocsPerRun` для `DoWork(any)` без утечки = 0 аллокаций.

**A01-3 · Low** — «потокобезопасные кэши потоков `mcache`»: `mcache` — по одному на **P** (`p.mcache`), безлоковость обеспечена этим, а не «потокобезопасностью»; «микросекундные STW» — зависит от числа горутин/стеков, типично десятки–сотни мкс; «duck typing» для неявных интерфейсов — в Go статическая структурная типизация. Доказательство: 📚 `runtime2.go`, GC guide.

**A01-4 · Low** — Интервью: «скрытые пути исполнения → утечки дескрипторов, гонки данных» — мнение, а не факт; не упомянуты `panic/recover` как исключения Go. Доказательство: 📚 Go FAQ «Why does Go not have exceptions?».

### Статья 2 · Установка, GOPATH, GOROOT

**A02-1 · High · «GOROOT: Дом для самого Go», `pkg/`**
- Утверждение: «`pkg/` — предкомпилированные пакетные файлы стандартной библиотеки, ускоряющие компоновку».
- Проблема: с Go 1.20 дистрибутив не содержит предкомпилированных `.a` стандартной библиотеки; пакеты собираются по требованию и кэшируются в `GOCACHE`. В `pkg/` остались `tool/` и `include/`.
- Доказательство: ✅ `ls /usr/local/go/pkg` → `include`, `tool`; 📚 Go 1.20 release notes («the standard library is no longer shipped precompiled»).

**A02-2 · Medium · Диаграмма GOPATH**
- Утверждение: `/pkg` — «централизованный кэш модулей **и сборок**».
- Проблема: кэш сборки — отдельный `GOCACHE` (`~/.cache/go-build`, на Linux). В `GOPATH/pkg` лежат `mod/` (кэш модулей, внутри `mod/cache/download`) и `sumdb/`. Путь `GOPATH/pkg/sumdb` и `mod` в диаграмме указаны верно.
- Доказательство: ✅ `go env GOCACHE` = `/home/ut/.cache/go-build`; ✅ `ls ~/go/pkg` = `mod`, `sumdb`.

**A02-3 · High · «Первая программа»**
- Утверждение: `fmt.Printf("OS: %s<br>Arch: %s\n", runtime.GOOS, runtime.GOARCH)`.
- Проблема: в строке формата литерал `<br>` (артефакт Mermaid-санитайзера); программа выведет `OS: linux<br>Arch: amd64`.
- Доказательство: ✅ grep по блокам ```go; других вхождений `<br>` в кодовых блоках модуля нет.

**A02-4 · Medium · «Эпоха Go Modules»**
- Утверждение: «безальтернативный стандарт в Go 1.13».
- Проблема: в 1.11–1.15 `GO111MODULE=auto` (в GOPATH без `go.mod` — старый режим); по умолчанию модульный режим включён с **Go 1.16** (`GO111MODULE=on`). GOPATH-режим доступен и сегодня при `GO111MODULE=off`.
- Доказательство: 📚 Go 1.16 release notes.

**A02-5 · Medium · «Ранние версии вплоть до 1.10», «фатальная проблема»**
- Утверждение: версионный конфликт в `~/go/src` «неразрешим»; GOPATH — унаследованная философия монорепозитория Google.
- Проблема: обходился `vendor/` (с Go 1.5/1.6) и отдельными GOPATH на проект; монорепо Google собирается Blaze, а не GOPATH; граница «1.10» произвольна (GOPATH-режим по умолчанию — до 1.16).
- Доказательство: 📚 Go 1.5/1.6 release notes (vendor), blog «Go 1.11 modules».

**A02-6 · Medium · «Влияние CGO_ENABLED»**
- Утверждение: «по умолчанию cgo активен (`CGO_ENABLED=1`)».
- Проблема: с Go 1.20 cgo автоматически выключается, если в `PATH` нет C-компилятора; при кросс-компиляции по умолчанию выключен. Это влияет на «ELF statically linked».
- Доказательство: 📚 Go 1.20 release notes.

**A02-7 · Low–Med** — «модуль импортирован, но не вызван — ошибка; исключает мёртвый код в бинарнике»: ошибка выдаётся, если не использован ни один экспортируемый идентификатор (не только вызов); мёртвый код выкидывает линкер, а не эта проверка; пакет назван «модулем». Доказательство: ✅ `go_spec.html` («illegal … to directly import a package without referring to any of its exported identifiers»).

**A02-8 · Low–Med** — «`CGO_ENABLED=0` → прямые syscalls, игнорируя динамические библиотеки»: верно для Linux; на macOS (с 1.12) и OpenBSD Go вызывает libSystem/libc даже без cgo, на Windows — `kernel32.dll`. Доказательство: 📚 Go 1.12 release notes.

**A02-9 · Low** — `apt install golang` ставит версию дистрибутива (часто устаревшую); не упомянуты `GOTOOLCHAIN` (1.21), `GOBIN`, `go env`; для `scratch` кроме статической сборки нужны CA-сертификаты и tzdata (в ст. 31 tzdata упомянут отдельно); вывод `file` у современных сборок содержит `with debug_info`.

### Статья 3 · go run, go build, go test, toolchain

**A03-1 · High · «Под капотом: SSA и оптимизации» + диаграмма пайплайна**
- Утверждение: «именно на SSA-представлении компилятор выполняет Escape Analysis, Inlining»; диаграмма: `SSA → Opt(Inlining, Escape Analysis, Dead code)`.
- Проблема: в gc inlining/devirtualization и escape analysis работают на IR **до** построения SSA. В SSA — DCE, BCE, nilcheck-elimination, CSE, prove, regalloc и т.п.
- Доказательство: ✅ `cmd/compile/internal/gc/main.go`: `noder.LoadPackage` → `interleaved.DevirtualizeAndInlinePackage` → `escape.Funcs` → … → `enqueueFunc`/`ssagen`.

**A03-2 · Medium · `go test`**
- Утверждение: тестовый `main()` «замеряет такты процессора и потребление памяти»; «тестирование — неотъемлемая часть спецификации языка».
- Проблема: сгенерированный `main` лишь регистрирует `TestXxx` (`testing.MainStart`); время печатается, но такты/память — только у бенчмарков (`-benchmem`). `testing` и `go test` — стандартная библиотека и инструмент, но не часть Language Specification.
- Доказательство: 📚 `go help test`, `go_spec.html` (нет `testing`).

**A03-3 · Medium · Race Detector**
- Утверждение: при обнаружении гонки «выполнение прерывается»; «одновременный несогласованный доступ двух горутин».
- Проблема: по умолчанию отчёт печатается, программа **продолжает**, тест помечается failed, процесс выходит с кодом 66; прерывание — `GORACE=halt_on_error=1`. Алгоритм основан на happens-before (векторные часы): детектор ловит неупорядоченные обращения, а не «одновременные», и лишь на реально выполненных путях. С Go 1.20 на linux/amd64 не требует cgo.
- Доказательство: ✅ запуск `go run -race` — вывод `program continued, x = 1`, `exit status 66`; 📚 race detector doc.

**A03-4 · Medium · go vet**
- Утверждение: vet находит «недостижимые участки кода и потенциально бесконечные циклы».
- Проблема: анализатора бесконечных циклов в vet нет (есть `unreachable`); не упомянуто, что `go test` автоматически запускает подмножество vet.
- Доказательство: ✅ список анализаторов `cmd/vendor/golang.org/x/tools/go/analysis/passes/` (есть `unreachable`, `lostcancel`, `copylock`, `timeformat`, `waitgroup`, `loopclosure`, `modernize` …; нет «infinite loop»).

**A03-5 · Low** — «`-s -w` уменьшают бинарник на 25–35%» (зависит от программы; нет `-trimpath`); «сбои очистки `/tmp` исчерпают дескрипторы диска» — бессмысленная формулировка (inode?); `gofmt` описан «через `go/ast`» (парсер `go/parser`, вывод `go/printer`); `go` назван «линтером» (линтера нет, есть `vet`); не упомянут PGO (1.21) и `go build -cover` (1.20).

### Статья 4 · Структура программы, package/import/main

**A04-1 · High · «Mechanical Sympathy: настоящая точка входа»**
- Утверждение: «лишь после того как рантайм и все пакеты готовы, планировщик создаёт первую пользовательскую горутину и запускает в ней `main.main()`» (диаграмма: Sched → GC → InitPkgs → «Запуск горутины main.main»).
- Проблема: главная горутина (`runtime.main`) создаётся в `rt0_go` **до** инициализации пакетов; `doInit` всех пакетов и `main.main` выполняются в ней же. Инициализация идёт на зафиксированном главном потоке (`lockOSThread` на время `init`). `init` может запускать горутины.
- Доказательство: ✅ `runtime/proc.go: func main()` — `doInit(runtime_inittasks)`, `gcenable()`, цикл `doInit(m.inittasks)`, `fn := main_main; fn()` в одной горутине.

**A04-2 · Medium · `runtime.rt0_go`**
- Утверждение: переход в «платформонезависимую точку `runtime.rt0_go`».
- Проблема: `runtime·rt0_go` — ассемблерная функция каждой архитектуры; платформонезависимый Go-код начинается с `runtime.schedinit`/`runtime.main`.
- Доказательство: ✅ `runtime/asm_amd64.s: TEXT runtime·rt0_go`; 15 файлов `asm_*.s`.

**A04-3 · Medium · «Инициализирует фоновые потоки сборщика мусора»**
- Проблема: у GC нет «потоков» при старте; `gcenable()` запускает горутины `bgsweep`/`bgscavenge`, воркеры разметки стартуют лениво при первом цикле GC (`gcBgMarkStartWorkers`).
- Доказательство: ✅ `runtime.main` → `gcenable()`; 📚 `mgc.go`.

**A04-4 · Low–Med · Порядок init**
- Утверждение: порядок `init` между файлами «строго зависит от лексикографического порядка имён файлов».
- Проблема: спецификация лишь **рекомендует** build-системам передавать файлы в лексикографическом порядке (go command так и делает); не упомянут порядок инициализации package-level переменных по зависимостям и правило Go 1.21 (пакеты инициализируются в порядке: первый в списке, отсортированном по import path, чьи зависимости уже инициализированы).
- Доказательство: ✅ `go_spec.html` («build systems are encouraged to present multiple files … in lexical file name order»; «sorted by import path»).

**A04-5 · Low** — «одна директория = ровно один пакет»: исключения `foo_test`, файлы с build constraints; «компилятор сканирует файлы за один проход» — типизация многопроходная; параллельность сборки обеспечивает `go build` (action graph, `-p`), а не «компилятор»; `lib/pq` — проект в maintenance-режиме (рекомендуется `pgx`); `G0` «имеет стек потока ОС» — верно для `m0` и cgo, у остальных M на Linux без cgo g0-стек выделяет рантайм.

*Проверено, верно:* запрет неиспользуемых импортов — норма спецификации (не implementation restriction); «`init` нельзя вызвать вручную»; «паника в `init` не даст начаться `main`».

### Статья 5 · Переменные, константы, вывод типа

**A05-1 · Medium · «неявных преобразований нет»**
- Утверждение: «любые неявные преобразования типов категорически запрещены».
- Проблема: в Go есть неявная присваиваемость: нетипизированные константы, конкретный тип → интерфейс, двунаправленный канал → однонаправленный, значение именованного ↔ неименованного типа с одинаковым базовым (`var s []int = MySlice{}`), `nil`.
- Доказательство: ✅ `go_spec.html`, раздел Assignability.

**A05-2 · Medium · Пример `const secondsInHour = 60*60; var delay time.Duration = secondsInHour`**
- Утверждение: подано как «бесшовное» приведение.
- Проблема: получается 3600 **наносекунд** (3.6 мкс), а не час — пример показывает ловушку, а не достоинство нетипизированных констант (см. A31-1).
- Доказательство: ✅ запуск: `fmt.Println(d)` → `3.6µs`.

**A05-3 · Medium · «произвольная точность (сотни знаков)», Итог п.4 «неограниченная точность»**
- Проблема: спецификация требует лишь ≥256 бит для целых и мантиссы ≥256 бит у float; gc ограничен (~512 бит): `1 << 600` — `constant shift overflow`.
- Доказательство: ✅ запуск `const huge = 1 << 600` → ошибка компиляции; ✅ `go_spec.html` («at least 256 bits»).

**A05-4 · Medium · «Как работает зануление»**
- Утверждение: за очистку и стека, и кучи отвечает `runtime.memclrNoHeapPointers`, «нули блоками 16/32/64 байта за один такт»; Итог п.3: «обнуление регистров и ячеек RAM».
- Проблема: для кадров стека зануление инлайнит компилятор (DUFFZERO/векторные стором, X15 как нулевой регистр в ABIInternal), и не для всех переменных; `mallocgc` очищает кучу только если `span.needzero` (свежая память от ОС уже нулевая); «за такт» — фигура речи.
- Доказательство: 📚 `runtime/malloc.go` (needzero), `abi-internal.md` (X15 = zero) ⚠️.

**A05-5 · Low** — «`:=` в 95% случаев» (произвольная статистика; идиоматично `count := int32(10)`); `shadow` в `golangci-lint` «блокирующей проверкой» (много ложных срабатываний, включается явно); «константное выражение вычисляется на этапе парсинга» — на этапе проверки типов.

### Статья 6 · Базовые типы

**A06-1 · Medium · «Строки: string»**
- Утверждение: структура `reflect.StringHeader{Data uintptr; Len int}` «так строка представлена в рантайме и пакете reflect».
- Проблема: `reflect.StringHeader` deprecated с Go 1.20 (в ст. 20 это сказано верно); в рантайме тип `stringStruct{str unsafe.Pointer; len int}`; `Data uintptr` не удерживает объект от GC.
- Доказательство: ✅ `reflect/value.go`: «Deprecated: Use unsafe.String or unsafe.StringData instead».

**A06-2 · Medium · «Кэш-линия ровно 64 байта»**
- Проблема: на x86-64 и большинстве ARM-серверов — да, но не универсально: Go сам использует `CacheLinePadSize` = 128 (arm64, ppc64), 256 (s390x), 32 (arm, mips); «в 8 раз меньше промахов» — оценка сверху для линейного прохода.
- Доказательство: ✅ `internal/cpu/cpu_*.go`.

**A06-3 · Low–Med** — детект переполнения предложен через `bits.Add64`: это только беззнаковая арифметика; в stdlib нет checked-арифметики для `int`.

**A06-4 · Low** — «bool = 1 байт из-за аппаратных ограничений» (на x86 есть битовая адресация `BT/BTS`; размер `bool` спецификацией не зафиксирован); абсолютный `epsilon=1e-9` для сравнения float (нужна относительная погрешность/ULP); не упомянуты `NaN != NaN` и NaN-ключи (в ст. 18 упомянуты).

### Статья 7 · Rune, Byte, Unicode

**A07-1 · Medium · Вводная часть**
- Утверждение: UTF-8 придумали «в сентябре 1992 в обеденном перерыве … на бумажной салфетке»; «создатели языка — Пайк и Томпсон».
- Проблема: по рассказу Пайка — вечером за ужином в дайнере Нью-Джерси, на бумажной подложке (placemat), реализацию Томпсон дописал в те же выходные; создателей Go трое (+Гризмер); UTF-8 стандартизован отдельно (X/Open, Unicode, RFC 3629).
- Доказательство: 📚 Rob Pike, «UTF-8 history».

**A07-2 · Medium · «Срезы строк ломают UTF-8»**
- Утверждение: `fmt.Println(s[0:1]) // ... получаем ""`.
- Проблема: результат — строка из одного байта `0xD0` (длина 1, невалидный UTF-8), не пустая; противоречит абзацу ниже («одиночный байт `0xD0`»).
- Доказательство: ✅ запуск: `len(s[0:1])=1`, `%q` → `"\xd0"`.

**A07-3 · Medium · «Как работает декодирование UTF-8»**
- Утверждение: «процессор с помощью битовых масок проверяет старшие биты»; невалидный вход — это «байт продолжения без начального».
- Проблема: декодирование — программное (`runtime.decoderune`, `utf8.DecodeRune`), с быстрым путём для ASCII; невалидны также байты `0xC0/0xC1/0xF5–0xFF`, overlong-формы и суррогаты `U+D800–DFFF` — все дают `RuneError` шириной 1.
- Доказательство: 📚 `unicode/utf8` doc.

**A07-4 · Medium · «`[]rune(s)` выделяет O(N) в куче»**
- Проблема: для не убегающего результата небольшого размера аллокации нет.
- Доказательство: ✅ `AllocsPerRun`: `rr := []rune("Привет")` без escape → 0 аллокаций. «Zero-Allocation вариант через `utf8`» в статье состоит из одних комментариев (кода нет).

**A07-5 · Low** — `%c` для байта `0xD0` печатает руну `U+00D0` `Ð`, а не «битые байты»; «строка — неизменяемый срез байт» (нет `cap`); Итог п.6 «всегда используйте `RuneCountInString`» противоречит врезке про grapheme clusters; `RuneCountInString` не «валидирует», а считает каждый невалидный байт одной руной; опечатка «Кириллистическая».

### Статья 8 · Операторы и выражения

**A08-1 · High · «Инкремент и декремент: конец UB»**
- Утверждение: `a = b++ + ++c` — источник UB в C/C++; «в C, C++ и Java … порядок вычисления не фиксировался».
- Проблема: для разных объектов `b` и `c` это не UB (порядок вычисления не специфицирован, но модификации одного объекта дважды нет; UB — `i = i++ + ++i`); в Java порядок слева направо определён JLS жёстко; в C++17 порядок для ряда операторов закреплён.
- Доказательство: 📚 C11 §6.5p2, JLS §15.7, C++17 [expr.pre].

**A08-2 · High · «Арифметические сдвиги»**
- Утверждение: `fmt.Printf("%b\n", x>>1) // 11000000 (-64)` для `int8`.
- Проблема: `%b` для знакового отрицательного печатает знак и модуль: `-1000000`.
- Доказательство: ✅ запуск: `-1000000`; `uint8(x>>1)` → `11000000`.

**A08-3 · High · «Никакой перегрузки операторов»**
- Утверждение: `a = b + c` — «либо сложение чисел, либо конкатенация строк. Это пара инструкций CPU, никаких тяжёлых аллокаций»; «базовый оператор гарантирует O(1)».
- Проблема: конкатенация строк — `runtime.concatstrings` (аллокация O(len) и копирование; стековый буфер ≤32 байт возможен только для не убегающего короткого результата); индексирование и деление могут паниковать.
- Доказательство: ✅ `AllocsPerRun`: короткая конкатенация без escape — 0 аллокаций (стековый tmpBuf), для результата >32 байт или с escape — аллокация; 📚 `runtime/string.go`.

**A08-4 · High · «Деление и %»**
- Утверждение: при делении на переменную `y==0` «процессор сгенерирует `SIGFPE`, который рантайм перехватит и превратит в `panic`, аварийно завершив текущую горутину».
- Проблема: gc вставляет явную проверку делителя и вызывает `runtime.panicdivide`; неперехваченная паника останавливает **весь процесс** (exit 2), а не горутину; для float деление на 0 даёт `±Inf/NaN` без паники; `MinInt/-1` не паникует.
- Доказательство: ✅ `cmd/compile/internal/ssagen/ssa.go`: `s.check(cmp, ir.Syms.Panicdivide)`.

**A08-5 · Medium · «Ленивые вычисления»**
- Проблема: «Probability Based Optimization» — не устоявшийся термин (оптимальный порядок — по отношению стоимость/вероятность); не сказано, что порядок вычисления операндов в Go определён только частично (вызовы/каналы слева направо, но не относительно переменных: `[]int{a, f()}`), поэтому тезис «Go убрал класс ошибок порядка вычисления» — преувеличение.
- Доказательство: ✅ `go_spec.html`, «Order of evaluation».

**A08-6 · Low** — «решение Кена Томпсона» (++ как statement) — без источника; текст ошибки `syntax error: unexpected ++ at end of statement`; не упомянуты правила сдвигов (счёт ≥ ширины → 0/−1, отрицательный счёт паникует, знаковые счётчики допустимы с 1.13); на amd64 `&^` → `ANDN` только при `GOAMD64=v3` (иначе `NOT+AND`), на arm64 — `BIC` (верно).

### Статья 9 · if, switch, for

**A09-1 · High · «Самая известная ловушка Go (исправлено в 1.22)»**
- Утверждение: «Начиная с Go 1.22 … компилятор автоматически выделяет новую переменную на каждой итерации».
- Проблема: только если в `go.mod` модуля указано `go 1.22` или выше; изменение касается и трёхчастного `for i := 0; …; i++`, а не только `range` (Итог п.3 говорит только про `range`).
- Доказательство: ✅ запуск: `go 1.21` в `go.mod` на тулчейне 1.27 → `3 3 3`; ✅ `godebug.md`.

**A09-2 · Medium · Формы цикла**
- Проблема: перечень «четырёх форм» неполон: `for i := range 10` (1.22), range-over-func (1.23, `iter.Seq`); «три главные и единственные управляющие конструкции» не учитывает `select`, `goto`, метки.
- Доказательство: ✅ `go_spec.html` (range over integer / function).

**A09-3 · Medium · «Как оптимизируется switch»**
- Утверждение: «в процессе SSA» компилятор по плотности меток строит jump table; она «полностью устраняет промахи предсказателя ветвлений».
- Проблема: lowering `switch` выполняется до SSA в фазе walk; jump tables — для целочисленных (и, отдельно, для строк по длине/значению) с порогами `minCases=8`, `minDensity=4`; на архитектурах, где реализовано; косвенный переход предсказывается через BTB и может промахиваться. Версия (1.19) и платформы не указаны.
- Доказательство: ✅ `cmd/compile/internal/walk/switch.go` (`minCases = 8`, `minDensity = 4`, `binarySearchMin = 4`).

**A09-4 · Low–Med · Type switch**
- Проблема: описано через `eface._type`; для непустых интерфейсов и интерфейсных `case` используются `itab`/`interfaceSwitch` (с кэшем в точке использования с 1.22); `interface{}` вместо `any`.
- Доказательство: ✅ `runtime/iface.go`: `typeAssert`, `interfaceSwitch`.

**A09-5 · Low** — интервью про `range` по слайсу 1 КБ «безусловно падение производительности» (зависит; для массивов `range` копирует массив целиком — не сказано); `for { msg := <-ch }` не обрабатывает закрытый канал; `break` внутри `switch` в цикле выходит из `switch`; `goto fail` — баг Apple Secure Transport (iOS и macOS, 2014).

### Статья 10 · Функции

**A10-1 · High · «Register-based ABI»**
- Утверждение: пара `(int, error)` — `int` в `RAX`, «указатель на структуру `error`» в `RBX`; диаграмма: «Результат в RAX, error в RBX».
- Проблема: `error` — интерфейс из двух слов (`itab`, `data`); в ABIInternal это `RAX` (int), `RBX` (itab), `RCX` (data). Противоречит ст. 12 («16 байт через регистры»).
- Доказательство: ✅ `cmd/compile/abi-internal.md`: целочисленные регистры `RAX, RBX, RCX, RDI, RSI, R8, R9, R10, R11`, `X0–X14`; интерфейс — пара слов.

**A10-2 · Medium · «Начиная с Go 1.17 … перешла на Register-based ABI»**
- Проблема: в 1.17 — только linux/amd64, darwin/amd64, windows/amd64 (arm64 — 1.18, riscv64 — 1.19 и т.д.); часть платформ по-прежнему на стековом ABI0; ускорение ~5% (release notes); фраза «передача со скоростью тактовой частоты кристалла» не отражает spill-области.
- Доказательство: 📚 Go 1.17/1.18/1.19 release notes.

**A10-3 · Low–Med · «Слайсы и мапы по ссылке — это ложь»**
- Проблема: формально верно для слайса; для `map` переменная — указатель на runtime-структуру, поведение (вставка видна вызывающему) близко к ссылочному (Effective Go прямо называет map ссылочным типом); не упомянут алиасинг общего массива при `f(s...)`.

**A10-4 · Low** — пример `evens := filter(...)` без использования (compile error); функциональные опции не упомянуты; «нет перегрузки/дефолтов — наследие Bell Labs» — мотивация Go FAQ, остальное интерпретация.

### Статья 11 · Именованные возвраты и defer

**A11-1 · Medium · Введение**
- Утверждение: «GC освобождает только память, но понятия не имеет о дескрипторах ОС».
- Проблема: `os.File` имеет финализатор (`runtime.SetFinalizer(f.file, (*file).close)`), закрывающий fd при сборке мусора (не гарантированно и не вовремя) — корректнее «нельзя полагаться на GC».
- Доказательство: ✅ `src/os/file_unix.go:225`.

**A11-2 · Medium · «defer гарантированно выполнится»**
- Проблема: не выполняется при `os.Exit`, `log.Fatal*`, фатальных ошибках рантайма (`all goroutines are asleep`, `concurrent map writes`, OOM, stack overflow), `kill -9`; выполняется при `runtime.Goexit`.
- Доказательство: ✅ запуск: `os.Exit(3)` — отложенный `fmt.Println` не печатается.

**A11-3 · Medium · Open-coded defers**
- Утверждение: условие — «≤ 8 defer и не в цикле».
- Проблема: плюс `число return × число defer ≤ 15`; отключается при `-N`, race-инструментации, heap-allocated result-параметрах; `deferBits` — переменная стека (не «битовая маска в регистре» как факт); при панике open-coded defers обрабатываются через сканирование стека/funcdata (медленнее); история «до 1.13 в куче (или на стеке)» путана (1.13 — defer на стеке, 1.14 — open-coded). Числа 35–50 нс → ~1 нс без источника.
- Доказательство: ✅ `ssagen/ssa.go` (`s.curfn.NumReturns*s.curfn.NumDefers > 15`, `base.Flag.N == 0`, `instrumentEnterExit`); 📚 proposal golang/go#34481.

**A11-4 · Low–Med** — `defer f.Close()` для файла на запись игнорирует ошибку `Close` (см. A29-1); сниппет с `defer fmt.Println("…", time.Since(start))` напечатает ~0 с (время вычисляется сразу; «0 миллисекунд» неточно); в комментарии артефакт `time.Since-start-`; не упомянуты `try-with-resources`/`using`.

**A11-5 · Low** — «Naked return — антипаттерн для функций длиннее 5–10 строк» (цифры произвольны); не упомянута ошибка компиляции `result parameter err not in scope at return` при затенении именованного результата.

### Статья 12 · Обработка ошибок

**A12-1 · Medium · `%w` и цепочки**
- Утверждение: `%w` «формирует связный список».
- Проблема: с Go 1.20 допускается несколько `%w`, `Unwrap() []error`, `errors.Join` — структура дерево; не описаны метод `Is(target) bool`, паника `errors.As` при некорректной цели; в Go 1.26+ есть `errors.AsType[E]` (generic).
- Доказательство: ✅ `src/errors/wrap.go:167: func AsType[E error](err error) (E, bool)`.

**A12-2 · Low–Med** — sentinel-ошибки названы «глобальными неизменяемыми переменными» (это изменяемые переменные пакета; экспорт sentinel — часть API); в примере `if err == ErrUserNotFound` без `errors.Is`, которым статья же советует заменять `==`.

**A12-3 · Low** — «ошибки не требуют таблиц раскрутки стека и передаются через регистры» верно только для ABIInternal на поддерживаемых платформах; typed-nil-пример верен (✅ `fmt.Println(err)` печатает `<nil>`, потому что `fmt` перехватывает панику nil-receiver) — стоит пояснить; «в `itab` записывается указатель на тип `*MyError`» — это указатель на `itab`, а не на `_type`; «утиная типизация» — статическая структурная.

### Статья 13 · Panic, Recover, stack trace

**A13-1 · High · «net/http и паники»**
- Утверждение: «паника внутри HTTP-обработчика не роняет сервер. Клиент получает `HTTP 500 Internal Server Error`».
- Проблема: `net/http` перехватывает панику, логирует stack trace и **закрывает соединение** (`c.close()`); ответ 500 не отправляется (клиент видит EOF/reset; в HTTP/2 — RST_STREAM). 500 возвращают middleware фреймворков. `http.ErrAbortHandler` подавляет логирование.
- Доказательство: ✅ `net/http/server.go` (`conn.serve`: `recover()` → `logf("http: panic serving …")` → `c.close()`; ответ не пишется).

**A13-2 · Medium · «`runtime.gorecover` проверяет аппаратный счётчик инструкций (PC)»**
- Проблема: механизм — подсчёт «не-обёрточных» кадров между `gopanic` и `gorecover` через unwinder (ровно один кадр) и сравнение с `p.startSP`; не PC. «Несанкционированный перехват чужих паник» — не мотивация спецификации.
- Доказательство: ✅ `runtime/panic.go: gorecover` (комментарий «exactly one non-wrapper frame between gopanic and gorecover»).

**A13-3 · Medium · Формат stack trace**
- Утверждение: пример `main.process(0xc0000100a0, 0x3, 0x3)`; «физические значения регистров или ячеек стека»; `traceback` «считывает `RSP` и `RBP`».
- Проблема: в современном Go аргументы печатаются как `main.process({0x…?, 0x…?, 0x…?})` (скобки для составных значений, `?` — «значение может быть неточным», т.к. при register ABI не обязаны сохраняться); инлайн-функции показываются как `main.process(...)`. Раскрутка идёт по `pclntab` (SP-дельты), а не по frame pointers.
- Доказательство: ✅ запуск: `main.process({0xd2ea67efe68?, 0xd2ea66fc030?, 0xd2ea67efe90?})`.

**A13-4 · Medium · Что `recover` не ловит**
- Проблема: не сказано, что `fatal error` рантайма (`concurrent map writes`, `all goroutines are asleep`, `stack exceeds 1000000000-byte limit`, OOM, `unlock of unlocked mutex`) не перехватываются; после Go 1.21 `panic(nil)` даёт `*runtime.PanicNilError` (в `go 1.20` — `panicnil=1`: `recover()` возвращает nil, и `if r != nil` пропускает такую панику).
- Доказательство: ✅ `godebug.md` (`panicnil`).

**A13-5 · Medium · Вводная часть**
- Утверждение: философия Go «наследует „Let it crash“ Армстронга»; выход за границы среза означает, что «память может быть скомпрометирована».
- Проблема: в Erlang «процесс» — лёгкий изолированный; в Go паника в горутине убивает весь процесс ОС — противоположность подхода; в memory-safe Go bounds check **предотвращает** порчу памяти, риск — логика/`unsafe`/гонки.

**A13-6 · Low–Med** — неявные паники сведены к `SIGSEGV`; большинство runtime-паник (index out of range, nil map write, integer divide by zero, type assertion, send on closed channel) — явные проверки (`runtime.panicIndex` и др.); описание `gopanic` через список `_defer` не учитывает open-coded defers (1.14+) и переписанную в 1.22 реализацию; STW при фатальной панике — это `freezetheworld`, а не обычный GC-STW; «ровно два сценария, когда panic оправдан» противоречит абзацу выше (внутренние panic/recover в парсерах, как в `encoding/json`, `text/template`); не описаны `GOTRACEBACK=none`, `ulimit -c` для `crash`.

### Статья 14 · Указатели

**A14-1 · Medium · «Миф: передавать по указателю всегда быстрее»**
- Утверждение: «перемещение объекта в Кучу обязывает GC … выше паузы Stop-The-World»; обращение по указателю в кучу «гарантирует промахи кэша».
- Проблема: передача `&x` вниз по стеку вызовов не переносит `x` в кучу — только escape (возврат, сохранение в куче/интерфейсе, `go`/`defer`/замыкание, утечка параметра); STW-паузы современного GC почти не зависят от размера кучи — растёт стоимость mark/assist и частота циклов; «гарантирует» — преувеличение.
- Доказательство: ✅ `AllocsPerRun`: `DoWork(any)` без утечки — 0 аллокаций.

**A14-2 · Medium · «Пакет unsafe»**
- Утверждение: `unsafe` нужен для «высокоскоростной сериализации в `encoding/json`».
- Проблема: стандартный `encoding/json` не импортирует `unsafe` (построен на `reflect`); unsafe используют сторонние сериализаторы (sonic, easyjson-генерация).
- Доказательство: ✅ `grep -l '"unsafe"' src/encoding/json/*.go` — пусто.

**A14-3 · Medium · «Опасность uintptr»**
- Утверждение: опасность — GC «переместит стек».
- Проблема: стек перемещается при росте/сжатии, а не «решением GC»; кроме того, `uintptr` не удерживает объект: если это единственная ссылка, объект кучи может быть собран (heap Go не перемещающая). Не показан безопасный `unsafe.Add` (1.17), `unsafe.Slice/String/StringData`, шесть допустимых паттернов `unsafe.Pointer`.
- Доказательство: 📚 `unsafe` package doc.

**A14-4 · Low–Med** — «`*p = 100`: адрес идёт по шине адреса в контроллер памяти» — запись обрабатывается AGU/TLB/store buffer/L1, контроллер памяти участвует при промахе в LLC; эвристика «≤64–128 байт по значению» без источника (Go Code Review Comments: выбор по семантике, `sync.Mutex`, согласованности); `var u *User; u.Greet()` при value-receiver паникует на стороне вызова — не сказано.

### Статья 15 · Массивы

**A15-1 · Medium · «Нулевые аллокации», размещение на стеке**
- Утверждение: компилятор резервирует массив «во фрейме стека без единой динамической аллокации»; `var data [1000000]int` (8 МБ) копируется «на стек».
- Проблема: явные локальные переменные > 128 КБ (`MaxStackVarSize`) и неявные (`new`, `&T{}`, `make`) > 64 КБ уходят в кучу; массив, на который берётся убегающий указатель/срез, тоже. «Дефолтный 2 КБ стек» — минимум; с Go 1.19 стартовый размер адаптивный.
- Доказательство: ✅ `cmd/compile/internal/ir/cfg.go` (128 КБ/64 КБ); ✅ `runtime/stack.go: startingStackSize`/`adaptivestackstart`.

**A15-2 · Medium · «Сравнение массивов — побитовое»**
- Проблема: `==` для массивов поэлементно по правилам типа: для `float` не побитовое (`NaN != NaN`, `+0 == -0`), для строк/интерфейсов — по значению/динамическому типу; сравнение `[N]any` с несравнимыми динамическими типами паникует.
- Доказательство: ✅ `go_spec.html` (Comparison operators).

**A15-3 · Low–Med** — «в C массив — это просто указатель на первый элемент» (массив ≠ указатель: `sizeof`, `&arr`; decay происходит в выражениях — ниже в тексте сказано верно); не упомянуты массивы как ключи `map`, копирование при `for i, v := range arr`, преобразование срез→массив (1.20) и срез→указатель на массив (1.17).

### Статья 16 · Slice

**A16-1 · Medium · Несогласованность с ст. 6** — см. X-3 и A06-1: здесь `SliceHeader` корректно deprecated, в ст. 6 — `StringHeader` без оговорок.

**A16-2 · Medium · Итог п.4 / раздел «make»**
- Утверждение: `make([]T, 0, cap)` «минимизирует системные вызовы аллокации и устраняет фрагментацию»; «резервируем блок в куче».
- Проблема: аллокации не делают syscalls (`mallocgc` берёт из `mcache`/`mcentral`; `mmap` — при росте кучи); фрагментацию не «устраняет», а уменьшает число промежуточных аллокаций/копирований; небольшой константный `make` без escape может быть на стеке (≤64 КБ).
- Доказательство: ✅ `ir/cfg.go` (`MaxImplicitStackVarSize`).

**A16-3 · Low–Med** — пример `modify`: `fmt.Println(nums)` выводит `[999 2 3]` (не `[999, 2, 3]`); не сказано, что `append` при `cap=3` реаллоцирует (поэтому исходный массив тоже цел), а при `cap>len` записал бы 42 в общий массив, видимый через `nums[:4]`.

**A16-4 · Low** — не упомянуты `s[a:b:c]` (вынесено в ст. 17), `copy`, `clear` (1.21), `slices` (1.21); «всегда используйте make» — преувеличение для маленьких результатов.

### Статья 17 · Slice под капотом

**A17-1 · Medium · Врезка про memmove**
- Утверждение: «для среза 100 МБ в RAM одновременно будут старые 100 МБ и новые **200** МБ».
- Проблема: противоречит следующему разделу (для больших срезов рост ≈1.25×): новые ≈125–130 МБ + округление.
- Доказательство: ✅ эксперимент: capacity `[]int` растёт `256 → 512 → 848 → 1280 → 1792 …`.

**A17-2 · Medium · Алгоритм роста**
- Проблема: не сказано, что при `newLen > 2*oldCap` (append нескольких элементов) берётся `newLen`; затем округление до size class; для разных `sizeof(T)` итоговый `cap` разный. Формула `newcap += (newcap + 3*threshold) >> 2` и порог 256 — **верны**; 24 для `[]int8` из `cap=10` — **верно**.
- Доказательство: ✅ `runtime/slice.go: nextslicecap`; ✅ запуск: `cap([]int8)` 10→24.

**A17-3 · Low–Med** — «Утечка №2: заражение через append» — это алиасинг/порча данных, не утечка памяти; настоящая третья утечка не описана: после `s = s[:n]`/удаления указатели в «хвосте» массива удерживают объекты (нужен `clear(tail)`; `slices.Delete` зануляет хвост с 1.22). Доказательство: ✅ `slices.Delete` вызывает `clear(s[len(s):oldlen])`.

**A17-4 · Low** — «GC Sweep уничтожает старый массив» (недостижимость определяет mark, sweep лишь освобождает span); `slices.Clone` сохраняет nil-ность и может вернуть `cap > len`; `memmove` — «32/64 байта за такт» (выбор по размеру: AVX2, `REP MOVSB`, non-temporal); нет упоминания write barrier и амортизированной O(1) оценки `append`.

### Статья 18 · Map. Хеш-таблица

**A18-1 · High · Вся статья (преаллокация, rehashing, «бакеты»)**
- Утверждение: `make(map, n)` «выделит необходимое число бакетов»; «эвакуация (rehashing)»; рост описан через бакеты/оверфлоу.
- Проблема: с Go 1.24 встроенные `map` — Swiss tables: нет `B`/`oldbuckets`/overflow-бакетов; группы по 8 слотов с контрольным словом; directory таблиц (extendible hashing); таблица ≤1024 слотов; рост удвоением/расщеплением отдельной таблицы; tombstones. Версионная оговорка есть только во врезке ст. 19.
- Доказательство: ✅ `src/internal/runtime/maps/map.go` (комментарий: «design is based on Abseil’s Swiss Table»), `table.go: maxTableCapacity = 1024`, tombstones.

**A18-2 · Medium · «Требования к ключам»**
- Проблема: интерфейсы разрешены, но если динамический тип несравним, `m[k]` паникует в рантайме (`hash of unhashable type`); сравнение структур «побитово» неверно (строки по содержимому, float по IEEE, padding игнорируется); каналы тоже допустимые ключи.
- Доказательство: ✅ `go_spec.html` (Comparison operators, Map types).

**A18-3 · Medium · «Потокобезопасность»**
- Утверждение: при чтении+записи рантайм «мгновенно завершит процесс»; ошибка — «аппаратная», «`abort` на уровне ядра ОС».
- Проблема: детектор best-effort (проверка флага `writing` в части путей), гонка может остаться незамеченной и тихо испортить данные; это `fatal error` рантайма (`throw`, exit 2 + traceback), не сигнал ядра.
- Доказательство: ✅ `internal/runtime/maps` (флаг `writing`, `fatal("concurrent map …")`).

**A18-4 · Low–Med** — примеры `var m1…`, `m2 := …` на уровне пакета в блоке `package main` не компилируются (`:=` вне функции); порядок «`2:B 1:A 3:C`» для 3-элементной карты невозможен в реализации ≤1.23 (малая карта в одном бакете обходится циклическим сдвигом), допустим при Swiss; `sync.Map` с 1.24 переписана на HashTrieMap; не упомянуты `clear(m)`, `maps.Keys` + `slices.Sorted` (1.23), запрет `m[k].f = v` и `&m[k]`.

### Статья 19 · Map под капотом

**A19-1 · High · Тело статьи**
- Утверждение: `hmap`, `bmap`, `tophash`, `Load Factor > 6.5`, `same-size evacuation`, `overflow` — описаны как механика `map`; врезка «Swiss Tables (Go 1.24+) … фундаментальные свойства сохраняются».
- Проблема: для актуальных версий верны лишь внешние свойства (указатель на структуру, O(1), память не сжимается); механика роста/эвакуации/удаления другая. Читатель, открывший исходники Go 1.24–1.27, не найдёт ни `hmap`, ни `bmap`.
- Доказательство: ✅ см. A18-1; load factor 7/8, группы по 8 слотов, `H1` (57 бит)/`H2` (7 бит) в `map.go`.

**A19-2 · Medium · «Векторный поиск внутри бакета»**
- Утверждение: в `bmap` «процессор сканирует 8-байтный массив `tophash` быстрыми инструкциями (SIMD)».
- Проблема: в реализации `hmap/bmap` это обычный скалярный цикл по 8 байтам; параллельное сравнение 8 слотов — свойство Swiss tables (побитовые трюки/SWAR, SIMD — опционально).
- Доказательство: ✅ `internal/runtime/maps/map.go` («compare all 8 slots in parallel … clever bitwise manipulation»).

**A19-3 · Medium · «Великая утечка памяти»**
- Утверждение: для 1 000 000 элементов «около 150 000 бакетов», «сотни мегабайт».
- Проблема: число бакетов — степень двойки: при `load ≤ 6.5` нужно ≥153 847 → `B=18` → 262 144 бакета (+overflow); размер `map[string]int` ≈ 262 144 × 208 Б ≈ 54 МБ, `map[int64]int64` ≈ 38 МБ — «сотни МБ» верно лишь для крупных значений.

**A19-4 · Low–Med** — `hash0` «криптографически случайный», «атаки математически невозможны» (seed из `runtime.rand`; защита вероятностная; для 1.22+ `rand` на ChaCha8); «xxHash» в рантайме — не-AES fallback вдохновлён wyhash ⚠️ (проверить по версии); бакет «в одну–две кэш-линии» — для `map[int64]int8` 88 Б, для `map[string]int` 208 Б; ключи/значения >128 Б хранятся косвенно; «бакет компилируется на лету» — генерируется компилятором при сборке под каждый тип карты.

**A19-5 · Low** — `for k := range m { delete(m,k) }` компилятор превращает в `mapclear` (память не освобождается — совпадает с выводом статьи); не упомянут `clear(m)`; не описана семантика итератора при росте.

### Статья 20 · Строки

**A20-1 · Medium · `strings.Builder`**
- Утверждение: структура «защищена специальным маркером, предотвращающим последующую мутацию буфера после `.String()`»; Итог п.3: Builder «обеспечивает сборку без аллокаций».
- Проблема: поле `addr` — `copyCheck` (паника `illegal use of non-zero Builder copied by value`) против копирования самого Builder; после `String()` писать можно (`append` не меняет уже возвращённые байты `[0:len]`); аллокации есть (минимум одна при `Grow`), zero-copy — только в `String()`.
- Доказательство: ✅ `strings/builder.go`; ✅ запуск: после `String()` повторная запись работает.

**A20-2 · Medium · «`[]byte(s)` всегда выделяет в куче»**
- Проблема: для результата, не убегающего и не изменяемого, копирования нет (даже для 1 МБ строки); для изменяемого результата ≥32 байт — аллокация; `m[string(b)]` — 0 аллокаций; «гарантированная» оптимизация — деталь реализации gc, не гарантия языка.
- Доказательство: ✅ `AllocsPerRun`: read-only non-escaping (100 Б и 1 МБ) → 0; mutated → 1; `m[string(bs)]` → 0.

**A20-3 · Medium · «String Interning»**
- Проблема: описаны только литералы; не упомянут `unique` (Go 1.23, `unique.Make`/`unique.Handle`) — стандартный способ интернировать динамические строки; `strings.Clone` (1.18) не упомянут; обещанная во введении «колоссальная утечка памяти» при срезе подстроки (подстрока держит весь исходный массив) в тексте не показана (подстрока подана только как плюс).
- Доказательство: ✅ `src/unique/` существует.

**A20-4 · Low–Med** — `io.WriteString` «не копирует» — только если Writer реализует `io.StringWriter` (`os.File`, `http.ResponseWriter`, `bytes.Buffer`, `strings.Builder`); иначе `w.Write([]byte(s))`.

**A20-5 · Low** — «5 ГБ временных байтов, многосекундные паузы»: суммарный объём ≈N²/2 верный, время обычно ~0.5–1.5 с; «неизменяемость защищает от гонок» не распространяется на конкурентную запись самой переменной (двухсловное значение может «порваться»); введение обещает «работу с Unicode», раздела нет (он в ст. 7).

### Статья 21 · Struct

**A21-1 · Medium · «Mechanical Sympathy: выравнивание»**
- Утверждение: «процессор читает память словами по 8 байт; невыровненный `int64` требует двух циклов шины».
- Проблема: на x86-64 и современных ARM невыровненный доступ внутри одной кэш-линии обычно бесплатен; штраф — на границе линии/страницы; на ряде архитектур — trap. Реальные причины выравнивания в Go — переносимость, 64-битные атомики и GC; на 32-битных платформах `int64` выровнен по 4 — известная ловушка атомиков.
- Доказательство: 📚 Intel SDM (unaligned accesses), `sync/atomic` doc («64-bit alignment»).

**A21-2 · Medium · «Сортируйте поля по убыванию размера»**
- Проблема: оптимум — по убыванию **выравнивания** (`[9]byte` — размер 9, align 1; `string` — 16/8); `fieldalignment` учитывает «pointer bytes» (поля-указатели ближе к началу уменьшают область сканирования GC); перестановка может ухудшить читаемость и локальность «горячих» полей; false sharing (нужен padding) не упомянут.
- Доказательство: ✅ запуск: `Sizeof(BadStruct)=24`, `Sizeof(GoodStruct)=16` (числа статьи верны).

**A21-3 · Low–Med** — «парсер тега разбивает строку через `strings.Split`» (`reflect.StructTag.Get` разбирает вручную; `encoding/json` кэширует поля типа — разбор один раз на тип); не упомянуты `encoding/json/v2` (Go 1.25, GOEXPERIMENT), sonic/go-json.

**A21-4 · Low–Med** — `done <- struct{}{}` на небуферизованном канале блокируется без читателя и будит одного получателя; идиома broadcast — `close(done)`; `map[string]struct{}` vs `map[string]bool` — выгода мала (слот выровнен); `struct{}` последним полем добавляет padding.

**A21-5 · Low** — «`fieldalignment` — линтер `golangci-lint`»: это анализатор из `golang.org/x/tools`, подключается через `govet`; `maligned` удалён; «все указатели на zero-size → один `zerobase`» — спецификация допускает разные адреса.

### Статья 22 · Методы

**A22-1 · Medium · «Правило консистентности»**
- Утверждение: «НИКОГДА не смешивайте Value и Pointer ресиверы»; названы «четыре правила стандартной библиотеки».
- Проблема: это рекомендация Go FAQ/Code Review Comments, не «правило stdlib»; stdlib нарушает его: у `time.Time` большинство методов value, но `UnmarshalJSON/UnmarshalText/UnmarshalBinary/GobDecode` — pointer. «НИКОГДА» неверно: допустимо при явной семантике (Unmarshal-методы).

**A22-4 · Low** — не упомянуты method values/expressions (`u.Rename` захватывает копию receiver; `(*T).Method`), запрет методов на неименованных/интерфейсных/указательных типах и типах другого пакета; «трансформация на этапе парсинга AST» — не парсер.

### Статья 24 · Интерфейсы под капотом

**A24-1 · Medium · «Boxing»**
- Утверждение: `DoWork(x) // АЛЛОКАЦИЯ! x «убегает» в кучу`.
- Проблема: для не утекающего/инлайнимого `DoWork` аллокации нет (интерфейс остаётся на стеке; константы — в read-only data; значения <256 — `staticuint64s`); аллокация (`runtime.convT64`) возникает при escape (`fmt.Println(x)`, сохранение, `go`). Не сказано, что pointer-shaped типы (указатель, `map`, `chan`, `func`, структура из одного указателя) кладутся в `data` напрямую без boxing. Заголовок раздела «Утечка памяти и Boxing» — boxing не утечка.
- Доказательство: ✅ `AllocsPerRun`: `DoWork(x)` → 0; `box(x+1000)` (не инлайнится, возвращает `any`) → 1; `fmt.Sprint(x+1000)` → 2.

**A24-2 · Medium · «PGO в Go 1.22+»**
- Проблема: PGO — preview в 1.20, GA в 1.21; девиртуализация вызовов интерфейсных методов по профилю — с 1.21 (расширена в 1.22). Статическая девиртуализация без PGO существует давно.
- Доказательство: 📚 Go 1.20/1.21/1.22 release notes.

**A24-3 · Medium · «Механика Type Assertion»**
- Утверждение: `val.(T)` — сравнение `_type` двух указателей, «в `iface` предварительно сверяется `hash`»; для интерфейсов — `assertI2I2`/`assertE2I2` и `itabTable`.
- Проблема: для `iface → T` gc сравнивает указатель `itab` со статическим `go:itab.T,I` (в `dottype1` есть параметр `targetItab`), для `eface → T` — `_type`; `hash` используется в type switch (бинарный поиск по хэшам). Для «interface → interface» в 1.22+ — `runtime.typeAssert`/`interfaceSwitch` с кэшем на call site; `assertE2I` остался вспомогательным.
- Доказательство: ✅ `runtime/iface.go` (`typeAssert`, `interfaceSwitch`); ✅ `ssagen/ssa.go: dottype1(… targetItab …)`.

**A24-4 · Low–Med** — «рантайм вычисляет `itab` один раз и хранит в `itabTable` с атомарными блокировками»: для преобразований, известных компилятору, `itab` статический (`go:itab.*`); динамически (`getitab`) строятся при assertion/reflect; чтение таблицы lock-free, запись под `itabLock`.

**A24-5 · Low** — `i == nil` проверяет слово типа/itab (инвариант: nil-тип ⇒ nil-data), а не «оба слова»; «налог 1–2 нс» — типичная оценка без источника.

### Статья 26 · Пакеты

### Статья 27 · Видимость имён

**A27-1 · High · «Как компилятор это понимает?»**
- Утверждение: правило «зашито в лексический анализатор»: `scanner.Scan()` проверяет `unicode.IsUpper`; «Name Mangling»: экспортируемые символы пишутся под чистыми именами (`User`), неэкспортируемые дополняются префиксом пакета; «линковщик аппаратно пресекает» доступ.
- Проблема: вымышленный механизм. В объектных файлах **все** символы квалифицированы путём пакета; видимость проверяет type checker на этапе компиляции; сканер экспортируемость не определяет. Обход возможен через `//go:linkname` (с Go 1.23 «pull»-linkname ограничен флагом `-checklinkname`) и ассемблер.
- Доказательство: ✅ `go tool nm`: `fmt.Fprintln` (экспортируемый) и `fmt.newPrinter`, `fmt.(*pp).doPrintln` (неэкспортируемые) — оба с префиксом пакета; ✅ `grep IsUpper|IsExported` по `cmd/compile/internal/syntax/scanner.go` и `go/scanner/scanner.go` — пусто; 📚/⚠️ про `-checklinkname` — Go 1.23 release notes (linker), по памяти.

**A27-2 · Medium · «JSON и рефлексия»**
- Утверждение: рантайм «жёстко пресекает любые попытки рефлексии читать или записывать неэкспортируемые поля»; сделать поле неэкспортируемым — «самый надёжный способ» не допустить утечки.
- Проблема: `reflect` позволяет **читать** значение неэкспортируемых полей (`v.Field(i).String()/Int()`; запрещены `Interface()` и `Set*`); `fmt` с `%+v`/`%#v`, `spew`, `go-cmp`, логирование с `%+v` печатают неэкспортируемые поля (в т.ч. `password`). Верно для `encoding/json/xml/gob`, но не для логов.
- Доказательство: ✅ запуск: `fmt.Printf("%+v", User{1, "secret"})` → `{ID:1 password:secret}`.

**A27-3 · Medium · «Неэкспортируемые типы в публичном API»**
- Утверждение: «идиоматичное решение — возвращать абстрактный интерфейс, следуя правилу „Accept interfaces, return structs“».
- Проблема: внутреннее противоречие — правило велит возвращать структуру (экспортируемый тип); корректный совет — экспортировать тип. Линтеры (`revive: unexported-return`) предупреждают именно об этом.

**A27-4 · Medium · «Sealed Interfaces»**
- Утверждение: сторонний пакет «физически не сможет реализовать метод `internal()`»; компилятор отклонит любую стороннюю реализацию.
- Проблема: внешний тип удовлетворяет такому интерфейсу встраиванием самого интерфейса (`type Fake struct{ events.Event }` продвигает `internal()`); запечатывание защищает от явной реализации, но не от встраивания (так и мокают `testing.TB`).
- Доказательство: ✅ эксперимент: `ext.Fake{events.Event}` из другого пакета передан в `events.Handle` — компилируется и работает (`fake`); пример с `testing.TB` (`private()`) — подтверждён (`testing/testing.go:1001`).

**A27-5 · Low–Med** — пример `u.password == hash(input)` небезопасен (нужны bcrypt/argon2 и `subtle.ConstantTimeCompare`); сообщение компилятора для литерала — `cannot refer to unexported field password in struct literal`; не упомянуто, что идентификатор, начинающийся с не-регистровой буквы (иероглифы), неэкспортируем (кириллица — работает); в unsafe-примере лучше `unsafe.Offsetof`/`unsafe.Add`.

### Статья 29 · Файлы и IO

**A29-1 · High · «Ловушка: ошибки при закрытии файлов на запись»**
- Утверждение: «Вызов `Close()` неявно инициирует сброс накопленных грязных страниц ядра на физический диск (внутренний аналог `fsync`)».
- Проблема: `close(2)` не делает `fsync` и не гарантирует запись на диск; ошибки записи чаще всплывают на `write`, при отложенных — на `fsync` (и на `close` для NFS/квот). Для надёжности нужны проверка `Write`, `f.Sync()` (и `fsync` каталога при создании/`rename`); проверка `Close` — лишь дополнение. Пример с `defer func(){ … err = cerr }` требует именованного результата `err` — не оговорено.
- Доказательство: 📚 `man 2 close` («A successful close does not guarantee that the data has been successfully saved to disk»).

**A29-2 · Medium · «Zero-copy магия io.Copy»**
- Утверждение: «из сетевого сокета в локальный `os.File` — `sendfile`».
- Проблема: `sendfile` — файл → сокет (`File.writeTo`); сокет → файл — `splice`, файл → файл — `copy_file_range`; оптимизация срабатывает только для «голых» `*os.File`/`*net.TCPConn` (обёртки `bufio`, `TeeReader` её отключают), не работает при `O_APPEND`.
- Доказательство: ✅ `src/os/zero_copy_linux.go` (`writeTo` → `SendFile`; `readFrom` → `copyFileRange` / `spliceToFile`; комментарий про `O_APPEND`).

**A29-3 · Medium · «Блокирующее IO и Планировщик»**
- Утверждение: «1000 горутин → 1000 потоков → фатальная ошибка `fork/exec: resource temporarily unavailable`».
- Проблема: это сообщение относится к `exec`; при исчерпании потоков Go печатает `runtime: program exceeds N-thread limit` / `fatal error: thread exhaustion` (лимит `debug.SetMaxThreads`, 10 000); новый M создаётся лишь если syscall блокируется дольше ~20 мкс (retake `sysmon`), чтения из page cache возвращаются быстро; не сказано, что pipes/tty/FIFO/сокеты идут через netpoller, а обычные файлы — нет (epoll отвечает EPERM). В ст. 35 то же сообщение дано верно.
- Доказательство: ✅ `runtime/proc.go:989–990`.

**A29-4 · Medium · Введение** — «Спустя сорок лет те же авторы (Томпсон и Ритчи) перенесли принцип в Go» — см. X-4.

**A29-5 · Medium · «Как это решается в production»**
- Проблема: `io_uring` подан как готовое решение, но стандартная библиотека и рантайм его не используют (issue golang/go#31908); `afero` — абстракция файловой системы (in-memory/mock), а не «кэширование и мемоизация файловых операций» и не лекарство от блокировки потоков.
- Доказательство: 📚 golang/go#31908, README `spf13/afero`.

**A29-6 · Low–Med** — «syscall — тысячи тактов, инвалидируются строки TLB»: пустой syscall — сотни нс (зависит от mitigations KPTI/retpoline), TLB при PCID не сбрасывается целиком; `io.MultiWriter` пишет в приёмники последовательно (не «параллельно») и останавливается на первой ошибке.

**A29-7 · Low** — не упомянуты ключевые семантики IO: `Read` может вернуть `n>0` и `err!=nil` одновременно; `io.ReadFull`, `io.ErrUnexpectedEOF`; `http.MaxBytesReader` для лимита тела; `0644` модифицируется umask; `os.Root` (1.24) против path traversal.

### Статья 30 · JSON

**A30-1 · High · «Ловушка: omitempty и time.Time»**
- Утверждение: при `json:"created_at,omitempty"` нулевое `time.Time` «будет неожиданно вырезано из JSON».
- Проблема: `omitempty` никогда не считает структуру пустой — нулевой `time.Time` сериализуется как `"0001-01-01T00:00:00Z"`. Решение — `*time.Time` или (с Go 1.24) тег `omitzero` (использует `IsZero()`); статья описывает обратное поведение и не упоминает `omitzero`.
- Доказательство: ✅ запуск: `{"id":1,"t":"0001-01-01T00:00:00Z"}` для `omitempty`; `omitzero` поле опущено.

**A30-2 · Medium · «Unmarshal: JSON → Struct»**
- Утверждение: без указателя `Unmarshal` «заполнит локальную копию на стеке, которая мгновенно исчезнет».
- Проблема: `Unmarshal` вернёт `*json.InvalidUnmarshalError` (`json: Unmarshal(non-pointer main.User)`), копии не будет.
- Доказательство: ✅ запуск.

**A30-3 · Medium · «Encoder и Decoder»**
- Утверждение: `Encoder` пишет «напрямую в `w` без промежуточного `[]byte`»; `Decoder` читает из `r.Body` «без загрузки всего тела в RAM»; «стриминговый `Decoder` побеждает `Unmarshal` на больших объёмах».
- Проблема: `Encode` сначала маршалит во внутренний буфер (`encodeState` из `sync.Pool`), затем делает один `Write`; `Decode` буферизует весь очередной JSON-value до полного разбора — для одного гигантского документа в структуру экономии памяти нет (выигрыш — для потока значений NDJSON или токенного разбора `Token()/More()`). Не упомянуты `http.MaxBytesReader`, проверка хвостовых данных.

**A30-4 · Medium · «Mechanical Sympathy: рефлексия и аллокации»**
- Утверждение: при каждом `Unmarshal` «парсинг тегов и `FieldByName + Set`».
- Проблема: `encoding/json` кэширует описание полей типа (`cachedTypeFields`, `sync.Map`) и использует индексы полей; теги разбираются один раз на тип. Реальные источники медленности — рефлексия, `any`-аллокации, двойной проход (сканер+декодер), валидация. В диаграмме дефект разметки (X-6): `A["Входящий []"]:::processbyte`.

**A30-5 · Medium · «Потеря точности»**
- Проблема: `json.Number` назван «потоковым типом» без указания, что в `map[string]any` число станет `json.Number` лишь после `Decoder.UseNumber()`; не упомянуто, что `Unmarshal` сопоставляет ключи регистронезависимо (частый источник багов/уязвимостей, мотив `encoding/json/v2`).

**A30-6 · Low–Med** — `go-json` «со специализированными ассемблерными вставками» (goccy/go-json на unsafe + VM опкодов, не на ассемблере); `sonic` «самый производительный», «AVX-512», «32/64 байта за такт» — без источников, поддержка ARM64 ограничена; `easyjson` «2–4×» зависит от структуры; не упомянуты `encoding/json/v2` (GOEXPERIMENT=jsonv2, Go 1.25) и `omitzero` (1.24). Доказательство: 📚 README проектов, Go 1.24/1.25 release notes.

**A30-7 · Low** — лимит глубины 10 000 действует и для `Unmarshal`, не только `Decoder` (`«аппаратно»` — просто счётчик); невалидный UTF-8 не отвергается, а заменяется на U+FFFD; ссылка `[[7. Глубокий Go. Внутреннее устройство]]` ведёт на модуль, а не на статью; «техника встраивания DTO из ст. 25» — в ст. 25 такой техники нет.

### Статья 31 · Время

**A31-1 · High · «time.Duration: типобезопасные интервалы»**
- Утверждение: «Вы не можете случайно передать голое число `10` туда, где ожидается интервал. Компилятор заставит написать `10 * time.Second`».
- Проблема: для констант это неверно — `time.Sleep(10)` и `var d time.Duration = 10` компилируются (нетипизированная константа → `Duration`, 10 нс); запрещено лишь передавать **переменные** типа `int` без приведения. Это классическая ловушка.
- Доказательство: ✅ запуск: `time.Sleep(10)` компилируется.

**A31-2 · Medium · «Аллокации и утечки с time.After», «Ticker»**
- Утверждение: «В Go 1.23+ таймеры без ссылок утилизируются GC, `Reset` безопасен, канал небуферизованный»; «без `ticker.Stop()` тикер останется в памяти навсегда».

- Доказательство: ✅ `doc/godebug.md` («Go 1.27 removed the `asynctimerchan` setting»).

**A31-3 · Medium · «Устройство time.Time»**
- Утверждение: при наличии monotonic `ext` хранит «секунды от старта ОС».
- Проблема: `ext` — **наносекунды** монотонных часов от старта **процесса**; `wall` при наличии monotonic: 1 бит флага, 33 бита секунд с 1885 года, 30 бит наносекунд (в статье — верно). Не упомянуты: `t == u` сравнивает `loc` и monotonic (нужно `Equal`), `Round(0)` снимает monotonic, при `Format/Marshal` он теряется.
- Доказательство: ✅ `src/time/time.go` (комментарий у `type Time struct`).

**A31-4 · Medium · История таймеров**
- Утверждение: «до Go 1.14 все таймеры в одной глобальной куче с одним глобальным мьютексом».
- Проблема: с Go 1.10 таймеры шардированы по 64 корзинам (каждая — своя куча, мьютекс и `timerproc`); глобальный мьютекс был до 1.9. Go 1.14 перенёс таймеры в per-P (верно); Go 1.23 — ещё одна переработка.
- Доказательство: 📚 Go 1.10 release notes / CL 34784 ⚠️.

**A31-5 · Low–Med** — «`CLOCK_MONOTONIC` не подвержены NTP»: не «прыгает» при step-коррекции, но подвержен slewing (подстройка частоты); `CLOCK_MONOTONIC_RAW` — нет; не учитывает suspend; «vDSO: чтение из памяти без смены привилегий» — при clocksource без vDSO-поддержки (часть ВМ) уходит в syscall.

**A31-6 · Low** — «опечатка в шаблоне `2006-02-01` — компилятор и рантайм не выбросят ошибку» — `go vet` (`timeformat`) ловит; `Parse` по такому шаблону для `2024-10-15` вернёт ошибку месяца 15; в `alpine` нет tzdata (верно), в `scratch` нужен ещё `ca-certificates`; не упомянуты `time.AfterFunc`, `context.WithTimeout`, лимит `Duration` ≈292 года. Доказательство: ✅ `go vet`: `2006-02-01 should be 2006-01-02`.

- Проблема: это предобъявленные идентификаторы языка; не упомянуты `cmp.Ordered`, пакеты `slices`/`maps` (1.21) и встроенные `min/max/clear` (1.21) — мотивирующий пример `Min` сегодня решается встроенным `min`; с 1.20 `comparable` удовлетворяют и интерфейсные типы (возможна паника в рантайме).

**A32-4 · Low–Med** — GC shape определяется по базовому типу (`int` и `type UserID int` делят форму) — не сказано; Go 1.21 улучшил вывод типов (`Add(1, 2.5)`, передача generic-функций как аргументов); интерфейсы-ограничения с type sets нельзя использовать как обычный тип.

**A32-5 · Low** — «методы не могут иметь собственных type parameters» — верно (на 1.27 всё ещё); сообщение компилятора `methods cannot have type parameters`.

### Статья 34 · Горутины

**A34-1 · Medium · «Проблема 1: размер стека»**
- Утверждение: стек потока «по умолчанию от 1 до 2 МБ»; «100 000 × 2 МБ = 200 ГБ оперативной памяти; память заблокирована».
- Проблема: стек потока — виртуальная резервация, физически резидентны лишь затронутые страницы (десятки КБ + ядерный стек 16 КБ + `task_struct`); типичные значения: glibc pthread 8 МБ (`ulimit -s`), Java 1 МБ, macOS secondary 512 КБ, Windows 1 МБ. Реальные пределы — `vm.max_map_count`, `kernel.threads-max`, `pid_max`, cgroup `pids.max`.

**A34-2 · Medium · Сравнение моделей**
- Проблема: «поток на запрос» (Java/C#) без учёта Java 21 virtual threads (Project Loom), C# `async/await`, Kotlin coroutines и пулов потоков — актуальное сравнение должно учитывать, что виртуальные потоки Java — прямой аналог горутин; «PHP-FPM — процесс на запрос» — процесс из пула обслуживает один запрос за раз; C10K — 1999 год.

**A34-3 · Medium · Состояния G**
- Утверждение: `_Gidle` — «структура только что создана или возвращена в пул свободных».
- Проблема: возвращённые в free-list G имеют статус `_Gdead`; `_Gidle` — только что выделенная, ещё не инициализированная. Не перечислены `_Gsyscall`, `_Gpreempted`, `_Gcopystack`, `_Gscan`-варианты.
- Доказательство: ✅ `runtime/runtime2.go` (комментарии к `_Gidle`/`_Gdead`/`_Gsyscall`/`_Gpreempted`).

**A34-4 · Low–Med** — новый стек «в куче», старый «отдаётся GC» (стеки — из stack pool/manual spans, освобождение — немедленное `stackfree`); пролог сравнивает SP с `g.stackguard0`, а не `stack.lo`, и пропускается для малых листовых функций (`nosplit`); `go func()` «без системных вызовов» — `newproc` кладёт G в `runnext` и может вызвать `wakep()` (futex/clone); G берётся из free-list (`gfget`); стартовый стек 2 КБ — минимум, с 1.19 адаптивный (✅ `runtime/stack.go: startingStackSize`).

**A34-5 · Low** — для loopvar не указано условие `go.mod` (X-1); не упомянуты инструменты поиска утечек (`runtime.NumGoroutine`, pprof goroutine profile, `goleak`, и в 1.26 — экспериментальный goroutine-leak profile ⚠️); не сказано, что «main завершилась — все горутины убиты».

### Статья 35 · Планировщик

**A35-1 · Medium · «Роль P и GOMAXPROCS»**
- Утверждение: «Количество P по умолчанию равно количеству логических ядер вашего CPU».
- Проблема: с Go 1.25 на Linux по умолчанию учитывается cgroup CPU quota (и значение периодически пересчитывается); до 1.25 в контейнерах он равнялся числу ядер хоста (отсюда `uber-go/automaxprocs`). Новая логика включается при `go ≥ 1.25` в `go.mod` (`containermaxprocs`, `updatemaxprocs`). Для бэкенда в Kubernetes это критично и в статье отсутствует.
- Доказательство: ✅ `runtime/debug.go` (doc `GOMAXPROCS`: cgroup quota; «`containermaxprocs=0` is default for language version 1.24 and below»); ✅ `runtime/cgroup_linux.go`.

**A35-2 · Medium · «Блокировки: Syscall и Handoff»**
- Утверждение: «Рантайм обнаруживает, что M1 ушёл в блокирующий Syscall. M1 отцепляется от P1…»; диаграмма — немедленная передача.
- Проблема: обычный syscall (`entersyscall`) переводит P в `_Psyscall` и **не** отдаёт его сразу; P забирает `sysmon` (retake), если вызов длится >20 мкс и есть работа; немедленный `handoffp` — только для заведомо блокирующих (`entersyscallblock`). Поэтому короткие syscalls не создают новые M.
- Доказательство: 📚 `runtime/proc.go` (`entersyscall`, `retake`) ⚠️.

**A35-3 · Low–Med** — не описан `p.runnext` (новая/разбуженная G кладётся сюда и наследует остаток time slice; кража `runnext` — в последнюю очередь), spinning-потоки (≤ GOMAXPROCS/2), `wakep`; `sysmon`, кроме preempt, ретейкает P из syscalls, запускает forced GC (раз в 2 мин) и netpoll; `GODEBUG=schedtrace` не упомянут.

**A35-4 · Low** — «GRQ получает горутины от netpoller и GC» — результат `netpoll` вставляется через `injectglist` (в GRQ или в LRQ при простаивающих P), GC-воркеры — отдельный механизм; «LRQ владеет только один M» — другие P воруют из неё атомарно; async preemption на Windows делается без SIGURG (SuspendThread). Подтверждено: `schedtick%61` (`proc.go:3458`), `forcePreemptNS = 10ms`, порог 256 в LRQ, 10 000 потоков.

### Статья 37 · Каналы под капотом

**A37-1 · Low–Med · «Каналы НЕ Lock-Free»**
- Утверждение: «любая операция начинается с захвата мьютекса канала»; «системный мьютекс».

**A37-2 · Low–Med · «Сценарий блокировки при отправке»**

- Проблема: в таком порядке это была бы гонка (получатель мог бы `goready` ещё не запаркованную G1); реально `lock` отпускается внутри парковки через `chanparkcommit` после перехода на g0.
- Доказательство: ✅ `runtime/chan.go` (`gopark(chanparkcommit, …)`, `func chanparkcommit`).

**A37-3 · Low** — Direct handoff описан для ждущего получателя; симметричный путь (`recv` из полного буферизованного канала при ждущем отправителе: значение берётся из головы буфера, значение отправителя копируется в хвост) не описан; «кольцевой буфер лучше списка из-за prefetcher» — верно качественно, но стоимость канала доминируется мьютексом и park/ready. *Проверено, верно:* `selectgo` (scrambling, lockorder по адресам, три прохода), `sudog`, `hchan.lock`.

### Статья 38 · Select

**A38-1 · Medium · «Паттерн Fan-In»**
- Утверждение: для динамического числа каналов «статический `select` не поможет, приходится использовать `reflect.Select`»; «в 10–100 раз медленнее».
- Проблема: стандартный fan-in для N каналов — по горутине-«пересыльщику» на каждый вход + `sync.WaitGroup` + горутина, закрывающая выходной канал после `wg.Wait()`; `reflect.Select` — крайний случай. Множитель без источника (порядка 5–20×); аллокация `[]reflect.SelectCase` — на стороне вызывающего.

**A38-2 · Medium · Пропущенная ловушка** — `break` внутри `select` (в т.ч. в `for { select {…} }`) выходит только из `select`, не из цикла (нужны метка/`return`); `select` с `default` в цикле — busy-wait, 100% CPU.

**A38-3 · Low–Med** — `select {}` в `main` без других работающих горутин даёт `fatal error: all goroutines are asleep - deadlock!`; детектор не срабатывает при горутинах в syscall/netpoll/таймерах; происхождение Go-`select` (CSP/Newsqueak/Alef) смешано с POSIX `select()/epoll`; `time.After` vs `NewTimer` — см. A31-2.

### Статья 39 · Context

**A39-1 · Medium · Концепция отмены**
- Утверждение: «все пять горутин обязаны немедленно прекратить работу».
- Проблема: нигде не сказано, что отмена **кооперативна** — `cancel()` лишь закрывает `Done()`; горутины/IO, не проверяющие `ctx`, не остановятся. Не упомянуты `ctx.Err()` (`context.Canceled`, `DeadlineExceeded`, `errors.Is`), `Background().Done() == nil`, `http.Request.Context()`, `signal.NotifyContext` (1.16), `WithDeadlineCause/WithTimeoutCause` (1.21), `go vet lostcancel`.
- Доказательство: ✅ список vet-анализаторов (`lostcancel`).

**A39-2 · Low–Med** — «контексты — направленное дерево (DAG)»: это дерево (у узла один родитель); `propagateCancel` для пользовательских реализаций `Context` запускает отдельную горутину, ожидающую `parent.Done()`; в `cancelCtx` (1.20+) есть поле `cause` — в статье его нет.

**A39-3 · Low–Med** — «никогда не храните Context в struct» — слишком категорично (блог «Contexts and structs», 2021: допустимы исключения, `http.Request` содержит `ctx`); «`ctx.Value` — крайне медленно» — типичная цена десятки нс на уровень, главные недостатки — типобезопасность и скрытые зависимости; в примере `type contextKey string` — Staticcheck/документация рекомендуют пустой struct-тип, чтобы избежать аллокации при конвертации в `any`. Совет с `WithCancelCause/AfterFunc/WithoutCancel` (1.20/1.21) — **верен**.

### Статья 40 · sync.WaitGroup, Mutex, RWMutex

**A40-1 · Medium · «У него всего три метода»**
- Проблема: с Go 1.25 добавлен `WaitGroup.Go(func())` (создаёт и учитывает горутину, закрывает ловушку `Add` внутри горутины); для ошибок — `errgroup` (x/sync); `go vet` содержит анализатор `waitgroup` (ловит `Add` внутри горутины); «упрощена начиная с Go 1.18 (`state atomic.Uint64`)» — `atomic.Uint64` появился в 1.19, поэтому «с 1.18» заведомо неверно (⚠️ на какой версии `WaitGroup` перешёл на него — 1.20 по памяти, проверить по git log).
- Доказательство: ✅ `sync/waitgroup.go:236: func (wg *WaitGroup) Go(f func())`; ✅ `go vet`: `WaitGroup.Add called from inside new goroutine`; ✅ раскладка `state` (`Add(delta<<32)`, счётчик в верхних 32 битах) подтверждена.

**A40-2 · Medium · Ограничения Mutex/RWMutex**
- Проблема: не описаны: нерентабельность рекурсивной блокировки (повторный `Lock` в одной горутине — deadlock; для `RWMutex` повторный `RLock` при ожидающем писателе — deadlock, прямо запрещено документацией), невозможность апгрейда `RLock→Lock`, неперехватываемый `fatal error: sync: unlock of unlocked mutex`, допустимая разблокировка из другой горутины, `TryLock` (1.18); writer-preference `RWMutex` (поле `readerWait`, внутренний `w Mutex`) в механике пропущены.
- Доказательство: ✅ `sync/rwmutex.go` (doc `RLock`: «should not be used for recursive read locking»).

**A40-3 · Low–Med** — «Компилятор и линтер находят копирование Mutex» — компилятор не проверяет, это `go vet` (`copylocks`: `Set passes lock by value: Cache contains sync.Mutex`, ✅ подтверждено); эпиграф «Используйте то, что проще и выразительнее» приписан Пайку — формулировка из Go wiki («Use whichever is most expressive and/or most simple»).

**A40-4 · Low** — «Fast path ~20 тактов» — типично (`LOCK CMPXCHG`); spin — только при GOMAXPROCS>1, ≤4 итерации по 30 `PAUSE`; Starvation Mode (1 мс, Go 1.9) и миф про `RWMutex` (кэш-линия `readerCount`) описаны **верно**; в 1.24 реализация вынесена в `internal/sync` (поведение то же).

### Статья 41 · sync.Once, Cond, Pool, atomic

**A41-1 · Medium · `sync.Cond`: «Spurious Wakeups»**
- Утверждение: цикл `for` нужен из-за ложных пробуждений — «рантайм Go может разбудить горутину даже без явного `Signal()`/`Broadcast()`».
- Проблема: документация Go прямо говорит обратное: «Unlike in other systems, Wait cannot return unless awoken by Broadcast or Signal». Цикл нужен потому, что условие могло измениться между пробуждением и повторным захватом мьютекса (несколько ждущих, `Broadcast`).
- Доказательство: ✅ `src/sync/cond.go` (doc `Wait`).

**A41-2 · Medium · `sync.Pool`**
- Утверждение: пример `Put(buf)` для `[]byte` «без аллокации»; `buf = buf[:0]` защищает от утечки конфиденциальных данных.
- Проблема: помещение `[]byte` (не pointer-like) в `any` при `Put` аллоцирует заголовок слайса (staticcheck SA6002); корректный пример — хранить `*[]byte`. `buf[:0]` не зануляет содержимое: для секретов нужен `clear(buf)`; не упомянут рост буферов (большие буферы удерживаются в пуле — `fmt` отбрасывает >64 КБ).
- Доказательство: ✅ `AllocsPerRun`: Get/Put слайса — 1 аллокация/операцию; Get/Put `*[]byte` — 0.

**A41-3 · Low–Med** — «`shared` — общий список с минимальным спин-локом»: `shared` — lock-free `poolChain` (`pushHead/popHead` — владелец, `popTail` — любой P); диаграмма в статье говорит lock-free, текст — спин-лок (внутреннее противоречие); victim-кэш в тексте про Get упущен (в gotcha упомянут верно). Доказательство: ✅ `sync/pool.go:70`.

**A41-4 · Medium · `sync.Once`**
- Проблема: не сказано, что `Do` считает `f` выполненной, **даже если она запаниковала** (`defer o.done.Store(true)`) — повторные `Do` не вызовут `f`; не упомянуты `sync.OnceFunc`, `OnceValue`, `OnceValues` (1.21) — современный способ ленивой инициализации; диаграмма «`f()` затем `Store(done,1)`» упрощает порядок (Store — в `defer`).
- Доказательство: ✅ `sync/once.go: doSlow`; ✅ `sync/oncefunc.go`.

**A41-5 · Low** — типизированные атомики и `atomic.Pointer[T]` появились в 1.19 (верно), не упомянут `atomic.Value`/copy-on-write паттерн; выравнивание 64-битных атомиков на 32-битных платформах; `LOCK`-префикс «блокирует шину» — современный CPU использует cache locking, bus lock — только split-lock.

### Статья 42 · Race Condition и Memory Model

**A42-1 · Medium · «Data Race = Undefined Behavior»**
- Утверждение: «В Go наличие Data Race означает Undefined Behavior»; Итог п.2: «фатальная аппаратная ошибка».
- Проблема: документ Go Memory Model прямо противопоставляет Go C/C++: «less like C and C++, where the meaning of any program with a race is entirely undefined». Гонки на односложных значениях имеют ограниченный эффект; на многосложных (интерфейсы, слайсы, строки, map) возможны несогласованные пары (pointer, type)/(pointer, length) — это нарушение memory safety (пример torn interface в статье по сути верен). Гонка — программная, не «аппаратная» ошибка.
- Доказательство: ✅ `doc/go_mem.html` («Implementation Restrictions for Programs Containing Data Races»; «races on multiword data structures can lead to inconsistent values»).

**A42-2 · Medium · Собеседование про `for !flag {}`**
- Утверждение: «ядро процессора может кэшировать значение `flag` в L1 и никогда не сверяться с оперативной памятью».
- Проблема: кэши когерентны (MESI), задержанное значение рано или поздно станет видно; причина зависания — оптимизация компилятора (значение держится в регистре); утверждение противоречит собственной врезке про MESI в той же статье.

**A42-3 · Medium · «Иллюзия последовательности»**
- Проблема: пример `A=1; B=2` описан как нарушаемый «в железе (x86-64, ARM64)» — на x86-64 (TSO) аппаратно записи друг с другом не переставляются, возможна только перестановка store→load; для A=1/B=2 перестановка возможна у компилятора и на ARM64/POWER.
- Доказательство: 📚 Intel SDM Vol.3 §8.2 (memory ordering), Go memory model.

**A42-4 · Medium · «Под капотом: -race»**
- Утверждение: «на каждые 8 байт памяти TSAN выделяет 16 байт метаданных»; «история последних 4 доступов».
- Проблема: арифметика не сходится: в TSan v2 4 shadow-ячейки по 8 байт на 8 байт памяти = 32 байта; общий оверхед по документации Go — память ×5–10, время ×2–20 (эти числа верны).
- Доказательство: 📚 TSan v2 algorithm (compiler-rt) ⚠️.

**A42-5 · Low–Med** — не перечислены гарантии HB для `sync.Once`/`WaitGroup`/`Cond`, бессмысленно опущено правило буферизованного канала («k-й приём синхронизирован с завершением (k+C)-й отправки» — основа семафоров); `sync.WaitGroup` и `sync.Once` описаны в ревизии модели 1.19; ограничение «race detector находит только гонки, реально случившиеся при данном прогоне» не упомянуто. Эпиграф Дейкстры («The purpose of abstracting is not to be vague…», «The Humble Programmer», 1972) — **верно**.

### Статья 43 · Deadlock, Livelock

**A43-1 · Low–Med · «Глобальный vs локальный deadlock»**
- Утверждение: `checkdead` срабатывает, когда «все горутины `_Gwaiting` (спят на каналах, мьютексах или таймерах)» и нет активного netpoll.
- Проблема: в список «спящих навсегда» нельзя включать таймеры — программа, чьи горутины ждут таймеров, не является deadlock (проверка по числу работающих M и состоянию P/таймеров); `fatal error: all goroutines are asleep - deadlock!` неперехватываем — верно. Сообщение рантайма при `runtime.Goexit` в `main` другое (`no goroutines (main called runtime.Goexit) - deadlock!`).
- Доказательство: ✅ `runtime/proc.go: checkdead`.

**A43-2 · Low** — livelock-пример: оба воркера должны брать мьютексы в **разном порядке** (`worker(mu1,mu2)` и `worker(mu2,mu1)`), в тексте оба вызываются как `worker(mu1, mu2)` (при одинаковом порядке livelock не возникает); `badDesign` (запись в закрытый канал) назван «Закрытие закрытого»; «режим голодания гарантирует отсутствие Tail Latency» — ограничивает, но не гарантирует; пример утечки: `case result := <-ch:` — неиспользованная переменная (compile error).

**A43-3 · Low** — в диагностике не упомянуты mutex/block-профили (`SetMutexProfileFraction`, `SetBlockProfileRate`), `goleak`; `go tool trace` для lock contention — допустимо; «горутина никогда не удаляется GC» — верно.
