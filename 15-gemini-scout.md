### Кандидат 1: Фальшивое утверждение о том, что `t.Fatal()` в дочерних горутинах завершает тест зеленым («PASS») и прячет сбой
* **article/section:** 
  1. `02. testing пакет/1. testing пакет. Основы.md` (строки 136–148)
  2. `07. Конкурентность/1. Тестирование конкурентного кода.md` (строки 107–127)
* **claim:**  
  В обеих статьях категорически утверждается, что вызов `t.Fatal()` / `t.Fatalf()` / `t.FailNow()` внутри дочерней горутины приводит к ложноположительному успешному прохождению теста:
  > *«КАТАСТРОФА! Вызов t.Fatalf убьет дочернюю горутину, но основная горутина TestConcurrencyGotcha продолжит работу, выйдет из функции, и тест может быть ложно помечен как PASS! Если вызов t.Fatalf происходит внутри горутины, runtime.Goexit() уничтожает эту отдельную горутину, не оказывая прямого влияния на основной поток... тест помечается зеленым, полностью скрыв фатальный сбой!»* (`02. testing пакет/1. testing пакет. Основы.md`, строки 136–147).
  >
  > *«В приведенном фрагменте дочерняя горутина умирает, но перед смертью добросовестно выполняет defer wg.Done(). Счетчик барьера WaitGroup сбрасывается в ноль. Главная горутина беспрепятственно проскакивает барьер wg.Wait() и... завершает тест со статусом PASS! Сообщение об ошибке появится в выводе, но статус бинарника тестов останется нулевым (успешным).»* (`07. Конкурентность/1. Тестирование конкурентного кода.md`, строки 126).
* **why it needs checking:** Это опасный технический миф, противоречащий исходному коду стандартной библиотеки `testing` и поведению рантайма Go:
  1. В `src/testing/testing.go` метод `FailNow()` определен следующим образом:
     ```go
     func (c *common) FailNow() {
         c.mu.Lock()
         c.failed = true
         c.mu.Unlock()
         runtime.Goexit()
     }
     ```
  2. `*testing.T` содержит вложенную структуру `common`, разделяемую всеми горутинами, имеющими ссылку на `t`. Вызов `t.Fatalf()` под мьютексом выставляет `c.failed = true`.
  3. Когда главная горутина выходит из функции теста (например, пройдя `wg.Wait()`), раннер `tRunner` проверяет флаг:
     ```go
     if t.Failed() {
         t.signal <- true // помечает тест как FAIL
     }
     ```
  4. **Эмпирическая верификация:** Тестовый прогон приведенного в статье кода `TestWorker_BadFatal` в среде Go выдает:
     ```text
     --- FAIL: TestWorker_BadFatal (0.00s)
         bad_test.go:14: something went wrong
     FAIL
     exit status 1
     ```
     Тест **всегда падает со статусом FAIL**, а процесс завершается с кодом **1**. Тест **никогда не становится зеленым (PASS)**, если дочерняя горутина успела вызвать `t.Fatalf()` до завершения теста!
  5. В чем же заключается *реальная* опасность вызова `t.Fatal` в горутинах?
     - `runtime.Goexit()` завершает *только* вызвавшую его горутину. Другие горутины продолжают работать, а если горутина должна была отправить сигнал в небуферизованный канал, тест зависнет в дедлоке.
     - Если дочерняя горутина вызовет `t.Fatal` *после* того, как основная функция теста вернула управление, рантайм запаникует: `panic: Fail in goroutine after TestX has completed`.
     - Официальная документация `testing.FailNow` гласит: *"FailNow must be called from the goroutine running the test or benchmark function, not from other goroutines created during the test. Calling FailNow does not stop those other goroutines."*
* **evidence/source needed:** Исходный код `src/testing/testing.go` (методы `FailNow`, `tRunner`); запуск `go test` на листинге из статьи; официальный Go issue tracker (рассуждения о поведении `FailNow` в горутинах).
* **priority:** 🔴 **High**

### Кандидат 2: Миф о том, что `t.Parallel()` вызывает `runtime.Goexit()` и уничтожает горутину теста
* **article/section:** 
  1. `02. testing пакет/3. go test под капотом.md` (строки 133, 141)
  2. `02. testing пакет/6. Параллельные тесты t.Parallel.md` (строки 18–19, 45)
* **claim:**  
  В тексте обеих глав, а также на Mermaid-диаграммах утверждается, что вызов `t.Parallel()` инициирует вызов `runtime.Goexit()`, который замораживает горутину и помещает ее в очередь:
  > *«Test->>Main: runtime.Goexit() -> перехват рантаймом... 1. Фаза откладывания: Вызов t.Parallel() инициирует вызов runtime.Goexit(). Горутина текущего теста паркуется, помещается в очередь отложенных задач...»* (`02. testing пакет/3. go test под капотом.md`, строки 133, 141).
  >
  > *«1. Маркировка и парковка: Когда внутри теста вызывается t.Parallel(), рантайм Go вызывает низкоуровневую функцию runtime.Goexit(). Горутина текущего теста немедленно замораживается и помещается в очередь ожидания...»* (`02. testing пакет/6. Параллельные тесты t.Parallel.md`, строки 18–19, 45).
* **why it needs checking:** Это грубейшая ошибка в описании рантайма Go.
  1. Функция `runtime.Goexit()` безвозвратно завершает текущую горутину с раскруткой `defer`. Никакая горутина в Go не способна «возобновиться» или «проснуться» после вызова `runtime.Goexit()`. Если бы `t.Parallel()` вызывал `Goexit()`, выполнение тела теста после строчки `t.Parallel()` было бы физически невозможно!
  2. Исходный код `testing.T.Parallel()` в `src/testing/testing.go` показывает реальный механизм:
     ```go
     func (t *T) Parallel() {
         ...
         t.isParallel = true
         t.duration += highPrecisionTimeSince(t.start)
         t.parent.sub = append(t.parent.sub, t)
         ...
         t.signal <- true   // Сигнализирует вызывающему раннеру
         <-t.parent.barrier // Блокирует ТЕКУЩУЮ горутину до завершения барьера!
         t.tstate.waitParallel() // Ожидание слота в семафоре
         ...
         t.start = highPrecisionTimeNow()
     }
     ```
  3. Горутина теста никуда не уничтожается — она **синхронно блокируется** на чтении из канала `<-t.parent.barrier`, а затем ожидает освобождения слота в семафоре `waitParallel()`. Когда все последовательные тесты завершаются, канал закрывается, и горутина продолжает исполнение следующих строк кода.
  4. Примечательно, что в главе `10. Практика и CI/4. Параллелизм в CI.md` (строки 54–60) сам автор опровергает свои предыдущие утверждения и корректно пишет: *«рантайм testing: 1. Приостанавливает выполнение теста (блокирует его на канале/семафоре)»*. Модуль прямо противоречит сам себе!
* **evidence/source needed:** `src/testing/testing.go` (`func (t *T) Parallel()`); документация пакета `runtime` по поведению `runtime.Goexit()`.
* **priority:** 🔴 **High**

### Кандидат 3: Вредный антипаттерн бенчмаркинга: `b.StopTimer()`/`b.StartTimer()` внутри цикла и порча замеров памяти
* **article/section:** `09. Производительность/1. Benchmarking в Go.md` (строки 102–119)
* **claim:**  
  В подразделе «Канонический паттерн сложной подготовки данных» приводится следующий листинг:
  ```go
  func BenchmarkComplexSort(b *testing.B) {
      for i := 0; i < b.N; i++ {
          b.StopTimer() // Временно останавливаем прецизионный секундомер
          
          // Генерируем новый несортированный массив на 100 000 элементов 
          // (тяжелая операция выделения памяти и генерации случайных чисел)
          data := generateRandomData(100000) 
          
          b.StartTimer() // Вновь активируем измерительный таймер

          // Измеряем исключительно чистую скорость работы алгоритма сортировки!
          algorithms.Sort(data)
      }
  }
  ```
* **why it needs checking:** Этот пример представляет собой хрестоматийный антипаттерн, категорически осуждаемый авторами Go (Dave Cheney, Bryan Boreham, Ian Lance Taylor):
  1. **Искажение метрик памяти (`ReportAllocs`):** Методы `b.StopTimer()` и `b.StartTimer()` управляют **исключительно замером процессорного времени** (`duration`). Они **НЕ останавливают учет аллокаций памяти**! Под капотом `testing.B` замеряет разницу между `memStats.Mallocs` и `TotalAlloc` на старте и финише всего прогона `b.runN(n)`. В результате все 100 000 аллокаций массива и генератора случайных чисел, выполняемые на каждой итерации, будут целиком записаны на счет `algorithms.Sort(data)`! Метрики `B/op` и `allocs/op` окажутся безнадежно испорчены.
  2. **Взрывной рост времени выполнения (Таймаут бенчмарка):** В Go значение `b.N` масштабируется по экспоненте (1, 2, 3, 5, 10, 20, 50, 100, 200, 500, 1000, 2000...). Если `generateRandomData(100000)` занимает 2 мс, то при `b.N = 2000` тест потратит 4 секунды неучтенного астрономического времени только на подготовку. При больших `b.N` бенчмарк легко вылетает по дефолтному таймауту (`panic: test timed out after 10m`).
  3. **Колоссальный оверхед системных вызовов:** Вызовы `StopTimer`/`StartTimer` внутри циклового тела добавляют паразитный оверхед чтения системных часов (до сотен наносекунд на шаг).
  4. **Идиоматичный паттерн Go:** Генерация срезов данных должна производиться *до* входа в измерительный цикл (например, предгенерация `b.N` наборов данных или переиспользование единого шаблона с копированием среза `copy()`, либо применение суббенчмарков). Называть этот листинг «каноническим паттерном» педагогически опасно.
* **evidence/source needed:** `src/testing/benchmark.go` (методы `StopTimer`, `StartTimer`, расчет `memStats`); руководство Дейва Чейни *«High Performance Go Workshop»* (раздел «Avoid StopTimer/StartTimer in inner loops»).
* **priority:** 🔴 **High**

### Кандидат 4: Состояние гонки (Data Race) и потеря каналов в эталонном `MockClock`
* **article/section:** `07. Конкурентность/7. Deterministic concurrency testing.md` (строки 86–117)
* **claim:**  
  В качестве эталона для тестирования конкурентного кода предлагается реализация:
  ```go
  type MockClock struct {
      currentTime time.Time
      triggers    map[time.Duration]chan time.Time 
  }

  func (m *MockClock) Now() time.Time {
      return m.currentTime
  }

  func (m *MockClock) After(d time.Duration) <-chan time.Time {
      ch := make(chan time.Time, 1)
      m.triggers[d] = ch
      return ch
  }

  func (m *MockClock) Advance(d time.Duration) {
      m.currentTime = m.currentTime.Add(d)
      if ch, exists := m.triggers[d]; exists {
          ch <- m.currentTime
      }
  }
  ```
* **why it needs checking:** В главе, посвященной детерминированному тестированию конкурентности, приводится код, содержащий две критические ошибки:
  1. **Data Race на чтение/запись map и time.Time:** Структура не содержит ни `sync.Mutex`, ни атомиков. В реальном тесте часы `MockClock` передаются в фоновые воркеры, которые конкурентно вызывают `m.Now()` и `m.After()`, пока основная горутина теста вызывает `m.Advance()`. Запуск с флагом `-race` немедленно завершится ошибкой детектора гонок либо рантайм-паникой `fatal error: concurrent map read and map write`.
  2. **Потеря каналов при одинаковых интервалах (Lost Channels):** В качестве ключа словаря используется `time.Duration`. Если две горутины вызовут `After(5 * time.Second)`, вторая горутина перезапишет `m.triggers[5*time.Second] = ch2`. При вызове `Advance(5 * time.Second)` время получит только `ch2`. Первая горутина навсегда зависнет в ожидании ответа в `ch1`, вызвав зависание всего тестового набора!
  3. Неправильная логика `Advance(d)`: если было зарегистрировано два таймера на `2s` и `5s`, вызов `Advance(5s)` активирует только таймер на `5s`, проигнорировав таймер на `2s`, хотя виртуальное время ушло вперед на 5 секунд.
* **evidence/source needed:** Запуск `go test -race` с параллельными горутинами, использующими данный `MockClock`; сравнение с проверенными библиотеками (например, `jonboulle/clockwork` или `benbjohnson/clock`).
* **priority:** 🔴 **High**

### Кандидат 5: Ошибочное утверждение о фатальной панике `assert.Equal` на структурах с функциями
* **article/section:** `03. Assertions и tooling/2. Testify. assert и require.md` (строки 142–144)
* **claim:**  
  > *«Ловушка 1: Функциональные типы внутри структур.  
  > Если ваша структура содержит поле первого класса вроде `Callback func()`, рефлексивный вызов `assert.Equal` завершится фатальной паникой. В Go функции являются непрозрачными указателями на код, и рантайм запрещает их прямое сравнение на равенство (допустимо лишь сравнение с nil).»*
* **why it needs checking:** Это утверждение технически недостоверно.
  1. Пакет `testify/assert` в функции `Equal` вызывает внутренний метод `ObjectsAreEqual`, который опирается на `reflect.DeepEqual`.

### Кандидат 7: Состояние гонки и вечная блокировка пользователя (`TTL = -1`) в Redis Rate Limiter
* **article/section:** `05. Интеграционные тесты/6. Тестирование Redis.md` (строки 256–267)
* **claim:**  
  В качестве примера реального сервиса для интеграционного тестирования представлен лимитер:
  ```go
  func (r *RateLimiter) Allow(ctx context.Context, userID string) (bool, error) {
      key := fmt.Sprintf("%s:%s", r.prefix, userID)
      count, err := r.client.Incr(ctx, key).Result()
      if err != nil {
          return false, err
      }
      if count == 1 {
          _ = r.client.Expire(ctx, key, time.Minute).Err()
      }
      return count <= 5, nil
  }
  ```
* **why it needs checking:** Этот листинг содержит две классические ошибки распределенных систем:
  1. **Игнорирование ошибки `Expire` и вечный бан (Permanent Lockout):** Вызов `_ = r.client.Expire(...).Err()` молча проглатывает ошибку. Когда счетчик превысит 5, пользователь будет заблокирован **навсегда**, пока администратор вручную не удалит ключ из Redis!
  2. **Гонка при параллельных запросах:** Если от одного пользователя одновременно приходят два запроса, один из них может получить `count = 2` до того, как завершится вызов `Expire` от первого запроса. Если процесс, получивший `count = 1`, упадет до выполнения `Expire`, ключ снова останется без TTL.
  3. Для надежной реализации требуется либо атомарный Lua-скрипт (`EVAL`), либо команда `SET key 1 EX 60 NX` с последующим инкрементом, либо транзакция `MULTI/EXEC`. В учебном материале для Senior-бэкендеров код с потенциальным вечным баном без валидации ошибок недопустим.
* **evidence/source needed:** Официальная документация Redis (паттерны Pattern: Rate Limiter); Redis command reference (`INCR`, `EXPIRE`).
* **priority:** 🔴 **High**

  1. В **Go 1.24** представлен революционный новый API бенчмаркинга: цикл `for b.Loop()`.
  2. `b.Loop()` устраняет все исторические ловушки:
     - Не нужно вручную вызывать `b.ResetTimer()` после тяжелой подготовки до цикла.
     - Исключаются ошибки с затиранием `b.N` или некорректным шагом.
     - Значительно улучшен контроль над оптимизациями компилятора.
  3. Хотя в статье 07.07 автор упоминает Go 1.24 (`testing/synctest`), появление `b.Loop()` в бенчмарках полностью проигнорировано.
* **evidence/source needed:** Go 1.24 Release Notes; предложение `testing: add B.Loop` (Go issue #61515).
* **priority:** 🟢 **Low**

### Кандидат 18: Риск взаимоблокировок и коллизий уникальных ключей при `t.Parallel()` в транзакционных тестах с БД
* **article/section:** `05. Интеграционные тесты/3. Транзакции и rollback подход.md` (строки 108–138)
* **claim:**  
  Утверждается, что паттерн отката транзакции (`tx.Rollback()`) позволяет безбоязненно запускать любые интеграционные тесты параллельно:
  > *«Теперь мы можем смело и безопасно запускать тесты в параллель! t.Parallel()...»*  
  При этом в коде выполняется вставка со статическим именем: `repo.Create(ctx, "Gopher")`.
* **why it needs checking:** 
  - В реляционных СУБД (PostgreSQL, MySQL) транзакции изолируют данные, но **уникальные индексы и внешние ключи проверяются на уровне таблицы**.
  - Если два параллельных теста попытаются вставить запись с одинаковым уникальным полем (например, логин `"Gopher"` или одинаковый email), вторая транзакция заблокируется на блокировке индекса в ожидании исхода первой транзакции. Если они вставляют связанные сущности в разном порядке, СУБД выбросит ошибку дедлока: `ERROR: 40P01: deadlock detected`.
  - Для параллельных тестов с транзакциями критически необходима генерация уникальных фикстур (например, `"Gopher-" + uuid.NewString()`). Об этой опасности в статье нет предупреждения.
* **evidence/source needed:** Документация PostgreSQL по блокировкам индексов (Index-level Locks and Unique Constraints in concurrent transactions).
* **priority:** 🟢 **Low**

## 🔍 Системные белые пятна и архитектурно-педагогические пробелы модуля (Blind Spots)

В ходе сквозного аудита 80 статей модуля выявлены важные системные пробелы, требующие усиления на этапе авторской вычитки:

1. **Недостаточное освещение пакета `testing/synctest` (Go 1.24+):**
   Пакет `synctest` упоминается лишь вскользь в одной сноске. Между тем, появление «пузырей» виртуального времени (`synctest.Run`) — это самое масштабное изменение в культуре тестирования конкурентного кода в Go за последние 10 лет, делающее самодельные `MockClock` ненужными.
2. **Отсутствие глубокого анализа фаззинга со структурами данных:**
   В главе 08.01 утверждается, что фаззер принимает только примитивные типы, но не показан современный подход с использованием библиотеки `google/gofuzz` или генерации структурированных входных данных через десериализацию Protobuf/JSON.
3. **Игнорирование риска исчерпания соединений в пуле `database/sql` при массовом `t.Parallel()`:**
   При запуске десятков параллельных интеграционных тестов дефолтный лимит пула `MaxOpenConns` быстро приводит к взаимным блокировкам, если тесты не настраивают кастомные параметры пула.
