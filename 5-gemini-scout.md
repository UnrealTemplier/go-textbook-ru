## Статья 3. go run, go build, go test и базовый toolchain

### [3-1] Порядок фаз компилятора: Inlining и Escape Analysis на этапе SSA
- **Утверждение:** «На этапе SSA компилятор выполняет ключевые оптимизации: Escape Analysis, Inlining...»

Фазы **Inlining** и **Escape Analysis** выполняются на более высоком уровне (ранее AST/Node IR) **до** преобразования в SSA-форму. SSA применяется позже — для машинно-независимых оптимизаций (Dead Code Elimination, распределение регистров).
- **Источники:** Исходный код `cmd/compile/internal/` (файл `README.md`), официальная документация по архитектуре компилятора Go.
- **Приоритет:** Medium

## Статья 5. Переменные, константы и вывод типа

### [5-1] Нулевое значение строки как «нулевой указатель»
- **Утверждение:** «Строковый тип (string) получает пустую строку "" (срез с длиной 0 и нулевым указателем на байты)»
- **Почему требует проверки:** Термин «нулевой указатель» (nil pointer) для пустой строки некорректен. В Go `""` имеет длину 0, но внутренний указатель Data обычно **не nil**, а указывает на статический zero-size base адрес. Это принципиально отличает пустую строку от nil-среза.
- **Источники:** Поведение `unsafe.StringData("")`, исходный код пакета `runtime`.
- **Приоритет:** Low

## Статья 6. Базовые типы данных. int, float, bool, string

### [6-1] Устаревший `reflect.StringHeader` представлен как актуальный
- **Утверждение:** «В недрах рантайма строка — это компактная двухсловная структура StringHeader... // Так строка представлена в рантайме и пакете reflect»
- **Почему требует проверки:** Начиная с Go 1.21, тип `reflect.StringHeader` **официально deprecated**. Разработчикам предписывается использовать `unsafe.String` и `unsafe.StringData`. Приводить `StringHeader` как актуальный код без пометки о deprecation — значит учить писать legacy-код.
- **Источники:** Go 1.21 Release Notes, документация `reflect` пакета.
- **Приоритет:** Low

## Статья 7. Rune, Byte и Unicode в Go

### [7-1] Строка названа «срезом» (slice) байт
- **Утверждение:** «Строка (string) — это неизменяемый срез (slice) байт (byte)»
- **Почему требует проверки:** Терминологически строка в Go **не является срезом**. Slice состоит из трёх машинных слов (ptr + len + cap), строка — только из двух (ptr + len) и не имеет поля capacity. Называть строку «срезом» формирует неверную ментальную модель о раскладке памяти. Корректнее: «неизменяемая последовательность байт».
- **Источники:** Спецификация языка Go (разделы String types и Slice types).
- **Приоритет:** Medium

## Статья 13. Panic, Recover и stack trace

### [13-1] `panic(nil)` и невидимость для `recover()`
- **Утверждение:** «`recover()` возвращает `nil` только если паники не было»
- **Почему требует проверки:** До Go 1.21 вызов `panic(nil)` приводил к тому, что `recover()` возвращал `nil`, делая панику неотличимой от «паники не было». **Начиная с Go 1.21** поведение изменилось: генерируется `*runtime.PanicNilError`. Эта version-sensitive деталь критически важна для корректного обработчика recover.
- **Источники:** Go 1.21 Release Notes (раздел про `panic(nil)`), `runtime/panic.go`.
- **Приоритет:** High

### [13-2] «Stop-The-World» при панике
- **Утверждение:** Упоминание «Stop-The-World» в контексте паники.
- **Почему требует проверки:** STW — термин сборщика мусора (GC). Паника же делает дамп стека и завершает процесс (`exit(2)`). Это не классический STW в понимании GC; путаница терминов вводит в заблуждение.
- **Источники:** Исходный код `runtime/panic.go`, `runtime.crash()`.
- **Приоритет:** Medium

## Статья 15. Массивы и их особенности

### [15-1] Массив в C/C++ описан как «просто указатель»
- **Утверждение:** «В мире C и C++ массив — это просто указатель, указывающий на первый элемент непрерывного блока памяти...»
- **Почему требует проверки:** Классическое педагогически опасное заблуждение. В C/C++ массив — это полноценный блок памяти (`sizeof(arr)` вернёт реальный размер). Указателем он становится только из-за механизма «Array-to-pointer decay» при передаче в функцию. Формулировка запутает читателей с C-бэкграундом.
- **Источники:** Спецификация языка C (разделы про массивы и array decay).
- **Приоритет:** Medium

## Статья 19. Map под капотом. hmap, buckets и рост

### [19-1] Архитектурное противоречие: hmap vs Swiss Tables
- **Утверждение:** Детально описывается архитектура `hmap` с 8-слотовыми бакетами `bmap`, массивом `tophash` и overflow buckets — при одновременном упоминании перехода на Swiss Tables в Go 1.24.
- **Почему требует проверки:** **Внутреннее противоречие.** Если рантайм переведён на Swiss Tables (Go 1.24), вся описанная архитектура устарела. Swiss Tables работают принципиально иначе: открытая адресация, control bytes (metadata), группы по 8 слотов без linked lists переполнения. Статья либо должна чётко разграничить «до 1.24» и «после», либо переписать внутреннюю архитектуру под Swiss Tables.
- **Источники:** Исходный код `internal/runtime/maps` (Go 1.24), официальный proposal «Swiss Tables for Go maps».
- **Приоритет:** High

## Статья 20. Строки в Go. Immutable string и работа с Unicode

### [20-1] Конвертация `[]byte(s)` — безоговорочное утверждение о heap allocation
- **Утверждение:** При конвертации `b := []byte(s)` рантайм «выделяет совершенно новый блок памяти в куче» (Heap Allocation).
- **Почему требует проверки:** Утверждение избыточно категорично. Если результирующий срез не «убегает» из функции, компилятор благодаря Escape Analysis может разместить копию **на стеке**.
- **Источники:** Флаг `-gcflags="-m"` (escape analysis output).
- **Приоритет:** Medium

## Статья 24. Интерфейсы под капотом. iface и eface

### [24-1] Boxing Value-типов безоговорочно приводит к heap allocation
- **Утверждение:** «Операция Boxing вынуждает компилятор аллоцировать память именно в куче, чтобы получить адрес для поля `data`».
- **Почему требует проверки:** Escape Analysis в современных версиях Go способен локализовать boxing на стеке, если интерфейсная переменная используется только локально и не «убегает» наружу. Категоричное «всегда в кучу» — упрощение.
- **Источники:** Примеры через `-gcflags="-m"` с локальными интерфейсами.
- **Приоритет:** Low

## Статьи 25–29 (ручная проверка)

### [27-1] Name Mangling для неэкспортируемых символов
- **Утверждение:** «Неэкспортируемые символы принудительно дополняются префиксом полного пути пакета» (в контексте Name Mangling).
- **Почему требует проверки:** Механизм идентификации неэкспортируемых символов в Go реализован через систему объектных файлов, а не через Name Mangling в классическом понимании C++. Нужно уточнить терминологию и соответствие описания реальному механизму компоновщика.
- **Источники:** Документация `cmd/link`, исходный код компоновщика.
- **Приоритет:** Low

### [28-1] `go.sum` сравнивается с `package-lock.json` только для отрицания, но формулировка путает
- **Утверждение:** «Распространённое заблуждение: считать `go.sum` аналогом `package-lock.json` или `yarn.lock`. Это в корне неверно.»
- **Почему требует проверки:** Технически `go.sum` и lock-файлы выполняют частично перекрывающиеся функции. Формулировка «в корне неверно» может быть излишне категоричной и само по себе создаёт потенциальную точку путаницы. Стоит уточнить, в чём именно разница (hash-only vs version pinning).
- **Источники:** Документация Go Modules, RFC о `go.sum`.
- **Приоритет:** Low

### [29-1] bufio.Writer — буфер по умолчанию «4 КБ»
- **Утверждение:** «`bufio.Writer` накапливает байты в собственном внутреннем срезе (по умолчанию 4 КБ)».
- **Почему требует проверки:** Необходимо проверить актуальный размер буфера по умолчанию в `bufio.NewWriter`. Исторически это `4096` байт = 4 КБ, но значение стоит верифицировать по исходникам текущей версии Go.
- **Источники:** `bufio/bufio.go`, константа `defaultBufSize`.
- **Приоритет:** Low

### [29-2] `io.MultiWriter` — байты пишутся «параллельно»
- **Утверждение:** «Каждый байт, отправленный в `MultiWriter`, **параллельно** записывается во все дочерние потоки»
- **Почему требует проверки:** Слово «параллельно» педагогически опасно. `io.MultiWriter.Write()` записывает в писатели **последовательно**, один за другим, в цикле. Никакого goroutine-параллелизма там нет. «Параллельно» в смысле «в несколько мест» — допустимо, но может быть неверно понято.
- **Источники:** `io/multi.go` — метод `MultiWriter.Write()`.
- **Приоритет:** Medium

### [29-3] `io_uring` упомянут как решение для дискового IO в Go
- **Утверждение:** «Применение асинхронного движка `io_uring` (доступного в современных ядрах Linux 5.1+)» — как способ решить проблему блокирующего файлового IO.
- **Почему требует проверки:** Стандартная библиотека Go **не использует** `io_uring` нативно. `io_uring` доступен только через CGo-обёртки или сторонние библиотеки. Утверждение может создать впечатление, что это встроенная поддержка.
- **Источники:** Текущий статус `io_uring` в Go runtime, proposals в issue tracker.
- **Приоритет:** Medium

## Статья 34. Горутины. Легковесная конкурентность в Go

### [34-1] Изменение семантики переменных цикла в Go 1.22
- **Утверждение:** «Начиная с Go 1.22, на каждую итерацию цикла `for` создаётся новая переменная, что решает Loop Variables Closure Trap».
- **Почему требует проверки:** Критически важный version-sensitive нюанс: это поведение активируется только если директива `go` в `go.mod` указывает версию **≥ 1.22**. Для модулей со старой директивой `go 1.21` семантика остаётся прежней. Необходимо явно предупредить читателя об этом условии.
- **Источники:** Go 1.22 Release Notes (Loop scoping), документация `go.mod` директивы.
- **Приоритет:** High

### [34-2] Стартовый размер стека горутины — «2 КБ»
- **Утверждение:** Стартовый размер стека горутины — ровно 2 КБ.
- **Почему требует проверки:** Исторически значение менялось (в ранних версиях было 4 КБ, затем 8 КБ, потом снижено до 2 КБ в Go 1.4). Это деталь реализации (`_StackMin`), которую следует верифицировать в актуальных исходниках.
- **Источники:** `runtime/stack.go`, константа `_StackMin`.
- **Приоритет:** Low

## Статья 36. Каналы. Передача данных между горутинами

### [36-1] Передача указателя в канал — безоговорочный heap allocation
- **Утверждение:** «Передача указателя в канал гарантированно приводит к Heap Allocation, так как компилятор не знает жизненного цикла на стороне получателя».
- **Почему требует проверки:** Escape Analysis в Go постоянно совершенствуется. В некоторых тривиальных случаях (особенно при инлайнинге) компилятор может доказать безопасность стека. «Гарантированно» — слишком категорично.
- **Источники:** Флаг `-gcflags="-m"` на свежих версиях компилятора.
- **Приоритет:** Medium

## Статья 43. Deadlock, Livelock и ошибки конкурентности

### [43-1] Условие deadlock-детектора: «все потоки ОС спят»
- **Утверждение:** «Рантайм Go генерирует ошибку "all goroutines are asleep - deadlock!" когда количество активно выполняющихся потоков ОС равно нулю».
- **Почему требует проверки:** Технически фоновый поток `sysmon` всегда активен и не спит. Утверждение может быть неточным — фактически детектор ориентируется на отсутствие выполнимых пользовательских горутин, а не на «все потоки ОС спят».
- **Источники:** Исходники рантайма, алгоритм `runtime.checkdead()`.
- **Приоритет:** Medium
